# Task Review Gate - ревью-гейт для каждой задачи декомпозиции

Протокол завершения каждой задачи из файла декомпозиции в `docs/plans/`.
Цель: до того как код увидит человек, его проверяет независимый агент
@code-reviewer; после согласования процесс останавливается и ждёт человека,
который **сам** делает коммит.

**Абсолютное правило: ни один агент не выполняет `git add`, `git commit`,
`git push`. Коммит делает только человек после собственного ревью.**

## Статусы задач

Статусы ведутся в таблице «Ход выполнения» в начале файла декомпозиции:

| Статус | Значение | Кто выставляет |
| --- | --- | --- |
| `pending` | Не начата | task-decomposer (начальное), project-manager |
| `in-progress` | senior-developer реализует | senior-developer |
| `review` | Реализовано, идёт code-review | senior-developer |
| `approved` | Разработчик и ревьюер согласились, ждёт человека | senior-developer после вердикта APPROVED |
| `committed` | Человек проверил и закоммитил | project-manager после подтверждения пользователя |

## Цикл одной задачи

1. **Старт (project-manager или primary-сессия).**
   Возьмите ровно одну задачу со статусом `pending` с учётом порядка
   зависимостей. Передайте её @senior-developer.

2. **Реализация (senior-developer).**
   Статус -> `in-progress`. Реализуйте только рамки этой задачи.
   Напишите/дополните тесты, запустите тесты и сборку затронутых сервисов.
   Выполните самопроверку, переведите статус в `review` и подготовьте отчёт:
   - задача (путь к файлу декомпозиции и раздел);
   - список изменённых файлов;
   - команды проверки и их фактические результаты;
   - допущения и отклонения от плана.

3. **AI code-review (@code-reviewer).**
   Ревьюер проверяет реализацию по критериям приёмки задачи, ADR из
   `docs/adr/` и конвенциям проекта и выдаёт вердикт:
   - `CHANGES_REQUESTED` - список blockers; senior-developer исправляет и
     передаёт код на новый раунд ревью;
   - `APPROVED` - blockers отсутствуют, тесты проходят.
   Максимум 3 раунда. Если согласие не достигнуто - эскалация человеку с
   позициями обеих сторон (`ESCALATED`).

4. **Сводка для человека (senior-developer).**
   Сразу после `APPROVED` переведите статус задачи в `approved` и создайте
   сводку изменений в `docs/reviews/<feature-slug>/<NN>-<task-slug>.md`
   (формат ниже).

5. **Остановка.**
   Цикл завершён. Агент НЕ берёт следующую задачу и НЕ коммитит.
   Сообщите пользователю: задача выполнена, сводка доступна по пути
   `<path>`, ждём ручного ревью и коммита.

6. **Продолжение.**
   Только после подтверждения человека («закоммичено, продолжай»)
   project-manager выставляет статус `committed` и запускает шаг 1 для
   следующей задачи.

## Формат сводки для человека

```markdown
# Задача <NN> - <название>

- **Задача**: docs/plans/<файл>.md#<раздел>
- **Дата**: <YYYY-MM-DD>
- **Ревью**: раундов - <N>, вердикт APPROVED

## Что сделано
2-5 предложений простым человеческим языком: какая часть функциональности готова.

## Изменённые файлы
- `<путь>` - что там изменилось

## Как проверено
- `<команда>` - результат

## Итоги ревью
- Исправлено по замечаниям ревьюера: ...
- Оставлено без изменений (с обоснованием): ...

## Заметки для коммита
- Рекомендуемое сообщение коммита
- На что обратить внимание при ручной проверке
```

## Правила

- **Одна задача - один цикл.** Не объединяйте выполнение нескольких задач декомпозиции в один заход.
- Никакая задача не получает `approved` без вердикта @code-reviewer.
- Статус `committed` выставляется только после явного подтверждения пользователя.
- Если человек после ручного ревью вернул задачу на доработку - статус -> `in-progress`, цикл начинается с шага 2.
- В сводках и отчётах — русский язык, без эмодзи.
