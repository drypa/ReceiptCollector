# Docker Compose Deploy — развёртывание проекта через Docker Compose

Скил — **инструкция, как принято делать**, а не набор шаблонов. Готовых файлов
«под ключ» внутри нет: примеры ниже — ориентиры, агент пишет файлы сам и
адаптирует их под конкретный проект.

Стек (Go / Node / Python / что угодно) — **вне зоны скила**. Выбор базового образа,
системных зависимостей и менеджера пакетов — задача агента по месту; скил задаёт
только ограничения (например, glibc при cgo — шаг 2). Скил отвечает за структуру
сборки, compose, секреты, тома, политику перезапуска и проверку результата.

---

## Порядок действий

### Шаг 1. Проанализировать проект

**Ничего не создавай, пока не ответил на эти вопросы:**

| Вопрос | Зачем |
|---|---|
| Что запускается и как собирается? | точки входа, бинарь / скрипт / образ |
| Что должно работать **долго**, а что — **однократно**? | долгоживущие сервисы попадают в compose, джобы — в таргеты Dockerfile |
| Какие данные нужны на хосте? | каталоги под bind-mount, режим доступа |
| От какого пользователя должны работать сервисы? | свои — не root; сторонние образы проверить и согласовать (шаг 3) |
| Какие переменные окружения нужны? | `.env.example`, обязательность, дефолты |
| Есть ли уже `Dockerfile` / compose-файл? | см. шаг 9 — адаптация вместо перезаписи |
| Нужны ли соседние сети / внешние API? | healthcheck, зависимости между сервисами |
| Какие контексты сборки? | см. шаг 13 — свой `.dockerignore` на каждый контекст |
| Есть ли web-UI (фронтенд, админка, дашборд)? | если да — нужен прокси, см. шаг 5 |
| Нужен ли HTTPS и откуда взять сертификаты? | см. шаг 5: готовые с хоста / выпускает внешний инструмент / самоподписанные для dev по явному запросу |
| Как устроены два окружения: production и dev? | dev-окружение должно быть у любого проекта, см. шаг 4: в dev в контейнерах живут только сторонние сервисы и прокси |
| Есть ли в проекте `AGENTS.md` / ADR / README о деплое? | см. шаг 15 — актуализировать по итогам реализации |

Сформулируй результат анализа пользователю **до** генерации файлов: какие
сервисы, какие тома, какие переменные, что поднимается в prod, а что — в dev.
Если проект непонятен — спроси, а не угадывай.

### Шаг 2. Dockerfile — multi-stage

Три стадии, разделённые явно:

1. **build** — тулчейн, сборка и unit-тесты, не требующие внешней инфраструктуры. Всё, что не нужно в рантайме.
2. **runtime-base** — минимальный образ приложения: системные пакеты, шрифт,
   локали, **непривилегированный пользователь**, `WORKDIR`, `ENV TZ`.
3. **финальная(ая) стадия(ии)** — копирование бинаря из `build` в `runtime-base`,
   `USER`, `ENTRYPOINT` в exec-форме.

Правила:

```dockerfile
# syntax=docker/dockerfile:1
ARG GO_VERSION=1.27

FROM golang:${GO_VERSION}-bookworm AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod,sharing=locked go mod download
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod,sharing=locked \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -trimpath -ldflags="-s -w" -o /out/app ./cmd/app

FROM debian:bookworm-slim AS runtime-base
RUN set -eux; \
    apt-get update; \
    apt-get install -y --no-install-recommends tzdata; \
    rm -rf /var/lib/apt/lists/*; \
    groupadd --system --gid 10001 app; \
    useradd --system --uid 10001 --gid 10001 --create-home --shell /usr/sbin/nologin app
ENV TZ=UTC
WORKDIR /

FROM runtime-base AS app
RUN apt-get update && apt-get install -y --no-install-recommends ca-certificates \
    && rm -rf /var/lib/apt/lists/*
COPY --from=build /out/app /usr/local/bin/app
USER app:app
ENTRYPOINT ["/usr/local/bin/app"]
```

- **Ограничение на базовый образ: glibc, не Alpine**, если в проекте есть cgo, нативные
  зависимости или готовые бинарные библиотеки. musl + cgo требует отдельного
  тулчейна и флейкает; экономия ~30 МБ не окупает риск. Вернуться к Alpine или
  distroless можно позже, отдельным решением с замерами.
- **ca-certificates — только тем, кто ходит наружу.** Не ставь его в общий
  `runtime-base`: это лишний код в образах, которым сеть не нужна.
- Слой зависимостей отделён от слоя кода — правка исходников не должна
  пересобирать зависимости.
- `-trimpath -ldflags="-s -w"` для скомпилированных языков: меньше образ, нет
  абсолютных путей сборки.
- Кэш-монти (`--mount=type=cache`) **ускоряют**, но не влияют на корректность: сборка должна проходить и
  без них.
- **В финальном образе секретов быть не должно.** Секреты для доступа к сборочной
  инфраструктуре (приватный registry, зеркало пакетов, лицензионный сервер) можно
  передавать при сборке. При multi-stage они могут остаться в промежуточных
  стадиях — это допустимо, если промежуточные образы не публикуются. В финальную
  стадию секреты не копируй и не передавай: используй BuildKit-секреты
  (`RUN --mount=type=secret`) или `ARG`/`ENV`, ограниченные стадией `build`.
  `ARG`/`ENV` с паролями в финальной стадии — ошибка.
- Каждая финальная стадия — свой образ. Не кладите несколько бинарей в один образ
  и не переключайте их через `command:`: теряется изоляция, в образ попадает
  лишнее, и непонятно, что реально запущено.

### Шаг 3. docker-compose.yml

Базовый шаблон сервиса, который собирается из этого Dockerfile (обязательные и опциональные элементы помечены):

```yaml
name: ${COMPOSE_PROJECT_NAME:-project}

# Общий блок для повторяющихся переменных — DRY.
x-env: &env
  TZ: "${TZ:-UTC}"

services:
  app:
    image: project-app:latest
    build:
      context: .
      dockerfile: Dockerfile
      target: app
    restart: on-failure:5        # см. шаг 8
    init: true
    stop_signal: SIGTERM
    stop_grace_period: 20s
    read_only: true              # по необходимости
    tmpfs:
      - /tmp:size=16m,mode=1777
    cap_drop: [ ALL ]            # по необходимости
    security_opt: [ "no-new-privileges:true" ]   # ОБЯЗАТЕЛЬНО
    environment:
      <<: *env
      TOKEN: "${TOKEN:-}"        # валидируется приложением, не compose
      DATA_DIR: "/data"          # путь в контейнере фиксирован
    volumes:
      - type: bind
        source: "${DATA_HOST_DIR:-./data/db}"
        target: "/data"
    healthcheck:                 # ОБЯЗАТЕЛЬНО для долгоживущих, см. шаг 7
      test: ["CMD", "/usr/local/bin/app", "healthcheck"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
```

- **Пути внутри контейнеров** фиксированы в compose и не настраиваются.
  Настраиваются только **источники на хосте**, через переменные окружения.
- Значения — через `${ПЕРЕМЕННУЮ}` с дефолтом `${ПЕРЕМЕННАЯ:-значение}`.
- **`${ПЕРЕМЕННАЯ:?обязательна}` не используй.** Ошибка возникает на стадии
  интерполяции — вне логов контейнера, и оператор её не видит там, где смотрит.
  Валидацию обязательных переменных делает приложение: сообщение в лог и ненулевой
  код возврата.
- Обязательные переменные передавай как `"${ПЕРЕМЕННАЯ:-}"` — пустое значение
  проходит compose, и приложение даёт внятную ошибку. Так сборка не зависит от
  наличия секрета, а ошибка видна в `docker compose logs`.
- `no-new-privileges:true` — **всегда**, без исключений.
- `read_only`, `cap_drop: [ALL]` — по необходимости проекта, но предлагай их
  пользователю явно, а не молча. Пользователь контейнера — отдельное правило
  ниже: он **не** «по необходимости».

**Пользователь, от которого работает сервис.**

- **Свои сервисы — никогда от root.** `USER` в Dockerfile обязателен (см. шаг 2);
  если uid нужно подогнать под владельца каталога на хосте — вынеси его в `.env`
  и задай в compose: `user: "${APP_USER_ID:-10001}:${APP_GID:-10001}"` (см. шаг 11).
  Не добавляй `user: root`, `privileged: true` и `cap_add: [ALL]` «чтобы не
  возиться с правами»: это отменяет изоляцию контейнера целиком.
- **Сторонние образы — проверь, от кого они стартуют**, а не догадывайся:

  ```bash
  docker image inspect <image> --format '{{.Config.User}}'   # пусто = root
  docker run --rm <image> id -u                              # 0 = root
  ```

- **Если сторонний образ работает от root — предупреди пользователя и получи
  явное согласие.** Объясни последствия: uid 0 внутри контейнера при уязвимости
  означает root на хосте, а файлы, записанные в bind-mount, останутся
  принадлежать root, и оператор не сможет их удалить без sudo. Предложи
  альтернативы: образ с непривилегированным пользователем, `user:` поверх
  официального (если entrypoint это поддерживает), rootless Docker. Молча
  оставлять root нельзя.
- **Проверь на живом контейнере:** `docker compose exec <service> id -u` —
  ожидается не `0`. Если пришлось оставить root, это должно быть записано в
  отчёте (шаг 14) и в документации (шаг 15).

### Шаг 4. Два окружения: production и dev

**Ключевое правило: в dev окружении запускаются только сторонние сервисы и прокси.**
Приложение, фронтенд и миграции в разработке запускаются на хосте (hot reload,
отладчик, dev-сервер), поэтому в dev-compose их нет.

| | `docker-compose.yml` (production) | `docker-compose.develop.yml` (dev) |
|---|---|---|
| Что поднимается | все долгоживущие сервисы проекта + инфраструктура (джобы — шаг 10) | **только сторонние сервисы + прокси**: СУБД, очереди, брокеры, кэши, nginx |
| Порты наружу (`ports`) | только у входа (прокси/шлюз) | у БД и у прокси — чтобы работать с хоста |
| Внутренние сервисы | `expose` | не описаны (кроме БД и прокси) |
| Каталоги данных | пути, заданные оператором (`${DATA_HOST_DIR}`) | `${DEV_DB_DATA:-./data/dev-db}` внутри репозитория |
| Имя проекта compose | `name: ${COMPOSE_PROJECT_NAME:-project}` | `name: ${COMPOSE_PROJECT_NAME:-project}-dev` |
| Скрипты | `up.sh` / `down.sh` | `up.dev.sh` / `down.dev.sh` |

- **Отдельные файлы, а не `override.yml`.** Dev-окружение — короткий
  самостоятельный список инфраструктуры, который читается за полминуты. Не
  переписывай prod-сервис, чтобы «отменить» его в dev: этих сервисов в dev
  просто нет.
- **Разные имена проекта — обязательно.** Иначе контейнеры и тома prod и dev
  столкнутся: dev поднимется не на своих портах или, хуже, переиспользует том
  с продакшен-данными.
- Своя пара скриптов: `up.dev.sh` / `down.dev.sh` — те же тонкие обёртки, но со
  своим `-f docker-compose.develop.yml` и своим именем проекта.
- Порты в dev поднимай на свободные значения, чтобы не конфликтовать с
  prod-стендом на той же машине.
- Dev-окружение — не опция: оно должно быть у любого проекта. Если его ещё нет —
  создай; если уже есть — адаптируй по этому шагу (см. шаг 9), а не заводи
  второе.

```yaml
# docker-compose.develop.yml — только инфраструктура разработки
name: ${COMPOSE_PROJECT_NAME:-project}-dev

services:
  db:
    image: postgres:18
    restart: on-failure:5           # см. шаг 8
    ports: [ "${DEV_DB_PORT:-55432}:5432" ]   # свободный порт, не 5432 из prod
    security_opt: [ "no-new-privileges:true" ]   # ОБЯЗАТЕЛЬНО
    volumes:
      - type: bind
        source: "${DEV_DB_DATA:-./data/dev-db}"  # каталог создай вручную
        target: "/var/lib/postgresql/data"
    healthcheck:                    # ОБЯЗАТЕЛЬНО для долгоживущих, см. шаг 7
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 10s
```

### Шаг 5. Прокси и web-интерфейс (nginx)

**Если в проекте есть web-UI (фронтенд, админка, дашборд) — точка входа в систему
это прокси (nginx).** Само приложение порты наружу не публикует:
только у прокси в compose есть `ports`, внутренние сервисы — `expose` или ничего.

- Конфигурация прокси — **bind-mount файла с хоста**, а не файл, запечённый в
  образ: `nginx.prod.conf:/etc/nginx/nginx.conf:ro`. Правки конфига не должны
  требовать пересборки.
- **Поведение зависит от окружения — это и есть главная разница:**

| | production | dev |
|---|---|---|
| `/` (корень, статика) | nginx **раздаёт статику сам**: `root`, SPA-fallback на `index.html`, кэш ассетов с `immutable` | nginx **проксирует на dev-сервер фронтенда** на хосте (HMR), статику не раздаёт |
| `/api` | проксирует на внутренний сервис по имени контейнера | проксирует на API, запущенный на хосте |
| Конфиг | `nginx.prod.conf` | `nginx.dev.conf` — отдельный файл |

- Путь API (`/api`) должен быть **одинаков в обоих окружениях**, иначе
  фронтенду придётся переключать `baseURL` между сборками.
- SPA-fallback в prod: `try_files $uri $uri/ /index.html;`, иначе перезагрузка
  страницы на `/dashboard/42` отдаст 404.
- Имена контейнеров резолвь **динамически** (`resolver 127.0.0.11;` + переменная
  в `proxy_pass`) — иначе nginx не переживёт перезапуск апстрима и будет
  возвращать `host not found in upstream`. В dev апстримы живут на хосте: добавь
  `extra_hosts: ["host.docker.internal:host-gateway"]` и проксируй на
  `host.docker.internal:<port>`; `resolver 127.0.0.11` для хоста не работает.
- **TLS: скил не заменяет CA и не продлевает сертификаты — он отвечает за
  доставку готовых сертификатов в контейнер.** Исключение — самоподписанные для
  dev по явному запросу (ниже). Сертификаты приходят bind-mount'ом **каталога**
  (в нём обычно лежат цепочка, ключ и корень CA — соседние файлы нужны
  приложению и прокси); путь внутри контейнера зафиксирован в конфиге, источник
  на хосте — переменная окружения.
- **Нужны сертификаты — сначала спроси, потом пиши.** TLS не заводи «по
  умолчанию» и ключи молча не генерируй. Уточни у пользователя:
  - откуда файлы: уже лежат на хосте, выпускает Certbot/acme.sh, внутренний CA,
    или их нужно создать с нуля;
  - домен (CN/SAN) — он должен совпадать с адресом, по которому откроют UI,
    иначе браузер отклонит соединение;
  - кто продлевает и что делать при истечении.
  Ответ занеси в `.env.example`: что оператор кладёт в каталог и с какими
  правами (приватный ключ — `0600`).
- **Если пользователь просит самоподписанные** (dev, стенд внутри сети) —
  предложи скрипт генерации (`generate-ssl-cert.sh`, либо имя, принятое в
  проекте). Требования к нему: идемпотентность (существующие сертификаты не
  перетирает), CN/SAN и срок действия берутся из переменных окружения, каталог
  назначения — тот же, что примонтирован в compose, права на ключ `0600`, вывод
  с подсказкой, что делать дальше. Сам сертификат в git не попадает
  (`.gitignore` + `.dockerignore`). В продакшене самоподписанные — только как
  осознанное решение пользователя: предупреди, что браузер покажет
  предупреждение, а клиентское приложение — ошибку доверия.
- **Скрипт генерации — отдельная команда оператора, не шаг `up.sh`.** Ключи не
  должны генерироваться при каждом старте: `up.sh` остаётся тонким, а вызов
  `./generate-ssl-cert.sh` описан в документе деплоя проекта (шаг 15) как
  подготовительный шаг.
- Внутренние ручки, которые не должны быть видны снаружи (генерация токенов,
  отладочные эндпоинты), закрывай **точным** `location = /путь { return 404; }` —
  это не ломает соседние пути.
- Публичные порты — через переменные: `${NGINX_HTTP_PORT:-80}`,
  `${NGINX_HTTPS_PORT:-443}`; опиши их в `.env.example`, а в документе деплоя
  дай ссылку.

### Шаг 6. Тома и монтирования

Это отдельный обязательный раздел. Ошибки здесь самые дорогие, потому что они
молчаливые.

**Bind-mounts — основной вариант.** Оператор должен видеть данные на хосте:
перенос между машинами, бэкап, отладка — всё остаётся возможным.

```yaml
volumes:
  - type: bind
    source: "${LIBRARY_HOST_DIR:-./data/library}"
    target: "/library"
    read_only: true
```

- **Источник — переменная окружения**, цель внутри контейнера — константа.
- **Монтируй каталог, а не отдельный файл данных.** Если приложению нужны соседние
  файлы (SQLite `-wal`/`-shm`, lock-файлы, каталоги кэша), bind-mount
  отсутствующего файла создаст на его месте **каталог**, и приложение упадёт с
  невнятной ошибкой. Пример: `- ${DATA_HOST_DIR}:/data`, а не
  `- ${DB_HOST_FILE}:/data/app.db`. Конфиги — исключение: их можно монтировать
  файлом (см. шаг 5).
- **Один и тот же каталог в разных сервисах может требовать разного режима.**
  Явно проставляй `read_only: true` там, где запись не нужна, — не полагайся
  на умолчание.
- **Каталоги-источники создаёт оператор вручную.** Если каталога нет, docker
  создаст его сам от `root`, оператор этого не заметит, и следующий шаг падает с
  Permission denied. Отрази это в `.env.example` комментарием и в документе
  деплоя (шаг 15).
- **Права.** Контейнер работает от непривилегированного uid. Либо оператор
  выдаёт права на каталог, либо uid/gid выносится в `.env`, чтобы его можно было
  подстроить без пересборки образа.
- **Файловая система.** Каталог базы данных — на локальной ФС (ext4/xfs), не на
  NFS/SMB: там не работает WAL и файловая блокировка.
- **Named volumes** — только когда данные оператору на хосте не нужны. Если они
  нужны — bind-mount. Преимущество named volume в том, что docker создаёт её с
  правильным владельцем сам; недостаток — нельзя посмотреть и забэкапить руками.

### Шаг 7. Healthcheck — обязателен

**У каждого долгоживущего сервиса в compose должен быть явный `healthcheck`.**

- `test` — самодостаточная команда внутри контейнера: `CMD` для бинаря с
  health-эндпоинтом, `CMD-SHELL` для проверки процесса, порта или файла.
- `interval`, `timeout`, `retries`, `start_period` подбирай так, чтобы
  `start_period` покрывал реальное время старта, иначе контейнер будет помечен
  `unhealthy` во время нормальной инициализации.
- Если у приложения **нет** health-эндпоинта, добавь его — это дешёвый и
  правильный путь. Если добавить нельзя (чужой бинарь, нет исходников), проверь
  процесс: `["CMD-SHELL", "pgrep -f /usr/local/bin/app"]` — и явно скажи
  пользователю, что проверка поверхностная.
- **`depends_on: condition: service_healthy` не используй.** Healthcheck нужен
  для наблюдаемости (`docker compose ps` показывает `(healthy)`), а не для
  автоматической сборки зависимостей.
- Порядок запуска можно задать обычным `depends_on` (без `condition`), но он не
  гарантирует готовность зависимости. Если сервису нужна готовая БД/очередь,
  приложение должно само ретраить подключение с backoff; `depends_on` этого не
  заменяет.
- Для сервисов без входящего порта (боты, воркеры, потребители очередей) явный
  `test: ["CMD", "<бинарь>", "healthcheck"]` с кодом выхода — нормальное решение.

### Шаг 8. Политика перезапуска — обязательна

**У каждого сервиса в compose должна быть явно указанная политика.**

| Тип сервиса | Значение | Почему |
|---|---|---|
| Долгоживущий, нужен автозапуск после ребута хоста | `restart: unless-stopped` | поднимается после рестарта демона; **не выбирай** для сервиса, который падает из-за ошибки конфигурации — получишь бесконечный цикл и потеряешь сообщение об ошибке |
| Долгоживущий, важнее остановиться после N ошибок | `restart: on-failure:<N>` | после N неудачных стартов остаётся `Exited (1)` вместо restart-loop; **ребут хоста не переживает** — для автозапуска нужен `unless-stopped` |
| Одноразовая джоба (если описана в compose) | `restart: "no"` | иначе restart-loop |

- `restart: on-failure:5` — разумный дефолт, если сервис должен останавливаться
  после серии ошибок: 5 попыток с backoff, дальше сервис останавливается и его
  видно в `docker compose ps` как `Exited (1)`. Если нужен автозапуск после
  ребута хоста — `unless-stopped`, но только для сервисов, которые не падают
  из-за конфигурации.
- `init: true` — reaper зомби-процессов и корректная передача `SIGTERM` (PID 1 в
  контейнере не выполняет эти функции по умолчанию).
- `stop_signal: SIGTERM` + `stop_grace_period: 20s` — если приложение ловит
  сигналы. Предупреди пользователя, что состояние, держимое только в памяти,
  при этом теряется.

### Шаг 9. Если Dockerfile или compose уже есть

**Не перезаписывай молча.**

1. Прочитай существующие файлы целиком.
2. Собери список того, что предлагаешь изменить и **почему**.
3. Покажи список пользователю и дождись подтверждения.
4. Правь точечно, сохраняя то, что уже соответствует правилам.

Если файл соответствует правилам — так и скажи, менять нечего, и объясни,
какое правило закрывает этот файл. Если конфликт принципиальный (например,
сервис в compose, который должен быть одноразовым) — объясни последствия и
предложи вариант.

### Шаг 10. Одноразовые джобы

Собираются в Docker, но **по умолчанию в compose не включаются**.

- Каждая джоба — отдельная финальная стадия в `Dockerfile` со своим
  `ENTRYPOINT` и сборкой из общей `build`-стадии.
- В `.dockerignore` исключи рабочие данные (`*.log`, артефакты, базы), чтобы
  они не попадали в build-контекст.
- Скрипт запуска джобы — `docker build --target <stage> -t <name> . && docker run
  --rm …`. Том, если нужны данные с хоста, передаётся флагом `-v`, а не через
  compose.
- Если джоба всё-таки описана в compose — `restart: "no"` и `profiles: ["tools"]`,
  чтобы она не попадала в `up`.

### Шаг 11. `.env.example`

**Единый источник правды по переменным окружения.** Файл `.env` создаётся из
него копированием и в git не попадает.

Для каждой переменной:

- название и обязательность;
- значение по умолчанию;
- **что переменная делает** — одной строкой;
- **типичная ошибка или следствие** при неверном значении;
- где значение должно совпадать с чем-то другим (например, uid контейнера с
  владельцем каталога на хосте).

Пример:

```bash
# ── обязательные ────────────────────────────────────────────
# Токен бота от @BotFather. Пустое значение — бот не стартует:
# в логах будет «missing required environment variables: TOKEN».
TOKEN=

# ── пути ────────────────────────────────────────────────────
# Каталог с данными на хосте, bind-источник для /data.
# Создай его вручную: docker иначе создаст пустой каталог от root,
# и оператор этого не заметит.
DATA_HOST_DIR=./data/db

# ── dev ─────────────────────────────────────────────────────
# Каталог данных dev-БД. Отдельный от prod, чтобы dev не примонтировал
# продакшен-данные. Создай его вручную.
DEV_DB_DATA=./data/dev-db
# Порт dev-БД на хосте. Должен быть свободен: не 5432 из prod.
DEV_DB_PORT=55432

# ── безопасность ────────────────────────────────────────────
# uid:gid, от которого работает сервис (не root!) и которому нужны
# права на запись в DATA_HOST_DIR. Должен совпадать с владельцем
# каталога на хосте: иначе получишь Permission denied при старте.
# Значение по умолчанию должно совпадать с USER в Dockerfile.
APP_USER_ID=10001
APP_GID=10001

# ── compose ─────────────────────────────────────────────────
COMPOSE_PROJECT_NAME=project
```

Комментарии пиши по-русски, в стиле README проекта, если проект русскоязычный.

### Шаг 12. up.sh и down.sh

**Скрипты — тонкие обёртки. Они только запускают.**

```bash
#!/usr/bin/env bash
# Поднимает сервисы проекта: docker compose up -d
set -euo pipefail
cd "$(dirname "${BASH_SOURCE[0]}")"

docker compose up -d

echo "Статус:  docker compose ps"
echo "Логи:    docker compose logs -f <service>"
```

```bash
#!/usr/bin/env bash
# Останавливает сервисы проекта: docker compose down
# Данные не теряются: bind-mount'ы остаются на хосте,
# named volumes — до явного `docker compose down -v`.
set -euo pipefail
cd "$(dirname "${BASH_SOURCE[0]}")"

docker compose down

echo "Данные не удалены: bind-mount'ы на хосте, named volumes — до 'docker compose down -v'."
```

Правила:

- `set -euo pipefail` — ошибка в любой команде роняет скрипт.
- `cd "$(dirname "${BASH_SOURCE[0]}")"` — скрипт работает из любого каталога.
- Не делай `set -a; . ./.env; set +a` — это исполняет shell-код из
  пользовательского файла и ломается на значениях с пробелами, кавычками и `?`
  в DSN. Compose читает `.env` сам.
- Указывай chmod `+x` на файлы скриптов.
- Если скриптов больше двух, общие хелперы вынеси в `scripts/common.sh` и
  подключай через `. ./scripts/common.sh`.
- `down` не удаляет данные: bind-mount'ы живут на хосте, named volumes (если
  есть) остаются до `docker compose down -v`. Напиши это в выводе скрипта —
  оператор должен знать.

### Шаг 13. Гигиена репозитория

- `.dockerignore` — исключи `.git`, `.github`, `.idea`, `docs`, `.env`,
  `.env.*` (кроме `.env.example`), рабочие данные (`data`, `*.log`, `*.sqlite3*`,
  артефакты сборки, собранные бинари), кэш сборки (`.cache/`, `*.tmp`).
- `.gitignore` — `.env`, рабочие данные, собранные бинари, артефакты сборки,
  ключи и сертификаты (`ssl/`, `*.key`, `*.pem`).
- Никогда не запекай секреты в образ и не коммить `.env`, а добавь его в `.dockerignore` и `.gitignore`.

**`.dockerignore` — свой на каждый контекст сборки.** В монорепо у разных сервисов
разные `context:`, и `.dockerignore` в корне репозитория действует **только** на
контекст = корень. В других контекстах его следует уточнять.

- Свой `.dockerignore` лежит **в каталоге контекста**: `context: .` → корень,
  `context: ./service-b` → `service-b/.dockerignore`.
- Минимум, кроме секретов, для любого контекста: `**/node_modules/`,
  `**/bin/`, `**/obj/`, `**/dist/`, `**/build/`, `**/target/`, `**/out/`,
  `logs/`, `ssl/`, `*.key`, `*.pem`, `data/`.
- **Контекст = корень монорепо — главный источник мусора в сборке.** Чужие
  подпроекты исключай целиком (`service-a/`, `frontend/`): иначе сборка одного
  сервиса тащит в контекст сотни мегабайт чужих `node_modules` и артефактов
  и упирается в память и время.
- Артефакты, которые Dockerfile собирает сам (фронтенд, publish-каталог,
  собранные вручную бинари), исключай: локальная копия в образ не нужна и может
  перекрыть собранную (`COPY --from=frontend … ./dist`).
- После правки `.dockerignore` проверь контекст: размер и состав должны быть
  ожидаемыми, а не «всё подряд».

### Шаг 14. Верификация

**Генерация без проверки не считается завершённой.** Проверь и отчитайся.

1. **Валидность compose и интерполяции:**

   ```bash
   docker compose config -q
   docker compose -f docker-compose.develop.yml config -q   # dev-окружение
   ```

   **Только `-q`.** Без этого флага `docker compose config` напечатает
   содержимое `.env` в терминал и в лог CI. `-q` печатает исключительно ошибки
   интерполяции и синтаксиса.

2. **Сборка:**

   ```bash
   docker compose build
   ```

   Для сервисов за пределами compose — `docker build --target <stage> -t <name> .`
   из каталога **контекста** (шаг 13).

   Сборка может требовать секретов для доступа к сборочной инфраструктуре
   (приватный registry, зеркало пакетов, лицензионный сервер). Они не должны
   попадать в финальный образ: используй BuildKit-секреты
   (`RUN --mount=type=secret`) или `ARG`/`ENV`, ограниченные стадией `build`.
   Промежуточные образы со сборочными секретами не публикуй.

3. **Проверка финального образа:**

   ```bash
   docker image ls
   docker history <final-image> --no-trunc   # секретов в слоях быть не должно
   ```

   В финальном образе не должно быть значений `ARG`/`ENV` с паролями и
   токенами. Промежуточные стадии могут содержать сборочные секреты — это
   допустимо, пока эти образы не публикуются.

4. **Проверка сертификатов** (если настроен HTTPS). **До `up`** — иначе
   контейнер прокси упадёт на чтении файлов:

   ```bash
   openssl x509 -in <cert.pem> -noout -subject -enddate
   openssl rsa  -in <key.pem>  -check -noout
   stat -c '%a %n' <key.pem>          # ожидается 600
   ```

   CN/SAN должен совпадать с адресом, по которому откроют UI; срок действия —
   не истёк. Если сертификатов нет и пользователь просил самоподписанные —
   сгенерируй их скриптом (шаг 5) и повтори проверку.

5. **Запуск и проверка логов на утечку секретов:**

   ```bash
   docker compose up -d
   docker compose logs <service> | grep -iE 'token|password|secret|key|dsn'
   ```

   Пустой результат — хорошо. Если в логах есть значения переменных, а не их
   имена — ищи место, где приложение печатает конфигурацию, и убери.
   Дополнительно проверь `docker inspect <container>`: секреты в
   `environment:` видны без ограничений — если это неприемлемо, вынеси их в
   `secrets:` или файл с правами `0600`.

6. **Проверка пользователя, от которого работают сервисы.** На тех же
   запущенных контейнерах:

   ```bash
   for s in $(docker compose ps --services); do
     printf '%-20s uid=%s\n' "$s" "$(docker compose exec -T "$s" id -u 2>/dev/null || echo '—')"
   done
   ```

   `uid=0` допустим только для стороннего образа, на который пользователь дал
   явное согласие (шаг 3); в остальных случаях это ошибка, которую нужно
   исправить, а не задокументировать.

7. **Отчёт пользователю:** какие файлы созданы, что проверено, какие команды
   запускать, что осталось за оператором (создать каталоги, выдать права,
   заполнить `.env`, положить сертификаты), от какого пользователя работают
   сервисы и где пришлось согласовать root, что изменено в документации проекта
   (шаг 15), и какие известные ограничения есть у результата.

### Шаг 15. Актуализировать документацию проекта

**Законченное развёртывание без актуальной документации — незаконченное развёртывание.**
После того как файлы созданы и проверены, обнови документ, который описывает
развёртывание в этом репозитории: `AGENTS.md`, `CLAUDE.md` или раздел README —
**тот, который уже есть в проекте**. Второй документ деплоя не создавай; ADR —
отдельный жанр, см. ниже.

Там должно быть **актуальное состояние деплоя**, а не история изменений:

- какие сервисы есть, как поднимаются и останавливаются (`./up.sh`, `./down.sh`,
  `./up.dev.sh`, `./down.dev.sh`), какие порты публикуются наружу, а какие —
  только внутри сети;
- какие тома живут на хосте и какие каталоги оператор создаёт вручную;
- переменные окружения — ссылкой на `.env.example` (не дублируй значения),
  с указанием обязательных;
- какие БД используются, где лежат их данные и как делается бэкап/восстановление;
- **от какого пользователя (uid) работают сервисы**, кому принадлежат каталоги
  на хосте и где сознательно оставлен root (сторонний образ) — с причиной;
- по dev-окружению — что поднимается в контейнерах, а что запускается на
  хосте;
- если есть web-UI — как попасть снаружи и через какой прокси;
- если настроен HTTPS — откуда берутся сертификаты, кто их продлевает и что
  делать при истечении (и как сгенерировать самоподписанные для dev).

Правила:

- Прочитай существующий файл целиком **до** правки и сохрани его структуру,
  язык и стиль. `AGENTS.md` — это инструкция агенту, а не отчёт о работе: пиши
  правила и состояние, без «мы добавили» и «было/стало».
- Правь точечно: не переписывай разделы, которых деплой не касался.
- Если состояние расходится с тем, что написано в файле (например, документация
  описывает старую версию образа, а в compose уже новая) — приведи документ в
  соответствие и явно скажи пользователю, что исправил.
- Если в проекте есть `docs/adr/` — структурное изменение деплоя (новое
  окружение, миграция БД, смена способа публикации образов) фиксируется там же.

## Правила

- **Сначала анализ, потом генерация.** Покажи пользователю план: сервисы,
  тома, переменные.
- **Не выдумывай то, о чём не спросили.** Не добавляй volumes, сети и
  `depends_on`, которые проект не требует. Healthcheck — исключение: для
  долгоживущих сервисов он обязателен (шаг 7). Каждое проектное решение — с
  обоснованием, предложенным пользователю.
- **Комментарии в файлах — по-русски**, если проект русскоязычный. Объясняй
  *почему*, а не *что*: `read_only` без причины выглядит как ритуальная
  безопасность.
- **Каждое «обязательно» из этого документа — обязательно:** `no-new-privileges`,
  `healthcheck` (для долгоживущих сервисов), политика перезапуска, `.env.example`
  с комментариями, multi-stage Dockerfile, `up.sh` / `down.sh`, актуальное
  состояние деплоя в документе проекта, запуск своих сервисов **не от root**.
- **Свои сервисы — не от root. Сторонние — проверь и спроси.** Для своего
  образа `USER` обязателен; для чужого сначала выясни (`docker image inspect`),
  не стартует ли он от root, и если да — предупреди пользователя и получи
  согласие (шаг 3).
- **Документация деплоя — часть результата.** Реализация без обновления
  документа деплоя проекта (`AGENTS.md` / README / ADR) не считается
  завершённой (шаг 15).
- **Данные теряются только при явном удалении.** Не добавляй в `down.sh` `rm`,
  `down -v`, очистку каталогов и не создавай шагов, которые трогают данные.
  Предупреждай, если предложенная пользователем операция необратима.
- **Скрипты `up`/`down` остаются тонкими.** Операционные скрипты (генерация
  сертификатов, бэкап) могут содержать узкую логику, но бизнес-логика — в
  приложении и тестах, а не в bash.

## Чего скил не делает

- Не выбирает базовый образ под язык стека (кроме ограничений шага 2,
  например glibc при cgo) и не занимается версиями зависимостей.
- Не добавляет healthcheck-и автоматически «по умолчанию», если сервис не
  запущен постоянно (одноразовые джобы по умолчанию в compose не включаются).
- Не генерирует `docker-compose.override.yml`, swarm-конфиги и ingress. Dev-окружение
  описывается отдельным `docker-compose.develop.yml` (шаг 4).
- Не заменяет CA и не продлевает TLS-сертификаты для production (Let's Encrypt,
  коммерческий CA, внутренний PKI), не заводит публичные домены и DNS, не берёт
  на себя бэкап и мониторинг. Конфигурация прокси и монтирование **уже готовых**
  сертификатов — шаг 5; где сертификат взять и кто за него отвечает — вопрос к
  пользователю. Исключение — скрипт генерации самоподписанных сертификатов для
  dev: он тоже шаг 5 и создаётся только по явному запросу пользователя.

## Пример структуры результата

```
project/
```
