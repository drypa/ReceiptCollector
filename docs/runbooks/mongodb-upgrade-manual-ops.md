# Инструкция для персонала: обновление MongoDB 4.1 → 8.2.3

> **Кому предназначен этот документ.** Оператору, выполняющему обновление базы
> данных MongoDB в проекте ReceiptCollector на сервере продакшена. Знание
> внутренней архитектуры проекта **не требуется** — достаточно уметь работать
> с командной строкой Linux и Docker.
>
> **Что делаем.** Переносим базу данных со старой версии MongoDB 4.1
> на актуальную 8.2.3. Данные переносятся полностью: сначала делается полная
> копия (дамп), затем она восстанавливается в новую пустую базу 8.2.3.
>
> **Сколько времени займёт.** Ориентировочно от 30 минут до пары часов
> (зависит от объёма данных). На это время сервисы сбора чеков будут
> остановлены — это допустимо и запланировано.
>
> **Главное правило.** Выполняйте шаги строго по порядку. Перед каждым шагом,
> помеченным как «⛔ Точка принятия решения», сверяйте фактический вывод команд
> с ожидаемым. Если результат не совпадает — **не переходите к следующему
> шагу**, обратитесь к разделу «Действия при проблемах» или выполните откат.

## 1. Обозначения и соглашения <a name="1-обозначения-и-соглашения"></a>

| Обозначение | Значение |
|---|---|

## Этап 0 <a name="этап-0"></a>. Подготовительные проверки (до простоя)

Всё, что делается на этом этапе, не останавливает работу сервисов.

### 0.1. Сервисы сейчас работают штатно

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
```

✅ Ожидаемый результат: в списке есть `receipt-mongo` с образом `mongo:4.1`
и статусом `Up ...`; также видны `receipt-collector`, `receipt-bot`,
`receipt-postgres`, `receipt-analytics`.

⛔ Если `receipt-mongo` отсутствует или статус не `Up` — сначала восстановите

### 0.2. Свободное место на диске

```bash
df -h "$(dirname "$MONGO_DATA")" && du -sh "$MONGO_DATA"
```

✅ Ожидаемый результат: свободного места **минимум в 3 раза больше**, чем

⛔ Если места меньше — освободите диск или перенесите `$MONGO_BACKUP`

### 0.3. Образ старой версии сохранён локально (нужен для отката)

✅ Ожидаемый результат: образ `mongo` с тегом `4.1` присутствует в выводе.

⛔ Если образа нет и доступа к интернету нет — **миграцию начинать нельзя**:

### 0.4. Новый образ целевой версии доступен


✅ Ожидаемый результат: `Status: Downloaded newer image for mongo:8.2.3`

⛔ Если коммита нет — запросите его у инженера до начала работ.

### 0.6. Зафиксируйте текущие значения конфигурации

Выпишите на бумагу / в заметки (понадобятся для возможного отката):

Выберите путь рядом со старым, например `/home/drypa/receipts/mongo82-data`

```bash

```

✅ Ожидаемый результат: каталог создан, команда прошла без ошибок.

⚠️ Каталог должен быть **пустым** — проверьте: `ls -la <NEW_MONGO_DATA>`
(только `.` и `..`).

**Итог этапа 0:** все проверки ✅. Если хоть одна ⛔ — миграция не начинается.

## Этап 1 <a name="этап-1"></a>. Контрольный дамп и проверка его восстановимости

Цель — убедиться, что данные вообще выгружаются и восстанавливаются, **до**
начала простоя.

### 1.1. Полный контрольный дамп

```bash
cd <REPO>
docker exec receipt-mongo mongodump \
  --gzip --archive=/backup/pre-upgrade-control.archive \
  --username "$MONGO_LOGIN" --password "$MONGO_SECRET" --authenticationDatabase admin
```

✅ Ожидаемый результат: в конце вывода строки вида
`done dumping <база>.<коллекция>` для всех коллекций, код возврата 0.

Проверьте размер файла на хосте (каталог `/backup` внутри контейнера — это
`$MONGO_BACKUP` на хосте):

```bash
ls -lh "$MONGO_BACKUP/pre-upgrade-control.archive"
```

✅ Ожидаемый результат: файл существует, размер существенно больше нуля
(обычно единицы–десятки МБ для этого проекта).

⛔ Файла нет или он нулевой — дамп не удался. Не продолжайте: разберитесь
(см. [«Действия при проблемах»](#проблемы), п. 1).

### 1.2. Сохраните эталонные счётчики документов

Эта команда печатает количество документов во всех коллекциях бизнес-баз.
Сохраните вывод в файл — он будет эталоном для сравнения:

```bash
docker exec receipt-mongo mongosh --quiet \
  --username "$MONGO_LOGIN" --password "$MONGO_SECRET" --authenticationDatabase admin \
  --eval '
    ["receipt-data", "receipt_collection"].forEach(function(dbName){
      print("== " + dbName);
      db.getSiblingDB(dbName).getCollectionNames().sort().forEach(function(c){
        print(c + ": " + db.getSiblingDB(dbName)[c].countDocuments({}));
      });
    });' | tee "$HOME/mongodb-counts-before.txt"
```

✅ Ожидаемый результат: список вида

```
== receipt-data
receipt_requests: 12345
== receipt_collection
receipt_requests: 12345
system_users: 67
...
```

(конкретные числа и состав коллекций могут отличаться — важно, что файл
`mongodb-counts-before.txt` создан и не пуст).

Если команда завершилась ошибкой `mongosh: not found` — на контейнере 4.1
используется старая утилита: замените `mongosh` на `mongo` в этой команде.

### 1.3. Проверка восстановимости дампа во временном контейнере 8.2.3

Поднимите временный одноразовый контейнер с новой версией:

```bash
docker run -d --name mongo82-test \
  -v "${MONGO_BACKUP}:/backup" \
  -e MONGO_INITDB_ROOT_USERNAME=test -e MONGO_INITDB_ROOT_PASSWORD=test \
  mongo:8.2.3
```

✅ Ожидаемый результат: выведен идентификатор контейнера.

Дождитесь готовности (повторяйте, пока не увидите `healthy`; обычно 20–60 сек):

```bash
docker inspect --format '{{.State.Health.Status}}' mongo82-test
```

Восстановите дамп во временный контейнер:

```bash
docker exec mongo82-test mongorestore \
  --gzip --archive=/backup/pre-upgrade-control.archive \
  --nsInclude='receipt-data.*' --nsInclude='receipt_collection.*' \
  --username test --password test --authenticationDatabase admin
```

✅ Ожидаемый результат: итоговая строка `12345 document(s) restored successfully`
(число документов — суммарное, точное значение не фиксируется) и отсутствие
строк `error` / `failed`.

Сверьте счётчики во временном контейнере:

```bash
docker exec mongo82-test mongosh --quiet \
  --username test --password test --authenticationDatabase admin \
  --eval '
    ["receipt-data", "receipt_collection"].forEach(function(dbName){
      print("== " + dbName);
      db.getSiblingDB(dbName).getCollectionNames().sort().forEach(function(c){
        print(c + ": " + db.getSiblingDB(dbName)[c].countDocuments({}));
      });
    });'
```

⛔ **Точка принятия решения.** Сравните вывод с файлом
`$HOME/mongodb-counts-before.txt` (команда `diff $HOME/mongodb-counts-before.txt <(вывод выше)`
или визуально):

- **Совпадает полностью** → временный контейнер можно удалить, дамп пригоден.
  Переходите к 1.4.
- **Расходится** → ⛔ СТОП. Миграцию не начинать. Обратитесь к разделу
  [«Действия при проблемах»](#проблемы), п. 2.

Удалите временный контейнер:

```bash
docker rm -f mongo82-test
```

✅ Ожидаемый результат: выведено имя удалённого контейнера.

## Этап 3 <a name="этап-3"></a>. Переключение на MongoDB 8.2.3

### 3.1. Остановите старый контейнер mongo

```bash
docker-compose -p receipt-collector stop mongo
```

✅ Ожидаемый результат: `Stopping receipt-mongo ... Done`.
Проверка: `docker ps -a --filter name=receipt-mongo --format '{{.Status}}'` — `Exited`.

### 3.2. Проверьте, что старый каталог данных не тронут

```bash
ls "$MONGO_DATA" | head
```

✅ Ожидаемый результат: видны служебные файлы WiredTiger
(`WiredTiger.wt`, `WiredTiger.lock`, `collection-*.wt` и т.п.).

⚠️ Этот каталог — ваша страховка для отката. **Ничего в нём не удаляйте
и не изменяйте.**

### 3.3. Примените обновлённую конфигурацию

```bash
cd <REPO>
git checkout <UPGRADE_COMMIT>   # или: git pull origin main
git log --oneline -1
```

✅ Ожидаемый результат: HEAD указывает на коммит обновления MongoDB.
Проверка состава: `grep 'image: mongo' docker-compose.yml` — должно быть
`image: mongo:8.2.3`, а healthcheck содержать `mongosh`:

```bash
grep -A1 'test:' docker-compose.yml | grep mongosh
```

⛔ Если в compose всё ещё `mongo:4.1` или healthcheck на `mongo` — коммит
не тот / не применился. Вернитесь к шагу 0.5 и сверьтесь с инженером.

### 3.4. Переключите `.env` на новый каталог данных

Откройте `.env` в редакторе и замените значение `MONGO_DATA=` на выбранный
на шаге 0.7 новый пустой путь:

```
MONGO_DATA=<NEW_MONGO_DATA>
```

Проверка:

```bash
grep '^MONGO_DATA=' .env
```

✅ Ожидаемый результат: новое значение `<NEW_MONGO_DATA>`. Старое значение
у вас записано с шага 0.6 — оно понадобится при откате.

### 3.5. Запустите только новый mongo

```bash
docker-compose -p receipt-collector up -d mongo
```

✅ Ожидаемый результат: контейнер создан и запущен.

Дождитесь готовности (первый запуск инициализирует новый каталог — может занять
до минуты; повторяйте команду каждые ~10 секунд):

```bash
docker inspect --format '{{.State.Health.Status}}' receipt-mongo
```

✅ Ожидаемый результат: `healthy`.

⛔ **Точка принятия решения.** Если спустя 2–3 минуты статус `unhealthy`
или `starting` — см. [«Действия при проблемах»](#проблемы), п. 3.
Если причина не устраняется за 15 минут — выполняйте [откат](#откат).

### 3.6. Проверьте авторизацию в новой базе

```bash
docker exec receipt-mongo mongosh --quiet \
  --username "$MONGO_LOGIN" --password "$MONGO_SECRET" --authenticationDatabase admin \
  --eval "db.adminCommand('ping')"
```

✅ Ожидаемый результат: `{ ok: 1 }`.

⛔ Ошибка аутентификации (`Authentication failed`) — см.
[«Действия при проблемах»](#проблемы), п. 4.

## Этап 4 <a name="этап-4"></a>. Восстановление данных и сверка счётчиков

### 4.1. Восстановите данные из финального дампа

```bash
docker exec receipt-mongo mongorestore \
  --drop --gzip --archive=/backup/final-pre81.archive \
  --nsInclude='receipt-data.*' --nsInclude='receipt_collection.*' \
  --username "$MONGO_LOGIN" --password "$MONGO_SECRET" --authenticationDatabase admin
```

✅ Ожидаемый результат: строки `done` по каждому namespace и итог
`N document(s) restored successfully`, `0 document(s) failed to restore`.

⛔ Наличие `failed to restore` или ошибок — см.
[«Действия при проблемах»](#проблемы), п. 5. Не запускайте сервисы, пока
restore не завершён успешно.

⏱ Ориентир по времени: restore небольших объёмов занимает минуты. Замеренное
на репетиции время указано в плане работ (docs/plans/mongodb-upgrade-8-2.md).
Если процесс длится непропорционально долго (> 30 минут) — проверьте
`docker logs receipt-mongo --tail 50` на предмет ошибок диска/памяти.

### 4.2. Сверьте счётчики документов

Выполните ту же команду подсчёта, что на шаге 1.2 (тот же самый текст команды),
и сравните вывод с файлом `$HOME/mongodb-counts-before.txt`:

```bash
diff "$HOME/mongodb-counts-before.txt" <новый_вывод>
```

✅ Ожидаемый результат: различий нет — имена коллекций и количества совпадают.

⛔ **Точка принятия решения.** Любое расхождение в количестве документов —
критично. Повторите restore (шаг 4.1 безопасно повторять: `--drop` очищает
коллекции перед загрузкой). Если после повтора расхождение осталось — см.
[«Действия при проблемах»](#проблемы), п. 5, либо выполняйте [откат](#откат).

### 5.2. Запустите весь стек

```bash
./up.sh
```

✅ Ожидаемый результат: все контейнеры созданы. Через 1–2 минуты:

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
```

✅ Ожидаемый результат: `receipt-mongo` — образ `mongo:8.2.3`, статус

⛔ Какой-то контейнер в `Restarting`/`Exited` — посмотрите его логи
(`docker logs <имя> --tail 50`) и см. [«Действия при проблемах»](#проблемы), п. 6.

### 5.3. Проверьте журнал backend на ошибки подключения к БД

```bash
docker logs receipt-collector --tail 100 | grep -iE 'mongo|connection|auth'
```

✅ Ожидаемый результат: нет сообщений об ошибках подключения/авторизации.

### 5.4. Функциональные проверки

Выполните последовательно:

1. **Бот**: отправьте боту в Telegram любую рабочую команду (например,
   команду отчёта). ✅ Ответ получен.
2. **Получение чека**: получите чек обычным способом (скан/штрихкод через
   бот). ✅ Чек появился.
3. **Новый чек в БД**: повторите подсчёт из шага 1.2 — число документов
   `receipt_requests` увеличилось относительно эталона (воркер пишет новые чеки).
   ✅ Число выросло.
4. **Аналитика**: откройте веб-интерфейс аналитики, убедитесь, что данные
   отображаются и количество чеков согласуется с БД. ✅ Отображается.

⛔ Любая из проверок не проходит — см. [«Действия при проблемах»](#проблемы)
или выполняйте [откат](#откат). **Не оставляйте систему частично работающей:**
до полного прохождения чек-листа либо доводим, либо откатываемся.

Перейдите к [чек-листу финальных проверок](#чек-лист).

## Откат на MongoDB 4.1 <a name="откат"></a>

Применяйте, если миграция не может быть завершена успешно. Откат возвращает
систему к состоянию «как до начала работ». Чеки, записанные **после** успешного
restore в 8.2.3, будут потеряны — это принятое ограничение, поэтому откат
выполняется сразу при обнаружении проблем, пока новых данных мало.

1. **Остановите всё:**

   ```bash
   cd <REPO> && ./down.sh
   ```

   ✅ Все контейнеры остановлены: `docker ps` — пусто (или только посторонние).

2. **Верните старый путь данных в `.env`:** установите
   `MONGO_DATA=<старый каталог>` (значение, записанное на шаге 0.6).
   Старый каталог не был изменён — данные 4.1 в нём сохранены.

3. **Верните прежнюю конфигурацию:**

   ```bash
   git checkout <предыдущий коммит/тег>   # или: git revert <UPGRADE_COMMIT>
   grep 'image: mongo' docker-compose.yml # должно снова быть mongo:4.1
   ```

4. **Убедитесь, что образ 4.1 на месте:**

   ```bash
   docker images mongo:4.1
   ```

5. **Запустите систему:**

   ```bash
   ./up.sh
   ```

   ✅ `receipt-mongo` — `mongo:4.1`, `healthy`; остальные сервисы поднялись.

6. **Проверьте данные:** выполните подсчёт из шага 1.2 и сравните с
   `$HOME/mongodb-counts-before.txt` — счётчики должны совпасть.

7. Сообщите ответственному инженеру о выполненном откате и причине.
   Архив `/backup/final-pre81.archive` сохраните — это самая свежая копия данных.

## Чек-лист финальных проверок <a name="чек-лист"></a>

Миграция считается успешной только когда отмечены **все** пункты:

- [ ] `docker ps`: `receipt-mongo` — образ **mongo:8.2.3**, статус **healthy**;
- [ ] `db.adminCommand('ping')` отвечает `{ ok: 1 }` (шаг 3.6);
- [ ] счётчики документов всех коллекций `receipt-data` и `receipt_collection`
      совпадают с `$HOME/mongodb-counts-before.txt` (шаг 4.2);
- [ ] в журнале `receipt-collector` нет ошибок подключения/авторизации к Mongo (шаг 5.3);
- [ ] бот отвечает на команды (шаг 5.4.1);
- [ ] получение нового чека работает, счётчик чеков в БД растёт (шаг 5.4.2–5.4.3);
- [ ] веб-интерфейс аналитики показывает данные, количество чеков сходится (шаг 5.4.4);
- [ ] `receipt-analytics-migrations` завершён с кодом 0 (`Exited (0)`);
- [ ] старый каталог данных `$MONGO_DATA`(старый) и архив
      `$MONGO_BACKUP/final-pre81.archive` существуют и не удалялись.

После прохождения чек-листа система наблюдается 24–48 часов в штатном режиме.
**Удалять старый каталог данных и дампы в этот период запрещено** — они остаются
последней возможностью отката.

## Действия при проблемах <a name="проблемы"></a>

**1. `mongodump` завершается ошибкой / файл дампа пуст.**
Проверьте, что контейнер работает (`docker ps`), переменные загружены
(`echo "$MONGO_SECRET"` не пустой), а каталог `$MONGO_BACKUP` существует и
доступен на запись. Повторите дамп. Если не помогает — не останавливайте
работающие сервисы и привлекайте инженера.

**2. Контрольный restore расходится в счётчиках (шаг 1.3).**
Не начинайте миграцию. Возможные причины: дамп сделан при активной записи
(остановите приложения и снимите дамп заново по шагу 2.3 и повторите проверку);
повреждённый архив (снимите дамп заново). Привлекайте инженера, если повтор
не помог.

**3. Контейнер `receipt-mongo` (8.2.3) не становится healthy.**
Посмотрите причину: `docker logs receipt-mongo --tail 50`. Типовые причины:
в `MONGO_DATA` указан **непустой** каталог со старыми данными 4.x — сервер
завершается с ошибкой несовместимости формата. Решение: убедиться, что
`MONGO_DATA` указывает на новый **пустой** каталог (шаг 3.4), пересоздать
контейнер: `docker-compose -p receipt-collector up -d --force-recreate mongo`.
Не решается за 15 минут — [откат](#откат).

**4. `Authentication failed` при подключении к новой базе.**
Проверьте, что используются те же `$MONGO_LOGIN`/`$MONGO_SECRET`, что раньше
(`.env` не менялся в этих полях), и указан `--authenticationDatabase admin`.
Root-пользователь создаётся автоматически только на **пустом** каталоге данных.
Если каталог был не пуст и пользователь не создался — очистите новый каталог
(только новый!) и пересоздайте контейнер (см. п. 3).

**5. Restore сообщает о неудачных документах (`failed to restore`).**
Повторите restore целиком (шаг 4.1; `--drop` делает повтор безопасным).
Если ошибка повторяется — зафиксируйте полный вывод команды
(`... > $HOME/restore-errors.txt 2>&1`) и передайте инженеру;
до выяснения — [откат](#откат).

**6. Приложение (collector/bot/analytics) не стартует после миграции.**
Логи: `docker logs <имя> --tail 50`. Ошибки подключения к mongo — проверьте
шаг 3.6 (авторизация). Ошибки самого приложения — вероятно, не связаны
с миграцией; привлекайте инженера. Если система нужна пользователю срочно —
[откат](#откат).

**Общий критерий остановки работ:** если любая проблема не устранена за
30–60 минут или вы не уверены в состоянии системы — выполняйте откат.
Откат — штатная процедура, а не авария.

## Что нельзя удалять до окончания наблюдения <a name="наблюдение"></a>

В течение 24–48 часов (до подтверждения инженером) **сохранить**:

- старый каталог данных MongoDB 4.1 (прежнее значение `MONGO_DATA`);
- архив `$MONGO_BACKUP/final-pre81.archive`;
- архив `$MONGO_BACKUP/pre-upgrade-control.archive`;
- файл эталонных счётчиков `$HOME/mongodb-counts-before.txt`.

Только после успешного периода наблюдения старый каталог данных можно
архивировать/удалять (по согласованию с инженером); финальный архив
`final-pre81.archive` сохраняется постоянно как резервная копия.
