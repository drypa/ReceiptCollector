# План реализации: обновление MongoDB до 8.2.3 (dump/restore)

## Приоритет
HIGH

## Цель
Перевести MongoDB проекта с 4.1 на **8.2.3** во всех compose-окружениях (prod,
develop, dev-run) по схеме `mongodump → mongorestore` в новый чистый volume, без
изменения строк подключения приложений, с обновлением healthcheck и Go-драйвера,
а также подготовить самодостаточную инструкцию для персонала по ручным действиям
при миграции (FR-7).
Реализация строго по требованиям `docs/tasks/mongodb-upgrade-8-2.md` (FR-1…FR-7,
NFR-1…NFR-4) и архитектурному решению `docs/adr/015-mongodb-upgrade-8.2.md`
(D1–D6).

## Описание проблемы
MongoDB 4.1 — dev-релиз без исправлений безопасности. Формат данных несовместим
между мажорными версиями (запуск 8.2.3 на старом volume невозможен), healthcheck
compose использует удалённую из новых образов утилиту `mongo`, драйвер Go
v1.11.3 официально не поддерживает сервер 8.x. Дополнительно обнаружен дефект:
`backup.sh` дампит только базу `receipt_collection`, база `receipt-data` в бэкапы
не попадает.

## План работ

Работы сгруппированы в атомарные коммиты. Шаги 1–6 выполняются **до** окна
простоя; шаг 7 — сама миграция на проде; шаги 8–9 — закрытие задачи.

### Шаг 1. Обновление docker-compose конфигураций

- `docker-compose.yml`:
  - `image: mongo:4.1` → `image: mongo:8.2.3`;
  - healthcheck: `["CMD", "mongosh", "--quiet", "--eval", "db.adminCommand('ping').ok"]`,
    `start_period: 30s`;
  - volumes не меняются (`${MONGO_DATA}:/data/db`, `${MONGO_BACKUP}:/backup`);
  - `depends_on` сервисов не меняются (порядок старта обеспечивает `service_healthy`).
- `docker-compose.develop.yml`: `image: mongo:8.2.3`; healthcheck добавить
  опционально (в dev он отсутствует и не является блокером).
- Проверка: `docker compose config -q`, `docker compose -f docker-compose.develop.yml config -q`.

### Шаг 2. Обновление Go-драйвера (backend)

- `cd backend && go get go.mongodb.org/mongo-driver@v1.17 && go mod tidy`
  (последний доступный патч линейки v1.17.x);
- ожидаемых изменений кода нет (API v1.x стабильно); при ошибке компиляции —
  точечные правки по выводу компилятора;
- проверка: `go build ./...`, затем `go test ./...` против локального контейнера
  `mongo:8.2.3` (см. Шаг 4).

### Шаг 3. Скрипты бэкапа/восстановления и .env.example

- `backup.sh`: добавить второй дамп `--db receipt-data` (дефект покрытия);
- `.env.example`: новый дефолтный путь `MONGO_DATA` (чистый каталог для 8.2.3),
  комментарий о процедуре первого запуска;
- проверить, что `restore.sh` работает без изменений (инструменты вызываются
  внутри контейнера нового образа).

### Шаг 4. Репетиция миграции на dev

- поднять dev-mongo 8.2.3 (`./up.dev.sh`, предварительно очистив `./data`);
- восстановить копию продового дампа, прогнать `go test ./...` backend против неё;
- прогнать Analytics-миграцию Mongo→PostgreSQL, сверить количество чеков;
- замерить фактическое время restore — оценка длительности окна простоя.

### Шаг 5. Документация

- AGENTS.md / README: версия MongoDB, новый путь `MONGO_DATA`, обновлённая
  процедура бэкапа/восстановления, ссылка на ADR-015;
- финализировать runbook миграции (раздел «Процедура миграции» ADR-015) с
  результатами замеров из Шага 4.

### Шаг 6. Инструкция для персонала (FR-7)

Создать отдельный самодостаточный документ
**`docs/runbooks/mongodb-upgrade-manual-ops.md`** (новая директория `docs/runbooks`
— для операционных инструкций персонала; ADR и планы остаются внутренними
инженерными документами и не предназначены для исполнения оператором).

Требования к документу (FR-7, задача раздел 7):

- самодостаточность: оператор без знания внутренней архитектуры проекта
  выполняет миграцию, только следуя инструкции;
- подготовительный этап: проверки перед началом (свободное место на диске,
  локальное наличие образа `mongo:4.1` для отката, корректность `.env`,
  доступы, работоспособность текущих сервисов);
- пошаговые команды в порядке выполнения с **ожидаемым результатом каждой
  команды**;
- явные **точки принятия решений** между этапами: что проверить, как
  интерпретировать вывод, критерии «продолжаем / останавливаемся и откатываемся»;
- действия при проблемах: типовые сбои (healthcheck не зелёный, ошибка
  авторизации, расхождение счётчиков), критерии остановки;
- полная процедура отката на MongoDB 4.1;
- чек-лист финальных проверок и порядок запуска сервисов.

Структура документа:

1. Назначение и общее описание процедуры (что делаем, зачем, длительность);
2. Обозначения и соглашения (рабочий каталог, переменные `.env`, обозначения
   точек принятия решений);
3. Этап 0 — подготовительные проверки (чек-лист + команды);
4. Этап 1 — контрольный дамп до простоя и проверка его восстановимости
   во временном контейнере 8.2.3;
5. Этап 2 — начало окна простоя: остановка приложений, финальный дамп;
6. Этап 3 — переключение на MongoDB 8.2.3 (коммит, новый `MONGO_DATA`,
   старт только mongo);
7. Этап 4 — восстановление данных и сверка счётчиков документов;
8. Этап 5 — запуск сервисов и смоук-проверки;
9. Откат на MongoDB 4.1 (полная пошаговая процедура);
10. Чек-лист финальных проверок;
11. Действия при проблемах (типовые ошибки и реакции);
12. Что нельзя удалять до окончания периода наблюдения.

Источник содержимого — раздел «Процедура миграции», чек-лист и процедура отката
ADR-015; после репетиции (Шаг 4) в документ вносятся фактические значения
(длительность restore, реальные пути).

### Шаг 7. Миграция на прод (окно простоя)

По инструкции для персонала `docs/runbooks/mongodb-upgrade-manual-ops.md`
(Шаг 6); архитектурное описание — в ADR-015:

1. Контрольный полный дамп всех бизнес-баз + проверка восстановимости в тестовом
   контейнере 8.2.3 (сравнение счётчиков документов);
2. Остановка приложений (collector, bot, analytics; mongo оставить работать);
3. Финальный дамп `mongodump --gzip --archive=/backup/final-pre81.archive`;
4. Остановка контейнера mongo (каталог старого volume не трогать; убедиться, что
   образ `mongo:4.1` остался локально);
5. Применение коммитов (образ, healthcheck), переключение `MONGO_DATA` в `.env`
   на новый пустой каталог;
6. Старт только сервиса `mongo`, ожидание зелёного healthcheck (root создастся
   автоматически через `MONGO_INITDB_*`);
7. `mongorestore --drop --gzip --archive=... --nsInclude='receipt-data.*'
   --nsInclude='receipt_collection.*' --authenticationDatabase admin`;
   сверка счётчиков документов всех коллекций с дампом;
8. Смоук-проверки (чек-лист ниже), запуск сервисов в порядке: collector → bot →
   analytics (+ migrations) → nginx; `./up.sh`.

Чек-лист послемиграционных проверок:
- [ ] `receipt-mongo` на `mongo:8.2.3`, статус healthy;
- [ ] счётчики документов `receipt-data` и `receipt_collection` совпадают с дампом;
- [ ] backend без ошибок подключения в логах; регистрация, чеки, отчёты работают;
- [ ] воркеры опрашивают nalog.ru, новые чеки появляются в БД;
- [ ] бот отвечает на команды;
- [ ] Analytics: синхронизация Mongo→PostgreSQL проходит, число чеков сходится;
- [ ] `go test ./...` backend зелёный против новой БД.

### Шаг 8. Наблюдение и очистка

- наблюдение 24–48 часов после миграции;
- только после успешного периода: архивировать/удалить старый каталог `MONGO_DATA`
  и промежуточные дампы (финальный `final-pre81.archive` сохранить по политике
  бэкапов).

### Шаг 9. Закрытие

- отметить выполнение критериев приёмки задачи (раздел 5);
- зафиксировать фактическую длительность простоя и отклонения от инструкции

## Тестирование

- `docker compose config -q` — валидация обоих compose-файлов;
- `cd backend && go build ./... && go test ./...` — сборка и тесты против
  контейнера `mongo:8.2.3`;
- интеграционная репетиция на dev: dump→restore→смоук (Шаг 4);
- ручной смоук prod по чек-листу инструкции для персонала (Шаг 7);
- CI (`build-backend-image.yml`, CodeQL) зелёный на ветке изменений.

## Критерии успеха
- Все compose-окружения используют `mongo:8.2.3`; healthcheck на `mongosh` зелёный.
- Все коллекции обеих бизнес-баз восстановлены, счётчики документов совпадают с дампом.
- Строки подключения (`MONGO_URL`, connection string Analytics) не изменялись.
- Backend-функционал (чеки, пользователи, отчёты, waste) и Analytics-миграция работают без ошибок.
- `backup.sh` дампит обе базы; `restore.sh` работоспособен.
- Процедура миграции и отката задокументирована (ADR-015 + этот план), AGENTS.md обновлён.
- Подготовлена инструкция для персонала `docs/runbooks/mongodb-upgrade-manual-ops.md`
  (FR-7): самодостаточная, с командами и ожидаемыми результатами, точками принятия
  решений, процедурой отката и чек-листом.
- Откат возможен возвратом `MONGO_DATA` + git revert, проверен на репетиции.
