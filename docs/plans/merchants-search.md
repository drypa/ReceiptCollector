- Источник истины по поведению — ADR-037 и критерии приёмки/edge cases задачи; ничего не отменяет ADR 008, 011, 032, 023, 027.
- Схему БД, миграции и новые индексы **не** добавлять.
- Wire-контракт `GET /api/merchants` не ломать: путь/метод/коды ответов/формат массива `MerchantDto` и смысл `X-Total-Count`/`limit`/`offset` прежние; `search` — существующий параметр, расширяется семантика (`name OR inn`) и переносится фильтрация в источник данных до подсчёта/пагинации.
- Null-безопасность ИНН: `Merchant.Inn` может быть `null`/отсутствовать — сравнение по ИНН не должно бросать исключения и не должно скрывать магазин, совпавший по названию.
- Пустой/пробельный `search` эквивалентен отсутствию фильтра. Термин — `Trim(search)`, частичное совпадение без учёта регистра по `Name` **или** `Inn` (OR). Один и тот же магазин не дублируется.
- Остальные эндпоинты модуля Merchants (`PUT` категории/имени/дефолта, `POST apply`, `GET /categories`), существующие действия страницы (таблица, размер страницы, обновление, действия с магазинами), доступ только для администратора, подсветка совпадений, прочие страницы/сервисы (чеки, «Товары», бот, backend, предкатегоризация), nginx/конфигурация/`docker-compose.yml`/`.env.example`/`AGENTS.md` — **вне области**.

## Задача 01. Репозиторий: постраничное чтение магазинов с фильтром `name OR inn`

**Статус:** `approved`

### Цель
Реализовать в слое данных постраничную выборку магазинов с необязательным поисковым термином: фильтр `name OR inn` применяется в запросе к БД **до** `COUNT`, `ORDER BY`, `SKIP/TAKE`; вернуть страницу и общее количество по тому же отфильтрованному предикату. Эндпоинт (задача 02) перестанет материализовать всю таблицу.

### Затрагиваемые области (ожидаемо)
- `Analytics/src/ReceiptCollector.Analytics.Domain/Modules/Merchants/IMerchantRepository.cs`
- `Analytics/src/ReceiptCollector.Analytics.Infrastructure/Persistence/Postgres/MerchantRepository.cs`
- При необходимости (по факту проекта/паттерну) — модель результата постраничного чтения в Domain/Application; существующие методы и их семантика не менять.
- Тесты инфраструктуры/репозитория (при наличии подходящей инфраструктуры в проекте): `Analytics/tests/ReceiptCollector.Analytics.Api.Tests/Infrastructure/*Merchant*Repository*` и/или новые тесты рядом с существующими тестами репозитория магазинов.

### Шаги реализации
1. Добавить **аддитивный** метод/контракт постраничного чтения с фильтром (например, `(IReadOnlyList<Merchant> Items, int TotalCount) GetPageAsync(int limit, int offset, string? searchTerm, CancellationToken ct)` или эквивалентный контракт по стилю проекта), не меняя сигнатуры и поведение `GetAllAsync`, `GetByIdAsync`, `GetByInnAsync`, `UpdateCategoryAsync`, `GetDefaultCommodityCategoriesAsync`, `AddAsync`.
2. В `MerchantRepository` сформировать запрос `AsNoTracking()` к `Merchants`:
   - без `searchTerm` — без фильтра;
   - с `searchTerm` (уже нормализованным/непустым на входе метода либо с явной нормализацией — зафиксировать единообразно) — предикат: `Name` содержит термин **ИЛИ** (`Inn != null` И `Inn` содержит термин), сравнение без учёта регистра. Для PostgreSQL/EF Core предпочтителен провайдерный перевод (`EF.Functions.ILike` или эквивалент) с параметризацией вида `%term%` (без конкатенации в сырой SQL) — семантика: substring, case-insensitive.
3. `COUNT` вычислять по **тому же** предикату, что и выборку страницы. Страница: `ORDER BY Name` + стабильный tie-breaker (например, `Id`) для детерминированной пагинации → `Skip(offset).Take(limit)`.
4. Убедиться, что условие по `Inn == null` не приводит к исключениям и не отбрасывает совпадения по имени (null-ИНН трактуется как «нет совпадения по ИНН»).
5. Пустой результат: корректно вернуть пустую страницу и `TotalCount = 0`.

### Критерии приёмки
- [ ] В `IMerchantRepository` есть аддитивная возможность получить страницу магазинов и `total` по фильтру `search`; существующие методы интерфейса/реализации не изменены по смыслу.
- [ ] Фильтр (при непустом термине) применяется в запросе до `COUNT`/сортировки/`Skip`/`Take`; в память не загружается вся таблица ради страницы.
- [ ] Предикат: частичное, регистронезависимое совпадение по `Name` **или** `Inn`; пустой/отсутствующий термин — без фильтра.
- [ ] `Inn == null` не вызывает ошибок; магазин без ИНН находится по совпадению имени.
- [ ] Порядок детерминирован (сортировка по `Name` со стабильным вторичным ключом).
- [ ] Миграции/схема БД/индексы не добавлены.

### Тесты / проверки
- Юнит/инфраструктурные тесты репозитория/запроса (по существующему паттерну проекта для `MerchantRepository`): фильтр до `COUNT/SKIP/TAKE` (страница и `total` соответствуют отфильтрованному набору при `limit/offset`), совпадение по `Name` и по `Inn`, null-ИНН не ломает фильтрацию, детерминированный порядок, пустой результат → пустая страница и `0`.
- Если полноценный тест репозитория против БД в проекте не принят — зафиксировать покрытие на уровне задачи 02 (эндпоинт с контролируемым репозиторием/интеграционный тест по факту инфраструктуры) и явно отразить в сводке; не ослаблять критерии ADR.
- `dotnet build` / `dotnet test` релевантных проектов Analytics (минимум затронутые тесты) — без регрессий.

### Что НЕ входит
- Изменения `GET /api/merchants` и HTTP-поведения (задача 02).
- Frontend (задача 03).
- Изменение существующих методов репозитория, схемы БД, миграций, индексов.
- Поиск/фильтрация на других страницах и в других сервисах.

## Задача 02. API `GET /api/merchants`: серверная фильтрация/пагинация и автотесты эндпоинта

**Статус:** `pending`

### Цель
Перевести `GET /api/merchants` на постраничное чтение из репозитория (задача 01): нормализовать `search`, вычислять `X-Total-Count` и страницу по отфильтрованному набору в источнике данных, сохранить контракт и коды ответов. Покрыть поиск автотестами эндпоинта по плану ADR.

### Затрагиваемые области (ожидаемо)
- `Analytics/src/ReceiptCollector.Analytics.Api/Modules/Merchants/MerchantEndpoints.cs` (`GetAll`)
- `Analytics/tests/ReceiptCollector.Analytics.Api.Tests/MerchantEndpointsTests.cs` (расширение существующих тестов `GetAll` и добавление новых)

### Шаги реализации
1. В `GetAll` после проверки прав (`401`/`403`) и валидации `limit > 0`, `offset >= 0` (`400`, тексты ошибок без изменений по смыслу) нормализовать `search`: `null`/whitespace → без фильтра, иначе `Trim(search)`.
2. Заменить `GetAllAsync()` + in-memory `Where/Count/OrderBy/Skip/Take` на вызов метода постраничного чтения из задачи 01 с нормализованным термином, `limit`, `offset`.
3. Сформировать ответ `200 OK` с массивом `MerchantDto` (маппинг/поля без изменений, порядок по `Name` как сейчас — детерминизм обеспечен репозиторием), заголовок `X-Total-Count` = общее число **после фильтра**.
4. Пустой результат: `200 OK`, тело `[]`, `X-Total-Count: 0` (не `404`).
5. Остальные хендлеры модуля (`UpdateCategory`, `UpdateMerchantName`, `ListCategories`, `UpdateDefaultCommodityCategory`, `ApplyDefaultCommodityCategory`) не менять.

### Критерии приёмки
- [ ] `search` (Trim) фильтрует по `Name` **или** `Inn` (частично, без учёта регистра) на стороне данных; `total` и страница считаются по отфильтрованному набору.
- [ ] Пустой/пробельный `search` возвращает полный список с корректным `X-Total-Count` и пагинацией.
- [ ] Магазин без ИНН находится по названию; отсутствие/`null` ИНН не приводит к ошибкам при фильтрации.
- [ ] Фрагмент, совпадающий с названием одного магазина и ИНН другого — оба в выдаче (каждый один раз).
- [ ] Пустой результат поиска → `200`, `[]`, `X-Total-Count: 0`.
- [ ] Сохраняются `401` (нет пользователя), `403` (не-админ), `400` (невалидные `limit/offset`), формат `MerchantDto` и поведение остальных эндпоинтов модуля.
- [ ] Адаптированы существующие тесты `GetAll`, которые завязаны на `GetAllAsync()`/старую семантику, без ослабления их смысла.

### Тесты / проверки (автотесты эндпоинта, обязательно)
- `401` без пользователя, `403` для не-админа (существующее поведение сохранено).
- Совпадение по названию: частичное, регистронезависимое.
- Совпадение по ИНН: частичное.
- Фрагмент совпадает и с названием одного магазина, и с ИНН другого — оба в выдаче.
- Магазин без ИНН находится по названию и не ломает фильтр по ИНН.
- Пустой/пробельный `search` = полный список.
- Пустой результат → `200`, `[]`, `X-Total-Count: 0`.
- `X-Total-Count` и содержимое страницы соответствуют отфильтрованному набору при `limit/offset`.
- `dotnet test` для `ReceiptCollector.Analytics.Api.Tests` (минимум тесты модуля Merchants) — зелёные.

### Что НЕ входит
- Репозиторий/запрос к БД сверх контракта, согласованного в задаче 01.
- Frontend, миграции, индексы, изменение других эндпоинтов/страниц.
- Переход на ProblemDetails, изменение текстов ошибок, не относящихся к поиску.

## Риски и примечания для исполнителей

- **Изменение семантики `search`**: раньше фильтр был только по имени, теперь — `name OR inn`. Для админского UI это ожидаемое расширение (ADR-037, «Последствия»); иных известных потребителей параметра нет.
- **Гонки запросов на фронте:** при быстром вводе/перелистывании актуален только последний запрос (AbortController), итоговое состояние не должно «мигать» устаревшими данными — ориентир на паттерн precategorization/useMerchants.
- **Производительность:** substring-поиск без спец. индекса линеен по таблице; при текущем масштабе приемлемо, индексы — отдельное решение (вне задачи).
- После реализации каждой задачи — сводка в `docs/reviews/<feature-slug>/` (slug предложен: `merchants-search`, например `docs/reviews/merchants-search/01-repo-paged-search.md` и т.д.) и остановка до ручного ревью/коммита человеком.
