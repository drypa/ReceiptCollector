## Что сделано

„Предкатегоризация“» (ADR-036). Код задача не меняет: прогнана полная регрессия всех
сервисов (Analytics — 851 тест зелёные, включая Architecture-тесты; фронтенд — lint и

конфигурации, ни новых настроек), финальная реализация сверена с ADR-036 §9 «Явно

без изменений, эндпоинт-файл аддитивен). Подготовлена карта «критерий приёмки →

Особое внимание (по запросу вызывающей стороны, всё подтверждено): инвариант
`MaxBulkIds = MaxLimit = 200` (константы с взаимным комментарием + рефлексивный тест
`MaxBulkIds_equals_get_max_limit` + поведенческий 200/201); отсутствие порционности и
прогресса в клиенте (один `await` на операцию, один `fetch`, busy без чисел); одна
транзакция на батч (`READ COMMITTED`, `SELECT … FOR UPDATE` raw-SQL, порядок
`(normalized_name, merchant_id, id)`, один `COMMIT`); skipped-причины (wire-константы,
агрегация в сводку); `500` «ничего не применено» (дедлайн 90 с / прочий сбой /

## Остаточные риски

1. **Пробел автотеста (зафиксирован ревьюером)**: две `proposed`-строки с одинаковым
   наименованием у разных мерчантов не засеяны ни в одном Testcontainers-тесте
   (частичный случай — «независимые наименования» и «повторный запуск» — покрыт).
   Корректность выводится из построчного пути применения: для второй строки
   `UPDATE commodities` по тому же имени не найдёт товаров без категории →
   `updatedCommodities = 0`, но строка применится и даст своё событие журнала
   (решение всё состоялось, D10 ADR-027). Риск низкий. Закрыт пунктом 16 чек-листа
   ручной приёмки; при желании — досев в `PrecategorizedBulkRepositoryTests` отдельным
  коммитом вне этой фичи.
2. **Плюриализация диалога** — см. «Оставлено без изменений», эскалация
   @software-architect.
3. **Дубль `BULK_LOCKED_TITLE`** (две копии константы) — отдельный гигиенический
   коммит человеком.
4. **Длительность на реальном объёме**: стоимость строки — Seq Scan по `commodities`
   без индекса на `name` (риск 6 ADR-027, индекс — отдельное решение). Замер на
   dev-стенде обязателен (пункт 8 чек-листа): при выходе за бюджет дедлайна 90 с —
   эскалация (уменьшение размера страницы или отдельное решение об индексе);
   порционность запрещена решением заказчика.

## Чек-лист ручной приёмки на dev-стенде

Пункты ADR-036 §8 «Ручной прогон» + задачи 10 (1–13) + замечания ревью сводок 07–10:

1. **Happy path confirm**: несколько страниц пагинации → «Подтвердить все» → диалог с
   `items.length` → busy без чисел → сводка «Подтверждено: N, пропущено: 0
   (+ обновлено товаров: K)» → автообновление, строки ушли из очереди.
2. **Happy path decline**: диалог с предупреждением «будут удалены безвозвратно»;
   сводка «Отклонено: N, пропущено: M»; `commodities` не изменились.
3. **Активный поиск**: `X-Total-Count > items.length`; payload запроса (DevTools)
   содержит только id отрисованных строк; строки других страниц под фильтром не тронуты.
4. **Второе окно**: строка подтверждена параллельно → в сводке «пропущено», причина
   «уже обработаны в другом окне»; операция не падает.
5. **Отмена диалога** — ни одного сетевого запроса (DevTools), ничего не меняется.
6. **Пустая страница** — обе массовые кнопки неактивны, `title` объясняет причину.
7. **Опустевшая страница**: последняя опустела → автопереход на предыдущую доступную,
   в Network ровно 2 запроса; полное опустошение очереди → пустое состояние
   «Нет предложений.», без ошибок (допустим один «лишний» запрос clamp 2→1 —
   предсуществующее поведение); восстановление после сбоя догрузки: при обрыве
   запроса-догрузки `currentPage` уже нормализован, рядом ошибка с «Попробовать
   снова» — повторная загрузка возвращает консистентные данные.
8. **Страница 100 строк**: busy-state без чисел, UI не «висит»; **замерить
   длительность операции и зафиксировать в этом файле/коммите** (ADR-036 §2.4).
   При выходе за бюджет дедлайна 90 с — эскалация @software-architect (уменьшение
   размера страницы или отдельное решение об индексе `commodities(name)`);
   порционность запрещена.
9. **Обрыв сети/дедлайн**: тост + inline «Операция не выполнена, изменения не
   применены.»; после обновления список консистентен; повторный запуск безопасен
   (обработанные → skipped).
10. **Двойной клик** — второй запрос не уходит; параллельная массовая операция из
    второго окна — вторая ждёт блокировки и пропускает уже обработанное.
11. **Не-админ**: кнопок нет; `curl` на `POST /api/precategorized-commodities/batch/confirm`
    и `/batch/decline` → `403`; поштучные `GET`, `PUT /{id}/category`,
    `POST /{id}/confirm`, `DELETE /{id}` отвечают как раньше.
12. **Кэш и журнал**: после confirm — `suggest` по имени даёт `source = cache`;
    в `categorization_decisions` по одному событию на applied-строку
    (`suggested` = исходное предложение, `final` = применённая категория);
    массовое отклонение событий не даёт.
13. **Правка админа**: категория, отредактированная через селект строки
    (`PUT /{id}/category`) до запуска, применяется массовым подтверждением.
14. **Доступность (замечание ревью 07)**: busy-строка и сводка — live-region'ы
    (`role="status" aria-live="polite"`), появляющиеся вместе с текстом; проверить
    ассистивными технологиями, что переход busy → сводка озвучивается без потери
    текста (в том числе вместе с дублирующим тостом).
15. **Узкие экраны (замечание ревью 08)**: третий flex-столбец `<header>` с
    `PrecategorizedBulkActions` корректно выглядит в media-запросе `.layout header`
    (`App.css`, ~строка 294).
16. **Одинаковые наименования у разных мерчантов (замечание ревью 10, остаточный
    риск 1)**: на странице две `proposed`-строки с одним названием товара, но разных
    мерчантов → массовое подтверждение применяет обе (у второй в сводке «обновлено
    товаров: 0» — товары первого уже с категорией), в журнале — два события, по одному
    на строку.
