- **Задача**: docs/plans/precategorized-bulk-operations.md#06-frontend-хук-массовых-операций-снимок-страницы-один-запрос-busyсводкаошибка
- **Дата**: 2026-11-13
- **Ревью**: раундов - 1, вердикт APPROVED

## Что сделано

Готов хук состояния массовых операций страницы «Предкатегоризация» —
`usePrecategorizedBulkOperations` (ADR-036 §5, инвариант 10 плана). Он инкапсулирует
UX-контракт «снимок — один запрос — итог»: в момент подтверждения диалога из переданных
`items` текущей страницы снимается `ids` (`items.map(i => i.id)`), далее уходит **ровно
один** вызов `confirmPrecategorizedBatch`/`declinePrecategorizedBatch` (A3), а по
завершении формируется итоговая сводка `BulkOperationSummary` (applied/declined,
skipped, updatedCommodities для подтверждения, сгруппированные счётчики причин пропусков
`already-applied`/`not-found`) и в `finally` вызывается `onCompleted()` — страница делает
`refresh()` и после успеха, и после ошибки.

Состояние хука: `isRunning` (busy без каких-либо чисел прогресса), `summary`, `error`,
`run(action, items)`, `reset()`. Повторный вызов `run` во время работающей операции —
no-op (синхронный guard через ref — edge case «одновременное нажатие двух кнопок»).
При ошибке в `error` попадает локализованный текст API-клиента («Операция не выполнена,
изменения не применены.»), серверный английский текст не подставляется (§1.5). Никакой
оркестрации на клиенте: ни порций, ни циклов, ни счётчиков, ни повторных запросов, ни
отмены (решения заказчика 4–5). Тосты, диалог и разметка в хук не входят — это задача 07.

## Итоги ревью

### Раунд 1 - APPROVED

Blockers нет: один сетевой вызов на `run`, снимок id в момент подтверждения, `onCompleted`
в `finally` при любом исходе, форма сводки и причин — по плану и §5, тостов/диалога в
хуке нет.

Принято и внедрено незаблокирующее замечание 1 (после него перепрогнаны lint и build):

1. **`runningRef.current = true` перенесён сразу после снимка `ids`** (был до
   `items.map(...)`, который вне `try/finally`): гипотетический синхронный бросок `map`
   больше не может оставить «залипший» флаг, блокирующий все последующие операции.
   Guard от двойного нажатия сохранён полностью: в однопоточном JS между проверкой и
   установкой флага нет точек переключения (первый `await` — только после установки).

Замечание 2 принято как заметка для задачи 07 (см. «Заметки для коммита»), код не менялся.

### Допущения и отклонения от текста плана

1. **Форма `BulkOperationSummary` — из плана дословно**; тип `action` — существующий
   `PrecategorizedBulkAction` (то же объединение `'confirm' | 'decline'`), `reasons` —
   через `PrecategorizedBulkSkipReason` вместо инлайн-литералов (тот же тип, меньше
   дублирования wire-имён).
2. **Пустой `items` в `run` не защищается отдельно**: единственная клиентская проверка
   «пустой список не отправляем» уже в API-клиенте (задача 05), UI пустой список не
   отправит (кнопки неактивны — задачи 07–08). При ошибочном вызове — `error` +
   `refresh()`, без падения. *Оценка ревьюера: принято, blocker не требуется.*
3. **Гонка «ответ пришёл после `reset()`» не обрабатывается generation-счётчиком**:
   `reset` вызывается при смене страницы/поиска, которые на время операции заблокированы
   (задача 08), а второй `run` невозможен guard'ом — сценарий недостижим; усложнение
   противоречило бы «клиентская логика минимальна». *Оценка ревьюера: принято, blocker
   не требуется.*
4. **Тосты не в хуке** — по границе задачи (презентация — 07): компонент 07 покажет тост
   ровно один раз, реагируя на переход `summary`/`error` из `null` (инвариант «без
   повторов на ре-рендерах» достигается тем, что сводка выставляется один раз на
   завершённую операцию).

## Заметки для коммита

Рекомендуемое сообщение коммита:

```text
t-06 Precategorized bulk FE: bulk operations hook (page snapshot, single request, busy/summary/error)
```

На что обратить внимание при ручной проверке:

- Состав коммита: новый хук, строка статуса в плане и эта сводка. Пересобранный
  `wwwroot/index.html` в коммите быть не должно. В диффе плана строка `05 → committed` —
  не правка этой задачи (её выставил оркестратор после коммита задачи 05); правка
  задачи 06 — только строка статуса `06`.
- Соответствие ADR прямо в диффе: ровно один `await` сетевого вызова на `run` (развилка
  `if/else` — два разных эндпоинта, но один путь на операцию); `ids` снимается до первого
  `await`; `finally` содержит `setIsRunning(false)` и `onCompleted()`; в коде нет чисел
  прогресса, циклов и `AbortController`.
- **Заметка для задачи 07 (по замечанию 2 ревью)**: если `onCompleted` (он же `refresh()`
  страницы) бросит, исключение уйдёт из `run()` как rejected promise — вызывающий код в
  компоненте 07 обязан либо не бросать в `refresh`, либо вызывать `run` с обработкой
  (`run(...).catch(...)` / обёртка вокруг колбэка). Состояние хука при этом остаётся
  корректным (`isRunning` уже сброшен в `finally`).
- Хук пока никем не вызывается (подключается в задачах 07–08); ручная проверка UX —
  в объёме задачи 10.
