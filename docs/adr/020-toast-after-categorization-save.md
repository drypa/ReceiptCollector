# ADR-020: Тост вместо модального окна после сохранения категоризации (Analytics UI)

## Статус

Принято (проект). Реализация — по плану
[docs/plans/toast-after-categorization-save.md](../plans/toast-after-categorization-save.md).

## Контекст

### Проблема

После сохранения категоризации товаров чека в Analytics UI появляется модальное окно
«Готово / Сохранено категорий: N» (`CustomDialog`), которое требуется закрыть нажатием кнопки.
Пользователь категоризирует товары пачками — лишний шаг замедляет работу. Задача
[toast-after-categorization-save](../tasks/toast-after-categorization-save.md) требует заменить
модальное окно на накапливающиеся тосты с авто-скрытием через 5 секунд.

### Текущее состояние кодовой базы (факты)

1. **Стек фронтенда Analytics** (`Analytics/frontend/`): React 19 + TypeScript, Vite,
   `react-router-dom` 7. **UI-кита и CSS-фреймворка нет** (нет MUI/antd/Bootstrap/Tailwind в
   `package.json`); стили — vanilla CSS в глобальных `App.css` и `index.css` с CSS-переменными
   (`--primary`, `--primary-hover`, `--muted-foreground`).
2. **Единственный переиспользуемый UI-компонент** — `components/CustomDialog.tsx` (модальное
   окно). Используется в `ReceiptDetails.tsx` в трёх сценариях: успех сохранения категорий, ошибка
   сохранения категорий, ошибки из других мест (категоризация, сохранение имени магазина).
3. **Точка изменения** — `components/ReceiptDetails.tsx`, функция `saveSelectedCategories()`
   (строки 177–197):
   - успех: `showDialog('Готово', 'Сохранено категорий: ${result.updated}.', onConfirm)` —
     обратный вызов `onConfirm` выполняет `setSuggestions(null); setSelectedCategories({}); onReceiptRefresh?.()`;
   - ошибка: `showDialog('Ошибка', error.message || fallback)`.
4. **Количество сохранённых** уже возвращается backend-контрактом без изменений:
   `saveReceiptCategories()` → `SaveCategoriesResult { receiptId, updated }` — текст тоста
   формируется на клиенте из `result.updated`. Изменений API/backend **не требуется**.
5. **Frontend-тестовой инфраструктуры в репозитории нет** (vitest/jest отсутствуют; регрессионный
   барьер — `npm run build` + `npm run lint` + ручная приёмка), зафиксировано в ADR 011 (решение E1).
6. Проект использует React-контексты как паттерн для сквозного состояния
   (`contexts/PageSizeContext.tsx`, `hooks/useAdmin.ts`).

### Бизнес-требования (из задачи)

1. Модальное окно «Готово» после сохранения категоризации больше не появляется.
2. Успех → тост «Сохранено категорий: N» с зелёным акцентом (N — фактическое число).
3. Ошибка → тост с красным акцентом, отличимый без чтения текста; модальное окно ошибки не
   возвращается.
4. Авто-скрытие через 5 секунд; ручное закрытие крестиком; тосты накапливаются (несколько
   одновременно).
5. Крайние случаи: быстрые повторные «Сохранить» (каждый ответ — свой тост, без наложений);
   ошибка сети/сервера; N = 0 (тост всё равно показывается).
6. Затрагивается только место после сохранения категоризации; остальные модальные окна Analytics
   не меняются.

## Рассмотренные варианты

### A. Реализация тостов: библиотека vs кастомный компонент

#### A1: Кастомный компонент на vanilla React + CSS — **выбран**

**Описание:** Собственный лёгкий тост-модуль (~100 строк): провайдер состояния, контейнер,
стили в `App.css`.

**Плюсы:**
- Ноль новых зависимостей (`package.json` не меняется) — соответствует требованию «внешних
  зависимостей нет» и практике проекта (без UI-кита).
- Целевая функциональность узкая (2 варианта: success/error, авто-скрытие, накопление) —
  библиотека (например, `react-hot-toast`) даёт 10× больше API, чем нужно.
- Стили тоста естественно ложатся на существующую дизайн-систему (CSS-переменные, те же
  цветовые палитры, что в `.state-error` / `.category-suggestion-ai`).

**Минусы:** Поддержка собственного кода (небольшая; компонент тривиален и стабилен).

#### A2: Внешняя библиотека тостов (`react-hot-toast` / `sonner`) — **отклонён**

**Минусы:** Новая runtime-зависимость ради одного места использования; конфликт со
сложившимся минималистичным стеком (vanilla CSS, свои компоненты); собственный компонент
по объёму сопоставим с «обвязкой» вокруг библиотеки. YAGNI.

### B. Архитектура тост-модуля

#### B1: Переиспользуемый модуль «Provider + hook», смонтированный в `App.tsx` — **выбран**

**Описание:** Один связный модуль `components/Toasts.tsx`: `ToastProvider` (контекст),
`useToast()` с методами `success(message)` / `error(message)`, внутренний контейнер тостов.
`ToastProvider` оборачивает дерево в `App.tsx` один раз. `ReceiptDetails` вызывает
`toast.success('Сохранено категорий: ' + result.updated)` / `toast.error(message)`.

**Плюсы:**
- Требование «тосты накапливаются» требует управляемого списка тостов — он естественно живёт
  в провайдере, а не в состоянии страницы; страница остаётся сфокусированной на бизнес-логике.
- Соответствует существующему паттерну проекта (контексты: `PageSizeContext`, `useAdmin`).
- Параллель с `CustomDialog`: переиспользуемый UI-компонент, а не одноразовая разметка внутри
  страницы; будущие места использования подключаются вызовом хука без рефакторинга.
- Изменение в `App.tsx` минимально (обёртка), поведение других модальных окон не затрагивается
  (требование 6).

**Минусы:** Небольшое «обобщение» сверх одного места использования — осознанный компромисс в
пользу единообразия с существующими паттернами и требования «накопления тостов».

#### B2: Локальное состояние списка тостов внутри `ReceiptDetails` — **отклонён**

**Описание:** Массив тостов + фиксированная разметка контейнера и таймеры внутри страницы.

**Минусы:** Дублирует контейнер/стили при любом следующем месте использования; раздувает
страничный компонент UI-логикой, не относящейся к деталям чека; сложнее тестировать изолированно.
Выигрыша нет: тост-модуль всё равно приходится писать, разница лишь в месте его объявления.

### C. Момент выхода из режима категоризации при успехе

#### C1: Выход из режима и обновление данных выполняются немедленно при успехе — **выбран**

**Описание:** Обратные вызовы подтверждающей кнопки модального окна
(`setSuggestions(null)`, `setSelectedCategories({})`, `onReceiptRefresh?.()`) выполняются сразу
после успешного ответа API и **до** показа тоста. Модальное окно с кнопкой «Ок», которая раньше
была единственным триггером этих действий, исчезает — поэтому действия должны выполняться
автоматически.

**Плюсы:** Соответствует сценарию задачи («сам исчезает, не требуя действий»); данные после
сохранения актуализируются сразу; режим категоризации не «застревает» после того, как
сохранение подтверждено.

**Минусы:** Меняется последовательность «сохранили → подтвердили → вышли из режима» на
«сохранили → вышли из режима». Это и есть цель задачи; риск ошибочного действия («не успел
проверить и нажал не туда») мал, т.к. выйти из режима можно кнопкой «Отмена».

#### C2: Сохранить подтверждающий шаг, заменив только визуализацию — **отклонён**

**Описание:** Тосты показываются, но выход из режима категоризации остаётся на пользователе.

**Минусы:** Воспроизводит тот же лишний шаг, который задача и устраняет; противоречит сценарию
использования.

### D. Обработка ошибки сохранения

#### D1: Ошибка сохранения → красный тост; другие ошибки ReceiptDetails остаются модальными — **выбран**

**Описание:** В `saveSelectedCategories` catch заменяется на `toast.error(...)` (текст берётся
из `error.message`, как сейчас). Остальные сценарии с `CustomDialog` (`runCategorization` —
ошибка определения категорий, `saveMerchantName`, «ID магазина отсутствует») **не трогаются** —
это соответствует границе задачи (требование 6).

**Плюсы:** Точное попадание в критерии приёмки («модальное окно ошибки не возвращается» для
сохранения); минимальный diff; остальные диалоги не регрессируют.

**Минусы:** После ошибки пользователь остаётся в режиме категоризации с прежними выборами —
это желаемое поведение (можно повторить сохранение, ничего не теряется).

#### D2: Все ошибки на странице перевести на тосты — **отклонён**

**Минусы:** Расширение области задачи сверх требований; риск скрыть блокирующие контекстные
ошибки (например, невозможность определить категории), которые релевантны текущему режиму.

### E. Стилизация и доступность тостов

#### E1: Акцентная планка + иконка, фиксированный стек в правом верхнем углу, ARIA-роли — **выбран**

**Описание:**
- `role="status"` (успех) / `role="alert"` (ошибка) — различие доступно и скринридерам;
- различие «без чтения текста» достигается двумя независимыми признаками: цвет левой планки-акцента
  (зелёный `#16a34a`-палитра / красный `#dc2626` — красный уже используется в проекте для ошибок)
  и иконка (✓ / ✕) контрастного цвета;
- контейнер — `position: fixed`, верхний правый угол, стек вертикальной колонкой с отступами;
  `z-index: 1100` (выше `dialog-overlay`, у которого `z-index: 1000` — гипотеза «тост поверх
  диалога» не нужна в текущем сценарии, но не повредит);
- плавное появление (слайд вниз + fade), без анимации закрытия (KISS: мгновенное удаление;
  авто-скрытие и так мягкое);
- кнопка закрытия — «×» с `aria-label`; каждый тост — свой таймер 5000 мс, очищаемый при
  ручном закрытии и unmount (без `setState` на размонтированном компоненте).

**Плюсы:** Полное покрытие критериев приёмки (отличимость по цвету и иконке, авто-скрытие,
ручное закрытие, накопление); доступность из коробки.

**Минусы:** Пауза по hover не реализуется (YAGNI — требование фиксирует 5 секунд без
исключений). Каждый тост висит ровно 5 секунд независимо от других.

## Решение

Выбраны: **A1** (кастомный тост-модуль без зависимостей), **B1** (переиспользуемый
`ToastProvider` + `useToast()`, смонтирован в `App.tsx`), **C1** (выход из режима категоризации
и обновление данных — немедленно при успехе), **D1** (ошибка сохранения → красный тост,
остальные диалоги не меняются), **E1** (акцентная планка + иконка + ARIA, авто-скрытие 5 с,
ручной крестик, стек в правом верхнем углу).

### Обоснование

1. **Соответствие стеку проекта:** vanilla CSS + React без UI-кита; ноль новых зависимостей
   (A1); контекст-паттерн уже используется (B1).
2. **Минимальность и границы задачи:** backend не меняется (`result.updated` уже в контракте);
   меняется только `saveSelectedCategories` и его обработка успеха/ошибки; остальные
   `CustomDialog` — без изменений (D1).
3. **Поведенческая корректность:** немедленный выход из режима категоризации и `onRefresh()`
   при успехе компенсируют исчезновение подтверждающей кнопки (C1); ошибки не «проглатываются» —
   текст ошибки попадает в тост (D1).
4. **KISS/YAGNI:** пауза при наведении, анимация закрытия, позиционирование под управлением
   пользователя сознательно не реализуются — требования задачи фиксируют единственный формат.

### Детали решения

**Новый модуль** `Analytics/frontend/src/components/Toasts.tsx`:

- `ToastProvider` — контекст с состоянием `ToastItem[]`
  (`{ id: string; type: 'success' | 'error'; message: string }`);
  метод `push(type, message)` добавляет тост с уникальным `id`
  (`crypto.randomUUID()`, fallback — счётчик) и планирует удаление через `setTimeout(…, 5000)`;
  `dismiss(id)` — ручное удаление (очищает таймер).
- `useToast()` — хук, возвращает `{ success(message: string): void; error(message: string): void }`.
- `ToastContainer` — рендер списка: `role="status"` / `role="alert"` для тоста, кнопка «×»
  (`aria-label="Закрыть уведомление"`), классы `.toast`, `.toast--success`, `.toast--error`.
- Очистка таймеров при unmount провайдера (общий `Map<id, timeoutId>` + `useEffect` cleanup).

**`Analytics/frontend/src/App.tsx`:**

- Дерево оборачивается `<ToastProvider>` (внутри `BrowserRouter`, вокруг `<PageSizeProvider>`).
  Другие провайдеры и маршруты не меняются.

**`Analytics/frontend/src/components/ReceiptDetails.tsx`** — меняется только
`saveSelectedCategories`:

- успех: сразу `setSuggestions(null); setSelectedCategories({}); onReceiptRefresh?.();`
  затем `toast.success('Сохранено категорий: ' + result.updated)` (текст без точки —
  тост, не предложение; при `updated = 0` текст корректен);
- ошибка: `toast.error(error instanceof Error ? error.message : 'Не удалось сохранить категории товаров')`;
  режим категоризации и выборы сохраняются — пользователь может повторить;
- `showDialog('Готово', …)` и связанный `dialog`-стейт для сценария успеха **удаляются из
  saveSelectedCategories**; `showDialog` и `CustomDialog` остаются для других сценариев страницы
  (категоризация, имя магазина) без изменений.

**`Analytics/frontend/src/App.css`** — новые стили:

- `.toast-container` — `position: fixed; top: 1rem; right: 1rem; display: flex; flex-direction:
  column; gap: 0.6rem; z-index: 1100;`
- `.toast` — белый фон, `border-radius`, тень, левая акцентная планка `4px solid currentColor`
  (через `border-left`), иконка ✓/✕ через псевдоэлемент или inline-SVG; анимация появления.
- `.toast--success` — зелёный акцент (`#16a34a`/`#22c55e`);
- `.toast--error` — красный акцент (`#dc2626`, палитра уже используется в `.state-error`).
- `.toast-close` — кнопка «×».

**Без изменений:** `package.json` (зависимости), конфигурация Vite/TS, backend (Go), .NET API,
`CustomDialog.tsx`, другие страницы и компоненты (`CommoditiesPage`, `CommodityTable`,
`MerchantsPage`, `ReceiptTable`, `Pagination`, `Layout`, `Sidebar`).

### Карта изменений (для плана)

| Файл | Действие |
|------|----------|
| `Analytics/frontend/src/components/Toasts.tsx` | новый модуль (provider + hook + container) |
| `Analytics/frontend/src/App.tsx` | обернуть дерево `<ToastProvider>` |
| `Analytics/frontend/src/components/ReceiptDetails.tsx` | `saveSelectedCategories`: успех → выход из режима + `onRefresh()` + `toast.success`; ошибка → `toast.error`; удалить вызов `showDialog('Готово', …)` для сохранения |
| `Analytics/frontend/src/App.css` | стили `.toast-container`, `.toast`, `.toast--success`, `.toast--error`, `.toast-close` |
| Backend, .NET API, остальной frontend | без изменений |

## Последствия

### Положительные

- Пользователь не застревает на модальном окне после каждого сохранения: тост сам исчезает
  через 5 секунд, ручное закрытие и накопление поддерживаются.
- Успех и ошибка различимы без чтения текста (цвет планки + иконка).
- Ноль новых зависимостей; решение вписывается в текущий стек (vanilla CSS, React-контексты).
- Выход из режима категоризации и обновление списка происходят сразу после успешного ответа —
  данные актуальны, лишних подтверждений нет.
- Модуль переиспользуем (любая будущая точка — один вызов `useToast()`), при этом не
  задействован нигде, кроме цели задачи.

### Отрицательные

- Немного усложняется `App.tsx` (обёртка-провайдер — косметика) и появляется новый UI-модуль.
- Меняется UX-последовательность «подтверждение успеха» — мгновенный выход из режима
  категоризации (осознанно, по сценарию задачи).
- Сообщения об ошибках в тостах могут остаться незамеченными после авто-скрытия (5 секунд);
  ошибка сохранения также не «блокирует» экран — пользователь остаётся в режиме категоризации,
  что позволяет сразу повторить.

### Компромиссы

- **Свой компонент вместо библиотеки** — простота и ноль зависимостей против небольшой
  собственной поддержки (A1).
- **Глобальный провайдер вместо локального состояния** — готовность к переиспользованию и
  чистота страницы против лёгкого «обобщения» сверх одного места (B1).
- **Немедленный выход из режима категоризации** — устранение лишнего шага против редкого
  сценария «нужно было перепроверить перед выходом» (C1).
- **Без паузы по hover и анимации закрытия** — строгое выполнение требований 5 секунд против
  более «мягкого» UX (E1).

### Риски

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Утечка таймеров / `setState` после unmount | Низкая | Общий `Map` таймеров + cleanup на unmount провайдера; `dismiss` очищает таймер |
| Тост поверх диалога ошибочно перекрывает контент | Низкая | `z-index: 1100`; колонка в правом верхнем углу, диалоги центрированы — пересечение маловероятно |
| «Незамеченная» ошибка сохранения (тост ушёл за 5 с) | Средняя (по дизайну задачи) | Красный акцент + автоблокирующей логики нет; пользователь остаётся в режиме категоризации, ошибка видна в действии «не сохранилось» |
| Дублирование `id` тостов при крайне быстрых нажатиях | Очень низкая | `crypto.randomUUID()` + fallback-счётчик |
| Регрессия других диалогов `ReceiptDetails` | Низкая | Меняется только `saveSelectedCategories`; `showDialog`/`CustomDialog` в остальных сценариях не трогаются; ручная приёмка по чек-листу задачи |
