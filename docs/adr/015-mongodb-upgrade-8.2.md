# 15. Обновление MongoDB с 4.1 до 8.2.3 через mongodump → mongorestore

## Статус
Принято. Решения по всем открытым вопросам подтверждены заказчиком
(docs/tasks/mongodb-upgrade-8-2.md, раздел 6):

1. **Окно простоя** — допустимо до нескольких часов (объём данных небольшой);
   жёстких ограничений по времени суток нет.
2. **Схема миграции** — только одношаговая: 4.1 → 8.2.3 сразу через
   `mongodump → mongorestore`.
3. Исправление дефекта покрытия `backup.sh` (база `receipt-data`) выполняется
   в рамках этой задачи.
4. Дополнительно зафиксировано требование **FR-7**: отдельная самодостаточная
   инструкция для персонала по ручным действиям при миграции —
   [docs/runbooks/mongodb-upgrade-manual-ops.md](../runbooks/mongodb-upgrade-manual-ops.md).
   Runbook в этом ADR остаётся архитектурным описанием процедуры; оператор
   выполняет работу по инструкции для персонала.

## Контекст

Проект использует MongoDB **4.1** (`image: mongo:4.1` в `docker-compose.yml` и
`docker-compose.develop.yml`, контейнер `receipt-mongo`). Версия 4.1 — нечётная,
то есть **dev-релиз**, который вендором никогда не рекомендовался для эксплуатации,
не является LTS и давно не получает исправлений безопасности.

Задача: docs/tasks/mongodb-upgrade-8-2.md. Цель — перевести хранилище на актуальную
версию **8.2.3** без потери данных, со строками подключения без изменений и с
проверенной процедурой отката.

### AS-IS (проверено по репозиторию)

| Элемент | Текущее состояние |
|---|---|
| Образ prod | `mongo:4.1` (docker-compose.yml:6), контейнер `receipt-mongo` |
| Образ dev | `mongo:4.1` (docker-compose.develop.yml:3), volume `./data:/data/db`, healthcheck отсутствует |
| Volumes prod | `${MONGO_DATA}:/data/db` (host bind, по умолчанию `/home/drypa/receipts/backup`) и `${MONGO_BACKUP}:/backup` |
| Healthcheck | `["CMD", "mongo", "--quiet", "--eval", "db.adminCommand('ping').ok"]` — утилита `mongo` удалена из образов начиная с 6.0 |
| Зависимости сервисов | `collector`, `bot`, `analytics` стартуют через `depends_on: mongo: condition: service_healthy` |
| Root-пользователь | создаётся автоматически через `MONGO_INITDB_ROOT_USERNAME/PASSWORD` при инициализации пустого datadir |
| Backend (Go) | драйвер `go.mongodb.org/mongo-driver v1.11.3`; подключение `options.Client().ApplyURI(url).SetAuth(Credential{...})` (backend/mongo_client/mongo-client.go:28), authSource по умолчанию — `admin`; базы `receipt-data`, `receipt_collection` |
| Analytics (.NET) | `MongoD­B.Driver 2.24.0`, строка подключения `mongodb://login:pass@mongo:27017/receipt_collection?authSource=admin`, только чтение |
| Бэкап | `backup.sh`: `mongodump --gzip --db receipt_collection` — **дампит только одну базу**; база `receipt-data` не попадает в бэкапы |
| Восстановление | `restore.sh`: `mongorestore --drop --gzip /backup/$1` |

### Ограничения, определившие решение

1. **Формат данных несовместим между мажорными версиями.** Файлы WiredTiger из
   datadir 4.1 не могут быть прочитаны сервером 8.x напрямую; запуск 8.2.3 на старом
   volume невозможен. Нужен либо логический перенос (dump/restore), либо цепочка
   последовательных in-place обновлений.
2. **In-place путь для 4.1 практически неприемлем**: официальные переходы требуют
   пошагового обновления через промежуточные минорные ветки (4.1 → 4.4 → 5.0 → 6.0 →
   7.0 → 8.0 → 8.2), каждая ступень — отдельный контейнер, ожидание, проверка FCV.
   Для single-node стенда это часы работ и высокий риск на каждой ступени.
3. **Драйвер Go v1.11.3 официально протестирован вендором максимум против сервера 7.0**
   (матрица совместимости MongoDB). Против сервера 8.x работа формально не
   гарантируется (wire protocol обратно совместим, но это не покрыто тестами вендора).
   Поддержка сервера 8.0 добавлена в драйвере начиная с линейки v1.17.
4. **Healthcheck сломается**: shell `mongo` удалён из образов с версии 6.0 — нужен
   `mongosh`.

## Решение

Логическая миграция **mongodump → mongorestore в новый чистый volume** одним шагом
(4.1 → 8.2.3), с обновлением драйвера Go до линейки v1.17.x и переводом healthcheck
на `mongosh`. Окно простоя закрывает вопрос консистентности: на время миграции
приложения остановлены, поэтому дельта данных между дампом и восстановлением
отсутствует. Подтверждённое окно простоя «до нескольких часов» с запасом покрывает
оценку длительности (минуты на restore при текущем объёме данных; точная цифра —
по результатам репетиции на dev, см. план работ, шаг «Репетиция миграции на dev»).

### D1. Путь миграции: dump/restore одним шагом

Полный дамп бизнес-баз (`receipt-data`, `receipt_collection`) из работающего
контейнера 4.1 → восстановление в свежепроинициализированный контейнер 8.2.3.

Обоснование:
- единственный надёжный способ перепрыгнуть 5 мажорных версий;
- механизм уже освоен командой (`backup.sh` / `restore.sh`);
- дамп одновременно служит точкой отката (FR-3);
- mongorestore восстанавливает документы и все индексы; счётчики документов
  проверяются по выводу restore (NFR-2).

Исключения из дампа: служебные базы `admin`, `local`, `config`. Пользователи из
старого `admin.system.users` **не переносятся** (см. D3).

### D2. Новый чистый volume, старый сохраняется как точка отката

Значение `MONGO_DATA` в `.env` меняется на новый пустой каталог хоста
(например, `${MONGO_DATA}` = `/home/drypa/receipts/mongo82-data`). Старый каталог с
файлами 4.1 остаётся нетронутым и используется только при откате.

- compose-файлы продолжают ссылаться на переменную `MONGO_DATA` — изменения
  инфраструктуры сводятся к правке образа, healthcheck и `.env`;
- откат = вернуть прежнее значение `MONGO_DATA` и тег образа, `up` — данные 4.1
  подхватятся как были;
- в dev-окружении (`./data`) локальные данные считаются расходными: каталог
  очищается перед первым стартом 8.2.3, восстановление из дампа опционально.

### D3. Пользователи: пересоздание через MONGO_INITDB_*, а не restore

На пустом datadir контейнер 8.2.3 сам создаст root-пользователя из уже заданных
`MONGO_INITDB_ROOT_USERNAME=${MONGO_LOGIN}` / `MONGO_INITDB_ROOT_PASSWORD=${MONGO_SECRET}`.
Новый пользователь получит механизмы SCRAM-SHA-1/SHA-256, оба клиента (Go-драйвер и
.NET-драйвер) поддерживают их без изменений строк подключения (NFR-3).

Восстановление `admin.system.users` из дампа 4.1 сознательно исключено: схема
хранения пользователей менялась между версиями, перенос устаревших записей —
избыточный риск ради единственного учётного записи root, который пересоздаётся
декларативно.

### D4. Обновление Go-драйвера до v1.17.x (в рамках этой задачи)

`go.mongodb.org/mongo-driver` обновляется с v1.11.3 до последнего релиза линейки
v1.17 (первая линейка с официальной поддержкой сервера 8.0+).

- API внутри линейки v1.x стабильно, ожидаемых изменений кода нет — только
  `go get … && go mod tidy` и прогон тестов;
- переход на мажорный драйвер v2 (`go.mongodb.org/mongo-driver/v2`) **не делается**:
  требует изменения import-path'ов и части API, не относится к цели задачи;
- .NET-драйвер `MongoDB.Driver 2.24.0` по матрице вендора совместим с сервером 8.x —
  не трогаем, подтверждаем смоуком Analytics (критерий FR-4).

### D5. Healthcheck на mongosh

```yaml
healthcheck:
  test: ["CMD", "mongosh", "--quiet", "--eval", "db.adminCommand('ping').ok"]
  interval: 10s
  timeout: 5s
  retries: 10
  start_period: 30s   # увеличен: первая инициализация datadir дольше, чем рестарт
```

Порядок старта сервисов менять не нужно: `depends_on: service_healthy` у
`collector`/`bot`/`analytics` уже гарантирует подключение только к готовому серверу;
меняется лишь сама команда проверки.

### D6. Актуализация скриптов бэкапа

Попутно исправляется дефект `backup.sh`: добавляется дамп второй базы
(`--db receipt-data`), чтобы регулярные бэкапы покрывали все бизнес-данные.
`restore.sh` остаётся без изменений по смыслу (инструменты берутся из нового образа
автоматически, т.к. выполняются внутри контейнера `receipt-mongo`).

## Процедура миграции (прод)

> **Примечание.** Ниже — архитектурное описание процедуры с обоснованием шагов.
> Для выполнения на проде оператор использует самодостаточную пошаговую
> инструкцию [docs/runbooks/mongodb-upgrade-manual-ops.md](../runbooks/mongodb-upgrade-manual-ops.md)
> (FR-7): в ней те же шаги, но с точными командами, ожидаемым выводом,
> точками принятия решений и критериями остановки/отката.

Предварительно вся процедура обкатывается на dev-окружении (`up.dev.sh` + копия
дампа прода).

1. **Подготовка (до окна простоя):**
   - обновить compose-файлы (образ 8.2.3, mongosh-healthcheck), go.mod, `.env.example`,
     документацию — закоммитить, но на прод не выкатывать;
   - убедиться, что образ `mongo:4.1` присутствует локально на проде
     (`docker images mongo:4.1`) — он нужен для отката без интернета;
   - выполнить контрольный дамп и проверить его восстановимость в тестовом
     контейнере 8.2.3 (сравнить счётчики документов).
2. **Начало окна простоя:** `./down.sh` (или остановить только приложения:
   collector, bot, analytics, nginx — mongo оставить работать).
3. **Финальный дамп всех баз:**
   ```bash
   docker exec receipt-mongo mongodump --gzip --archive=/backup/final-pre81.archive \
     --username $MONGO_LOGIN --password $MONGO_SECRET --authenticationDatabase admin
   ```
4. **Остановка старого контейнера:** `docker compose -p receipt-collector stop mongo`
   (volume-каталог 4.1 не удалять!).
5. **Переключение конфигурации:** применить коммит (образ 8.2.3, mongosh),
   указать в `.env` новый `MONGO_DATA`.
6. **Старт нового mongo:** запустить только сервис `mongo`, дождаться зелёного
   healthcheck (root создастся автоматически).
7. **Restore** (только бизнес-базы; служебные `admin`/`config`/`local` из архива
   не восстанавливаются — пользователь root уже создан через `MONGO_INITDB_*`,
   см. D3):
   ```bash
   docker exec receipt-mongo mongorestore --drop --gzip \
     --archive=/backup/final-pre81.archive \
     --nsInclude='receipt-data.*' --nsInclude='receipt_collection.*' \
     --username $MONGO_LOGIN --password $MONGO_SECRET --authenticationDatabase admin
   ```
   Сверить счётчики документов по всем коллекциям с этапом 1/3.
8. **Проверки:** смоук backend (`go test ./...` локально против новой БД +
   ручные запросы API), старт collector, воркер начал опрос nalog.ru, чеки
   создаются; затем bot, analytics (миграция Mongo→Postgres, число чеков сходится).
9. **Полный старт:** `./up.sh`, наблюдение 24–48 часов. Старый каталог `MONGO_DATA`
   и дамп не удалять до успешного закрытия периода наблюдения.

### Чек-лист послемиграционных проверок

- [ ] `docker ps` — `receipt-mongo` на `mongo:8.2.3`, статус healthy;
- [ ] healthcheck отвечает (`mongosh ... ping.ok` = 1);
- [ ] счётчики документов всех коллекций `receipt-data` и `receipt_collection` равны счётчикам из дампа;
- [ ] backend поднялся, в логах нет ошибок подключения/авторизации;
- [ ] регистрация пользователя, получение чека по штрихкоду, отчёты работают;
- [ ] воркеры опрашивают nalog.ru (логи `worker.GetReceiptStart`), новые чеки появляются в БД;
- [ ] бот отвечает на команды (report и др.);
- [ ] Analytics: синхронизация Mongo→PostgreSQL завершается, количество перенесённых чеков совпадает;
- [ ] `cd backend && go test ./...` зелёный против 8.2.3.

### Процедура отката

Применима в любой момент до удаления старых артефактов (полные команды с
ожидаемыми результатами — в инструкции для персонала, раздел «Откат»):

1. Остановить приложения и mongo: `./down.sh`.
2. Вернуть в `.env` прежний `MONGO_DATA` (каталог 4.1 не был изменён).
3. Откатить коммит переключения (образ `mongo:4.1`, старый healthcheck):
   `git revert <commit>` или checkout предыдущего тега.
4. Дамп `final-pre81.archive` сохранить — он же точка восстановления данных.
5. `./up.sh`. Потеря данных, накопленных после миграции, допускается и закрыта
   окном простоя (NFR-4): до прохождения всех проверок чек-листа collector
   не оставляется работать в прод-режиме.

## Последствия

- **Положительные**: поддерживаемая вендором версия (исправления безопасности до
  заявленного EOL); один шаг вместо цепочки in-place обновлений; дамп = готовая
  точка отката; строки подключения всех сервисов не меняются; попутно исправлен
  дефект покрытия бэкапа (только `receipt_collection`).
- **Отрицательные/риски**:
  - простой сбора чеков на время миграции — допустим до нескольких часов
    (решение заказчика); ожидаемая фактическая длительность — минуты, точная
    оценка фиксируется на dev-репетиции;
  - драйвер Go v1.17 может принести транзитивные обновления зависимостей в
    `go.sum` — гасится прогоном тестов и CodeQL;
  - если откат понадобится после того, как воркеры успели записать новые чеки в
    8.2.3, эта дельта будет потеряна (принято, NFR-4);
  - dev-окружение теряет локальные данные `./data` (расходные, восстановимы дампом).
- **Нейтральные**: FCV свежего инстанса = 8.2 сразу (restore не понижает FCV);
  репликации в системе нет (single-node), поэтому шаги replica set отсутствуют.

## Альтернативы

1. **Поэтапный in-place upgrade** (4.1→4.4→…→8.2 с сохранением volume) — отвергнуто:
   многоступенчатость на single-node, каждая ступень несёт риск и время, итоговое
   состояние то же, а точка отката хуже (обратно по цепочке почти невозможно).
2. **Запуск 8.2 на старом volume** — технически невозможно (несовместимость формата
   WiredTiger между мажорными версиями).
3. **Двойная запись / CDC (change streams)** в параллельный 8.2 — отвергнуто:
   требует изменений кода backend ради разовой миграции; оправдано только при
   недопустимости простоя, чего в требованиях нет (NFR-1).
4. **Не обновлять драйвер Go** — отвергнуто: v1.11.3 официально не поддерживает
   сервер 8.x; экономия одного `go get` не оправдывает негарантированную
   совместимость основного потребителя БД.

## Решения заказчика (раздел закрыт)

Все открытые вопросы подтверждены владельцем продукта (см. раздел «Статус»):

1. Окно простоя — до нескольких часов, ограничений по времени суток нет.
2. Одношаговая схема 4.1 → 8.2.3 (dump/restore) — подтверждена.
3. Исправление `backup.sh` включено в эту задачу.

Открытых вопросов не осталось.
