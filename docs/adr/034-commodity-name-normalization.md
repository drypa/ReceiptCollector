# ADR-034: Усиление нормализации названий товаров (снятие артикулов, штрихкодов и мусорных префиксов)

## Статус

[commodity-name-normalization](../tasks/commodity-name-normalization.md) (статус Draft, автор user,
дата 2026-11-09; FR-1…FR-5, NFR-1…NFR-4, критерии приёмки и edge cases обязательны к исполнению).
Реализация — по плану (декомпозиция задачи в `docs/plans/`).

> Go-сервисов, MongoDB, nginx; ретеншен журнала.

## Контекст

### Проблема

Текущая нормализация (`CommodityNameNormalizer.NormalizeName`) выполняет только
`Trim().ToLowerInvariant()` и схлопывание пробелов. В названиях из чеков встречаются технические
артикулы, SKU и EAN-13 в начале и в конце, а также ведущие `*`, `#`, `№`:

- `2417268000006 ПИРОГ С ВИШНЕЙ ПО РЕ` — ведущий EAN-13;
- `2444436000001 СЕТ ДУЭТ 256г` — ведущий EAN-13;
- `*3455614 РЖ.КРАЙ Хлеб нар.300г` — ведущая звёздочка + артикул;
- `2195738 Туалетная бумага "СВАЁ" (3сл, 4р) 4810981001530` — артикул в начале и EAN-13 в конце.

Последствия:

1. **Загрязнение запроса к ИИ.** В `CommodityCategoryResolver` в ИИ уходит сырое имя (шаг 5
   передаёт `g.First().Name`, а не ключ группировки); в фоне
   (`PrecategorizationBackgroundService`) — тоже сырое `candidate.Name`. Коды не несут смысла для
   категоризации и искажают промпт.
2. **Один товар — разные ключи.** Кэш, дедупликация пакетного suggest, журнал и поиск по очереди
   предкатегоризации используют нормализованное или точное имя. Из-за кодов один и тот же товар
   считается разными: повторно уходит в ИИ и дублируется в `precategorized_commodities`
   (4000+ записей).
3. **Очередь ищется по точному сырому имени** (`GetCategoriesByExactNamesAsync`:
   `nameList.Contains(p.Name)`), поэтому очистка кэша без изменения поиска по очереди не даёт
   эффекта.

### Требования (из задачи, сводка)

- **FR-1** — снимать непрерывные цифровые последовательности от 6 знаков в начале/конце и ведущие
  `*`, `#`, `№`; не трогать `256г`, `нар.300г`, `(3сл, 4р)`, `РЖ.КРАЙ`, `АИ-95`, `1000 ЛЕПЕСТКОВ`;
  сохранять lowercase/trim/collapse; при пустом результате — исходное имя.
- **FR-2** — очищенное имя уходит в ИИ во всех suggest-сценариях (чек, «Товары», фон).
- **FR-3** — очищенное имя — единый ключ кэша, дедупликации пакетного suggest, resolver'а, поиска
  по очереди и `normalized_name` новых событий журнала.
- **FR-4** — сырые данные не теряются: `commodity_name` журнала и имена в UI — исходные; история
  журнала не пересчитывается.
- **FR-5** — миграция удаляет `proposed`-строки очереди, сохраняет `applied`; безопасна на пустой
  таблице и идемпотентна.
- **NFR-1** — автопроставление запрещено.
- **NFR-2** — интерфейс и контракты API не меняются.
- **NFR-3** — нормализация детерминирована, без побочных эффектов, накладные расходы несущественны.
- **NFR-4** — существующие тесты `dotnet test` зелёные.

## Рассмотренные варианты

### A. Где живёт правило очистки

#### A1: расширить `CommodityNameNormalizer` (C#) — **выбран**

Единственная функция нормализации получает шаги снятия кодов/мусора. Все существующие call sites
(кэш, resolver, пакетный сервис, фон, журнал) уже вызывают её — новый ключ распространяется без
дублирования правила.

**Плюсы:** один источник истины (DRY); нет SQL-зависимости в runtime; тестируется обычными
юнит-тестами; изменение минимально.

**Минусы:** SQL-backfill миграции вынужден повторить правило (одноразово) — риск дрейфа, см. п. 2.

#### A2: SQL-функция `normalize_commodity_name(text)` в PostgreSQL — **отклонено**

**Минусы:** тесты создают схему через `EnsureCreatedAsync()` по EF-модели — функции из миграций там
нет; runtime-запросы стали бы зависеть от миграции; правило размножилось бы в двух местах
постоянно, а не одноразово; PostgreSQL-специфичный regex становится частью контракта.

#### A3: отдельные регулярки в каждом call site — **отклонено**

**Минусы:** нарушает DRY и инвариант «одна нормализация» (ADR-019/027/033); расхождения между
кэшем, очередью, журналом и ИИ неизбежны.

### B. Как хранить очищенный ключ в очереди

#### B1: колонка `normalized_name varchar(256) NOT NULL` — **выбран**

Сырое `name` остаётся для UI и журнала; `normalized_name` — ключ поиска/дедупликации. Значение
пишется один раз при вставке (`TryAddProposalAsync`) и backfill'ится для `applied`-строк.

**Плюсы:** индексный поиск; нет SQL-нормализации в runtime; сырые данные сохранены; тесты на
EF-модели видят колонку.

**Минусы:** +1 колонка и 2 индекса; нужен backfill и preflight длины.

#### B2: вычислять нормализацию SQL-выражением на лету — **отклонено**

**Минусы:** нет индексируемого ключа (seq scan по выражению); функция/выражение должны существовать
в тестовой схеме; дрейф с C#; усложнение каждого запроса.

#### B3: не менять схему, искать по точному имени — **отклонено**

**Минусы:** прямо не выполняет FR-3; коды продолжают размножать очередь и промахи кэша.

### C. Исключение уже обработанных кандидатов в фоне

`GetCandidatesAsync` уже исключает точные пары `(name, merchant_id)` в любом статусе и любые
`proposed`-строки с тем же сырым именем. После перехода на очищенный ключ этих условий недостаточно:
варианты с кодом и без кода должны считаться одним товаром.

#### C1: C#-pre-check `HasBlockingQueueEntryAsync(normalizedKey, merchantId)` — **выбран**

Перед existing/кэшем/ИИ фон проверяет по индексируемой колонке: есть ли строка с тем же
`normalized_name` у этого же магазина (любой статус) **или** любая `proposed`-строка с тем же ключом
(любой магазин). Один запрос на кандидата (BatchLimit ≤ 5), на порядки дешевле вызова ИИ.

**Плюсы:** нет SQL-нормализации; тестируется; точно повторяет семантику текущих NOT EXISTS, но по
очищенному ключу; сохраняет защиту от повторных предложений.

**Минусы:** N+1 в фоне (маленький, ограничен BatchLimit); сырые NOT EXISTS в `GetCandidatesAsync`
остаются как дополнительный фильтр (безвредная избыточность).

#### C2: SQL-нормализация внутри `GetCandidatesAsync` — **отклонено**

**Минусы:** см. B2/A2: функция/выражение, отсутствие в тестовой схеме, дрейф, seq scan.

#### C3: без pre-check, полагаться на unique-индекс и catch — **отклонено**

**Минусы:** фон снова и снова выбирал бы заблокированные кандидаты (после рестарта/сброса курсора),
делал бы лишние вызовы ИИ и писал Warning'и о конфликтах; очищенный ключ не участвовал бы в
исключении.

### D. Подтверждение строки очереди

#### D1: `commodities` — по точному сырому имени; sibling delete удаляется как мёртвая ветка — **выбран**

Семантика confirm (ADR-027 D10) сохраняется в части обновления: обновляются только товары с точно
таким же сырым именем и без категории; подтверждение остаётся человеческим, массового применения по
очищенному ключу нет (NFR-1).

Удаление «сестринских» `proposed`-строк **не реализуется**, потому что после T-02 их существование
невозможно. Шаг 2 миграции удаляет все `proposed`, а шаг 8 создаёт **глобальный** частичный
уникальный индекс `ux_precategorized_commodities_normalized_proposed (normalized_name) WHERE
status = 0`. Следовательно, в момент confirm подтверждаемая строка — единственная `proposed` своего
очищенного ключа, и любой `DELETE ... WHERE normalized_name = @key AND status = 0 AND id <> @id`
гарантированно удаляет 0 строк. Существующая ветка удаления по точному сырому имени мертва по той же
причине: одинаковое сырое имя даёт одинаковый очищенный ключ, а все старые `proposed` удалены
миграцией.

Обратная сторона сохранения точного имени: подтверждение варианта с кодом не проставит категорию
варианту без кода (и наоборот) — второй вариант получит предложение из кэша/очереди и потребует
отдельного подтверждения. Это осознанно: массовое применение к «похожим» именам было бы
автопроставлением (NFR-1).

> **Уточнение по итогам ревью T-02 (2026-11-09, смоук на реальном PostgreSQL).** Вторая `proposed`-
> строка с тем же очищенным ключом у другого магазина отклоняется `23505 unique_violation`. Значит
> состояние «sibling `proposed` с тем же ключом» недостижимо в проде, а delete-ветка — доказуемый
> no-op, а не «защита на всякий случай». Решение: **удалить ветку** и не добавлять её вариант по
> `normalized_name`. Confirm выполняет ровно три шага: `UPDATE commodities` по точному имени без
> категории, `status = applied` + `applied_at`, commit. Отклонение (`DELETE .../{id}`) по-прежнему
> удаляет ровно одну строку по `id`.

**Плюсы:** KISS/YAGNI — нет кода, который не может выполниться; на каждый confirm не тратится лишний
`DELETE`; инвариант держится в БД (самое надёжное место), а не в приложении; не нужен тест, который
пришлось бы создавать в обход собственного ограничения; при будущем ослаблении индекса код не начнёт
молча удалять предложения другого магазина по «похожему» ключу.

**Минусы:** нет. Если инвариант когда-нибудь будет ослаблен (снят или изменён partial unique),
решение пересматривается вместе с ним — это фиксируется здесь, а не «страхуется» недостижимой веткой.

#### D2: обновлять `commodities` по нормализованному ключу (массово) — **отклонено**

**Минусы:** требует нормализации `commodities` в SQL/runtime; массово меняет категории товаров,
которые администратор не видел; прямо конфликтует с NFR-1 и риском «разные товары слиплись».

#### D3: обновлять точное имя + все варианты, найденные в C# — **отклонено**

**Минусы:** неограниченная выборка/материализация вариантов; тот же риск массового применения;
сложнее транзакция и тесты.

#### D4: сохранить sibling delete как defense-in-depth — **отклонено**

Оставить удаление «сестринских» `proposed` (по сырому имени или по `normalized_name`) и покрыть его
тестом с искусственным сидом, где две `proposed`-строки имеют один очищенный ключ.

**Минусы:** ветка защищает от состояния, которое запрещает сама БД; чтобы создать его в тесте, нужно
обойти `ux_precategorized_commodities_normalized_proposed` (в тестовой схеме индекс создаётся по
EF-модели), то есть проверить недостижимый путь и получить ложное чувство покрытия; в проде ветка не
выполняется ни разу; при будущем ослаблении индекса delete по очищенному ключу начнёт удалять
предложения других магазинов — побочный эффект, которого никто не заказывал.

### E. Миграция данных

#### E1: delete `proposed` → backfill `applied` → NOT NULL → индексы — **выбран**

Соответствует FR-5: неподтверждённые предложения пересоберутся по новым правилам; `applied` —
история действий администратора — сохраняется и получает `normalized_name`.

#### E2: удалить все строки (`proposed` + `applied`) — **отклонено**

**Минусы:** теряется история подтверждений; нарушает FR-5; `applied`-строки защищают от повторных
предложений.

#### E3: backfill всех строк без удаления `proposed` — **отклонено**

**Минусы:** старые `proposed` остаются с прежними (загрязнёнными) именами и не пересобираются;
цель задачи не достигается.

#### E4: оставить колонку nullable, backfill лениво — **отклонено**

**Минусы:** инвариант «у каждой строки есть ключ» слабеет; lookup пропускает NULL; сложнее
эксплуатация; NOT NULL после backfill — дешёвая и проверяемая гарантия.

### F. Журнал решений

#### F1: сырое `commodity_name` + очищенный `normalized_name`; ключ сочетания — сырой — **выбран**

FR-4 требует сохранить сырое имя; ADR-033 E1 использует `(commodity_name, source, suggested, final)`
как ключ сочетания. Очистка меняет только производное `normalized_name`; история не пересчитывается.

**Плюсы:** не меняет семантику журнала; варианты с кодом и без остаются различимыми событиями;
поиск по `normalized_name` (ADR-033 п. 7) находит оба варианта.

**Минусы:** в журнале по-прежнему две строки для вариантов с кодом и без; это осознанно — журнал
фиксирует решения по конкретным сырым именам.

#### F2: нормализовать ключ сочетания — **отклонено**

**Минусы:** меняет FR-7 ADR-033 (дедуп по сырому имени), схлопывает разные решения, делает
несопоставимыми старые и новые события.

#### F3: пересчитать историю — **отклонено**

**Минусы:** прямо запрещено задачей (FR-4, «Вне объёма»).

## Решение

Сводка: **A1** (единственный C#-нормализатор), **B1** (колонка `normalized_name` в очереди),
**C1** (C#-pre-check кандидатов по очищенному ключу), **D1** (confirm: `commodities` — по точному
сырому имени; sibling delete отсутствует, так как глобальный unique `proposed` делает его
недостижимым), **E1** (delete `proposed` + backfill `applied`), **F1** (журнал: сырое имя +
очищенный `normalized_name`, ключ сочетания сырой).

### Обоснование

1. **Один источник правила** (A1): все ключи и промпты уже проходят через
   `CommodityNameNormalizer`; расширение функции — минимальное изменение с максимальным покрытием.
2. **Ключ там, где он нужен** (B1): очередь — единственное хранилище, где поиск шёл по точному
   имени; колонка + индекс дают дешёвый lookup без SQL-нормализации.
3. **Runtime без SQL-функций** (C1): тесты создают схему из EF-модели; перенос правила в SQL сделал
   бы поведение зависимым от миграции и породил бы постоянный дрейф.
4. **Никакого автопроставления** (D1): нормализация меняет только ключ/промпт; подтверждение
   остаётся человеческим и по-прежнему применяется к точному сырому имени.
5. **Сырые данные неприкосновенны** (F1): `commodities.name`, `precategorized_commodities.name` и
   `categorization_decisions.commodity_name` не переписываются; история журнала не пересчитывается.

### 1. Каноническое правило очистки

Единственный источник — `CommodityNameNormalizer.NormalizeName` (Domain). Вход — непустая ссылка
`name`, `null` → `ArgumentNullException` (как сейчас).

```text
1. base    = CollapseWhitespace(name.Trim().ToLowerInvariant())
             CollapseWhitespace(s) = Regex.Replace(s, @"\s+", " ")

2. cleaned = Regex.Replace(base, @"^(?:[\s*#№]+|[0-9]{6,})+", "")

3. cleaned = Regex.Replace(cleaned,
             @"(?:^|\s)[0-9]{6,}(?:\s+[0-9]{6,})*\s*$", "")

4. cleaned = CollapseWhitespace(cleaned.Trim())

5. если cleaned пуст ИЛИ в cleaned нет ни одной буквы
   [A-Za-zА-Яа-яЁё]  →  вернуть base
   иначе              →  вернуть cleaned
```

Смысл шагов:

- **Шаг 2** снимает в начале любые комбинации пробелов, `*`, `#`, `№` и непрерывные цифровые
  последовательности от 6 знаков. Комбинация повторяется, поэтому `**##№№ 2417268000006 ` снимается
  целиком.
- **Шаг 3** снимает в конце кластер цифровых последовательностей от 6 знаков, разделённых пробелами
  (например, `123456 7890123`). Кластер должен начинаться в начале строки или после пробела; код,
  примыкающий к букве/дефису, консервативно не снимается (см. «Явно зафиксированные семантики»).
- **Шаг 5** — защита от пустого ключа и от имени, состоящего только из кода/пунктуации: возвращается
  нормализованный оригинал (`base`), а не пустая строка.

Цифры — только ASCII `[0-9]`; «непрерывная последовательность» — без пробелов и дефисов внутри.
Регулярные выражения объявляются через `[GeneratedRegex]`; для ограниченной сложности и
предсказуемости допускается `RegexOptions.NonBacktracking` (шаблоны не используют lookaround/
backreference).

### 2. Схема PostgreSQL и миграция

Скрипт `Analytics/src/ReceiptCollector.Analytics.Migrations/Scripts/20261109120000_add_precategorized_normalized_name.sql`
(транзакция на скрипт, учёт в `migration_scripts_history` — повторный запуск runner'ом не выполняется):

```sql
-- 1. Колонка nullable: backfill ниже, затем NOT NULL.
ALTER TABLE precategorized_commodities
    ADD COLUMN normalized_name varchar(256);

-- 2. FR-5: неподтверждённые предложения удаляются и будут пересобраны фоном.
DELETE FROM precategorized_commodities
 WHERE status = 0;

-- 3. Одноразовая SQL-копия правила (только для backfill; в runtime не используется).
--    pg_temp — временная схема сессии, после миграции функция исчезает.
CREATE FUNCTION pg_temp.normalize_commodity_name(raw_name text) RETURNS text
LANGUAGE sql IMMUTABLE AS $$
    WITH base AS (
        SELECT regexp_replace(
                   regexp_replace(lower(raw_name), '^\s+|\s+$', '', 'g'),
                   '\s+', ' ', 'g') AS value
    ),
    cleaned AS (
        SELECT regexp_replace(
                   regexp_replace(
                       regexp_replace(value, '^(?:[\s*#№]+|[0-9]{6,})+', ''),
                       '(?:^|\s)[0-9]{6,}(?:\s+[0-9]{6,})*\s*$', ''),
                   '\s+', ' ', 'g') AS value
        FROM base
    )
    SELECT CASE
        WHEN btrim(c.value) = '' OR btrim(c.value) !~ '[A-Za-zА-Яа-яЁё]'
            THEN btrim(b.value)
        ELSE btrim(c.value)
    END
    FROM base AS b, cleaned AS c;
$$;

-- 4. Preflight: аномальное удлинение lowercase не должно молча обрезаться.
DO $$
BEGIN
    IF EXISTS (
        SELECT 1
        FROM precategorized_commodities
        WHERE status = 1
          AND length(pg_temp.normalize_commodity_name(name)) > 256
    ) THEN
        RAISE EXCEPTION
            'normalized_name exceeds varchar(256) for applied precategorized_commodities';
    END IF;
END $$;

-- 5. Backfill только applied (proposed уже удалены).
UPDATE precategorized_commodities
   SET normalized_name = pg_temp.normalize_commodity_name(name)
 WHERE status = 1
   AND normalized_name IS NULL;

-- 6. Инвариант: у каждой оставшейся строки есть ключ.
ALTER TABLE precategorized_commodities
    ALTER COLUMN normalized_name SET NOT NULL;

-- 7. Поиск по очищенному ключу (любой статус) и pre-check кандидатов.
CREATE INDEX ix_precategorized_commodities_normalized_name
    ON precategorized_commodities (normalized_name);

-- 8. Один proposed на очищенный ключ глобально (как FR-3.4 ADR-027, но по очищенному ключу).
CREATE UNIQUE INDEX ux_precategorized_commodities_normalized_proposed
    ON precategorized_commodities (normalized_name)
    WHERE status = 0;

-- 9. Временная функция больше не нужна.
DROP FUNCTION pg_temp.normalize_commodity_name(text);
```

Существующие ограничения сохраняются:

- `ux_precategorized_commodities_name_merchant (name, merchant_id)` — точная пара, история/защита
  от дублей;
- `ix_precategorized_commodities_status (status, created_at)` — админская выборка.

Новый partial unique-индекс **глобальный** (не по магазину): это продолжение семантики FR-3.4
ADR-027 («наименование с proposed-строкой у другого магазина не предлагается»), но по очищенному
ключу. `applied`-строки в него не входят и могут существовать у разных магазинов; для них работает
существующая уникальность `(name, merchant_id)`.

#### Порядок деплоя (обязателен)

`analytics-migrations` в `docker-compose.yml` — run-to-completion, `analytics` зависит от него через
`service_completed_successfully`. Миграция меняет схему, которую старый код не умеет заполнять
(`normalized_name NOT NULL`), поэтому:

1. Снять дамп таблицы (она небольшая): `pg_dump -t precategorized_commodities` (или общий
   `./backup.sh`) — для отката.
2. **Остановить Analytics** (или хотя бы фон):
   `docker compose stop analytics` (контейнер `receipt-analytics`); альтернатива —
   `Precategorization__Enabled=false` + рестарт, но для одного инстанса проще остановить.
3. Применить миграции: `docker compose run --rm analytics-migrations` (или
   `docker compose up analytics-migrations`).
4. Запустить новый образ: `docker compose up -d analytics`.

Если не остановить старый код, между `ADD COLUMN` и `SET NOT NULL` он может вставить `proposed`-
строки с `normalized_name = NULL`; `SET NOT NULL` упадёт (миграция откатится — это безопасно, но
деплой потребует повтора). После `SET NOT NULL` старый код будет падать на вставке с NOT NULL
violation и писать Warning'и — данные не повредятся, но фон будет «шуметь». Поэтому остановка —
часть процедуры, а не рекомендация.

#### Откат

- До миграции: остановить/запустить прежний образ, схема не менялась.
- После успешной миграции: простой откат образа **невозможен** — старый код не заполняет NOT NULL
  колонку. Варианты: (а) восстановить дамп `precategorized_commodities`, удалить новые индексы и
  колонку, запустить прежний образ; (б) forward-fix новым образом. `commodities` и
  `categorization_decisions` миграция не меняет, поэтому их данные не затрагиваются.
- Удалённые `proposed`-строки — намеренная потеря (FR-5); при необходимости восстанавливаются из
  дампа.

#### Идемпотентность и дрейф SQL ↔ C#

- Идемпотентность обеспечивает `MigrationRunner` (повторный запуск скрипта не выполняется). Сам
  `DELETE` безопасен на пустой таблице; ручное повторное выполнение только шага удаления без
  остановки фона удалит уже пересобранные `proposed` — это допустимый «сброс», но не штатная
  операция (полный скрипт повторно не выполняется: `ADD COLUMN` уже применён).
- SQL-копия правила — **одноразовая**, только для backfill. В runtime нормализация всегда C#.
  Дрейф поэтому влияет максимум на `normalized_name` исторических `applied`-строк, а не на текущие
  ключи.
- Меры против дрейфа: одинаковые regex в ADR, C# и SQL-комментариях; golden-corpus тест
  (см. п. 6); после миграции — контрольный запрос «нет `applied`-строк с пустым/несовпадающим
  ключом» на корпусе примеров; опционально — интеграционный тест на Testcontainers PostgreSQL,
  применяющий скрипт и сравнивающий значения с `CommodityNameNormalizer` на корпусе.

### 4. Потоки после изменения

#### 4.1. Suggest чека (`POST /api/receipts/{id}/categories/suggest`)

Порядок `existing → merchant-default → cache → precategorized → ai` не меняется
(ADR-028 п. 9, ADR-032). Меняются только ключи:

1. `existing` — без изменений (категория уже у позиции).
2. `merchant-default` — без изменений.
3. `cache`: `normalized = NormalizeName(item.Name)`; `TryGet(normalized)`.
4. `precategorized`: собрать `Distinct` очищенных имён позиций; один batch-запрос
   `GetCategoriesByNormalizedNamesAsync`; lookup по очищенному ключу.
5. `ai`: группировка по очищенному ключу; в `IAiClient` уходит **ключ группы** (очищенное имя), а не
   `g.First().Name`; результат словаря — по очищенному ключу; каждой позиции — её исход (по
   очищенному ключу). В ответе `name` — сырое.

Контракты, `503` при пустом `AI:BaseUrl`, коды и тексты ошибок — без изменений. Ошибка чтения
очереди по-прежнему логируется Warning и деградирует к ИИ (FR-9.6 ADR-027).

#### 4.2. Пакетный suggest страницы «Товары» (`POST /api/commodities/categories/suggest`)

Использует тот же resolver, поэтому п. 4.1 применим целиком. Дополнительно:

- серверный лимит `MaxUniqueNames` считается по сырым именам (как сейчас) — это защитный лимит
  размера порции, а не ключ дедупликации; клиент по-прежнему шлёт ≤ 5 уникальных названий;
- дедупликация вызовов ИИ — по очищенному ключу в resolver'е; два варианта с кодом и без кода дают
  один вызов ИИ и один и тот же результат;
- `aiAvailable`, `SuggestTimeout`, частичный `200`, assign-only сохранение — без изменений.

#### 4.3. Фон предкатегоризации (`PrecategorizationBackgroundService`)

Для каждого кандидата (BatchLimit ≤ 5 за сессию):

1. Проверка длины сырого имени (существующая, ≤ 256) — без изменений.
2. `normalized = NormalizeName(candidate.Name)` (один раз).
3. `HasBlockingQueueEntryAsync(normalized, candidate.MerchantId)`:
   есть строка с тем же ключом у этого магазина в любом статусе **или** любая `proposed`-строка с
   тем же ключом у любого магазина → кандидат пропускается, курсор двигается.
4. Глобальный `existing` — по **точному сырому** имени (без изменений; ограничение зафиксировано).
5. Кэш — по `normalized`.
6. ИИ — `SuggestCategoryAsync(normalized, …)` (очищенное имя).
7. `TryAddProposalAsync`: пишет сырое `name` + `normalized_name`; guard длины сырого и очищенного
   имени; unique-конфликт (любой из двух индексов) — no-op.

Сырое имя остаётся в логах/UI/строке очереди; в ИИ и ключах — очищенное. Ошибка pre-check'а
обрабатывается существующим per-candidate `catch` (Warning, кандидат пропускается — fail-safe, без
дубля предложения). Настройки фона (`Precategorization:*`), рабочее окно (ADR-030) и single-instance
допущение — без изменений.

#### 4.4. Журнал решений (`CategorizationDecisionRecorder`)

Код не меняется: `commodity_name` = сырое имя после `Trim`; `normalized_name` = новая
`NormalizeName`; guard на 256 для обоих. Следствия:

- новые события хранят очищенный `normalized_name` и сырое `commodity_name` (FR-4);
- ключ сочетания ADR-033 остаётся `(commodity_name, suggestion_source, suggested, final)` —
  варианты с кодом и без остаются разными строками выдачи;
- поиск ADR-033 по `normalized_name` находит оба варианта;
- накопленная история не пересчитывается (FR-4).

#### 4.5. Подтверждение и отклонение строки очереди

Контракты, коды ответов и статусы не меняются (ADR-027 D10). Confirm в одной транзакции:

1. загрузить строку по `id`; нет строки → `NotFound`, `applied` → `Conflict` (без изменений);
2. `UPDATE commodities SET category_id, category_name WHERE name = <точное сырое имя> AND
   (category_id IS NULL OR category_id = 0)` — только точное имя, без нормализации (NFR-1);
3. `status = applied`, `applied_at = now`, commit.

Шага «удалить сестринские `proposed`» нет: глобальный partial unique по `normalized_name`
гарантирует, что подтверждаемая строка — единственная `proposed` своего очищенного ключа (D1).
Отклонение (`DELETE .../{id}`) по-прежнему удаляет ровно одну строку по `id` и не затрагивает
`commodities`.

### 5. Явно зафиксированные семантики

| Вопрос | Решение |
|---|---|
| Что считается кодом | Непрерывная последовательность ASCII-цифр `[0-9]` длиной ≥ 6 в начале или в конце; разделители (пробел, дефис) внутри номера не распознаются |
| Ведущий мусор | `*`, `#`, `№` и пробелы в любой комбинации, повторно, только в начале |
| Хвостовой мусор | Не снимается; снимается только цифровой хвост (кластер через пробелы) |
| Цифры < 6 | Не снимаются: `АИ-95`, `256г`, `нар.300г`, `1000 ЛЕПЕСТКОВ`, `(3сл, 4р)` |
| Бренд `РЖ.КРАЙ` | Не снимается (буквы/точка, не цифровой код); применяется только lowercase |
| Пустой результат очистки | Fallback на `base` (нормализованный оригинал), не пустая строка |
| Нет букв после очистки | Fallback на `base` (имя из кода/пунктуации); «буква» — `[A-Za-zА-Яа-яЁё]`, другие письменности — см. открытый вопрос 8 |
| Регистр/пробелы | Lowercase + trim + collapse — как раньше |
| Код в середине названия | Не снимается (вне правила) |
| Код, примыкающий к дефису | Ведущий код снимается, дефис может остаться; хвостовой код, примыкающий к не-пробельному символу, не снимается (консервативно) |
| Ключ кэша | Очищенное имя |
| Ключ дедупликации ИИ | Очищенное имя (группировка resolver'а) |
| Ключ поиска в очереди | `normalized_name` (очищенное имя) |
| Ключ журнала | `commodity_name` (сырое) + source + suggested + final; `normalized_name` — производное, в ключ не входит |
| `commodities` при confirm | Точное сырое имя; массового обновления по очищенному ключу нет |
| Строки очереди | `name` — сырое (UI/журнал), `normalized_name` — ключ; `proposed` уникален глобально по ключу (следствие — sibling-строк с одним ключом не бывает), `applied` — по `(name, merchant_id)` |
| Sibling `proposed` при confirm | Не существуют (глобальный partial unique по `normalized_name WHERE status = 0`); confirm их не ищет и не удаляет (D1) |
| Статусы очереди | Без изменений (`proposed`/`applied`); confirm — та же транзакция |
| Автопроставление | Нет; нормализация меняет только ключ/промпт |
| API/UI | Без изменений контрактов; UI показывает сырые имена |
| История журнала | Не пересчитывается |
| Новые настройки | Нет |

> **Регресс-контроль перехода очереди на очищенный ключ.** Так как подтверждаемая строка всегда
> единственная `proposed` своего ключа, продуктового теста «sibling удалены» не существует. Инвариант
> («второй `proposed` с тем же очищенным ключом не создаётся, в том числе у другого магазина»)
> проверяется тестом `TryAddProposalAsync` на unique-conflict по
> `ux_precategorized_commodities_normalized_proposed`: вторая вставка возвращает `false`, в таблице
> остаётся одна `proposed`-строка. Этот тест и есть регресс-контроль; тест с искусственным сидом
> sibling-строк не нужен и не должен вводиться (он требует обхода собственного индекса, D4).

## Последствия

### Положительные

- Один товар с кодом и без кода даёт один ключ: меньше вызовов ИИ, меньше дублей в очереди,
  выше попадания в кэш.
- В ИИ уходит очищенное имя — промпт не засоряется артикулами/EAN.
- Поиск по очереди работает по очищенному ключу, поэтому очистка кэша и очереди даёт эффект.
- Новые события журнала получают очищенный `normalized_name` при сохранении сырого
  `commodity_name`.
- Сырые данные и история не переписываются; автопроставления нет; контракты API/UI не меняются.
- Один источник правила (C#), runtime не зависит от SQL-функций.

### Отрицательные / компромиссы

- **Слияние разных товаров по очищенному ключу.** Если код был единственным различием
  (`000001 пирог` vs `000002 пирог` с разными начинками, не отражёнными в имени), ключи совпадут.
  Это неизбежное следствие требования; смягчение — предложения требуют подтверждения человеком,
  автоприменения нет, ошибочную категорию можно исправить.
- **Очередь: один `proposed` на очищенный ключ глобально.** Вариант с другим кодом может не получить
  отдельного предложения; администратор увидит сырое имя одной строки и сможет разметить вариант
  вручную. `applied`-строки у разных магазинов сохраняются. Прямое следствие: состояние «sibling
  `proposed` с тем же ключом» недостижимо, поэтому confirm не содержит удаления сестринских строк
  (D1) — это не потеря функциональности, а отсутствие недостижимого кода.
- **Confirm не массовый.** Подтверждение варианта с кодом не проставит категорию варианту без кода;
  второй вариант получит предложение из кэша/очереди и потребует отдельного подтверждения. Это
  осознанно (NFR-1).
- **Журнал: ключ сочетания остаётся сырым.** Варианты с кодом и без остаются разными строками
  выдачи; поиск по `normalized_name` их находит. Изменение ключа — отдельное решение (F2 отклонено).
- **Глобальный `existing` фона остаётся по сырому имени.** Очищенный ключ там не используется, чтобы
  не нормализовать `commodities` в runtime; кэш (наполняется по очищенному ключу) смягчает разрыв.
- **Кэш first-wins при коллизиях.** Очищенные ключи сталкиваются чаще; при старте побеждает первая
  строка в порядке `OrderBy(Name)`. Это детерминированно, но не гарантирует «правильную» категорию;
  исправление — исправить/удалить исходную позицию в `commodities` и перезапустить Analytics.
- **Миграция требует короткой остановки Analytics.** Старый код не умеет заполнять NOT NULL колонку;
  простой откат образа после миграции невозможен без отката схемы/дампа.
- **SQL-копия правила в миграции.** Одноразовый дрейф-риск; runtime не затронут, но backfill требует
  проверки на корпусе.
- **Эвристика неполна.** Коды в середине, разбитые пробелом/дефисом и примыкающие к дефису хвосты не
  снимаются; это зафиксированные ограничения, а не баги.

### Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Разные товары слиплись, кэш отдаёт неверную категорию | Средняя | Подтверждение человеком; автоприменения нет; исправление категории/перезапуск; открытый вопрос 2 |
| Потеря различимости в очереди / ложные совпадения | Средняя | Сырое `name` в строке и UI; глобальный unique `proposed`; ручная разметка; открытый вопрос 3 |
| Дрейф SQL-backfill ↔ C# | Средняя | Одинаковые regex; golden corpus; контрольный запрос; опциональный Testcontainers-тест; runtime без SQL |
| Переполнение `varchar(256)` после lowercase | Низкая | Preflight в миграции (RAISE); guard сырого/очищенного в `TryAddProposalAsync`, guard очищенного в recorder'е; нормализация в основном сокращает |
| Окно деплоя: старый код пишет `proposed` | Средняя | Остановить Analytics/фон до миграции; дамп; NOT NULL падает громко, данные не портятся |
| Замедление suggest/сохранения из-за regex | Низкая | Вход ≤ 256 символов; ограниченная сложность; при необходимости `NonBacktracking`; замер в тестах |
| Регрессия существующих тестов нормализатора | Низкая | Текущие кейсы не содержат кодов ≥ 6; прогон `dotnet test`; новые кейсы — п. 6 |

## Открытые вопросы

1. **Буквальный `*3455614`.** Правило возвращает исходное имя (edge case «только код»). Если
   заказчик требует снять только `*`, а код оставить (`3455614`), это меняет fallback и должно быть
   подтверждено отдельно; текущая трактовка — критерий приёмки относится к полному примеру
   `*3455614 РЖ.КРАЙ Хлеб нар.300г`.
2. **Политика коллизий кэша.** First-wins сохраняется (ADR-019). Нужен ли last-wins, инвалидация по
   имени или приоритет «более свежей» категории — отдельное решение; сейчас коллизии учащаются, но
   автоприменения нет.
3. **Массовое применение при confirm.** Оставить точное сырое имя (текущее решение) или разрешить
   администратору применять категорию ко всем вариантам очищенного ключа — отдельное продуктовое
   решение; массовое применение граничит с автопроставлением.
4. **Глобальный `existing` фона.** Переводить ли его на очищенный ключ (потребует нормализованной
   колонки/индекса на `commodities`) — отложено; кэш смягчает разрыв.
5. **Расширение правила на разбитые коды.** `241 7268000006`, `241-7268000006`, хвост, примыкающий
   к дефису, — сейчас вне правила. Нужен ли token-based подход — отдельное решение с оценкой
   ложных срабатываний.
6. **Верификация SQL-backfill в CI.** Достаточно ли golden-corpus юнит-теста C# + ручного
   контрольного запроса, или нужен постоянный Testcontainers-тест, применяющий миграцию? Решить в
   декомпозиции с учётом времени CI.
7. **Отображение `normalized_name` в админке.** Показывать ли очищенный ключ/группировку вариантов в
   `/precategorized` — UX-решение; текущий UI показывает сырые имена.
8. **Класс букв fallback-проверки.** Проверка «есть ли буквы» использует `[A-Za-zА-Яа-яЁё]`;
   имя, целиком состоящее из букв вне этого класса (украинские `ї/є/ґ`, греческие, латиница с
   диакритикой — например, `αβγ 123456`), уходит в fallback и сохраняет код. Практическая
   вероятность низкая (названия чеков — кириллица/латиница), текущая семантика принята;
   расширение класса (например, `[\p{L}]` с явным исключением цифроподобных) — отдельное
   решение с оценкой ложных срабатываний.

## Допущения

- Названия товаров — преимущественно кириллица/латиница; если после очистки в имени не остаётся
  ни одной латинской/кириллической буквы, возвращается `base` (осознанное ограничение letter-check).
- Коды на краях — технические (SKU/EAN/артикул), а не смысловой различитель товара; если код был
  единственным различием, слияние считается допустимым.
- Analytics — один экземпляр; распределённой координации фона нет (D12 ADR-027).
- Миграция может выполняться с короткой остановкой Analytics; zero-downtime для внутреннего сервиса
  не требуется.
- `lower()` PostgreSQL и `ToLowerInvariant()` .NET совпадают на реальном корпусе названий; расхождения
  на экзотических Unicode-символах ограничены одноразовым backfill и проверяются корпусом.
- Таблица `precategorized_commodities` небольшая (тысячи строк); backfill и создание индексов
  быстрые.
- Исходные `commodities.name` укладываются в `varchar(256)`; очищенное имя укладывается в 256, кроме
  патологического lowercase-расширения, которое ловит preflight.
- Кэш in-memory и сбрасывается при рестарте; персистентности нет.
