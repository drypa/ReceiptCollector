## Контекст

### Проблема

Страница `/commodities` показывает плоский owner-scoped список позиций всех чеков с пагинацией и
фильтром по категории, но автоматической категоризации на ней нет. Администратор размечает товары
«по экрану»: увидел страницу, разметил, пошёл дальше. Сейчас для каждой позиции нужно открыть чек,
запустить там категоризацию, вернуться — на десятках и сотнях позиций это нерабочий цикл.

Единицей работы должна стать **видимая страница списка**, а не чек и не строка (C1, C2). При этом
синхронная категоризация 10 позиций не всегда укладывается в таймаут прокси/ИИ: «один длинный запрос
на всю страницу» ненадёжен — ожидание не должно превращаться в ошибку и потерю введённого (C3).

### Решения заказчика (обязательны к исполнению)

| # | Решение | Следствие для архитектуры |
|---|---|---|
| C1 | Категоризируются **только строки текущей страницы** | Сервер принимает произвольное подмножество товаров пользователя; «страница» — понятие клиента |
| C2 | Основной сценарий — **страницей**: один запуск, проверка и правка в таблице, одно сохранение; построчный запуск — только «повторить для этой строки» | Один и тот же request-shape для страницы и для одной строки |

| C4 | Пустое значение в селекте = **«не трогаем»**, не сброс в `null` | Новый контракт сохранения — assign-only, без reset |
| C5 | В режиме проверки пагинация, размер страницы и фильтр **заблокированы** с подсказкой | Фронтенд-состояние режима проверки + блокировка контролов |
| C6 | После сохранения под фильтром «Без категории»/«Не указана» строки уходят, страница **сама наполняется** следующими; пустая последняя страница → переход на предыдущую доступную | Нормализация страницы в `useCommodities` (сейчас отсутствует) |

| C8 | Подпись-источник — **у каждой строки**, включая повторяющиеся названия | Результат на каждую строку (по `commodityId`), не на название |

| C11 | Область — **только** `/commodities`; «Детали чека» не трогаем | Изменения контрактов — аддитивные и локальные |

## Решение

Сводка:

1. **Два новых stateless-эндпоинта** в группе `/api/commodities`: `POST /api/commodities/categories/suggest`
   (read-only, порция) и `PUT /api/commodities/categories` (пакетное сохранение только изменённых строк).
2. **Порционность — на клиенте**: последовательные запросы по ≤ 5 уникальных названий; сервер о
   «странице» не знает и состояния между запросами не держит.
3. **Серверный бюджет одного запроса** (`CommodityBatchCategorization:SuggestTimeout`, по умолчанию
   25 с): по его истечении незавершённые названия → `undefined` + текст ошибки, HTTP `200` с частичным
   результатом. Отмена запроса клиентом по-прежнему прерывает всё.
4. **Сохранение — assign-only**: `category == null`/отсутствует ⇒ «не трогаем»; `Undefined` запрещён;
   изменённые строки считаются по факту (old ≠ new); одна транзакция; owner-scoped.
5. **Алгоритм категоризации выносится в общий resolver** (`existing → cache → precategorized → ai`,
   дедупликация по нормализованному имени) — им пользуются и suggest чека, и suggest порции.
6. **Пустой `AI:BaseUrl` не блокирует** порционный suggest: ответ `200` + `aiAvailable = false`,
   строки из кэша/очереди заполняются, остальные — «не определена» (C7).
7. **Кэш (ADR-019)** пополняется только при сохранении (`TryAdd`, first-wins/no-op); **очередь
   предкатегорий (ADR-027)** только читается — никаких записей и смен статусов.
8. **Права — на сервере**: `401`/`403` на оба эндпоинта, независимо от скрытия кнопки в UI.
9. **Порядок строк стабилен**: режим проверки работает на неизменяемом снапшоте страницы, список во
   время проверки не перезапрашивается, сортировка серверная и не зависит от категории.
10. Миграций БД, новых индексов, изменений nginx и Go-сервисов **нет**.

### 1. Контракты API

Оба эндпоинта живут в новом файле `Api/Modules/Commodities/CommodityBatchCategorizationEndpoints.cs`
(регистрация `app.MapCommodityBatchCategorizationEndpoints()` в `Program.cs`), тег `Commodities`.
Стиль ошибок — текстовые тела, без ProblemDetails (эталон ADR-027 п. 7).

#### 1.1 `POST /api/commodities/categories/suggest` — предложения по порции

Запрос:

```json
{ "commodityIds": ["3f1c…", "9a02…"] }
```

Ответ `200`:

```json
{
  "items": [
    { "commodityId": "3f1c…", "name": "Молоко 3,2%", "categoryId": 23,
      "categoryName": "Молочные продукты", "source": "cache", "error": null },
    { "commodityId": "9a02…", "name": "Чайник электрический", "categoryId": null,
      "categoryName": null, "source": "undefined", "error": "ИИ не ответил за отведённое время." }
  ],
  "aiAvailable": true
}
```

- `items` — **по одной записи на каждую найденную строку** (включая повторяющиеся названия; порядок
  не гарантирован, клиент сопоставляет по `commodityId`). Форма элемента совпадает с существующим
  `ReceiptItemCategorizationResult` — тип **переиспользуется** (поля те же, wire-формат тот же).
- `source` — значения `CategorizationSourceNames` (`existing`/`cache`/`precategorized`/`ai`/`undefined`),
  аддитивных значений не добавляется.
- `error` — человекочитаемый текст для подсказки строки (`title`); `null` при успехе.
- `aiAvailable` — `!string.IsNullOrWhiteSpace(AI:BaseUrl)`. При `false` строки, которым не хватило
  кэша/очереди, помечаются `undefined` (без вызова ИИ), а клиент показывает постоянное предупреждение.
- Эндпоинт **read-only**: не пишет ни в `commodities`, ни в кэш, ни в очередь (проверяется тестом).

Коды:

| Код | Условие | Тело |
|---|---|---|
| `200` | всегда при успешной обработке, **в т.ч. при частичном результате/таймауте/недоступном ИИ** | `{ items, aiAvailable }` |
| `400` | `commodityIds` пуст/отсутствует; `> 200` элементов; `Guid.Empty`; дубликаты id; `> 20` уникальных названий в порции | текст |
| `401` | `UserContext.UserId` пуст | — |
| `403` | пользователь не админ (явный `Results.StatusCode(403)`) | — |

Неизвестные/чужие `commodityId` **не** дают ошибку: они просто отсутствуют в `items` (клиент
трактует отсутствие как «не определена»), факт пишется в лог Warning с количеством. Это осознанная
асимметрия с сохранением (п. 1.2): чтение терпит устаревшую страницу, запись — нет.

#### 1.2 `PUT /api/commodities/categories` — пакетное сохранение

Запрос:

```json
{ "items": [ { "commodityId": "3f1c…", "category": "Dairy" },
             { "commodityId": "9a02…", "category": null } ] }
```

- `category` — **имя значения enum** (`"Dairy"`), как в `PUT /api/receipts/{id}/categories`;
  числа отклоняются. `null`, пустая строка, пробелы или отсутствующее поле ⇒ строка **пропускается**
  («не трогаем», C4).
- `Undefined` запрещён к явному присвоению (`400`) — как в suggest/apply чека.
- Ответ `200`: `{ "updated": N }`, где `N` — число строк, у которых сохранённое значение **реально
  отличается** от запрошенного (сравнение выполняется на сервере: C9; запись «того же значения» не
  считается изменением и в кэш не попадает).
- Атомарность: все проверки — до записи; запись — одним `SaveChangesAsync` (одна транзакция). Если
  хотя бы один `commodityId` не найден среди **товаров текущего пользователя** → `409`, **ничего не
  записано** (черновик на клиенте сохраняется, см. «Ошибки» задачи).
- Сброс категории (`null`/`Undefined`) этим контрактом **не поддерживается** (C4). Reset остаётся
  возможным только через существующий одиночный эндпоинт — и это осознанное разделение ответственности,
  а не недосмотр.
- Кэш (ADR-019): после успешной фиксации — `TryAdd(normalizedName, category)` для каждой изменённой
  строки (first-wins, no-op при «замороженном» кэше). Очередь предкатегорий **не меняется**.
- Категория пишется **только в свои строки** (owner-scoped), в отличие от ADR-027 (там подтверждение
  массовое по имени для всех пользователей). Распространения по названию на другие строки нет:
  правка одной строки не обязана менять остальные (edge case задачи).

| Код | Условие | Тело |
|---|---|---|
| `200` | запрос обработан (в т.ч. если после пропуска «не трогаем» нечего менять → `updated = 0`, без записи в БД) | `{ updated }` |
| `400` | `items` пуст/отсутствует; `Guid.Empty`; дубликат `commodityId`; `category` — число, неизвестное имя или `Undefined` | текст |
| `401` / `403` | как в п. 1.1 | — |
| `409` | хотя бы один товар не найден среди товаров пользователя (устаревшая страница) | текст |

#### 1.3 Почему «страница» — не понятие сервера

Сервер принимает любое подмножество товаров пользователя: для одиночного повтора («повторить для
этой строки», C2) используется тот же эндпоинт с одним `commodityId`. Ограничение C1 («только строки
текущей страницы») обеспечивается клиентом: он отправляет ровно снапшот видимой страницы. Серверная
реализация «текущей страницы» потребовала бы передавать `limit/offset/categoryFilter` и повторять
выборку списка — лишняя связность без выгоды (и гонки: страница могла измениться между запросами).

### 2. Порционная оркестрация на клиенте (C3)

- Клиент в момент старта режима проверки фиксирует **снапшот** страницы (`CommodityItem[]` из
  `useCommodities`) и считает:
  - `candidates` — строки **без содержательной категории**: `categoryId == null || categoryId === 0`.
    `0` (`Undefined`) трактуется как «категории нет» — так же, как в `existing`-шаге алгоритма и в
    подтверждении ADR-027 (D11). Это делает кнопку осмысленной и под фильтром «Категория «Не указана»»;
  - `nameGroups` — группировка кандидатов по **точному** названию; `chunks` — последовательные
    порции по ≤ 5 названий (константа клиента `PAGE_SUGGEST_CHUNK_SIZE = 5`). В запрос порции уходят
    `commodityId` **всех** строк её названий (строк в порции может быть больше пяти).
- Запросы выполняются **строго последовательно** (один in-flight запрос на страницу): так
  соблюдается «порционность», нагрузка на ИИ не умножается, и порядок поступления результатов
  детерминирован. Параллелизм внутри запроса ограничен `AI:Concurrency` (как в ADR-009).
- Дедупликация: одинаковые названия внутри страницы попадают в одну порцию → один вызов ИИ на
  название (C8/критерий «без повторных вызовов по одному и тому же названию»); сервер дополнительно
  дедуплицирует по **нормализованному** имени внутри запроса (защита от повторов и от клиентов,
  нарушивших группировку). Разные варианты написания («Молоко» / «молоко ») могут попасть в разные
  порции — это допустимо (нормализация на клиенте не дублируется: единственный источник правила —
  `CommodityNameNormalizer` на сервере).
- Прогресс: счётчик в строках — `Y = candidates.length`, `X` увеличивается на число строк
  завершившейся порции; подпись «Определяем категории… X из Y». Прогресс **не** блокирует
  взаимодействие: селекты и «Сохранить» доступны сразу.
- Отмена/сохранение/размонтирование: текущий запрос прерывается `AbortController`, плюс
  монотонный `generation`-счётчик отбрасывает ответы, пришедшие после отмены (React StrictMode,
  гонки). Ответы никогда не применяются к снятому режиму проверки.
- Поступление результата порции не перезаписывает значение, которое администратор уже правил
  вручную: у строки есть флаг `touched`; для `touched`-строк подпись источника заменяется на
  «изменено вручную», значение остаётся пользовательским. Иначе поздняя порция молча стирала бы
  введённое (прямое следствие требования «потери введённого быть не должно»).

### 3. Бюджет запроса и деградация по таймауту (C3)

- Новая опция `CommodityBatchCategorization:SuggestTimeout` (по умолчанию `00:00:25`) — максимальное
  время обработки одного suggest-запроса. Обоснование: гарантия не может опираться на `AI:Timeout`
  (в `appsettings.json` фактически 80 с — ADR-027, риск 1), иначе при 5 названиях и `AI:Concurrency`
  = 3 худший случай (2 волны × 80 с) превысит `proxy_read_timeout 120s`.
- По истечении бюджета отменяются **только вызовы ИИ** (`CancellationTokenSource`, связанный с токеном
  запроса): незавершённые названия получают `source = "undefined"` и текст ошибки, ответ — `200` с
  частичным результатом уже полученных названий. Кэш/очередь к этому моменту уже отработали (они
  быстрые и не отменяются бюджетом).
- Отмена **запроса клиентом** (уход со страницы, «Отмена», `AbortController`) прерывает всё
  (`OperationCanceledException` не превращается в частичный результат).
- `AI:Timeout` остаётся таймаутом одного вызова (ADR-009) и работает как раньше: его истечение по
  названию → `AiClientException` → `undefined` по этому названию, остальные продолжаются.
- Тестируемость: дедлайн реализуется через внедряемый `TimeProvider` (уже зарегистрирован
  Singleton'ом в ADR-027, NFR-9) — тесты используют `FakeTimeProvider`, без реальных задержек.

### 4. Пустой/недоступный ИИ (C7)

- `aiAvailable = !string.IsNullOrWhiteSpace(AI:BaseUrl)`. При `false` порционный suggest **не**
  возвращает `503` (в отличие от suggest чека — там поведение не меняется, C11): выполняются шаги
  `existing` → `cache` → `precategorized`, остальные названия → `undefined` с ошибкой «ИИ не настроен».
- При недоступном по сети/ошибке ИИ (`AiClientException`) — то же поведение на уровне названия
  (`undefined` + текст), `aiAvailable` остаётся `true` (конфигурация есть, провайдер не ответил).
- Клиент показывает **постоянное** предупреждение (inline, `role="status"`) при `aiAvailable = false`,
  а не только тост: это состояние, а не событие. Тост остаётся для ошибок сохранения/сети.

### 5. Состояние фронтенда (C2, C5, C8, C9)

Новый хук `hooks/useCommodityPageCategorization.ts` — одна машина состояний страницы:

| Состояние | Смысл |
|---|---|
| `phase: 'idle'` | обычный вид (текущее поведение страницы) |
| `phase: 'review'` | режим проверки: снапшот страницы, черновик, идущие порции |
| `phase: 'saving'` | отправлен `PUT`, контролы заблокированы, черновик не редактируется |

- `draft: Record<commodityId, { value: string; initialValue: string; source?: string; error?: string; touched: boolean }>`
  — `value` — **ключ** категории (`Category.key`, имя enum), т.к. контракт сохранения принимает имя;
  пустая строка = «не трогаем».
- Инициализация: строки с содержательной категорией — `value = key существующей категории`,
  подпись «уже присвоена», в порции **не включаются**; строки без категории — `value = ''`, подпись
  появляется по мере готовности.
- `changed` = строки, где `value !== initialValue` **и** `value !== ''`. Только они уходят в `PUT`.
  Если `changed` пуст — запрос не отправляется, режим закрывается, тост «Сохранено категорий: 0»
  (правило ADR-020: `N = 0` — тост всё равно показывается).
- Блокировка (C5): `pageSize`-селект, `categoryFilter`-селект, `Pagination` (новый проп `disabled`),
  «Обновить», ссылка-дата строки (уход в чек) и построчный редактор «ред.» — все `disabled` с
  `title="Сначала сохраните или отмените изменения"`. Смена страницы/фильтра в режиме проверки
  невозможна → черновик не теряется и не уезжает «не туда».
- Сохранение в любой момент: `Сохранить категории` активна и во время обработки; при нажатии
  in-flight порция прерывается, сохраняется то, что видит администратор.
- После успеха: выход из режима → `refresh()` текущей страницы → тост `Сохранено категорий: {updated}`
  → нормализация страницы (п. 6).

### 6. Фильтр и наполнение страницы после сохранения (C6)

Хук `useCommodities` получает инвариант «текущая страница непустая и не больше последней»: если
очередная загрузка вернула `[]`, а `computedTotalPages < requestedPage`, выполняется догрузка
последней доступной страницы (с защитой от циклов). Это устраняет существующий дефект, когда хук
clamp'ит `currentPage`, но не перезапрашивает данные.

Поведение по фильтрам после сохранения:

| Фильтр | Поведение |
|---|---|
| `uncategorized` / `undefined` | размеченные строки уходят из выборки, страница сама наполняется следующими; если страница опустела и она не первая — переход на предыдущую доступную; `X-Total-Count` обновляется (он уже в контракте) |
| `any` | строки остаются на месте (сортировка `PurchasedAt DESC, Name` от категории не зависит) |

Пустой список не показывается как ошибка: «Товары не найдены» — штатное состояние.

### 7. Стабильность порядка строк

- Режим проверки рендерит **снапшот** страницы, взятый при старте; во время проверки список не
  перезапрашивается (ни по таймеру, ни после порции) — новые чеки/строки не «вклиниваются».
- Ключ строки — `commodityId` (не индекс): правки и порции не переупорядочивают DOM.
- Сортировка серверная и не зависит от категории → после сохранения и перезагрузки строки не
  меняют позиции (критерий приёмки).

### 8. Кэш (ADR-019) и очередь предкатегорий (ADR-027)

| Механизм | Влияние решения |
|---|---|
| In-memory кэш | Читается (`cache`-шаг, без изменений). Пополняется **только** при сохранении: `TryAdd` по нормализованному имени для каждой изменённой строки (first-wins, no-op при «замороженном» кэше). Suggest ничего не кэширует. |
| Очередь `precategorized_commodities` | Только **чтение** одним batch-запросом по точным именам порции (тот же шаг, что в ADR-027, FR-9.3). Записей/смен статусов со стороны страницы нет. |
| Фоновая предкатегоризация | Работает параллельно без конфликтов: фон не пишет в `commodities`, страница не пишет в очередь; единственная точка записи в `commodities` — подтверждение админа (здесь или в `/precategorized`), конфликт разрешается «последняя запись побеждает» (edge case задачи). Кэш — `TryAdd`, конкурентная запись безопасна по семантике ADR-019. |
| Пустой `AI:BaseUrl` | Фон и страница не вызывают ИИ; страница отдаёт `aiAvailable = false` (п. 4), фон — Warning (ADR-027, D5). |

### 10. Права (C1, критерий «не-администраторы»)

- Сервер: `UserContext.UserId` пуст → `401`; `IUserRepository.GetByIdAsync(...).IsAdmin != true` → `403`
  **явным** `Results.StatusCode(StatusCodes.Status403Forbidden)` (в приложении нет схемы аутентификации,
  `Results.Forbid()` даёт `500` — ADR-027, п. 7). Проверка выполняется **до** любых чтений/записей.
- Клиент: кнопка «Категоризировать страницу (N)» рендерится только при `isAdmin` (как колонка
  «Категория» сейчас); скрытие кнопки — UX, не механизм безопасности.
- Owner-scoping: обе операции работают только с товарами, у которых `receipts.user_id = :userId`.
  Для админа это означает «свои товары» — ровно то, что показывает `GET /api/commodities` сегодня.
  Чужие/несуществующие id неразличимы (нет утечки существования).

### 11. Наблюдаемость

- Suggest-порция: Debug — размер порции (ids, уникальных названий), длительность, распределение по
  `source`, число ошибок/таймаутов ИИ, `aiAvailable`, число пропущенных id; Warning — пропущенные id
  (количество), ошибки чтения очереди (деградация к ИИ — как сейчас), таймаут бюджета (количество
  неопределённых названий).
- Save: Information — `updated` и число пропущенных («не трогаем») элементов; Warning — `409`
  (устаревшая страница).
- Названия товаров — только на Debug (логи без ПД пользователей, прецедент ADR-027 FR-8).

### 12. Нефункциональные требования

| НФТ | Решение |
|---|---|
| Время ответа | Одна порция ≤ 5 названий, бюджет 25 с < `proxy_read_timeout 120s`; страница не «висит» — результаты приходят по порциям |
| Нагрузка на ИИ | ≤ `AI:Concurrency` вызовов внутри порции, порции последовательны; дедупликация по названию внутри страницы и внутри запроса; при пустом `AI:BaseUrl` вызовов нет |
| БД | Suggest: 1 owner-scoped запрос по PK (`id IN (…)`) + 1 batch-запрос очереди по `name` (существующий unique-индекс `(name, merchant_id)` пригоден — ведущая колонка `name`); Save: 1 запрос + 1 `SaveChangesAsync`. Новых индексов и миграций не требуется |
| Безопасность | admin-only + owner-scoped на сервере; никаких автоматических применений категорий; нет приёма `userId` из тела |
| Сопровождаемость | Один конвейер категоризации (resolver) на два сценария; контракты аддитивные; существующие тесты чека остаются зелёными и служат регрессионной сеткой для рефакторинга |
| Тестируемость | `TimeProvider` для дедлайна; EF InMemory + NSubstitute; эндпоинты проверяются исполнением `IResult` на `HttpContext` (как в ADR-027) |
| Совместимость | Старые эндпоинты и их поведение не меняются; wire-формат элементов предложений переиспользуется |

## Рассмотренные варианты

### A. Построчная категоризация (запрос на строку) — **отклонено**

Один `POST` на каждую строку, клиент параллелит/очередит.

**Минусы:** N round-trip'ов и N независимых транзакций; невозможно соблюсти «порциями по 5 названий»;
дедупликация одинаковых названий внутри страницы требует клиентского состояния, а синхронизация
результатов — сложной очереди; при 100 строках — 100 запросов вместо 20; больше точек отказа.
Построчный режим остаётся как **частный случай** того же контракта (один `commodityId`) — без
отдельного API.

### B. Один синхронный батч на всю страницу (масштабирование текущего suggest чека) — **отклонено**

Один `POST` с id всех строк страницы, сервер сам параллелит все вызовы ИИ.

**Минусы:** прямо противоречит C3; худшее время ответа (50–100 названий × волны ИИ) упирается в
таймаут прокси; любой сетевой сбой/таймаут = потеря всей работы страницы (нет постепенности);
`AI:Timeout = 80s` в текущем `appsettings.json` делает таймаут почти неизбежным. Это ровно та
проблема, которую задача требует устранить.

### C. Фоновая job-модель (POST job → GET статус с поллингом) — **отклонено (зафиксирован путь эволюции)**

`POST /api/commodities/categories/jobs` → `202 + jobId`, воркер обрабатывает, клиент поллит.

**Минусы:** новое состояние на сервере (таблица job'ов или in-memory), TTL/очистка, идемпотентность,
поведение при рестарте и при нескольких экземплярах; дублирование инфраструктуры ADR-027 (курсоры,
single-instance); для страницы результат нужен в течение секунд, а не «когда-нибудь» — поллинг даёт
худший UX при том же объёме работы. YAGNI. Если когда-нибудь появится «разметить всё», job-модель —
естественное продолжение (контракты предложений/сохранения при этом не меняются).

### D. Серверный стриминг результата (SSE / NDJSON / `IAsyncEnumerable`) — **отклонено**

Сервер держит один запрос и «выплёвывает» результаты по мере готовности.

**Минусы:** потоковый разбор на клиенте, поведение буферизации в nginx, отдельная обработка отмены и
ошибок стрима, сложность тестирования minimal API — при том что тот же эффект «постепенности»
даёт клиентская оркестрация из **stateless** запросов. Инфраструктурная сложность не оправдана
(KISS).

### E. Серверная сессия категоризации страницы (черновик на сервере) — **отклонено**

`POST /session` (страница + фильтр) → сервер хранит очередь и отдаёт порции, `GET /session/{id}/next`.

**Минусы:** серверное состояние и TTL, привязка к экземпляру, необходимость инвалидации при смене
фильтра/страницы, конфликт с «черновик живёт в UI». Не даёт ничего сверх клиентской оркестрации.

### F. Переиспользование `POST /api/receipts/{id}/categories/suggest` по каждому чеку страницы — **отклонено**

**Минусы:** страница состоит из строк разных чеков; эндпоинт категоризирует **весь** чек (лишние
вызовы ИИ за пределами страницы — нарушение C1); сохранение пришлось бы делать по чекам (N запросов),
а «одно сохранение» (C2) не выражается; семантика `PUT /api/receipts/{id}/categories` — сброс при
пустом значении (конфликт с C4).

### G. Семантика пустого значения как сброс (как в `PUT /api/receipts/{id}/categories`) — **отклонено**

**Минусы:** прямо противоречит C4; на странице с десятками строк пустой селект как «сброс» —
источник случайной потери данных (админ «прошёлся» по строкам, не заполнив их). Reset остаётся
возможным точечно через существующий одиночный эндпоинт; новый контракт assign-only.

### H. Порционная обработка на сервере (сервер сам режет страницу на порции и отдаёт их по одной) — **отклонено**

**Минусы:** сервер должен помнить, какие порции уже отданы (состояние, п. E), либо клиент передаёт
курсор — то же самое, но с лишним контрактом. Клиент и так знает названия страницы.

### I. Параллельные порции (2–3 запроса одновременно) — **отклонено (на текущем этапе)**

**Минусы:** каждый запрос имеет собственный `SemaphoreSlim` (поле scoped-сервиса), т.е. параллельные
порции умножают число одновременных вызовов ИИ (`k × AI:Concurrency`), что противоречит «порционности»
и повышает риск rate-limit. Порядок поступления результатов перестаёт быть детерминированным.
Если на страницах 100 строк последовательность окажется слишком медленной — включается как
**клиентское** изменение (размер порции/степень параллелизма), без изменения контрактов.

### J. Новый раздел конфигурации vs переиспользование `AI:Timeout` — **выбран раздел**

`AI:Timeout` — свойство провайдера (один вызов), а бюджет запроса — гарантия workflow страницы.
Смешивание сделало бы гарантию зависимой от конфигурации провайдера и от расхождения
`appsettings.json`/`AiOptions` (ADR-027, риск 1). Отдельная секция
`CommodityBatchCategorization:SuggestTimeout` явно документируется и пробрасывается через env (ADR-021).

## Явно зафиксированные семантики

| Вопрос | Решение |
|---|---|
| Пустое значение в селекте | «Не трогаем». `null`/отсутствие `category` в `PUT` — элемент пропускается; сброса нет (C4) |
| Сброс категории | Только существующим одиночным `PUT /api/commodities/{id}/category`; новым контрактом не поддерживается |
| Права | admin-only, проверка на сервере (`401`/`403`), owner-scoped выборка и запись |
| Не-админ | Кнопки нет; прямой вызов API → `403`; поведение страницы не меняется |
| Под фильтром «Без категории»/«Не указана» после сохранения | Размеченные строки уходят; страница наполняется следующими; пустая не-первая страница → предыдущая доступная; счётчик обновляется (C6) |
| Стабильность порядка | Снапшот страницы в режиме проверки, без перезагрузок; ключ — `commodityId`; сортировка от категории не зависит |
| Строки с `categoryId = 0` (`Undefined`) | Считаются «без категории» (входят в N, участвуют в suggest), селект пустой (значение `Undefined` не выбирается), сохранение без правки ничего не меняет |
| Пустое/отсутствующее название | Не уходит в ИИ: `undefined` + текст ошибки; строка не ломает порцию; входит в N (известное ограничение — см. риски) |
| Повторяющиеся названия | Одно предложение на все строки одной порции, подпись у каждой строки; правка одной строки не меняет остальные |
| Изменения в другой вкладке | После перезагрузки страницы — актуальное значение; при сохранении «последняя запись побеждает»; недоступная строка → `409`, ничего не записано, черновик цел |
| `updated` в тосте | Только реально изменённые строки (old ≠ new), считает сервер (C9) |
| Пустой `AI:BaseUrl` | Категоризация запускается, `aiAvailable = false`, кэш/очередь работают, остальное — «не определена» (C7) |
| Одиночный повтор | Тот же suggest-эндпоинт с одним `commodityId` (C2) |

## Последствия

### Положительные

- Администратор размечает товары «по экрану»: один запуск, проверка и правка в таблице, одно
  сохранение — рутина «через детали чека» исчезает.
- Постепенность и частичный результат снимают главный риск: таймаут/сбой ИИ больше не превращается
  в ошибку запроса и потерю работы.
- Контракты stateless: нет серверных сессий, TTL, распределённых блокировок, нет изменений nginx и
  схемы БД; «страница» — понятие клиента, поэтому одиночный повтор бесплатен (тот же эндпоинт).
- Один конвейер категоризации (`existing → cache → precategorized → ai`) на два сценария — нет
  расхождений алгоритма между чеком и страницей; кэш и очередь используются ровно по своим ADR.
- Права и owner-scoping проверяются на сервере; новых путей записи категорий (кроме явного
  сохранения админом) не появляется.
- Контракт сохранения assign-only защищает от случайного стирания категорий пустым селектом.

### Отрицательные / компромиссы

- **Больше запросов**, чем «один батч»: `ceil(уникальных названий / 5)` (для 100 строк — до 20).
  Плата за постепенность и устойчивость к таймаутам; каждый запрос дешёвый (один PK-запрос + один
  batch-запрос очереди).
- **Черновик живёт в браузере**: перезагрузка вкладки в режиме проверки теряет неразмеченные правки
  (навигация внутри приложения и контролы заблокированы; браузерный reload — вне контроля).
- **Два разных контракта сохранения** (чек — с reset, страница — assign-only) сосуществуют, пока
  «Детали чека» не выровнены (C11). Расхождение задокументировано здесь и в ADR-009 (amend).
- **`ReceiptItemCategorizationResult`** переиспользуется для элемента страницы: имя типа отражает
  происхождение, wire-формат идентичен. Переименование в нейтральное — косметика, отдельным шагом.
- **Дедлайн может «срезать» медленный ИИ**: часть названий останется «не определена» и потребует
  точечного повтора (это и есть согласованная деградация, C3).
- **Клиентская группировка по точному названию**: варианты написания, различающиеся регистром/пробелами,
  могут попасть в разные порции и вызвать два вызова ИИ (серверная дедупликация внутри порции
  работает по нормализованному имени). Нормализация на клиенте намеренно не дублируется.

### Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Регрессия suggest чека при выносе алгоритма в resolver | Средняя | Поведение зафиксировано существующими `CommodityCategorizationServiceTests` (остаются без изменений и должны быть зелёными); публичный контракт и порядок шагов не меняются |
| Таймаут прокси при неудачной конфигурации бюджета (`SuggestTimeout` ≥ 120 с) | Низкая | Дефолт 25 с; `ValidateOnStart` для `<= 0`; значение документируется вместе с `proxy_read_timeout` |
| Ошибка owner-scoping (глобальный query-filter здесь не активен) | Средняя | Явный фильтр `c.Receipt.UserId == userId` в репозиторных методах + тесты «чужой id → 409 / отсутствует в ответе» |
| Потеря правок при reload вкладки | Средняя | Блокировка навигации/контролов; рекомендация `beforeunload`-предупреждения в режиме проверки (шаг плана) |
| Долгая обработка страниц 50–100 строк (последовательные порции) | Средняя | Прогресс и доступное сохранение в любой момент; размер порции/параллелизм — клиентская настройка (вариант I) |
| Молчаливое перезаписывание ручной правки поздней порцией | Средняя | Флаг `touched`: пришедшие предложения не перезаписывают значение, изменённое вручную |
| Расхождение `AI:Timeout` (80 с в `appsettings.json`) и ожиданий | Средняя | Бюджет запроса независим от `AI:Timeout`; выравнивание `AI:Timeout` — отдельная задача (вне области) |

### Известные ограничения (вне области)

- Пустое название товара нельзя категоризировать: строка всегда «не определена» и всегда входит в N —
  на «грязных» страницах кнопка остаётся активной. Очистка данных — отдельная задача.
- Одиночный редактор `CommodityTable` при выборе «—» отправляет `categoryId: null` в non-nullable
  `int` → `400` (существующий дефект). Задачей не исправляется и новым контрактом не используется.
- Глобального лимита одновременных вызовов ИИ между разными клиентами нет (`SemaphoreSlim` —
  поле scoped-сервиса). Ведём себя консервативно: один in-flight запрос на страницу.
- Мультиэкземплярный Analytics: кэш (ADR-019) и отсутствие распределённой координации — известное
  ограничение, задача его не меняет.

## Связь с другими ADR

- **ADR-009** (amend-заметка): конвейер `existing → cache → precategorized → ai` вынесен в общий
  resolver; добавляется второй вход в тот же конвейер (порционный suggest страницы) и второй контракт
  сохранения (assign-only). Контракты `suggest`/`apply` чека не меняются.
- **ADR-019**: семантика кэша (`TryAdd`, first-wins, «замерзание», сквозной масштаб) переиспользуется
  без изменений; новый путь записи в кэш — только при сохранении страницы.
- **ADR-020**: тосты переиспользуются как есть; правило `N = 0` (тост показывается) сохраняется.
- **ADR-026**: провайдер ИИ не меняется — работа идёт через `IAiClient`; новый код не знает о
  провайдере, `aiAvailable` считается по `AI:BaseUrl` активного провайдера.
- **ADR-027**: очередь `precategorized_commodities` читается тем же batch-методом, не пишется;
  стиль админских эндпоинтов (`401`/`403` явным `StatusCode`, текстовые ошибки, отсутствие
  ProblemDetails) и паттерн `AuthorizeAdminAsync` переиспользуются; конфликтов с фоном нет.
- **ADR-021**: новая опция `CommodityBatchCategorization__SuggestTimeout` пробрасывается через
  `docker-compose.yml`/`.env.example` по тому же образцу.
