## Контекст

### Проблема

Админская страница `/merchants` показывает постраничный список магазинов
(`GET /api/merchants`, параметры `limit`/`offset`, заголовок `X-Total-Count`), но не
предоставляет поиска. При большом количестве магазинов администратору сложно быстро
найти нужный магазин по названию или ИНН — приходится просматривать страницы списка
вручную.

Нужен поиск по **названию** и **ИНН** магазина в одном поле (поведение/UI — как на
странице «Предкатегоризация»): ввод с задержкой (debounce), при изменении запроса
сброс на первую страницу, плейсхолдер в духе «Название или ИНН». Фильтрация
обязательна **на бэкенде** (через параметр поиска API), чтобы серверная пагинация не
ломалась: `total` (`X-Total-Count`) и навигация по страницам должны считаться по
отфильтрованному набору. Подсветка совпадений не требуется.

### Ключевые ограничения

1. **Фильтрация и счётчик — на бэкенде.** `X-Total-Count`, набор страницы и число
   страниц должны вычисляться по **отфильтрованному** результату; клиент не
   подмешивает и не фильтрует страницы локально.
2. **Совместимость контракта.** Путь, метод, коды ошибок, формат массива `MerchantDto`
   и смысл `X-Total-Count`/`limit`/`offset` не меняются; `search` — уже существующий
   query-параметр, меняется только его семантика (добавляется ИНН, условие становится
   `name OR inn`).
3. **Null-безопасность ИНН.** `Merchant.Inn` может быть `null`; сравнение не должно
   приводить к ошибке и не должно скрывать магазин, совпавший по названию.
4. **Референс UI — «Предкатегоризация».** Одно поле, debounce, сброс на первую
   страницу при изменении запроса; поиск и пагинация работают согласованно.

## Рассмотренные варианты

### Ключевое решение A: где и как применять фильтр

#### Вариант A1: оставить фильтрацию в памяти эндпоинта, расширить условие на ИНН — отклонён

Эндпоинт продолжает загружать всех магазинов через `GetAllAsync()` и фильтрует
`IEnumerable<Merchant>` перед `Count/OrderBy/Skip/Take`, добавляя проверку
`Inn?.Contains(search, OrdinalIgnoreCase) == true`.

**Плюсы:** минимальное изменение, без новых методов репозитория.

**Минусы:** сохраняет и усиливает текущую деградацию — полная загрузка таблицы на
каждый запрос (включая каждый «тик» поиска после debounce) и фильтрация в процессе
API; логика пагинации/поиска остаётся размазанной между слоем API и хранилищем.
Паттерн не масштабируется и расходится с эталонными постраничными списками проекта
(в т.ч. «Предкатегоризация», где поиск уходит в запрос данных). Приемлемо как
краткоживущее поведение, но не как целевое архитектурное решение.

#### Вариант A2: перенести фильтр и пагинацию в репозиторий/запрос к БД — **выбран**

Репозиторий получает постраничную выборку магазинов с необязательным поисковым
термином и возвращает (страница, общее количество по фильтру). Фильтр `name OR inn`
применяется в запросе данных **до** `COUNT`, `ORDER BY`, `SKIP/TAKE`; эндпоинт только
валидирует параметры, проверяет права и формирует HTTP-ответ.

**Плюсы:**

- `X-Total-Count` и страница вычисляются над одним и тем же отфильтрованным набором
  в источнике данных — пагинация корректна по определению.
- В память попадает только запрошенная страница, а не вся таблица.
- Единая точка ответственности: условие поиска, сортировка и пагинация сосредоточены
  в слое доступа к данным (как у «Предкатегоризации»), эндпоинт остаётся тонким.
- Условие легко сделать симметричным и null-безопасным (`Inn` может быть `null`).

**Минусы (приняты):**

- Требуется изменить контракт репозитория (аддитивно) и адаптировать эндпоинт;
  существующие вызовы `GetAllAsync()` для сценариев, которым действительно нужен весь
  список, сохраняются.
- Способ case-insensitive сравнения зависит от СУБД/провайдера EF (см. «Решение»).

#### Вариант A3: полнотекстовый поиск / отдельный поисковый индекс — **отклонён**

**Минусы:** избыточно для частичного совпадения по двум коротким полям (название,
ИНН) в админском списке; требует изменений схемы/индексов и усложняет деплой/миграции.
YAGNI относительно критериев задачи.

### Ключевое решение B: семантика совпадения

#### Вариант B1: частичное совпадение без учёта регистра, `name OR inn` — **выбран**

Термин поиска (после `Trim`) считается совпавшим, если он является подстрокой
названия **или** подстрокой ИНН (без учёта регистра). Магазин попадает в выдачу, если
совпало любое из полей; совпадение с обоими полями не удваивает запись (это один и
тот же магазин). Пустой/пробельный `search` эквивалентен отсутствию фильтра.

**Обоснование:** прямо следует из критериев приёмки и edge cases задачи; совпадает с
ожиданием пользователя при вводе произвольного фрагмента («цифры» могут оказаться и в
названии, и в ИНН).

#### Вариант B2: разные поля/режимы поиска (отдельный ввод ИНН или автоопределение) — **отклонён**

**Минусы:** противоречит требованию «одно поле» и референсу «Предкатегоризации»;
усложняет UI без пользы — один фрагмент естественно проверяется по обоим полям (B1).

#### Вариант B3: поиск только по префиксу — **отклонён**

**Минусы:** не покрывает критерий «частичное совпадение» (фрагмент в середине
названия/ИНН).

## Решение

Приняты **A2** (фильтр и пагинация в репозитории/запросе к БД, `count` по
отфильтрованному набору) и **B1** (частичное, регистронезависимое совпадение
`name OR inn`, пустой термин = без фильтра).

### 1. Контракт API

| Метод и путь | Назначение | Изменение |
|---|---|---|
| `GET /api/merchants?limit=&offset=&search=` | постраничный список магазинов (admin-only) | **без изменений пути/метода/кодов**; уточняется семантика `search` |

- **Параметры:** `limit` (по умолчанию 50, `> 0`), `offset` (по умолчанию 0, `>= 0`),
  `search` (необязательный). Существующие правила валидации (`400` при нарушении
  `limit/offset`) и проверки прав (`401` → `403`) сохраняются дословно.
- **Семантика `search`:** если параметр отсутствует, пуст или состоит только из
  пробелов — фильтр не применяется (полный список). Иначе термином считается
  `Trim(search)`; в выборку попадают магазины, у которых `Name` **или** `Inn` содержит
  термин как подстроку **без учёта регистра**.
- **Null-ИНН:** для магазинов с `Inn == null` условие по ИНН ложно, но магазин
  попадает в результат, если совпало `Name`. Сравнение по `Inn` не должно порождать
  ошибок/исключений.
- **Ответ:** `200 OK`, тело — массив `MerchantDto` (без изменений состава и имён полей,
  включая `inn`, `defaultCommodityCategoryId/Name` из ADR-032), заголовок
  `X-Total-Count` — общее число магазинов **после применения фильтра**. Порядок —
  по `Name` (как сейчас), стабилизированный при необходимости вторичным ключом
  (например, `Id`) для детерминированной пагинации.
- **Пустой результат:** `200 OK`, тело `[]`, `X-Total-Count: 0` (не `404`). Пагинация
  на клиенте интерпретирует это как ноль страниц/пустое состояние — корректно.
- **Ошибки:** `401` (нет пользователя), `403` (не админ, явный ответ по принятому в
  модуле стилю), `400` (невалидные `limit/offset`) — без изменений. Переход на
  ProblemDetails не выполняется (стиль модуля — текстовые тела).

### 2. Слой данных (репозиторий/запрос)

- `IMerchantRepository` получает **аддитивную** возможность постраничного чтения с
  фильтром (например, отдельный метод, возвращающий страницу и общее количество, либо
  эквивалентный контракт), чтобы эндпоинт не опирался на `GetAllAsync()` для списка.
  Существующие методы (`GetAllAsync`, `GetByIdAsync`, `GetByInnAsync`,
  `UpdateCategoryAsync`, `GetDefaultCommodityCategoriesAsync`, `AddAsync`) и их
  семантика **не меняются**.
- Реализация в `Infrastructure/Persistence/Postgres/MerchantRepository` формирует
  запрос к `Merchants` (`AsNoTracking`) с условием:
  - без `search` — без фильтра;
  - с `search` — `Name` содержит термин ИЛИ (`Inn` не `null` И `Inn` содержит термин),
    сравнение без учёта регистра. Для PostgreSQL предпочтителен перевод провайдером
    (`EF.Functions.ILike` либо эквивалент) с параметризацией (`%term%`), чтобы
    избежать SQL-инъекций и расхождений регистра; конкретная форма — деталь реализации
    при условии сохранения семантики «substring, case-insensitive».
- `COUNT` вычисляется по тому же предикату, что и выборка страницы; страница —
  `ORDER BY Name` (+ стабильный tie-breaker) → `Skip(offset).Take(limit)`.
- Индексы на `name/inn` в рамках этой задачи не добавляются: объём таблицы магазинов
  и частота запросов (админский экран) не требуют отдельного решения; при росте —
  отдельная задача/ADR (предикат совместим с будущим `pg_trgm`/индексом по выражению).

### 3. Слой API (эндпоинт)

- `MerchantEndpoints.GetAll` перестаёт загружать полный список и фильтровать его в
  памяти: после проверки прав и валидации параметров он нормализует `search`
  (`null`/whitespace → «нет фильтра», иначе `Trim`), запрашивает у репозитория
  (страница, `total`) по отфильтрованному набору и формирует ответ `200` + `X-Total-Count`.
- `limit/offset` продолжают валидироваться как сейчас; верхняя граница `limit` при
  необходимости может быть унифицирована с другими списками отдельным решением, но в
  рамках задачи не вводится (поведение по умолчанию и проверка `> 0` сохраняются).
- Остальные эндпоинты модуля (`PUT` категории/имени/дефолта, `POST apply`,
  `GET /categories`) — **без изменений**.

### 4. Frontend

| Место | Изменение (аддитивно к поведению страницы) |
|---|---|
| `api/merchants.ts` | Сигнатура `fetchMerchants` уже поддерживает `search` — контракт вызова сохраняется; параметр передаётся в query при непустом значении (как сейчас). Отдельных изменений формата ответа не требуется |
| `hooks/useMerchants.ts` | Добавляется состояние поискового запроса, аналогично `usePrecategorizedCommodities`: `searchInput` (значение поля) и применённый `search` (trim). Изменение `searchInput` с debounce ~300 мс устанавливает применённый `search` и **сбрасывает на первую страницу**. `loadPage`/`fetchMerchants` вызываются с `search` (или без него, если пусто). Смена `pageSize` также ведёт на первую страницу (существующее поведение). Пагинация, `totalPages/totalItems`, `refresh` работают по данным ответа (уже отфильтрованным сервером) |
| `components/MerchantsPage.tsx` | В шапку добавляется одно поле поиска (`type="search"`/`text`) с плейсхолдером «Название или ИНН», привязанное к состоянию хука; при вводе срабатывает debounce и сброс на первую страницу (через хук). Остальные контролы (размер страницы, «Обновить»), таблица, пагинация и действия — без изменений |
| `components/MerchantTable.tsx` | **Без изменений:** при пустом массиве уже показывает «Магазины не найдены.» — покрывает пустой результат поиска; подсветка совпадений не добавляется |

Поведение, эквивалентное референсу «Предкатегоризация» (debounce, сброс страницы),
реализуется тем же паттерном (`searchInput`/`search`, таймер, `setCurrentPage(1)`), но
без блокировок массовых операций (их на странице нет) и без изменений доступности для
не-админа (гейт сохраняется).

### 5. Edge cases и их обработка

| Случай | Поведение |
|---|---|
| Магазины без ИНН (`Inn == null`) | Условие по ИНН даёт «нет совпадения» без ошибки; магазин находится по названию. Пустой `Inn` в данных трактуется как отсутствие значения |
| Пустой результат поиска | `200`, `[]`, `X-Total-Count: 0`; таблица показывает существующее состояние «Магазины не найдены.»; пагинация соответствует нулевому набору |
| Фрагмент совпадает и с названием одного магазина, и с ИНН другого | В выдаче присутствуют оба магазина (OR по полям), каждый не более одного раза |
| Фрагмент совпадает и с названием, и с ИНН одного магазина | Магазин возвращается один раз |
| Поиск из цифр | Сопоставляется и с `Inn`, и с `Name` (если название содержит цифры) — единая семантика B1 |
| Пробельный запрос / очистка поля | После debounce интерпретируется как отсутствие фильтра; сброс на первую страницу; отображается полный список с корректным `X-Total-Count` и пагинацией |
| Запрос к несуществующей по номеру странице после сужения фильтра | Клиент запрашивает страницу относительно текущего состояния; `total/totalPages` пересчитываются по ответу сервера, навигация остаётся консистентной (паттерн, принятый на странице) |

- Отдельных метрик/логирования поисковых запросов не добавляется (админский экран,

- Новых настроек, env-переменных и правок инфраструктуры нет.

### 8. План тестирования (для декомпозиции)

| Уровень | Что проверяется |
|---|---|
| Эндпоинт `GET /api/merchants` | `401` без пользователя, `403` для не-админа; совпадение по названию (частичное, регистронезависимое); совпадение по ИНН (частичное); совпадение фрагмента и с названием, и с ИНН разных магазинов — оба в выдаче; магазин без ИНН находится по названию и не ломает фильтр по ИНН; пустой/пробельный `search` = полный список; пустой результат → `200`, `[]`, `X-Total-Count: 0`; `X-Total-Count` и содержимое страницы соответствуют отфильтрованному набору при `limit/offset` |
| Репозиторий/запрос | Фильтр применяется до `COUNT/SKIP/TAKE`, null-ИНН не вызывает ошибки, порядок детерминирован |
| Frontend (при наличии инфраструктуры — иначе ручная приёмка) | Поле поиска отображается, debounce, сброс на первую страницу при изменении запроса, очистка возвращает полный список, пагинация корректна после поиска/очистки; существующие действия страницы не затронуты. Барьер по факту проекта — `npm run build` + `npm run lint` + ручная проверка (см. ADR-011 E1) |

Критерии приёмки задачи считаются выполненными, когда поведение соответствует разделам
1–5 и проходит проверки уровня эндпоинта/репозитория и ручную приёмку UI.

## Последствия

**Положительные:**

- Администратор находит магазин по названию или ИНН без ручного перебора страниц;
  пагинация и счётчик отражают именно отфильтрованный набор.
- Логика поиска/пагинации концентрируется в слое данных, запрос не материализует всю
  таблицу — поведение предсказуемо при росте числа магазинов.
- Контракт ответа и существующие сценарии страницы сохраняются; изменение аддитивно.

**Отрицательные / риски:**

- Небольшое усложнение репозитория и эндпоинта (новый запрос постраничного чтения).
- Семантика `search` меняется (раньше — только имя, теперь — имя или ИНН): клиенты,
  полагавшиеся на поиск только по имени, получат более широкий результат. Для
  админского UI это ожидаемое улучшение; иных известных потребителей параметра нет.
- Регистронезависимый substring-поиск по двум полям без специализированного индекса —
  линейный по объёму таблицы на запрос; при текущем масштабе приемлемо, при росте может
  потребоваться отдельное решение (индекс/`pg_trgm`).

**Не изменяется:** схема БД, миграции, права доступа, остальные эндпоинты и страницы,
инфраструктура, Go-сервисы, MongoDB, nginx, конфигурация.

## Открытые вопросы (не блокируют ADR)

- Нужна ли единая верхняя граница `limit` для `GET /api/merchants` (сейчас проверяется
  только `> 0`, по умолчанию 50) — унификация с другими списками; вне объёма задачи.
- Потребуется ли индекс для ускорения поиска при существенном росте числа магазинов —
  отдельное решение при появлении измеримой деградации.
