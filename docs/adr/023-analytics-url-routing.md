# ADR-023: URL-роутинг состояния аналитики и ссылка на «Чеки по магазину» из списка магазинов

## Статус

Принято (проект). Реализация — по плану
[analytics-url-routing-merchant-receipts.md](../plans/analytics-url-routing-merchant-receipts.md).

## Контекст

### Проблема

Экран «Чеки по магазину» существует, но включается внутренним стейтом
`Analytics/frontend/src/components/ReceiptsPage.tsx:16` (`selectedMerchantId`) и доступен только
кликом по магазину в таблице чеков. Из списка магазинов (`/merchants`, админский раздел) в него
попасть нельзя. Состояние не отражено в адресе: F5, новая вкладка, закладка и кнопка «Назад» теряют
выбранный магазин или чек; параметр `receiptId` после загрузки чека активно удаляется из адреса
(`ReceiptsPage.tsx:88-94`) — то есть адрес не является источником истины ни для чека, ни для
магазина.

Задача [merchants-receipts-routing](../tasks/merchants-receipts-routing.md) фиксирует требования
(«Маршруты», «Требования к поведению», «Критерии приёмки», «Edge cases»). Настоящий ADR описывает
**техническое решение**: схему маршрутов и переходов, источник истины, стратегию ссылок/редиректов,
поведение кнопок браузера, восстановление состояния, декомпозицию `ReceiptsPage` и ответ на
«Открытый вопрос» задачи (различение «магазин не найден» / «у магазина нет чеков»).

### Текущее состояние кодовой базы (факты)

1. **Стек фронтенда** (`Analytics/frontend/`): React 19 + TypeScript, Vite, `react-router-dom` 7,
   `BrowserRouter` в `App.tsx`. UI-кита нет, стили — vanilla CSS с CSS-переменными. Новых
   зависимостей не требуется.
2. **Маршруты** (`App.tsx:22-28`) — ровно три, все плоские, все внутри `Layout`:
   `/` → `ReceiptsPage`, `/commodities` → `CommoditiesPage`, `/merchants` → `MerchantsPage`.
   Catch-all маршрута нет. `Layout` рендерит `<Outlet/>` внутри `<main className="content-area">`,
   а страницы — `<div className="layout">` (`MerchantsPage`, `CommoditiesPage`); исключение —
   `ReceiptsPage.tsx:97` с `<main className="layout">`, то есть вложенный `<main>` (невалидный
   HTML, но визуально безобидный). В этой задаче `<main>` заменяется на `<div>` при переносе
   разметки в `ReceiptsListView`.
3. **`ReceiptsPage.tsx` (191 строка) смешивает три режима**: общий список чеков, список чеков
   магазина и карточку чека. Признаки: два хука данных подняты одновременно
   (`useReceipts` + `useReceiptsByMerchant`, строки 33 и 46) и результат выбирается тернарной
   цепочкой из 10 переменных (строки 49-58); собственный `fetch` карточки (`handleReceiptClick`,
   строки 68-81) без abort-защиты; `useSearchParams` для `receiptId` + эффект, который после
   загрузки чека чистит адрес (`setSearchParams({}, { replace: true })`, строки 88-94).
4. **Ссылки**: `MerchantTable.tsx:170` рендерит имя магазина как `<span>` (кликабельно только в
   режиме инлайн-редактирования, ветка `editingNameId === merchant.id`, строки 132-181).
   `ReceiptTable.tsx:46-67` — две кнопки-колбэка («Магазин» → `onViewMerchantReceipts`,
   дата покупки → `onReceiptClick`).
5. **Навигация**: `Sidebar.tsx:13` — `NavLink to="/" end` (при `end` пункт «Чеки» перестанет
   подсвечиваться на `/receipts` после переноса раздела). `CommoditiesPage.tsx:36` —
   `navigate('/?receiptId=' + receiptId)` (единственный внутренний переход к чеку).
6. **Хуки данных**: `useReceipts` и `useReceiptsByMerchant` (119 строк) — почти построчные
   дубликаты; различие только в передаче `merchantId` в `fetchReceipts`
   (`api/receipts.ts:16-19` уже умеет оба URL). `useReceiptsByMerchant` не имеет abort при
   unmount и дублирует `loadPage(1)` в двух эффектах. `useReceiptsByMerchant` используется только
   в `ReceiptsPage`.
7. **API «Чеки по магазину»**: `GET /api/receipts/by-merchant/{merchantId:guid}`
   (`ReceiptEndpoints.cs:19, 62-85`) **всегда возвращает 200** + массив (возможно пустой) +
   `X-Total-Count`, независимо от существования магазина. Проверки «магазин существует» нет.
8. **API карточки чека**: `GET /api/receipts/{id:guid}` уже возвращает 404 для неизвестного/чужого
   чека (`ReceiptReadService.GetByIdAsync` — owner-scoped, ADR-009). Фронтенд это различие
   **теряет**: `handleReceiptClick` пишет в `console.error` и рисует «Чек не найден.» для любой
   ошибки, включая сеть и 5xx.
9. **Существование магазина на бэкенде проверить можно без новых сущностей**: `IMerchantRepository`
   (Domain) с `GetByIdAsync(Guid)` уже есть, реализован в `MerchantRepository` (PK-запрос,
   `AsNoTracking`), зарегистрирован как scoped (`DependencyInjectionExtensions.cs:41`) и уже
   внедряется в API-слой (`MerchantEndpoints.cs`, в т.ч. для 404-сценариев).
10. **Важная деталь инфраструктуры**: `Program.cs:36` — `app.MapFallbackToFile("/index.html")`.
    Сборка фронтенда кладётся в `src/ReceiptCollector.Analytics.Api/wwwroot` (vite `outDir`), и
    `index.html` в репозитории присутствует. Поэтому **неизвестный путь под `/api` без расширения
    возвращает 200 с HTML `index.html`, а не 404**: запрос
    `/api/receipts/by-merchant/abc` не попадёт в `HttpError(404)`, а упадёт на
    `response.json()` (JSON parse error). Это значит, что «мусорный» id в URL **нельзя**
    классифицировать по ответу бэкенда — нужна клиентская проверка формата (решение I1).
11. **SPA-fallback есть на всех контурах**: `nginx.prod.conf:70-72`
    (`try_files $uri $uri/ /index.html`) для продакшена, dev-сервер Vite — по умолчанию.
    F5/новые вкладки по глубоким ссылкам работают инфраструктурно, менять ничего не нужно.
12. **Карточка чека сегодня рендерится внутри `.layout`**: `ReceiptsPage.tsx:167-175` передаёт
    `ReceiptDetails` в `<main className="layout">`, а сам `ReceiptDetails` рендерит
    `<div className="receipt-details">` (свои `max-width: 1000px` и `padding: 2rem`). Без внешнего
    `.layout` (max-width 960 + свои отступы) карточка станет шире и с другими отступами, поэтому
    новый маршрут `/receipts/:receiptId` обязан сохранить обёртку `.layout` вокруг
    `ReceiptDetails` — это требование «без изменения вёрстки», а не стилистика.
13. **Тесты**: автотестов фронтенда нет (решение E1 в ADR-011), приёмка ручная; регрессионный
    барьер — `npm run build` (выполняется в CI внутри Docker-образа) и `npm run lint` (вручную).
    На бэкенде тесты есть: xunit + NSubstitute, `MerchantEndpointsTests.cs` показывает образец
    прямого вызова `public static` методов endpoint-ов, CI выполняет `dotnet test` для любого
    изменения в `Analytics/**`.

## Рассмотренные варианты

### A. Схема маршрутов

#### A1. Плоские маршруты-сиблинги под одним `Layout` + catch-all `*` — **выбран**

```
/                                  → редирект (см. C4)
/receipts                          → ReceiptsPage
/receipts/:receiptId               → ReceiptDetailsPage
/commodities                       → CommoditiesPage
/merchants                         → MerchantsPage (админ-гейт внутри компонента)
/merchants/:merchantId/receipts    → MerchantReceiptsPage (без админ-гейта)
/*                                 → NotFoundPage
```

**Плюсы:** полное совпадение с таблицей маршрутов задачи; каждый экран — отдельный компонент с
одним источником состояния (URL); `Layout`/`Sidebar` доступны на всех экранах, включая «Не
найдено»; `/merchants/:merchantId/receipts` **не наследует** админ-гейт `/merchants`, потому что
это сиблинг, а не вложенный маршрут.

**Минусы:** два маршрута с общим префиксом `/merchants` (дисплей — единственное место, где их
нужно различать).

#### A2. Вложенные маршруты (`/merchants/*` как `children`) — **отклонён**

**Минусы:** админ-гейт живёт в `MerchantsPage`; при вложенности «Чеки по магазину» стал бы
наследовать либо гейт (ломает критерий «не-админ может открыть „Чеки по магазину“ по прямой
ссылке»), либо потребовал бы выносить гейт в `layout`-route и дублировать его логику. Обмен
SRP внутри родителя на лишнюю вложенность — невыгодно.

#### A3. Query-параметры (`/receipts?merchantId=…&receiptId=…`) — **отклонён**

**Минусы:** прямо запрещено требованием задачи («Только сегменты пути»); плюс известная проблема
`:receiptId`-регрессии в `React.lazy`/соседних маршрутах, которую пришлось бы обходить.

#### A4. `HashRouter` — **отклонён**

**Минусы:** в репозитории уже есть SPA-fallback (факт 11), `#` в ссылках не нужен и ухудшает
читаемость/копируемость; переход на `HashRouter` — лишний риск без выигрыша.

### B. Источник истины для состояния

#### B1. URL — единственный источник для раздела/магазина/чека; остальное — локально — **выбран**

Параметры читаются через `useParams()` и передаются вниз как пропсы; зеркальные
`useState`-переменные (`selectedMerchantId`, `selectedReceiptId`, `receiptIdFromUrl`) удаляются.
Локальным остаётся ровно то, что задано вне URL: номер страницы (внутри хуков), размер страницы
(`PageSizeContext`, ADR-006 — решение принято ранее и задачей не пересматривается), режим
инлайн-редактирования имени, фильтр категорий в «Товарах».

**Плюсы:** перезагрузка, новая вкладка, закладка, «Назад»/«Вперёд», передача ссылки коллеге
работают без дополнительного кода; устранён целый класс рассинхрона «URL ≠ стейт» (сегодня
`receiptId` стирается из адреса, а `selectedMerchantId` в адресе не существует).

**Минусы:** страница/размер страницы по-прежнему не сохраняются — это осознанное требование задачи.

#### B2. Оставить стейт и синхронизировать его с URL — **отклонён**

**Минусы:** два источника истины; эффекты синхронизации ломаются при F5/«Назад» именно там, где
сейчас и наблюдается проблема (это текущее состояние кода, а не решение).

#### B3. URL + кэш последних данных в Context — **отклонён**

**Минусы:** кэш без TTL протухает (критерий приёмки про «данные предыдущего экрана»), а
react-router уже решает задачу «вернуться назад мгновенно» за счёт `history.state`. YAGNI.

### C. Стратегия ссылок и редиректов

#### C1. `<Link>` для ссылки на магазин; `navigate()` для кнопок; `replace` — только для редиректов — **выбран**

| Переход | Механизм | Обоснование |
|---|---|---|
| Имя магазина в таблице «Магазины» | `<Link to={merchantReceiptsPath(id)}>` | критерий «рабочие ссылки» (Ctrl/средняя кнопка), семантика `<a>` |
| Кнопка «Магазин» в таблице чеков | `<button onClick={() => navigate(path)}>` | задача: «остаётся кнопкой, а не ссылкой» |
| Клик по чеку (дата покупки) | `<button onClick={() => navigate(receiptPath(id))}>` | текущее поведение сохранено (кнопка), меняется только целевой URL |
| «Все чеки» на экране «Чеки по магазину» | `<button onClick={() => navigate(receiptsPath())}>` | задача называет её кнопкой; `push` сохраняет «Назад» |
| «Вернуться к списку чеков» на «Не найдено» | `<Link to={receiptsPath()}>` | это ссылка, а не действие с побочным эффектом |
| Пункты меню | `NavLink` (`to="/receipts"`) | уже ссылки |
| `/` и `/?receiptId={id}` | `<Navigate replace …>` | редиректы не должны попадать в историю |

**Плюсы:** ровно одна точка истины на экран; поведение кнопок браузера бесплатно; «Назад» после
любого клика возвращает на исходный экран.

**Минусы:** пути строятся в нескольких местах → нужен один модуль сборки путей (`src/routes.ts`),
иначе схема размазывается по шести файлам (DRY).

#### C2. Всё через `<Link>` — **отклонён**

**Минусы:** прямо нарушает требование «Кнопка „Магазин“ … остаётся кнопкой» и меняет вид/поведение
существующих кнопок (пункт «больше на этом экране не меняем» в задаче).

#### C3. Всё через кнопки и `navigate()` — **отклонён**

**Минусы:** имя магазина перестаёт быть ссылкой → не выполняются критерии про Ctrl+клик, среднюю
кнопку и «ссылка переносится между вкладками/устройствами».

#### C4. `replace` для всех внутренних переходов — **отклонён**

**Минусы:** «Назад» перестаёт работать (запись заменяется) — прямое нарушение критерия приёмки.
`replace` применяется **только** к редиректам (`/` и `?receiptId=`), где запись в истории не имеет
смысла и иначе пользователь возвращался бы на `/` и снова редиректился.

### D. Кнопки «Назад»/«Вперёд» и восстановление состояния

#### D1. Нативная история + ин-апп «Назад» = `navigate(-1)` при наличии в-апп истории, иначе `navigate('/receipts')` — **выбран**

Все переходы внутри приложения — `push` (`Link`/`navigate`), поэтому браузерные «Назад»/«Вперёд»
работают без вмешательства. Кнопка «← Назад к списку чеков» в карточке чека — единственное место,
где нужен «назад с возвратом в контекст»: из `/merchants/{id}/receipts` пользователь ожидает
вернуться к чекам магазина, а не к общему списку. Признак «в истории есть предыдущая
внутри-приложенческая запись» берётся из состояния истории react-router:
`window.history.state.idx > 0` (см. факт: `createBrowserHistory` пишет `idx`, `push` — `idx + 1`,
`replace` — `idx`, `go(n)` — нативный `history.go`; на свежей загрузке документа `idx` инициализируется
0). Если `idx === 0` (чека открыли по прямой ссылке/в новой вкладке) — fallback на `/receipts`.

**Плюсы:** сохраняет контекст возврата; не дублирует состояние в `location.state`; при прямой
ссылке не выкидывает пользователя из приложения (обычная проблема «назад»-кнопок в SPA).

**Минусы:** зависимость от внутреннего поля `history.state.idx` react-router (публичный,
стабильный, но всё же деталь реализации) — отсюда защитная проверка `typeof idx === 'number'`.

#### D2. Ин-апп «Назад» всегда `navigate('/receipts')` — **отклонён**

**Минусы:** совпадает с текущим поведением, но теряет контекст магазина: из чека магазина
пользователь попадает в общий список и вынужден искать заново.

#### D3. `location.state.from` во всех внутренних переходах — **отклонён**

**Минусы:** маршрут начинает дублироваться в `state` (второй источник истины, прямое нарушение
требования «внутренние стейты, дублирующие состояние из URL, не используются»); каждое место
навигации обязано не забыть передать `state`.

### E. Декомпозиция `ReceiptsPage`

#### E1. Три экрана + общий презентационный список — **выбран**

```
ReceiptsPage        → /receipts                        (только общий список)
MerchantReceiptsPage→ /merchants/:merchantId/receipts   (только список магазина)
ReceiptDetailsPage  → /receipts/:receiptId             (только карточка)
ReceiptsListView    → переиспользуемая разметка списка (без роутера и данных)
NotFoundPage        → «Не найдено» (переиспользуется 4 раза)
```

**Плюсы:** SRP — экран = маршрут; тернарная цепочка выбора «какой из двух хуков» исчезает; общая
разметка (заголовок, «Найдено чеков», выбор размера страницы, «Обновить», состояния загрузки/ошибки,
таблица, пагинация) не дублируется; каждый экран ~30-45 строк вместо 191.

**Минусы:** один новый презентационный компонент с набором пропсов (7 полей) — осознанная плата за
DRY; альтернатива «без него» даёт ~70 строк дублирующей разметки.

#### E2. Оставить один компонент и переключать режим по параметрам — **отклонён**

**Минусы:** это текущее состояние кода, от которого уходит задача (смешение трёх режимов).

#### E3. Вынести только данные, разметку оставить в странице — **отклонён**

**Минусы:** два места с почти идентичной разметкой; расхождение при правках (заголовок, счётчик,
кнопка «Все чеки», пагинация) — источник багов при следующей задаче.

### F. Слой данных (хуки)

#### F1. Объединить `useReceiptsByMerchant` в `useReceipts({ pageSize, merchantId? })` — **выбран**

`api/receipts.ts` уже умеет оба URL по наличию `merchantId`; тела хуков совпадают построчно.
Слияние даёт: один хук → одно место для логики «404 → не найдено», один abort-guard, один тип
возвращаемого состояния для `ReceiptsListView`; минус 119 строк дублирования; побочно —
`useReceiptsByMerchant` терял abort при unmount, а эта проблема исчезает вместе с ним.
`useReceiptsByMerchant` используется только в `ReceiptsPage` — других мест правки нет.

**Минусы:** трогается хук самого горячего экрана (все чеки) — но изменение механическое
(добавить необязательный параметр, передать его в уже существующий `fetchReceipts`).

#### F2. Оставить два хука и добавить `notFound` в оба — **отклонён**

**Минусы:** два места с одинаковой логикой 404/ошибки и два места, где со временем разъедутся
детали (abort, сброс данных) — ровно тот класс дефектов, который задача и устраняет.

#### F3. Отдельный хук `useReceiptDetails(receiptId)` для карточки — **выбран**

Согласуется с существующей архитектурой «данные — в хуках» (`useReceipts`, `useMerchants`,
`useCommodities`) и даёт карточке те же состояния, что и спискам: `isLoading` / `notFound` /
`error` + `refresh` (нужен для `onReceiptRefresh` после сохранения категорий) и abort-защиту,
которой сегодня нет.

### G. Защита от гонок при быстрой смене маршрутов

#### G1. `key={id}` на внутреннем компоненте экрана + `AbortController` + проверка «свой ли ответ» — **выбран**

Факт: react-router **не размонтирует** компонент при смене параметра в пределах одного маршрута
(`/receipts/A` → `/receipts/B` переиспользует тот же экземпляр). Поэтому «страница читает
`useParams()` и сама держит хук» недостаточно: первый кадр будет отрисован со старыми данными, а
поздно пришедший ответ может их перезаписать. Решение: внешний компонент экрана читает параметр,
при невалидном — сразу `NotFoundPage`, иначе рендерит внутренний экран с `key={id}`; пересоздание
ключа даёт свежий хук с пустым состоянием. Дополнительно — `AbortController` + проверка
`abortRef.current === controller` перед `setIsLoading(false)` (паттерн уже есть в `useReceipts`) и
abort в cleanup эффекта.

**Плюсы:** отсутствие «экрана предыдущего чека/магазина» без дополнительных стейтов и без
усложнения хуков; соответствует критерию edge case о гонках.

#### G2. Сброс данных в хуке при смене ключа (`loadedKey`-сравнение) — **отклонён**

**Минусы:** дублирует то же решение императивно внутри хука (лишний стейт во всех потребителях),
в то время как `key` решает задачу декларативно в одной строке.

### H. «Магазина не существует» vs «у магазина нет чеков» (открытый вопрос задачи)

Текущее состояние: `GET /api/receipts/by-merchant/{merchantId}` **не может** различить эти случаи —
обе ситуации дают `200` + `[]` + `X-Total-Count: 0` (факт 7). Значит, без изменения бэкенда критерии
«Несуществующий id магазина → „Не найдено“» и «Магазин существует, но чеков нет → пустое состояние»
одновременно невыполнимы.

#### H1. `404` от `GET /api/receipts/by-merchant/{merchantId}` для неизвестного магазина — **выбран**

В `ReceiptEndpoints.GetByMerchant` внедряется уже зарегистрированный `IMerchantRepository`
(тот же приём, что в `MerchantEndpoints`), первым запросом проверяется существование магазина;
`null` → `Results.NotFound("Merchant not found.")` (текст совпадает с уже используемым в
`UpdateCategory`/`UpdateMerchantName`, тело — plain text, как у них).

**Почему это не «поломка контракта»:**

- Для **существующего** магазина ответ побайтово прежний: `200`, тот же JSON-массив, тот же
  заголовок `X-Total-Count`. Ни один параметр не становится обязательным, ни одно поле не меняется.
- Меняется только код ответа для случая, который раньше был **семантически неверным**: ресурс
  (магазин) не существует, а endpoint отвечает `200` (RFC 9110, 15.5.5). Это ровно тот случай, где
  «отличать состояния» иначе нечем.
- Других потребителей эндпоинта в репозитории нет (единственный клиент — `useReceipts`); внешних
  клиентов API аналитики не имеет (закрытый контур, ADR-016).
- Дополнительная стоимость — один SELECT по первичному ключу в небольшой таблице `merchants`
  (проверка выполняется **первым** запросом, поэтому для несуществующего id не выполняются
  два лишних запроса за чеками).

**Почему не надо «только фронтендом»:** `GET /api/merchants` закрыт для не-админов
(`MerchantEndpoints.GetAll` → `Results.Forbid()`), это пагинированный список, и он недоступен
не-администратору — именно для него требуется различать состояния (критерии 8 и 11). Проверка
существования на клиенте невозможна в принципе.

#### H2. Всегда `200` + заголовок `X-Merchant-Exists: true|false` — **отклонён (запасной вариант)**

**Плюсы (перечислены честно):** формально ноль изменений существующего контракта; фронтенд
меняется точно так же — он и сейчас читает `X-Total-Count`.

**Минусы:** нестандартный, «договорной» заголовок вместо кода ответа; `200` на несуществующем
ресурсе остаётся неверным семантически; асимметрия с `GET /api/receipts/{id}` (там уже 404).

**Статус:** запасной путь, если заказчик сочтёт смену кода ответа недопустимой. Фронтенд при
этом правится **без изменений** (вместо `status === 404` проверяется заголовок в одном месте
`api/receipts.ts`), то есть решение можно переиграть без повторного релиза фронта.

#### H3. Новый `GET /api/merchants/{merchantId}` (проверка существования) — **отклонён**

**Минусы:** явно вне объёма задачи («имя магазина в заголовке … не нужно `GET /api/merchants/{id}`»);
требует два сетевых запроса на каждый заход на экран, что замедляет самый частый переход и создаёт
гонку между двумя ответами (магазин могут удалить между запросами).

#### H4. Не различать, показывать пустое состояние в обоих случаях — **отклонён**

**Минусы:** прямо нарушает критерии приёмки «Несуществующий id магазина или чека → экран „Не
найдено“, а не пустой список» и «Магазин существует, но чеков нет → пустое состояние».

#### H5. Отличать «не найдено» по непустому `X-Total-Count`/типу элемента — **отклонён**

**Минусы:** список всегда пустой в обоих случаях, различать нечем.

#### Сопутствующее решение: чек

Бэкенд для карточки чека **не меняется**: `GET /api/receipts/{id}` уже отдаёт `404` (факт 8).
Меняется только фронтенд — перестаёт «глотать» ошибку и различает `404` («Не найдено») и всё
остальное (сеть/5xx → блок ошибки с кнопкой «Попробовать снова»).

### I. Валидация идентификатора в URL

#### I1. Клиентская проверка формата GUID (regex) в точке входа экрана — **выбран**

Из-за `MapFallbackToFile` (факт 10) невалидный `merchantId`/`receiptId` **не даёт 404** — бэкенд
отдаёт `200` + HTML, и фронтенд упадёт на разборе JSON, показав экран «Не удалось загрузить…»
вместо «Не найдено». Поэтому формат id проверяется на клиенте до запроса: не-GUID → сразу
`NotFoundPage`. Побочная выгода: нет лишнего сетевого запроса и нет зависимости от
конфигурации `wwwroot`/nginx.

**Плюсы:** детерминированно закрывает edge case «мусорный путь → „Не найдено“»; предотвращает
«мусор» в пути (id экранируется при построении пути).

**Минусы:** проверка формата дублирует серверную (`{merchantId:guid}`), т.е. две «правды» о формате.
Приемлемо, потому что это чисто UX-проверка (fail fast), а источником истины остаётся БД.

#### I2. Полагаться только на ответ бэкенда — **отклонён**

**Минусы:** воспроизводимо ломает edge case (см. факт 10) — «Не найдено» превращается в «Ошибка
загрузки» из-за HTML вместо JSON.

### J. Что осознанно НЕ меняется (границы задачи)

- `CommoditiesPage` и раздел «Товары» — внутренний переход к чеку остаётся legacy-формой
  `/?receiptId=…` (`CommoditiesPage.tsx:36`); он корректен через редирект (см. C1). Смена этой
  строки на `/receipts/{id}` — отдельная задача (косметика, 1 строка), здесь она вне объёма.
- `ReceiptTable` — **без изменений**: API презентационного компонента (`onViewMerchantReceipts`,
  `onReceiptClick`) не меняется, целевые URL вычисляет страница. Критерий «кнопка „Магазин“ остаётся
  кнопкой» выполняется автоматически.
- `ReceiptDetails` (карточка) — **без изменений**: пропсы `onBack`/`onReceiptRefresh` те же; ветка
  «`receipt === null` → „Чек не найден.“» остаётся как защитный fallback, страница на неё не
  опирается. Сам чек карточка не грузит — `receipt` приходит пропом (внутри только справочник
  категорий, `ReceiptDetails.tsx:72-80`), поэтому перенос загрузки в `useReceiptDetails` её не
  ломает.
- `useAdmin`/`adminService`, админ-гейт внутри `MerchantsPage`, `Layout`, `Pagination`, `Toasts`,
  `CustomDialog`, `PageSizeContext` — без изменений.
- nginx, docker-compose, Go-бэкенд, бот, миграции БД — без изменений (SPA-fallback уже есть).
- Автотесты фронтенда (Vitest и т. п.) — не вводим (ADR-011, решение E1).

## Решение

Выбраны: **A1** (плоские маршруты + catch-all), **B1** (URL — единственный источник истины),
**C1** (`<Link>` для ссылки на магазин, `navigate()` для кнопок, `replace` только для редиректов),
**D1** (`navigate(-1)` при `history.state.idx > 0`, иначе `/receipts`), **E1** (три экрана +
`ReceiptsListView`), **F1** (слияние хуков) + **F3** (`useReceiptDetails`), **G1** (`key` + abort),
**H1** (404 от by-merchant для неизвестного магазина; запасной путь — **H2**), **I1** (клиентская
проверка GUID), **J** (жёсткие границы).

### Таблица маршрутов (итог)

| URL | Экран | Компонент | Доступ |
|---|---|---|---|
| `/` | редирект на `/receipts` (или `/receipts/{id}`, если есть `?receiptId=`) | `RootRedirect` (в `App.tsx`) | все |
| `/receipts` | Все чеки («Мои чеки») | `ReceiptsPage` | все |
| `/receipts/:receiptId` | Карточка чека | `ReceiptDetailsPage` | все |
| `/commodities` | Товары | `CommoditiesPage` | все (без изменений) |
| `/merchants` | Список магазинов | `MerchantsPage` | только админ (гейт внутри) |
| `/merchants/:merchantId/receipts` | Чеки по магазину | `MerchantReceiptsPage` | все |
| `*` | «Не найдено» + ссылка на `/receipts` | `NotFoundPage` | все |

### Что в URL, а что нет (граница состояния)

| Состояние | Где хранится | Обоснование |
|---|---|---|
| Открытый раздел | URL (маршрут) | требование задачи |
| Выбранный магазин | URL (`merchantId`) | требование задачи; имя магазина в адрес не попадает — переименование не ломает ссылки |
| Открытый чек | URL (`receiptId`) | требование задачи; `?receiptId` из старых ссылок — редирект |
| Номер страницы | локально в хуке | прямо запрещено требованием |
| Размер страницы | `PageSizeContext` (ADR-006) | прямо запрещено требованием; смена `pageSize` = перезагрузка данных без смены URL; ADR-006 сознательно отклонил `?pageSize=` |
| Режим редактирования имени/категории | локально в `MerchantTable` | прямо запрещено требованием |
| Фильтр категорий в «Товарах» | локально в `CommoditiesPage` | вне объёма |

### Сценарии переходов и что происходит с историей

| Сценарий | Последовательность записей истории |
|---|---|
| Список магазинов → клик по имени | `push /merchants/{id}/receipts`; «Назад» → `/merchants` |
| Список магазинов → F5 | одна запись `…/merchants/{id}/receipts`, состояние восстановлено из URL |
| Ссылка скопирована в другую вкладку/пользователю | тот же маршрут, тот же экран; не-админ видит «Чеки по магазину», а не «Доступ запрещён» |
| Список чеков → кнопка «Магазин» | `push /merchants/{id}/receipts` |
| Чеки магазина → «Все чеки» | `push /receipts`; «Назад» → чеки магазина |
| Список → клик по чеку | `push /receipts/{id}`; кнопка «Назад» в карточке → `navigate(-1)` (список/чеки магазина); F5 → тот же чек |
| Прямая ссылка `/receipts/{id}` в новой вкладке | `idx = 0` → кнопка «Назад» → `/receipts` |
| Старая закладка `/` | `replace` → `/receipts` (одна запись, «Назад» не возвращает на `/`) |
| Старая закладка `/?receiptId={id}` | `replace` → `/receipts/{id}` |
| Неизвестный/мусорный путь | catch-all → «Не найдено» + ссылка на `/receipts` |

`ReceiptsListView` — презентационный компонент (без `useNavigate`/загрузки): пропсы
`title`, `list: ReturnType<typeof useReceipts>`, `onViewMerchantReceipts`, `onReceiptClick`,
`headerAction?: ReactNode` (кнопка «Все чеки»). Он же решает, что показывать при
`isLoading`/`error`/пустом списке. Ветку `notFound` обрабатывает **страница** (она решает, какой
экран «Не найдено» показать), а не `ReceiptsListView`.

Ошибки HTTP на уровне API: `api/receipts.ts` начинает бросать `HttpError` (наследник `Error` с
полем `status`) вместо голого `Error` и экспортирует предикат `isNotFound(error)`. Место, где
решается «404 → не найдено / иначе → ошибка», — одно (`fetchReceipts`/`fetchReceiptDetails` +
`useReceipts`/`useReceiptDetails`), а не размазано по компонентам.

### Контракт API: минимальное изменение бэкенда

`Analytics/src/ReceiptCollector.Analytics.Api/Modules/Receipts/ReceiptEndpoints.cs`, метод
`GetByMerchant`: добавить `[FromServices] IMerchantRepository merchantRepository` и проверку
существования **до** выборки чеков.

| Запрос | Было | Стало |
|---|---|---|
| `by-merchant/{существующий guid}` | `200` + массив + `X-Total-Count` | **без изменений** |
| `by-merchant/{неизвестный guid}` | `200` + `[]` + `X-Total-Count: 0` | `404` + `Merchant not found.` |
| `by-merchant/{не-guid}` | `200` + HTML (SPA-fallback) | без изменений (фронт такие id не отправляет, решение I1) |
| `by-merchant` без аутентификации | `400` | без изменений |
| `receipts/{неизвестный guid}` | `404` | без изменений (фронт теперь это различает) |

Изменения вне `GetByMerchant` не требуются: новых эндпоинтов нет, `IMerchantRepository` уже
зарегистрирован, `Api → Domain` разрешён архитектурным тестом (`ProjectDependencyTests.cs:52-53`),
миграций нет. Для тестируемости методы `GetByMerchant` (и `GetById`) делаются `public static` —
ровно как уже сделано в `MerchantEndpoints`; набор тестов добавляется в
`Analytics/tests/ReceiptCollector.Analytics.Api.Tests/ReceiptEndpointsTests.cs` по образцу
`MerchantEndpointsTests`.

### Порядок развёртывания

Изменение backend и frontend **совместимо в обе стороны, но не симметрично**:

1. **Сначала backend.** Если выкатить только фронт, неизвестный магазин вернёт `200 + []` и
   пользователь увидит пустое состояние вместо «Не найдено» — критерий приёмки не выполнен, но
   ничего не сломано.
2. **Затем frontend.** Между шагами старый фронт на неизвестном магазине покажет
   «Не удалось загрузить чеки: Merchant not found.» вместо пустого состояния — окно в десятки
   минут между выкатками, приемлемо.
3. Никаких «feature flags» и версионирования API не вводим (оснований нет, YAGNI).

| 12. Старые `/` и `/?receiptId=` работают | `RootRedirect` с `replace` (этап 8) |
| 13. `npm run build` проходит | типизация в `routes.ts`/хуках/страницах; проверяется в CI |
| 14. `npm run lint` проходит | порядок хуков в новых экранах (G1), отсутствие `useSearchParams`/`setState`-зеркал |
| Edge: мусорный путь/пустой id → «Не найдено» | `isGuid` (I1) + catch-all |
| Edge: быстрая смена маршрутов без гонок | `key={id}` + abort (G1) |
| Edge: переименование магазина не ломает ссылку | в адресе `merchantId`, не имя |

## Последствия

### Положительные

- Любое состояние раздела воспроизводится по ссылке: F5, новая вкладка, закладка, «Назад»/«Вперёд»,
  передача коллеге (включая не-админа).
- Ссылка на магазин из админского списка — основной путь к его чекам; Ctrl/Cmd/средняя кнопка
  работают штатно.
- `ReceiptsPage` из 191 строки с тремя смешанными режимами превращается в три экрана с одной
  ответственностью; −119 строк дублирующего хука; тернарная цепочка выбора «чьи данные»
  исчезла.
- Ошибка загрузки и «не найдено» больше не смешаны: сетевая ошибка даёт блок с «Попробовать
  снова», отсутствующий объект — экран «Не найдено» с возвратом к списку.
- Единственный источник истины (URL) исключает класс дефектов «экран и адрес показывают разное».
- Ноль новых зависимостей; ноль изменений в инфраструктуре (nginx/миграции/Go).

### Отрицательные

- Стало больше маленьких файлов (5 новых модулей) — навигация по коду требует знать карту
  «экран ↔ маршрут» (карта приведена выше и продублирована в плане).
- `useReceipts` (горячий экран) изменён — основной риск регрессии; компенсируется сборкой,
  линтером и ручной приёмкой.
- Добавлен один SQL-запрос на каждый вызов by-merchant (проверка существования).
- Эндпоинт по строгим мероприятиям изменился: неизвестный `merchantId` → `404` вместо `200 + []`.
  Внешних потребителей API нет; запасной вариант (H2) — без изменения фронта.
- Появилась зависимость от `history.state.idx` react-router для кнопки «Назад» в карточке (с
  защитной проверкой типа).
- Клиентская проверка GUID дублирует серверную: при смене формата идентификаторов в БД фронт
  придётся обновить (риск низкий: идентификаторы — UUID, фиксированы схемой).

### Компромиссы

- **Сиблинги вместо вложенных маршрутов** (A1) — чуть более плоская схема взамен отсутствия
  риска унаследовать админ-гейт.
- **`push` для всех внутренних переходов** (C1) — история длиннее взамен рабочих «Назад»/«Вперёд».
- **Слияние двух хуков** (F1) — трогаем горячий экран взамен единственного места для логики 404.
- **`ReceiptsListView` с 6 пропсами** (E1) — плата за DRY против дублирования ~70 строк.
- **404 вместо заголовка-признака** (H1) — семантически правильно и совпадает с
  `GET /api/receipts/{id}`, но это единственное изменение API-контракта в задаче.
- **Клиентская валидация GUID** (I1) — дублирование правила формата взамен детерминированного
  поведения на мусорных ссылках.

### Нефункциональные аспекты

- **Производительность:** +1 PK-SELECT на экран «Чеки по магазину» (выполняется первым, до
  выборки). Объём запросов на экраны списка не меняется. Смена `merchantId`/`receiptId` =
  пересоздание экрана (один запрос) — это и есть требуемое поведение.
- **Масштабируемость:** изменений в схеме БД нет; индекс по `merchants.id` — PK, проверка
  существования его использует.
- **Безопасность:** новых эндпоинтов и новых способов аутентификации нет; `UserContext.UserId`
  остаётся обязательным. Эндпоинт по-прежнему отдаёт только чеки текущего пользователя. Ответ
  `404` раскрывает факт существования чужого `merchantId` — риск ничтожен: магазины и так видны
  пользователю в его чеках, а административные эндпоинты закрыты.
- **Сопровождаемость:** пути собраны в `src/routes.ts`; «какой экран на каком маршруте» читается
  в одном месте (`App.tsx`).
- **Обратная совместимость ссылок:** `/` и `/?receiptId=…` поддержаны (критерий 12); прямые
  обращения к API не менялись, кроме одного кода ответа (см. контрактную таблицу).
- **Локализация/UX:** «Не найдено» и «Чеки не найдены» — разные тексты (критерии 8 и 9),
  «Доступ запрещён» остался только на `/merchants` (критерий 11).

### Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Регрессия списка всех чеков из-за слияния хуков | Низкая | Изменение механическое; `npm run build` + `npm run lint` + ручная приёмка обоих списков; `ReceiptsListView` — единственная развёртка |
| Ошибка 404 на существующем магазине (например, другая БД) | Очень низкая | Проверка идёт по тому же `IMerchantRepository`, что и админские операции; тест «существующий магазин → 200» |
| Мусорный id даёт не «Не найдено», а ошибку загрузки | Средняя без I1 | `isGuid` до запроса; отдельный пункт ручной приёмки |
| Показ данных предыдущего экрана при быстрых переходах | Низкая | `key={id}` + `AbortController` + проверка «свой ли ответ» (паттерн G1) |
| Подсветка «Чеки» в меню пропала на `/receipts` | Средняя без правки | `Sidebar` переводится на `to="/receipts"` без `end`; проверяется вручную |
| Кнопка «Назад» в карточке выкидывает из приложения | Низкая | `idx > 0` + fallback на `/receipts`; проверка на прямой ссылке |
| Старый фронт после выкатки бэкенда показывает ошибку вместо пустого списка | Низкая | Порядок выкатки: сначала backend (риск обратный — пустое состояние вместо «Не найдено») |
| Линтер/сборка не замечают нарушения правил хуков (ранний `return` до `useReceipts`) | Низкая | В плане зафиксировано: проверка `isGuid` — во **внешнем** компоненте, хуки — во внутреннем; `npm run lint` обязателен |
| Регрессия `ReceiptDetails` (карточка) | Низкая | Файл не меняется; новый экран лишь передаёт прежние пропсы |
