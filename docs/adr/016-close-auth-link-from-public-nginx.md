# 16. Закрытие эндпоинта генерации auth-ссылки от внешнего мира на nginx

## Статус

Принято (проектирование). Техническое решение согласовано и представлено менеджеру
проекта. Реализация — по задаче
[docs/tasks/close-auth-link-endpoint-from-nginx.md](../tasks/close-auth-link-endpoint-from-nginx.md),
раздел «Критерии приёмки» (1–5). Дополнительно выявлен и частично закрыт скрытый
дефект: в production-композе у сервиса `bot` не задан `ANALYTICS_URL`, из-за чего бот
не стартует — исправляется в рамках этой же задачи (см. D2).

## Контекст

Публичный nginx (`nginx.prod.conf`, блок
`location /api { proxy_pass http://analytics_api; }`) проксирует наружу **весь**
префикс `/api` на Analytics-сервис. В результате эндпоинт
`GET /api/users/auth/link?telegramId=...` доступен любому пользователю интернета.

Этот эндпоинт реализован в Analytics (.NET) — `UserAuthEndpoints.RequestAuthLink`:
путь группы `/api/users` (из `Endpoints.AuthGroup`) + `/auth/link` (из
`AuthLinkRequestPath`). Он генерирует **одноразовую auth-ссылку** для пользователя с
заданным `telegramId`: переход по ссылке ставит аутентификационную cookie
(`ConsumeAuthLink`). То есть атакующий, перебирая `telegramId`
(`?telegramId=1`, `?telegramId=2`, ...), может генерировать валидные auth-ссылки для
произвольных пользователей и **захватывать аккаунты** пользователей и администраторов
админ-панели Analytics.

### Легитимный клиент

Единственный легитимный вызывающий этот эндпоинт — **Telegram-бот** (внутренний
сервис), в момент, когда пользователь запрашивает выдачу ссылки на вход в админку:
- `bot/analytics/client.go` → `GetLoginLink(ctx, telegramId)` →
  `GET {ANALYTICS_URL}/api/users/auth/link?telegramId={id}`;
- вызывается из `bot/commands/login.go` (`GetLoginLinkCommand`).

Фронтенд админ-панели этот эндпоинт **не** использует (проверено по frontend-коду:
браузер ходит только в `/api/users/is-admin` и `/api/users/auth?token=...`).

### Сетевой контур (проверено по репозиторию)

| Элемент | Состояние |
|---|---|
| `nginx.prod.conf` | `location /api { proxy_pass http://analytics_api; }`, upstream `analytics:5039`; монтируется в prod-сервис `nginx` (docker-compose.yml) |
| `nginx.dev.conf` (корневой) | `location ~ ^/api { proxy_pass http://analytics_api; }`, upstream `host.docker.internal:5039`; dev-контур |
| `docker/nginx/nginx.dev.conf` | legacy-контур (проксирует `/api` на Go backend `172.17.0.1:8888`, фронтенд на `:4200` — Angular); **не трогаем** (out of scope) |
| Analytics в проде | `expose: "5039"`, наружу не экспонирован; снаружи через compose доступен только `nginx` (порты 80/443) |

### Выявленный скрытый баг (не стартует бот)

В `docker-compose.yml` у сервиса `bot` **не задан** `ANALYTICS_URL` (есть только
`BOT_TOKEN`, `BACKEND_GRPC_ADDR`, `REPORTS_GRPC_ADDR`, `HTTP_PROXY`). При этом
`bot/options.go` + `bot/bot.go` (`validate()`) требуют непустой `ANALYTICS_URL`,
иначе процесс падает при старте. Локальный шаблон `_ .env` / `.env.example` задаёт
`ANALYTICS_URL=http://localhost:5039` — пригоден только для запуска бота вне контейнера,
внутри прод-контейнера он не резолвится и бот без значения этой переменной не поднимется.

Для безопасного закрытия эндпоинта на публичном nginx необходимо, чтобы бот обращался
к Analytics **по внутренней сети** (`http://analytics:5039` в `collector-net`), а не
через публичный nginx. Иначе блокировка сломает легитимную выдачу ссылок.

### Взаимосвязь с существующим планом

Есть план [docs/plans/analytics-fix-user-enumeration-vulnerability.md](../plans/analytics-fix-user-enumeration-vulnerability.md),
который «маскирует» перечисление пользователей на уровне приложения (возврат 200 OK +
GenericMessage вместо 404). Он не предотвращает захват аккаунта через **валидную**
auth-ссылку, если атакующему известен реальный `telegramId`, и не закрывает внешний
вектор. Настоящее nginx-решение устраняет внешний вектор целиком. Два подхода
совместимы и дополняют друг друга (**defence-in-depth**): одно маскирует факт
существования пользователя на уровне приложения, второе полностью убирает маршрут из
внешней области видимости. Данный ADR не отменяет и не заменяет тот план.

## Рассмотренные варианты

### V1. Способ блокировки на nginx: точное совпадение пути vs регулярное выражение

- **Точечное-точное совпадение `location = /api/users/auth/link { return 404; }`** —
  **выбрано.** Точное совпадение (модификатор `=`) захватывает только этот путь и
  гасит все query-параметры, не задевая `/api/users/auth?token=...` (consume-ссылка,
  открытая фронтенду), `/api/users/is-admin` и прочие `/api/*`. Область видимости
  минимальная и предсказуемая; «лишних» совпадений не возникает.
- **Регулярное выражение `location ~ ^/api/users/auth/link`** — отвергнуто: regex в
  nginx имеет приоритет над префиксными location (за исключением `^~`/`=`), что
  усложняет прогнозирование порядка обработки и повышает риск случайного перехвата
  соседних маршрутов. Точное совпадение надёжнее и проще для аудита.

### V2. Код ответа: 404 vs 403

- **404 Not Found** — **выбрано.** Не раскрывает существование маршрута/ресурса;
  снаружи маршрут выглядит «как будто его никогда не было», что согласуется с целью
  не давать атакующему информации. 403 подсказывает, что ресурс существует, но закрыт, —
  лишняя разведка.
- **403 Forbidden** — отвергнуто: сигнализирует о наличии маршрута и тем самым о
  существовании функциональности, что вредит цели. (Критерий приёмки задачи допускает
  «4xx, например 403/404»; 404 строго лучше по семантике.)

### V3. Где блокировать: на nginx vs на уровне приложения (Analytics)

- **На публичном nginx** — **выбрано.** Маршрут физически не попадает наружу —
  внешний вектор устранён целиком, независимо от логики приложения. Не требует правки
  C#-кода, тестов и пересборки Analytics. Согласуется с принципом наименьших
  привилегий: сервис не должен выставлять наружу то, что предназначено только для
  внутренних серверных клиентов.
- **На уровне приложения (rate limiting / маскирование из плана
  `analytics-fix-user-enumeration-vulnerability.md`)** — недостаточно само по себе:
  маскирование не мешает захвату через валидную ссылку. Approved как дополнение
  (defence-in-depth), но не как замена nginx-блокировке.

### V4. Путь бота к Analytics: внутренний адрес vs публичный nginx

- **Внутренний адрес `http://analytics:5039`** — **выбрано.** Бот ходит напрямую по
  внутренней сети `collector-net` к сервису `analytics` (у которого в проде
  `expose: "5039"`, наружу не экспонирован). Это: (а) не зависит от публичного nginx;
  (б) сохраняет легитимный сценарий после закрытия маршрута; (в) не создаёт заход
  «через себя» (nginx → analytics же) и не нагружает публичный листенер.
- **Публичный nginx как путь бота** — отвергнуто: противоречит цели (бот стал бы сам
  себя «обходить», но именно ради бота маршрут и оставался открытым наружу); после
  блокировки маршрут всё равно станет 404 для бота. Осталось бы доступным только
  внутренне.

### V5. Менять ли dev-конфиги

- **`nginx.dev.conf` (корневой)** — **закрываем аналогично.** В dev перебор
  `telegramId` тоже нежелателен; симметричность prod/dev облегчает сопровождение.
- **`docker/nginx/nginx.dev.conf`** — **не трогаем** (out of scope): это legacy-контур
  (Angular-фронтенд + Go backend), он не проксирует `/api` на Analytics и не имеет
  отношения к эндпоинту `auth/link`. Наследуется/эксплуатируется отдельным сценарием.

## Решение

Закрыть эндпоинт `GET /api/users/auth/link` от внешнего мира на уровне nginx точным
совпадением пути и перевести бота на внутренний адрес Analytics. Дополнительно
исправить скрытый баг конфигурации бота (незаданный `ANALYTICS_URL`).

### D1. nginx.prod.conf — блокировка маршрута

Перед общим `location /api` добавить блок точного совпадения, возвращающий **404**:

```nginx
# Закрытие эндпоинта генерации auth-ссылки от внешнего мира (см. ADR-016).
# Точное совпадение — не задевает /api/users/auth?token=... и /is-admin.
location = /api/users/auth/link {
    return 404;
}

# API -> Analytics
location /api {
    proxy_pass http://analytics_api;
    ...
}
```

Порядок блоков не критичен (точное совпадение `=` всегда имеет приоритет над
префиксным `location /api`), но размещение над общим `/api` повышает читаемость и
явно фиксирует намерение. Модификатор `=` гарантирует, что затронут строго один путь;
query-параметры (`?telegramId=...`) на точное совпадение не влияют.

### D2. docker-compose.yml — внутренний адрес Analytics для бота (и фикс бага)

В сервис `bot` добавить `ANALYTICS_URL` на внутренний адрес Analytics, минуя
публичный nginx:

```yaml
  bot:
    environment:
      - BOT_TOKEN=${BOT_TOKEN}
      - BACKEND_GRPC_ADDR=collector:15000
      - REPORTS_GRPC_ADDR=collector:15001
      - HTTP_PROXY=${HTTP_PROXY}
      - ANALYTICS_URL=http://analytics:5039   # внутренняя сеть collector-net, минуя публичный nginx
    networks: [collector-net]
    ...
```

Это одновременно:
- устраняет внешний вектор (бот больше не ходит через публичный nginx);
- чинит скрытый баг «бот не стартует без `ANALYTICS_URL`» (validate() в
  `bot/options.go` / `bot/bot.go`).

Сервис `analytics` в проде объявлен как `expose: "5039"` — снаружи не доступен,
поэтому подключение бота по этому адресу не открывает новых внешних путей.

### D3. nginx.dev.conf (корневой) — та же блокировка для dev

Для симметрии с prod добавить в `nginx.dev.conf` (корневой) тот же блок перед общим
`location ~ ^/api`:

```nginx
location = /api/users/auth/link {
    return 404;
}
```

`docker/nginx/nginx.dev.conf` (legacy-контур) не изменяется — см. V5.

### D4. _.env / .env.example — уточнить комментарий к ANALYTICS_URL

Значение **не меняется** (`http://localhost:5039`), но комментарий уточняется, чтобы
прояснить два сценария — прод-контейнер и локальный запуск бота:

```bash
# URL Analytics API для бота.
# - prod (контейнер): задаётся в docker-compose.yml как http://analytics:5039
#   (внутренняя сеть collector-net, минуя публичный nginx; значение из .env игнорируется);
# - локальный запуск бота вне контейнера: http://localhost:5039 (шаблон ниже).
ANALYTICS_URL=http://localhost:5039
```

(Текст в ADR — иллюстрация намерения; фактическое значение из файла не меняется.)

### Прочее (вне scope / follow-up)

- **Чистка мёртвого кода** `backend/users/link/client.go` и параметра
  `client *link.Client` в `users.Processor` (`backend/users/processor.go`) — выносится
  в отдельную задачу (follow-up). Не меняется в рамках данного ADR.
- **`docker/nginx/nginx.dev.conf`** — legacy-контур, не трогаем (см. V5).

## Последствия

- **Положительные**:
  - внешний вектор захвата аккаунтов через перебор `telegramId` полностью устранён:
    маршрут недостижим снаружи;
  - легитимный сценарий сохранён: бот выдаёт ссылку пользователю по внутренней сети;
  - попутно исправлен скрытый дефект «бот не стартует в проде» (незаданный
    `ANALYTICS_URL`);
  - 404 не раскрывает существование маршрута; соседние `/api/*` маршруты не затронуты;
  - не требует пересборки/передеплоя Analytics — только конфигурация.
- **Отрицательные/риски**:
  - если где-то ещё внешне ожидается доступ к `/api/users/auth/link` (кроме бота),
    он будет сломан; по проверке единственный легитимный клиент — бот, поэтому риск
    принят;
  - добавление `ANALYTICS_URL` в compose дублирует значение, которое иначе бралось бы
    из `.env`; важно, что compose-значение имеет приоритет и не должно конфликтовать с
    локальным запуском бота вне контейнера — в `.env` комментарий это разъясняет;
  - не устраняет enumeration на уровне приложения (остаётся план
    `analytics-fix-user-enumeration-vulnerability.md`), но делает его неактуальным для
    внешних атак.
- **Нейтральные**: `backend/users/link/client.go` остаётся нетронутым (вне scope),
  `docker/nginx/nginx.dev.conf` — без изменений.

## Критерии приёмки

Соответствуют критериям приёмки задачи (раздел 5):

1. Снаружи (через публичный nginx, порты 80/443) запрос
   `GET /api/users/auth/link?telegramId=...` возвращает **404**, не выдавая валидную
   ссылку; перебор `telegramId` извне невозможен.
2. Другие маршруты `/api/*` (например `/api/users/auth?token=...`,
   `/api/users/is-admin`, API чеков/товаров/продавцов) работают снаружи без изменений
   (проверить curl-запросами и реальными сценариями фронтенда).
3. Команда бота `GetLoginLink` успешно выдаёт ссылку пользователю в production,
   обращаясь к Analytics по внутреннему адресу `http://analytics:5039` (минуя
   публичный nginx).
4. Внутренние маршруты не затронуты в худшую сторону.
5. Работоспособность: `nginx -t` без ошибок конфигурации; контейнеры поднимаются
   (`./up.sh`); бот стартует (validate() проходит — `ANALYTICS_URL` задан); при
   наличии тестов `cd bot && go test ./...` и `cd Analytics && dotnet test` проходят.

`docs/plans/analytics-fix-user-enumeration-vulnerability.md` маскирует enumeration на

рекомендуются к применению совместно (layer of defence), либо при полном принятии
настоящего решения применение прикладного плана может быть пересмотрено как
необязательное — решение остаётся за менеджером проекта.
