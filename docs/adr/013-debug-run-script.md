# 13. Bash-скрипт запуска debug-окружения (dev-run.sh)

## Статус
Принято

## Контекст
Запуск всех сервисов ReceiptCollector в режиме отладки требует ручного выполнения ~7 шагов из README.md в разных терминалах: `./up.dev.sh`, генерация TLS-сертификатов, экспорт переменных, `go run .` (backend), миграции и API Analytics (`dotnet run`), `npm run dev` (frontend), `go run .` (bot). Это трудоёмко, ошибкоопасно и не воспроизводимо. Заказчик зафиксировал требования (docs/tasks/dev-debug-run-script.md): один скрипт `dev-run.sh` в корне проекта, все переменные из `.env`, шаблон `.env.example`, переиспользование `up.dev.sh` и `generate-ssl-cert.sh`, корректное завершение по Ctrl+C.

Анализ кода выявил факты, влияющие на архитектуру решения:

1. **Жёстко зашитые пути.** `backend/main.go` читает TLS-ключи из `/usr/share/receipts/ssl/certs/{certificate.crt,private.key}` (строки 87-90), бот — из `/usr/share/receipts/ssl/certs/certificate.crt` (`bot/main.go:21`). Воркеры backend пишут в `/var/lib/receipts/raw/` и `/var/lib/receipts/error/` (`backend/nalogru/client.go:142,221,226,275`). Переменные `RAW_TICKET_DUMP_PATH`/`GET_TICKET_ERROR_PATH` используются только в docker-compose как volume-маунты, кодом не читаются. Следовательно, для локального `go run .` каталоги `/usr/share/receipts/ssl/certs`, `/usr/share/receipts/templates`, `/var/lib/receipts/{raw,error}` должны существовать и быть доступны на запись.
2. **Место генерации сертификатов.** `generate-ssl-cert.sh` пишет сертификаты в `<корень проекта>/ssl/`, а не в `/usr/share/receipts/ssl/certs`. Нужен шаг синхронизации.
3. **Непереиспользуемость повторной генерации.** `generate-ssl-cert.sh` пересоздаёт leaf-сертификаты при каждом вызове (строки 29-76). Повторный вызов при уже работающем backend инвалидирует TLS-сессии бота (нарушение NFR-2 «идемпотентность»).
4. **Конфигурация .NET.** Migrations (Program.cs) читают конфигурацию из appsettings + env с префиксом `RECEIPTCOLLECTOR_`; в `appsettings.json` миграций `ConnectionString` пуст — он обязан прийти через env. API в Development использует `appsettings.Development.json` с захардкоженными localhost-строками, которые могут расходиться с `.env` (например, `user:user@...` для Mongo), поэтому API также должен получать конфигурацию через `RECEIPTCOLLECTOR_*`, собранные из `.env`.
5. **Run-to-completion миграции.** Миграции — одноразовая задача, завершающаяся после применения SQL. Их нельзя запускать «в фоне и забыть»: API должен стартовать только после успешных миграций (FR-5.3).
6. **Готовность зависимостей.** Бот имеет встроенный `WaitForReady` с retry (ADR-004), но ожидание до 5 минут маскирует реальные проблемы; дешевле дождаться TCP-порта backend `:15000` до запуска бота. Аналогично: MongoDB — до backend, PostgreSQL — до миграций, `:5039` — до frontend.
7. **Повторный запуск = перезапуск сервисов разработки.** Решение заказчика №6 / FR-9 / NFR-2: при повторном запуске не-инфраструктурные сервисы (backend, Analytics API, frontend, бот) останавливаются и запускаются заново с актуальным кодом (hot reload не используется, применяется только перезапуск), инфраструктурные docker-контейнеры (mongo/pg/nginx) не трогаются. Останавливаться должны в том числе экземпляры, запущенные вручную вне скрипта (FR-9.5).

## Решение

Создаётся исполняемый скрипт `dev-run.sh` в корне проекта и шаблон `.env.example`. Скрипт — оркестратор в одном процессе: последовательно поднимает инфраструктуру и запускает сервисы фоновыми процессами, пишет логи в файлы, держит терминал живым через `tail -f`, по Ctrl+C корректно останавливает все запущенные им процессы.

### D1. Модель процессов: оркестратор + фоновые сервисы в отдельных группах процессов

- Каждый сервис запускается через `launch()`: `( cd <dir> && exec setsid <cmd> ) >> logs/<service>.log 2>&1 &`.
- `setsid` помещает сервис в новую сессию/группу процессов; `go run .` и `dotnet run` порождают дочерние бинарники — убийство по PID родителя оставило бы их сиротами. Убийство всей группы (`kill -TERM -- -PID`) гарантирует остановку дерева процессов (FR-8.3, критерий приёмки 8).
- Миграции — исключение: выполняются синхронно (foreground), результат проверяется, при ошибке скрипт выходит с ненулевым кодом и срабатывает cleanup.
- Логи: каталог `logs/` в корне проекта (добавляется в `.gitignore`), файл `logs/<service>.log` на сервис. В конце скрипт выводит сводку и запускает `tail -f` по логам всех сервисов — живой вывод в одном терминале.

### D2. Завершение: единственный `trap cleanup EXIT`

- `cleanup` итерируется по массиву `PIDS` (имена+pid запущенных **этим экземпляром** скрипта процессов), шлёт `SIGTERM` в группы процессов, ждёт 2 секунды, затем `SIGKILL` не завершившимся, и удаляет PID-файлы (`logs/<service>.pid`).
- `trap cleanup EXIT` покрывает все пути выхода: Ctrl+C (SIGINT → exit → EXIT-trap), `set -e` (ошибка шага → exit), явный `exit 1`.
- `cleanup` останавливает **только собственные** процессы (D8). Чужие экземпляры (запущенные вручную) скрипт при завершении не трогает: их остановка — задача фазы stop-and-restart при повторном запуске (FR-9.1, FR-9.5), а не cleanup.

### D3. `.env`: безопасное подключение и дефолты

- Проверка существования `$PROJECT_ROOT/.env` с понятной ошибкой и подсказкой `cp .env.example .env` (FR-2.2).
- `set -a; source .env; set +a` — все переменные экспортируются дочерним процессам.
- Для совместимости с `set -u`: после source каждый используемый параметр переэкспортируется с дефолтом через `${VAR:-default}` (дефолты из раздела 7 задачи).
- Производные переменные для .NET (`RECEIPTCOLLECTOR_Infrastructure__*`, connection strings для Postgres/Mongo, `MigrationScripts__*`) собираются скриптом из примитивов `.env` и экспортируются — это устраняет расхождение с захардкоженными значениями `appsettings.Development.json`.
- Скрипт работает из любого каталога: `PROJECT_ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"` и далее `cd "$PROJECT_ROOT"` (FR-1.3).

### D4. Переиспользование существующих скриптов без дублирования

- `./up.dev.sh` вызывается напрямую (FR-3.1). Он сам выбирает `docker-compose`/`docker compose`; docker compose автоматически подхватывает `.env` из корня.
- `./generate-ssl-cert.sh` вызывается напрямую, но **только если** `ssl/certificate.crt` или `ssl/private.key` отсутствуют (FR-3.2 «если ещё не созданы»). Это сохраняет идемпотентность и не инвалидирует TLS-сессии работающего backend. При необходимости перевыпустить сертификаты разработчик удаляет `ssl/`.
- Скрипт не содержит docker-compose/openssl-логики — только оркестрация (NFR-5).

### D5. Бутстрап системных путей

Каталоги `/usr/share/receipts/ssl/certs`, `${TEMPLATES_PATH}`, `/var/lib/receipts/raw`, `/var/lib/receipts/error` создаются при отсутствии (`sudo mkdir -p`), владелец переводится на текущего пользователя (`sudo chown`), чтобы последующие запуски не требовали sudo. После генерации/проверки сертификаты копируются из `ssl/` в системный каталог, шаблоны чеков — из `backend/render/templates/` в `${TEMPLATES_PATH}` (FR-3.3).

### D6. Readiness-проверки через `/dev/tcp` (bash)

- Хелпер `wait_for_port <host> <port> <name> [timeout]` на `/dev/tcp` (не зависит от `nc`/`curl`) с дедлайном и понятной ошибкой при таймауте — для проверки готовности зависимостей.
- Порядок и ожидания: MongoDB `:27017` → запуск backend → gRPC `:15000` (backend готов) → PostgreSQL `:5432` → миграции (синхронно) → API `:5039` → frontend `:5173` → bot.
- **Занятый порт не-инфраструктурного сервиса НЕ является причиной пропуска запуска** (прежняя логика «skip» отменена, NFR-2). Перед фазой запуска выполняется фаза stop-and-restart (D8), которая освобождает порты; после неё `wait_for_port` проверяет готовность зависимостей, а `wait_port_free` подтверждает фактическое освобождение портов после остановки.
- Инфраструктурные порты (`:27017`, `:5432`, `:8080`) в фазах stop/ready проверяются только на «живость» контейнеров и никогда не передаются в функции остановки (защита FR-9.3).

### D7. Порядок запуска

1. Подготовка (корень проекта, `.env`, дефолты, зависимости, `logs/`).
2. Инфраструктура: `./up.dev.sh` (контейнеры не пересоздаются без необходимости).
3. Сертификаты и системные пути (guard генерации сертификатов).
4. **Фаза stop-and-restart (D8):** остановка всех уже запущенных не-инфраструктурных сервисов.
5. Backend (`go run .`) → ожидание gRPC `:15000`.
6. Миграции Analytics (синхронно) → API (`dotnet run`) → ожидание `:5039`.
7. Frontend (`npm install` при необходимости, `npm run dev`) → ожидание `:5173`.
8. Bot (`go run .`).
9. Сводка → `tail -f` логов.

Каждый шаг запуска не-инфраструктурного сервиса выполняется безусловно (все сервисы запускаются всегда, решение заказчика №1); «пропуск из-за занятого порта» не применяется.

### D8. Перезапуск при повторном запуске (stop-and-restart, FR-9)

**Механизм детекции уже запущенных сервисов — комбинация (вариант «c»): PID-файлы в первую очередь, fallback на занятость порта/процесс.**

- **PID-файлы** (`logs/<service>.pid`): `launch()` пишет PID лидера группы процессов (`$!` после `setsid`) в `logs/<name>.pid`. При повторном запуске `stop_service`:
  1. читает файл, проверяет живость процесса (`kill -0`);
  2. проверяет совпадение рабочего каталога (`readlink /proc/$pid/cwd` == каталог сервиса) — защита от подмены PID;
  3. если всё совпало — убивает группу процессов `kill -TERM -- -PID` (собственный экземпляр, тот же набор процессов, что и в cleanup), ждёт завершения, удаляет PID-файл.
  Устаревший PID-файл (процесс мёртв после `kill -9`/падения скрипта) распознаётся по `kill -0` и удаляется без вреда.
- **Fallback по порту** (чужой экземпляр, запущенный вручную): для сервисов с портами (backend `:8888/:15000/:15001`, API `:5039`, frontend `:5173`) — `port_pids()` по `ss -tlnp` (iproute2, де-факто стандарт на Linux) с fallback на `lsof -ti tcp:<port>` и `fuser <port>/tcp`. Жёсткой зависимости нет: при старте проверяется наличие хотя бы одной из трёх утилит; на практике `ss` присутствует везде.
- **Бот (без портов):** PID-файл в первую очередь; fallback — `pgrep` по командной строке (`go run`, скомпилированный бинарник `bot`) с фильтром по `readlink /proc/$pid/cwd` == каталог `bot/`. Фильтр по cwd диз-амбигизирует бот от backend, у которого та же командная строка `go run .`.
- **Остановка чужого процесса — рекурсивное убийство дерева, не группы:** чужой процесс обычно находится в группе процессов терминала разработчика, и `kill -- -PID` мог бы убить терминал. Поэтому для найденного по порту/cwd процесса применяется `kill_tree` (TERM, ожидание до 10с, KILL): рекурсивно через `pgrep -P` убиваются все потомки (дочерние бинарники `go run`/`dotnet run`/`node`), затем сам процесс (FR-9.4).
- **Защита инфраструктуры (FR-9.3):** `stop_service` вызывается только для не-инфраструктурных сервисов; внутри — assert: порты `27017/5432/8080` запрещены. Инфраструктура получает только `./up.dev.sh`, который не останавливает работающие контейнеры.
- **Фазы:** остановка всех не-инфраструктурных сервисов выполняется до фазы запуска (после шага 3), затем сервисы запускаются заново в порядке D7. Освобождение портов подтверждается `wait_port_free` (таймаут ~15с, затем ошибка с понятным сообщением).

## Последствия

- **Положительные**: одна команда вместо ~7 ручных шагов; воспроизводимое окружение; единый источник переменных `.env`; нет осиротевших процессов; повторный запуск перезапускает сервисы разработки с актуальным кодом (FR-9); инфраструктурные контейнеры не перезапускаются (NFR-2); остановка работает и для вручную запущенных сервисов (FR-9.5); локи в файлах доступны для grep/debug.
- **Отрицательные**: один терминал занят скриптом (ожидаемо для debug-режима); `sudo` может потребоваться при первом запуске (создание `/usr/share/receipts`, `/var/lib/receipts`); сертификаты не перевыпускаются автоматически при смене `BACKEND_GRPC_HOST` (требуется удалить `ssl/`); для остановки чужих экземпляров требуется хотя бы одна из утилит `ss`/`lsof`/`fuser` (проверяется при старте).
- **Нейтральные**: новый каталог `logs/` в `.gitignore` (лог-файлы и PID-файлы `logs/<service>.pid`); `.env.example` попадает в git; обновляется README.md.

## Альтернативы

1. **tmux/screen с окнами на сервис** — зависимость от внешних утилит, сложнее интеграция с CI и автоматизацией; лог-файлы удобнее.
2. **foreman/honcho (Procfile)** — добавление новой зависимости и формата; оркестрация docker+системные пути остаётся за скриптом.
3. **docker-compose как единственный способ debug** — противоречит решению заказчика (hot reload не используется, запуск через `go run .`).
4. **Запуск каждого сервиса в отдельном фоновом терминале через `xterm`/`gnome-terminal`** — платформозависимо (NFR-3), нет единого trap.
5. **`docker exec`/volume-симлинк вместо копирования сертификатов** — симлинк `/usr/share/receipts/ssl/certs` на `ssl/` требует одноразового sudo и удобен, но хрупок при разных правах; копирование проще и предсказуемее.
6. **Только PID-файлы (вариант «a») для детекции** — не покрывает сервисы, запущенные вручную (FR-9.5); PID-файл отсутствует.
7. **Только занятость порта (вариант «b»)** — не покрывает бота (без портов); при порте, занятом посторонним процессом (не нашим сервисом), требует осторожности при идентификации.
8. **`fuser -k <port>/tcp` как основной механизм** — не убивает дочерние бинарники (`go run`/`dotnet run` остаются сиротами), не даёт grace-period и контроля над сигналом.
