# 31. Новая категория товаров «Бытовая химия» и группа UI «Для дома»

## Статус

Проект (предложено к рассмотрению; задача: `docs/tasks/household-chemicals-category.md`).

## Контекст

Расходы на бытовую химию (чистящие средства, стиральные порошки, средства для мытья
посуды и посудомоечных машин, освежители воздуха, губки/перчатки, бумажные полотенца,
мусорные пакеты, средства от насекомых) сейчас размазаны между «Товары для дома»
(`HomeGoods`) и «Косметика и гигиена» (`CosmeticsAndHygiene`) и не видны отдельной
строкой аналитики.

Заказчик принял два решения:

1. **Новая категория «Бытовая химия»** — доступна во всех местах использования
   категорий: ручная категоризация (страница чеков и страница товаров), AI-подсказки
   `suggest`, фоновый precategorization (ADR 027/030), кэш (ADR 019).
2. **Новая группа UI «Для дома»**: в неё переносятся «Товары для дома» (`HomeGoods`),
   «Бытовая техника» (`HomeAppliances`), «Мебель» (`Furniture`) и новая категория.

### Текущее состояние (AS-IS)

- `CommodityCategory` — enum в `Analytics/src/ReceiptCollector.Analytics.Domain/Modules/Commodities/CommodityCategory.cs`
  (52 категории + `Undefined = 0`, `Other = 255`). Последние расширения (коды 48–52)
  добавлялись по правилу «только добавление» без миграций БД (ADRs 010/022).
- `CommodityCategoryHelper` содержит `DisplayNames` (52 записи + `Undefined`, `Other`),
  `GetAll()` (порядок словаря = порядок отображения) и явный словарь `CategoryGroups`
  «категория → группа» (ADR 022, решение B1): «Продукты», «Транспорт», «Прочее»;
  категории вне словаря возвращают `""` — плоский список без `<optgroup>`.
- Справочник для UI/промта генерируется из `CommodityCategoryHelper.GetAll()`:
  - `GET /api/commodities/categories` (`CommodityEndpoints.ListCategories`,
    `CategoryDto { Id, Key, Name, Group }`), `GET /api/receipts/categories`;
  - `CategoryNames` (без `Undefined`) → `OpenAiCompatibleAiClient.BuildPayload`.
- `GetGroup()` — источник истины групп на бэкенде (решение D1 ADR 010); фронт
  (`Analytics/frontend/src/utils/categoryOptions.tsx`, функция `groupCategories`)
  — **универсальный**: группирует по полю `group`, порядок групп = порядок первого
  появления в массиве, категория с пустой группой выводится плоско. Фронт ничего
  не хардкодит.
- PostgreSQL: категории хранятся denormalized как `commodities.category_id (int?)`
  + `category_name (varchar(128))` (ADR 005) и `precategorized_commodities.proposed_category_id int NOT NULL`.
  Нет lookup-таблицы категорий, нет FK, нет CHECK-констрейнтов на коды; имя при
  каждой записи пересчитывается через `GetDisplayName` (`CommodityRepository`,
  `PrecategorizedCommodityRepository`, `CommodityCategoryResolver`).
- Миграции — проект raw SQL-скриптов (`ReceiptCollector.Analytics.Migrations`,
  runner по каталогу `Scripts/*.sql` + история в `migration_scripts_history`); EF-миграций нет.
- Предыдущие прецеденты добавления категорий (коды 42–52) не требовали SQL-скриптов:
  `category_id` принимает новые int-коды без изменения схемы (ADR 022, «Контракты и данные»).
- AI-промт содержит блок «Разграничения схожих категорий», в т.ч. строки для
  `Furniture`/`HomeAppliances` — обе разграничиваются от `HomeGoods`
  («товары для дома — посуда, текстиль, хранение, интерьер»).
- Состав новой категории зафиксирован заказчиком (10 видов товаров); мыло/
  шампуни/зубная паста остаются в `CosmeticsAndHygiene` — см. «Edge cases».

### Edge cases из задачи

- Мыло, шампуни, зубная паста (личная гигиена) остаются в `CosmeticsAndHygiene`.
- Уже категоризированные товары **не переносятся** — миграция данных не требуется.
- Товары, ранее попавшие в `HomeGoods`, при повторной AI-категоризации могут быть
  отнесены к новой категории (прямой перезаписи нет) — допустимо.

## Рассмотренные варианты

### A. Нумерация и имя новой категории

- **A1 (выбрано):** `HouseholdChemicals = 53` — следующий свободный код после 52.
  Диапазон 0–17 (legacy), 18–52 (детализация/новые), 255 (`Other`) заняты; коллизий нет.
  Имя соответствует задаче (`household-chemicals-category`), уникально в enum
  (обязательно для `{"category": "<имя>"}` и `Enum.TryParse`), читаемо.
- A2: `HouseholdChemistry = 53` — тоже корректно, но слово «chemicals» чаще
  используется в товарных классификациях и прямо совпадает со слагом задачи.
- A3: имя `CleaningProducts` — уже, чем состав категории (в неё входят также
  мусорные пакеты, бумажные полотенца, средства от насекомых); отклонено.
- A4: переиспользовать код `HomeGoods`/влить в него — противоречит цели задачи
  (отдельная строка аналитики); отклонено.

### B. Числовой код: следующий по порядку vs «дыра»

- **B1 (выбрано):** 53 подряд — как в ADR 022 (компромисс «коды без
  резервирования, серия»); `Other = 255` сохраняется.
- B2: резервировать диапазон (например, 60–69) под будущие домашние категории —
  YAGNI: группировка UI с ADR 022 не зависит от числовых значений (словарь),
  резервирование ничего не даёт.

### C. Позиция в словарях `DisplayNames` и `CategoryGroups`

- **C1 (выбрано):** запись в `DisplayNames` добавляется после
  `FitnessAndSports`, перед `Other` (порядок словаря = порядок отображения);
  в `CategoryGroups` — новая константа `HomeGroup = "Для дома"` и четыре записи:
  `HomeGoods`, `HomeAppliances`, `Furniture`, `HouseholdChemicals`.
  Минимальное, локализованное изменение.
- C2: перенести записи `HomeGoods`/`Furniture`/`HomeAppliances` в блок 48–52 в
  словаре `DisplayNames` — меняет исторический порядок отображения README-тестов
  и списка без необходимости; отклонено.

### D. Последствия переноса трёх категорий в группу (изменение поведения UI)

Сейчас `HomeGoods` (позиция в legacy-блоке), `Furniture`, `HomeAppliances`
выводятся **плоско**. После решения С1 они попадут в `<optgroup>` «Для дома».
Анализ фронта (`categoryOptions.tsx`, использован в `CommodityTable.tsx`,
`ReceiptDetails.tsx`, `PrecategorizedCommodityTable.tsx`):

- Группировка и рендер универсальны — **изменения фронтенда не требуются**.
- Порядок групп на UI = порядок первого появления категории в массиве `GET .../categories`:
  плоские legacy-категории (0–17) идут первыми, затем по позиции `HomeGoods`
  открывается группа «Для дома» (состав: `HomeGoods`, `Furniture`, `HomeAppliances`,
  `HouseholdChemicals` — по порядку их позиций в `DisplayNames`), затем «Продукты»,
  «Транспорт», «Прочее», и плоский `Other`. Изменение порядка отображения по
  сравнению с сегодня (плоский список вместо optgroup) — это **прямо
  запрошенное** изменение заказчика, а не регресс: контракт `CategoryDto`
  не меняется (поле `Group` уже есть, меняются лишь его значения; фронт не кэширует группы).

### E. Миграция БД / SQL-скрипт

- **E1 (выбрано):** SQL-скрипт **не требуется**. Обоснование:
  - схема не содержит lookup-таблиц категорий, FK и CHECK-констрейнтов на коды —
    `category_id integer` принимает 53 без изменений (как при кодах 42–52);
  - `category_name` пересчитывается на каждой записи через `GetDisplayName`;
    готовых строк с кодом 53 нет — backfill не нужен;
  - уже категоризированные товары не переносятся (edge case задачи);
  - проект `ReceiptCollector.Analytics.Migrations` остаётся без изменений.
- E2: добавить идемпотентный data-fix, пересчитывающий `category_name` по
  `category_id` — не нужен для этой задачи (нет рассинхронизации для нового кода);
  прецедент такого скрипта есть (`2026..._fix_commodity_category_food_name.sql`),
  но он решал переименование отображаемого имени, а не добавление категории.
- E3: EF-миграция — не применимо, миграции в проекте raw-SQL.

### F. Состав AI-определения

- **F1 (выбрано):** новая категория попадает в реестр промта автоматически через
  `CategoryNames` (как в ADR 022, FR-4); сверх этого — добавить **одну строку
  разграничений** для «Бытовая химии»: полный состав по заказчику + границы с
  `HomeGoods` (посуда, текстиль, хранение, интерьер) и `CosmeticsAndHygiene`
  (мыло, шампуни, зубная паста — личная гигиена) — главный риск смешения
  (edge case задачи: химию тянут обе эти категории).
- F2: не менять промт (`BuildPayload`) — не выбирается: товары вида «Стиральный
  порошок»/«Мистер Мускул» исторически относились AI к `HomeGoods` или
  `CosmeticsAndHygiene` (реестр — единственный источник смысла в промте ADR 009),
  новая категория почти никогда не была бы предложена без таргетированного
  блока, что ломает критерий приёмки «AI валидно возвращает её».

## Решение

### 1. Enum `CommodityCategory` — новая категория (53 значения)

После `FitnessAndSports = 52`, до `Other = 255` — отдельной строкой с комментарием
(в блок «снеков/фитнеса» не вписывается):

```csharp
// Бытовая химия — код 53 (см. ADR 031)
HouseholdChemicals = 53, // Бытовая химия: чистящие средства, стиральные порошки,
                         // средства для мытья посуды и посудомоечных машин,
                         // освежители воздуха, губки/перчатки для уборки,
                         // бумажные полотенца и салфетки, мусорные пакеты,
                         // средства от насекомых
```

Гарантии: только добавление (`Other = 255` и все прежние коды не меняются),
код 53 уникален, `category_id` в PostgreSQL принимает его без миграции.

### 2. `CommodityCategoryHelper`

```csharp
...
private const string OtherGroup = "Прочее";
private const string HomeGroup = "Для дома";
```

- `DisplayNames` — одна новая запись после `FitnessAndSports`, перед `Other`:
  `{ CommodityCategory.HouseholdChemicals, "Бытовая химия" }`.
- `CategoryGroups` — новая константа группы и **четыре** записи (новая группа
  и перенос в неё трёх существовавших категорий):

```csharp
// Для дома (4 категории)
{ CommodityCategory.HomeGoods, HomeGroup },
{ CommodityCategory.Furniture, HomeGroup },
{ CommodityCategory.HomeAppliances, HomeGroup },
{ CommodityCategory.HouseholdChemicals, HomeGroup },   // NEW 53
```

Механика `GetGroup` (`GetValueOrDefault`, `""` для отсутствующих) не меняется;
legacy 0–17 (кроме переехавших трёх в группу) и `Other` остаются плоскими.

### 3. AI-подсказка (`OpenAiCompatibleAiClient.BuildPayload`)

- Новая категория появляется в реестре промта автоматически (`CategoryNames`,
  список без `Undefined`) — валидация ответа `Enum.TryParse` + `Enum.IsDefined`
  примет `HouseholdChemicals`.
- В блок «Разграничения схожих категорий» добавить одну строку (компактно, как
  прецеденты ADR 022):

```
- Бытовая химия (HouseholdChemicals): чистящие и моющие средства, стиральные
  порошки, средства для мытья посуды и посудомоечных машин, освежители воздуха,
  губки и перчатки для уборки, бумажные полотенца, мусорные пакеты, средства
  от насекомых — не HomeGoods (посуда, текстиль, хранение, интерьер) и
  не CosmeticsAndHygiene (личная гигиена: мыло, шампуни, зубная паста).
```

Существующие строки разграничений `Furniture` и `HomeAppliances` остаются
(они разграничивают с `HomeGoods` по другим признакам, конфликта нет).

### 4. Эндпоинты/сервисы — без изменения контрактов

- `GET /api/commodities/categories`, `GET /api/receipts/categories` — список
  генерируется из `GetAll()`/`GetGroup()`; контракты (`CategoryDto`) не меняются.
- `PUT /api/commodities/categories`, `POST/PUT /api/receipts/{id}/categories*` —
  валидация через `Enum.IsDefined` принимает новый код без правок; поведение
  аддитивно (ADR 028) — семантика «пустая категория = не трогать» (empty = «do not
  touch», assign-only) сохраняется.
- Precategorization (ADR 027/030) и кэш (ADR 019) — общие механизмы «имя → категория»,
  от состава категорий не зависят и изменений не требуют. Проверка
  при реализации: валидация `proposed_category_id != 0` и опция
  `Precategorization__Enabled` правок не требуют.

### 5. Фронтенд — изменений нет

`Analytics/frontend/src/utils/categoryOptions.tsx` группирует по полю `group`,
фронт не хардкодит группы (критерий приёмки «группа приходит с бэкенда» выполняется
существующей реализацией D1 ADR 010 + словарём `CategoryGroups` ADR 022).
Изменение поведения `<select>` (три категории из плоского списка в `<optgroup>`
«Для дома») достигается только сменой значений `Group` на бэкенде.

### 6. Go-backend и Bot — не затрагиваются

Проверено по коду: в `backend/` и `bot/` нет ни одного упоминания `CommodityCategory`
или товарных категорий — категоризация целиком живёт в слое Analytics; Backend/Bot
работают только с чеками MongoDB. Ни один контракт между сервисами категорий
товаров не касается.

## Обоснование

1. **Только добавление** (правило ADR 010/022): код 53 подряд, ничего не
   перекодируется, существующие классификации не тронуты.
2. **Единственный источник истины** (ADR 005/010/022): enum + `CommodityCategoryHelper`;
   UI-группы и реестр промта подхватываются автоматически.
3. **Группа — это данные, а не код**: добавление группы «Для дома» в словарь
   «категория → группа» не требует изменения ни логики `GetGroup` (ADR 022 B1),
   ни фронтенда (универсальная группировка D1 ADR 010) — и работает одинаково
   для select на страницах чеков, товаров и precategorized-админки.
4. **Ноль миграций** (E1): категории в PostgreSQL — целые числа без метаданных в БД;
   имя вычисляется при записи; данные не переносятся.
5. **Качество AI** (F1) — один таргетированный блок разграничений вместо пассивного
   добавления в реестр: критерий «AI валидно возвращает её на реальном товаре»
   достижим только при явном описании границы `HomeGoods`/`CosmeticsAndHygiene`.
6. **KISS/YAGNI**: без типизированных объектов групп и без вынесения групп в
   таблицу/конфигурацию; при росте числа групп можно перейти
   на конфигурацию/БД без смены API `GetGroup`.

## Компромиссы

- **Имя enum `HouseholdChemicals` vs `HouseholdChemistry`**: выбор субъективен,
  но приоритет отдан совпадению со слагом задачи и товарной терминологией; имя
  — часть формата ответа AI (`{"category": "HouseholdChemicals"}`), после релиза
  переименование недопустимо без ломки исторических ответов/логов.
- **Позиция в `DisplayNames` в конце списка**: в `<select>` группа «Для дома»
  «открывается» на позиции legacy-`HomeGoods` (порядок групп = порядок первого
  появления, `groupCategories`), а сама новая категория — последней в группе;
  альтернативная перетасовка словаря отклонена как лишний diff.
- **Одна строка в промт вместо полного набора few-shot** (как и в ADR 022,
  реализационный долг ADR 009): пограничные случаи (комбинированные товары,
  «порошок для посудомойки» vs «капсулы для посудомойки») не специфицированы,
  цена — риск единичных неточных подсказок, компенсируется ручной коррекцией.
- **Данные не переносятся, аналитика набирается заново**: старые товары, оставшиеся в
  `HomeGoods`/`CosmeticsAndHygiene`, остаются там до ручной или повторной
  AI-категоризации — статистика по новой категории будет набираться постепенно
  (заказчиком принято, edge case задачи).

## Последствия

### Положительные

- Расходы на бытовую химию видны отдельной строкой аналитики и в фильтрах.
- Группа «Для дома» консолидирует 4 домашние категории в `<select>` — UI понятнее.
- Нулевая цена инфраструктуры: без SQL-скриптов, без изменений
  `ReceiptCollector.Analytics.Migrations`, Go-backend, бота, nginx, фронтенда.
- Промт и UI обновляются автоматически; изменение локализовано в 3 файлах
  (enum + промт + тесты, по факту 2 файла исходников).

### Отрицательные

- Промт растёт на ~3 строки; UI-список — на 1 категорию (54 значения, без `Undefined`).
- Поведение `<select>` для трёх существующих категорий меняется (плоский
  список → группа) — осознанное требование, но визуально заметно пользователям.

### Риски

- **AI путает новую категорию с `HomeGoods`/`CosmeticsAndHygiene`** («Мистер
  Мускул» → HomeGoods). **Митигация:** строка разграничений (F1), строгая
  валидация ответа, ручное подтверждение администратором из
  precategorized-админки; при сохранении проблемы — отдельная задача на few-shot.
- **Пропуск записи в `DisplayNames`/`CategoryGroups`** → fallback «Не указана»/`""`.
  **Митигация:** обновить юнит-тесты консистентности — каждый член enum имеет
  отображаемое имя; `HouseholdChemicals`, `HomeGoods`, `HomeAppliances`,
  `Furniture` — в группе «Для дома» (группы остальных категорий без изменений).
- **Устаревшие тест-ассерты**: `CommodityCategoryTests.NewRetailCategories_HaveExpectedCodes_And_NoGroup`
  сегодня утверждает, что `Furniture`/`HomeAppliances` **не имеют группы**,
  `CommodityEndpointsTests` аналогично — эти ассерты переносятся в новую группу;
  `OpenAiCompatibleAiClientTests` (строка 296, `HomeAppliances` в промте)
  дополняется проверкой `HouseholdChemicals` и текста разграничения.
