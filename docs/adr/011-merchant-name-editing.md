# 11. Редактирование имени магазина в списке магазинов (/merchants)

## Статус

Принято (проектирование; реализация — по плану `docs/plans/merchant-name-editing.md`)

## Контекст

По [задаче merchant-name-editing](../tasks/merchant-name-editing.md) администратор должен получить
возможность переименовывать магазины inline-способом прямо в таблице на странице `/merchants`,
по аналогии с уже существующим редактированием имени в «Деталях чека» (`ReceiptDetails.tsx`).

Фактическое состояние кодовой базы на момент проектирования:

1. **Эндпоинт обновления имени уже существует**, но живёт в «чужой» доменной группе:
   `PUT /api/receipts/merchants/{merchantId:guid}/name` в
   `Api/Modules/Receipts/ReceiptEndpoints.cs` (`UpdateMerchantName`). Он уже проверяет
   `UserContext.UserId` → `401`, права администратора → `403`, существование магазина → `404`,
   и обновляет имя через `Merchant.UpdateName` + `IMerchantRepository.AddAsync` (upsert).
   При этом:
   - **пустое / состоящее из пробелов имя приводит к необработанному `ArgumentException`**
     из `Merchant.UpdateName` → HTTP **500**, а не 400;
   - **trim не выполняется** (требование задачи — обрезать пробелы до сохранения);
   - **нет ограничения длины**: колонка `merchants.name` объявлена `varchar(256) NOT NULL`
     (`MerchantConfiguration.HasMaxLength(256)`); имя длиннее 256 символов вызовет ошибку БД
     `22001` (string data right truncation) → 500.
   - Размещение в группе `/api/receipts` противоречит решению C3 из ADR 008
     («receipts-группа смешивает две сущности» — этот вариант был явно отклонён для категорий).

2. **Frontend.** В `api/receipts.ts` есть `updateMerchantName(merchantId, newName)`, которая делает
   PUT на `/api/receipts/merchants/{id}/name`. Используется только из `ReceiptDetails.tsx`.
   В `MerchantTable.tsx` уже реализован inline-паттерн редактирования **категории**
   («ред.» → select → «Сохранение...» → `onRefresh()`), который служит UX-референсом.
   В `api/receipts.ts` (`updateMerchantName`, строки 61–64) `credentials: 'include'` ошибочно
   помещён **внутрь объекта `headers`** вместо опций `fetch` — латентный баг, сейчас не
   проявляется только потому, что запрос same-origin (nginx) и используется дефолт
   `credentials: 'same-origin'`.

3. **Согласованность данных.** Имя магазина **нигде не денормализовано**:
   - `ReceiptEntity` ссылается на `merchants` через `MerchantId` (FK);
   - список чеков и детали чека читаются через `.Include(receipt => receipt.Merchant)`
     (`ReceiptReadService`);
   - список товаров — через join `c.Receipt.Merchant.Name` (`CommodityReadService`);
   - поиск/фильтрация магазинов (`GET /api/merchants?search=`) фильтрует по `Name`
     в памяти эндпоинта.
   Следовательно, переименование в таблице `merchants` **автоматически** отображается во всех
   представлениях (список магазинов, детали чека, список чеков, список товаров, поиск).
   Никакой миграции данных не требуется.

4. **Тесты.** В `tests/ReceiptCollector.Analytics.Api.Tests/MerchantEndpointsTests.cs` уже есть
   три теста на `UpdateMerchantName` (успех, 403, 404), но они вызывают метод из
   `ReceiptEndpoints`. **Фронтенд-тестов в репозитории нет вообще** (нет vitest/jest,
   нет test-скрипта в `package.json`) — упоминание «существующие тесты frontend» в задаче
   фактически не имеет объекта проверки.

### Бизнес-требования (из задачи)

1. Администратор на `/merchants` может inline-переименовать любой магазин; имя обновляется
   без перезагрузки страницы.
2. Новое имя отображается во всех связанных представлениях (детали чека, список чеков, поиск).
3. Пустое имя / имя из пробелов не сохраняется — понятное сообщение об ошибке.
4. Не-администратор не видит возможность редактирования (страница `/merchants` недоступна —
   проверяется в `MerchantsPage`).
5. При ошибке сети/сервера данные в поле не теряются, поле остаётся в режиме редактирования.
6. Редактирование категории и прочие функции `/merchants` не регрессируют.
7. UX консистентен с редактированием имени в «Деталях чека» и с паттерном редактирования
   категории в той же таблице.

## Рассмотренные варианты

### Ключевое решение A: Размещение backend-эндпоинта

#### Вариант A1: Перенос в группу `/api/merchants` (`PUT /api/merchants/{merchantId:guid}/name`) — **выбран**

**Описание:** Метод `UpdateMerchantName` перемещается из `ReceiptEndpoints.cs` в
`MerchantEndpoints.cs` (группа `app.MapGroup("/api/merchants")`), контракт тела запроса
(`{ "name": "..." }`) и логика проверок сохраняются. Старый маршрут удаляется, frontend
переключается на новый URL.

**Плюсы:**
- Устраняет противоречие с решением C3 ADR 008: у магазинов есть собственная доменная группа,
  и все операции управления магазином (категория, имя) собраны в ней.
- Единый тег Swagger «Merchants», единый префикс `/api/merchants` — консистентная
  API-поверхность для управления магазинами.
- Monorepo и единый релизный цикл (оба образа — `analytics` и `nginx` — собираются через
  `build.sh` и деплоятся вместе), поэтому атомарная смена контракта безопасна.

**Минусы:**
- Небольшой риск при «rolling deploy» (новый frontend против старого API): старый API не знает
  новый URL. Для self-hosted проекта с единым релизом риск принят. Если потребуется
  бесшовный переход — можно оставить старый маршрут как deprecated-shim (см. вариант A2).

#### Вариант A2: Оставить старый маршрут как deprecated-shim

**Описание:** Новый маршрут добавляется, старый `/api/receipts/merchants/{id}/name` остаётся,
помеченный `[Obsolete]`/комментарием, и делегирует в тот же обработчик. Удаление — отдельной
задачей.

**Плюсы:** Бесшовный rolling deploy; «мягкое» устаревание.

**Минусы:** Постоянное дублирование маршрутов в двух модулях; соблазн «оставить навсегда»;
поддержка двух путей для одного действия (нарушение DRY).

#### Вариант A3: Ничего не менять, использовать существующий эндпоинт из `/api/receipts`

**Описание:** Frontend вызывает `PUT /api/receipts/merchants/{id}/name` как есть.

**Плюсы:** Ноль изменений на backend.

**Минусы:** Консервирует нарушение ADR 008 (C3); операция управления магазином остаётся в
receipts-модуле; при любом будущем расширении управления магазинами несоответствие будет
усугубляться.

**Вывод:** выбран **A1**. Монолитная поставка проекта делает атомарную смену контракта
безопасной; единообразие управления магазинами важнее сохранения «исторического» URL.

### Ключевое решение B: Валидация имени

#### Вариант B1: Валидация на уровне эндпоинта + усиление доменного инварианта — **выбран**

**Описание:** В обработчике выполняется нормализация и валидация:

- `var normalized = request.Name?.Trim();`
- пустое/пробелы (`string.IsNullOrWhiteSpace(normalized)`) → `400 BadRequest`;
- `normalized.Length > 256` → `400 BadRequest`;
- далее `merchant.UpdateName(normalized)`.

Параллельно усиливается `Merchant.UpdateName`: доменный метод сам выполняет trim и бросает
`ArgumentException` при длине > 256 (defense-in-depth, защита от будущих вызовов мимо
эндпоинта). Лимит 256 берётся из `MerchantConfiguration.HasMaxLength(256)` — он же ответ на
открытый вопрос задачи «максимальная длина».

**Плюсы:**
- Единый источник лимита — ограничение БД; клиент и сервер используют одну и ту же цифру.
- Закрывает два реальных дефекта текущего кода: 500 на пустом имени и 500 на слишком длинном.
- Стиль совпадает с существующей валидацией эндпоинтов (`limit > 0`, `offset >= 0`,
  `Enum.IsDefined`).

**Минусы:**
- Дублирование правил «пусто/длина» между клиентом и сервером (неизбежно для веб-приложений;
  серверная проверка остаётся источником истины).

#### Вариант B2: Только доменная валидация (без проверок в эндпоинте)

**Описание:** Полагаться на `Merchant.UpdateName`, а `ArgumentException` преобразовывать
в `400` через middleware/фильтр исключений.

**Плюсы:** Меньше кода в эндпоинте.

**Минусы:** В проекте нет глобального маппера исключений в `400`; добавление такого механизма —
новый сквозной механизм (scope creep), несовместимый с текущим стилем ручной валидации в
эндпоинтах; тесты эндпоинтов в проекте проверяют явные `IResult`, а не исключения.

#### Вариант B3: Клиентская валидация без серверной

**Описание:** Считать, что frontend не пропустит невалидное имя.

**Минусы:** Нарушает принцип «клиентская валидация — UX, серверная — безопасность»; не
закрывает текущий баг с 500 (эндпоинт уже доступен из ReceiptDetails).

**Вывод:** выбран **B1**.

### Ключевое решение C: Frontend — размещение API-функции

#### Вариант C1: Перенос `updateMerchantName` в `api/merchants.ts` — **выбран**

**Описание:** Функция переезжает из `api/receipts.ts` в `api/merchants.ts` (URL меняется на
`/api/merchants/{id}/name`), заодно исправляется баг с `credentials` (переносится в опции
`fetch`). `ReceiptDetails.tsx` обновляет импорт.

**Плюсы:**
- API-слой ложится на доменную группировку: «всё про магазины — в `api/merchants.ts`»,
  симметрично решению A1.
- Единая функция для обоих мест использования (MerchantTable и ReceiptDetails) — DRY.

**Минусы:**
- Косметическое изменение импорта в `ReceiptDetails.tsx` (компилятор поймает забытые места).

#### Вариант C2: Оставить функцию в `api/receipts.ts`

**Описание:** Только обновить URL внутри существующей функции.

**Плюсы:** Меньше изменений.

**Минусы:** Функция про магазин живёт в модуле про чеки; при появлении третьего места
использования начнётся путаница; рассинхронизируется с группировкой backend.

**Вывод:** выбран **C1**.

### Ключевое решение D: Frontend — inline-редактирование имени в `MerchantTable.tsx`

#### Вариант D1: Отдельное состояние редактирования имени + явные кнопки «Сохранить»/«Отмена» — **выбран**

**Описание:** Добавляются состояния `editingNameId`, `nameDraft`, `nameSavingId`, `nameError`
(в дополнение к существующим `editingId`/`savingId` для категории — они не пересекаются, т.к.
редактировать имя и категорию в одной строке одновременно нельзя). В ячейке «Название»:
- режим просмотра: `merchant.name` + кнопка «ред.» (видна только для админа; колонка
  категории уже скрывается при `!isAdmin`, аналогично скрывается кнопка переименования);
- режим редактирования: `<input>` (с `maxLength={256}`, `autoFocus`) + «Сохранить»/«Отмена»
  с классами из `App.css` (`.merchant-edit-controls`, `.merchant-name-input`,
  `.save-merchant-btn`, `.cancel-merchant-btn` — переиспользуются из ReceiptDetails);
- сохранение: trim, клиентская валидация (пусто → ошибка, >256 → ошибка), вызов
  `updateMerchantName`, при успехе — `onRefresh()` (обновление списка без перезагрузки
  страницы, тот же паттерн, что у категории);
- «Сохранение...» — по образцу категории (`savingId`);
- ошибка: инлайн-сообщение в строке, режим редактирования сохраняется, `nameDraft` не
  сбрасывается (требование задачи п. 5 критериев приёмки);
- отмена: кнопка «Отмена» и клавиша `Escape`.

**Почему не «отмена по потере фокуса» (onBlur):** в задаче (user story 3) допускается отмена
по потере фокуса, но при наличии кнопки «Сохранить» blur-cancel создаёт гонку: клик по кнопке
начинается с mousedown → инпут теряет фокус → состояние сбрасывается → кнопка удаляется из DOM
до события click, и сохранение не срабатывает. Надёжнее явная отмена (кнопка + Escape),
что соответствует и поведению «Деталей чека» (там тоже только явная кнопка «Отмена»).

**Плюсы:**
- Консистентно с «Деталями чека» и с паттерном категории.
- Нет гонки blur/click; состояние явное и тестируемое.

**Минусы:**
- Немного больше состояния, чем у select-паттерна категории (но это цена текстового ввода
  с валидацией).

#### Вариант D2: Без кнопок, по паттерну категории (select-подобный ввод + blur/Enter)

**Описание:** Сохранение по Enter, отмена по blur/Escape.

**Плюсы:** Короче; симметрично категории.

**Минусы:** Не совпадает с референсом «Деталей чека» (там кнопки «Сохранить»/«Отмена» —
это прямое требование задачи); blur-отмена рискованна для кнопки сохранения; сложнее показать
инлайн-ошибку валидации.

**Вывод:** выбран **D1**.

### Ключевое решение E: Тесты frontend

#### Вариант E1: Инфраструктуры нет — backend-тесты обязательны, frontend-тесты по минимуму — **выбран**

**Описание:** В репозитории отсутствует какая-либо frontend-тестовая инфраструктура
(vitest/jest/testing-library нет, `npm test` не существует). Добавление полного стека тестов —
отдельное инфраструктурное решение, выходящее за рамки данной задачи.

- **Backend:** обязательные тесты — перенос трёх существующих тестов `UpdateMerchantName`
  в `MerchantEndpointsTests` + новые кейсы валидации (пустое имя → 400, пробелы → 400,
  длина > 256 → 400, trim).
- **Frontend:** в рамках задачи — ручная проверка по чек-листу приёмки + сборка/lint
  (`npm run build`, `npm run lint`) как регрессионный барьер. Опциональный P2-шаг —
  добавление Vitest + React Testing Library и одного компонентного теста `MerchantTable`
  (решение о долгосрочной стратегии тестирования frontend — отдельная задача архитектора).

#### Вариант E2: Обязательно добавить vitest + RTL в этой задаче

**Плюсы:** Автоматическое покрытие UX-логики.

**Минусы:** Расширение области задачи (новые dev-зависимости, конфигурация vite,
CI-изменения), при том что весь остальной frontend проекта тестами не покрыт —
несогласованное вложение в «первый тест» именно в этой задаче.

**Вывод:** выбран **E1** (опциональный P2 — E2-подмножество по решению PM).

## Решение

Выбраны: **A1** (перенос эндпоинта в `/api/merchants`), **B1** (валидация в эндпоинте +
усиление доменного инварианта, лимит 256), **C1** (перенос `updateMerchantName` в
`api/merchants.ts` + фикс `credentials`), **D1** (inline-редактирование имени с явными
кнопками «Сохранить»/«Отмена», отдельное состояние от категории), **E1** (backend-тесты
обязательны; frontend — сборка/lint + ручная проверка, тестовая инфраструктура — отдельное
решение).

Максимальная длина имени: **256 символов** (совпадает с `HasMaxLength(256)` колонки
`merchants.name`). Аудит-логирование действий администратора на текущем этапе **не вводится**
(YAGNI; при необходимости — отдельная задача).

### Обоснование

1. **Согласованность с проектом:** перенос эндпоинта закрывает противоречие с ADR 008 (C3)
   и группирует все операции управления магазином в одном модуле; frontend-API повторяет ту же
   группировку.
2. **Закрытие реальных дефектов:** валидация превращает два необработанных сценария (пустое
   имя, слишком длинное имя) из `500` в `400`; исправляется баг `credentials` в fetch.
3. **Согласованность данных без миграций:** имя магазина не денормализовано (FK + joins),
   поэтому переименование автоматически видно в чеках, деталях, товарах и поиске — это
   подтверждается кодом `ReceiptReadService`/`CommodityReadService` и не требует фоновых задач.
4. **Минимальность (KISS/YAGNI):** не создаются новые сервисы, фильтры, DTO или миграции;
   переиспользуются существующие репозиторий (`AddAsync`), CSS-классы, паттерн `onRefresh`.
5. **Единый лимит 256** — ответ на открытый вопрос задачи; константа на клиенте и проверка на
   сервере ссылаются на одну цифру (сверяются тестом длины).

### Детали решения

**Backend** (`Analytics/src/ReceiptCollector.Analytics.Api/`):
- `Modules/Merchants/MerchantEndpoints.cs`:
  - добавлен маршрут `group.MapPut("/{merchantId:guid}/name", UpdateMerchantName)` (после
    `/{merchantId:guid}/category`; констрейнт `:guid` исключает коллизию со статическим
    `/categories`);
  - обработчик `UpdateMerchantName` перенесён из `ReceiptEndpoints` (код проверок 401/403/404
    сохраняется дословно, `UpdateMerchantNameRequest` — тоже);
  - добавлена валидация: trim; пустое/пробелы → `400 BadRequest("Merchant name is required.")`;
    длина > 256 → `400 BadRequest("Merchant name must be at most 256 characters.")`.
- `Modules/Receipts/ReceiptEndpoints.cs`: удалены `UpdateMerchantName` и
  `UpdateMerchantNameRequest` (переезжают в Merchants-модуль).

**Domain** (`Analytics/src/ReceiptCollector.Analytics.Domain/Modules/Merchants/Merchant.cs`):
- `UpdateName(string name)`: добавить `name = name.Trim()` и проверку
  `name.Length > 256 → ArgumentException` (порядок: trim → проверка пустоты → проверка длины).
  Конструктор не меняется (защита от пустоты там уже есть; лимит длины конструктора не
  добавляется, чтобы не рисковать импортом данных nalog.ru — при необходимости отдельным ADR).

**Frontend** (`Analytics/frontend/src/`):
- `api/merchants.ts`: добавлена `updateMerchantName(merchantId, newName)` (PUT
  `/api/merchants/${merchantId}/name`, `credentials: 'include'` в опциях fetch, а не в headers).
- `api/receipts.ts`: функция `updateMerchantName` удалена.
- `components/ReceiptDetails.tsx`: импорт `updateMerchantName` из `../api/merchants`; логика
  не меняется.
- `components/MerchantTable.tsx`: inline-редактирование имени в ячейке «Название» по D1
  (состояния `editingNameId`, `nameDraft`, `nameError`; индикатор «Сохранение...» через
  существующий `savingId`); кнопка «ред.» скрывается при `!isAdmin`; после успеха — `onRefresh()`;
  при ошибке — инлайн-сообщение и сохранение режима редактирования; отмена — кнопка и `Escape`;
  `maxLength={256}` на `<input>`; клиентская валидация (пусто/пробелы после trim → ошибка;
  длина > 256 → ошибка).
- `App.css`: новых стилей не требуется — переиспользуются `.merchant-edit-controls`,
  `.merchant-name-input`, `.save-merchant-btn`, `.cancel-merchant-btn` (для ячейки таблицы при
  необходимости — небольшие уточнения отступов, но не новые сущности).

**Тесты** (`Analytics/tests/ReceiptCollector.Analytics.Api.Tests/MerchantEndpointsTests.cs`):
- три существующих теста `UpdateMerchantName_*` переезжают на вызов `MerchantEndpoints.UpdateMerchantName`;
- новые тесты: пустое имя → `400`; имя из пробелов → `400`; длина 257 → `400`; граничное
  256 → успех; trim (имя с ведущими/хвостовыми пробелами сохраняется обрезанным).

**Без изменений:** БД (нет миграций), nginx, Go-backend, бот, DI-регистрации, Swagger-тег.

## Последствия

### Положительные

- Администратор получает управление именами магазинов прямо в `/merchants`, консистентное
  с «Деталями чека».
- Устранены три скрытых дефекта: 500 на пустом имени, 500 на длинном имени, некорректный
  `credentials` в fetch.
- Эндпоинт имени встаёт в доменную группу магазинов (закрыт долг по ADR 008 C3).
- Согласованность данных обеспечивается схемой БД (FK, без денормализации) — новые имена
  автоматически видны в чеках, деталях, товарах и поиске.

### Отрицательные

- Смена URL эндпоинта ломает совместимость со сторонними клиентами старого
  `/api/receipts/merchants/{id}/name` (для проекта приемлемо; при необходимости — deprecated-shim).
- Дублирование правил валидации на клиенте и сервере (неизбежно; сервер — источник истины).
- `MerchantTable` получает дополнительное состояние редактирования (небольшое усложнение
  компонента).

### Компромиссы

- **Атомарная смена контракта** вместо deprecated-shim — принято в пользу чистоты и
  единообразия; проект self-hosted, релиз монолитный.
- **Только `UpdateName` усиливается лимитом 256, конструктор — нет** — защита ингресста
  данных nalog.ru от новых отказов; при желании унифицировать — отдельное решение.
- **Отказ от blur-отмены** в пользу явной кнопки/Escape — принято для устранения гонки
  blur/click и консистентности с ReceiptDetails.
- **Отсутствие frontend-тестов в рамках задачи** — зафиксирован инфраструктурный пробел
  проекта (нет vitest/jest); стратегия тестирования frontend — отдельное решение.

### Риски

- **Rolling deploy frontend→API**: при развёртывании «новый frontend + старый API» новый URL
  даст 404. **Митигация:** монолитный релиз (build.sh собирает оба образа, up.sh поднимает
  вместе); вручную следить, чтобы frontend и API обновлялись в одном релизе.
- **Регрессия сортировки/пагинации** после переименования: список магазинов отсортирован по
  имени, после `onRefresh()` строка может уйти на другую страницу — это ожидаемое поведение,
  но при приёмке проверить вручную.
- **Гонка в `AddAsync` (upsert)**: имя обновляется через существующий upsert-метод
  репозитория (поиск по Inn, затем по Id) — при гипотетическом дубле Inn двух магазинов
  можно обновить не тот. **Митигация:** уникальный индекс на `Inn` уже существует; отдельный
  `UpdateNameAsync` вводить не требуется (YAGNI).
