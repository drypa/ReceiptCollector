# 10. Расширение справочника категорий товаров (Commodity Categories Expansion)

## Статус

Принято (предложено к реализации; **требуется проверка допущения о данных — п. 4 «Решение» — до деплоя**)

## Контекст

Справочник `CommodityCategory` слишком крупнозернистый: категория «Продукты питания» (`Food = 1`) объединяет все продовольственные товары, а транспортные расходы (платные дороги, общественный транспорт, билеты) не выделены вовсе. Требуется детализировать справочник, чтобы строить осмысленную аналитику расходов и подготовить базу для автокатегоризации через ИИ (ADR 009).

### Текущее состояние (AS-IS)

- `CommodityCategory` — enum, **19 значений** (0–17 + `Other = 255`) в `Analytics/src/ReceiptCollector.Analytics.Domain/Modules/Commodities/CommodityCategory.cs` + статический `CommodityCategoryHelper` (русские `DisplayNames`, `GetDisplayName()`, `GetAll()`). **Единственный источник истины** для справочника.
- Категория товара хранится в PostgreSQL **denormalized**: `commodities.category_id` (int?) + `commodities.category_name` (varchar(128)). Значения enum пишутся как int.
- `GET /api/commodities/categories` (`CommodityEndpoints.ListCategories`) отдаёт `CategoryDto[]` из `CommodityCategoryHelper.GetAll()` — **без изменений контракта** подхватит новый состав автоматически.
- `PUT /api/commodities/{id:guid}/category` валидирует `Enum.IsDefined(typeof(CommodityCategory), request.CategoryId)` — новые значения примутся автоматически.
- Frontend (`Analytics/frontend/src/components/CommodityTable.tsx`) загружает список категорий динамически через `fetchCategories()`; **отображение имени категории в строках таблицы идёт из denormalized `commodity.categoryName`**, а не из словаря.
- Автокатегоризация через ИИ (ADR 009) **ещё не реализована**; промт генерируется из `GetAll()` без `Undefined` — расширение справочника автоматически повлияет на промт.
- Унификация `MerchantCategory`/`CommodityCategory` **не выполняется** (ADR 008) — справочники остаются независимыми.
- Миграционный раннер (`ReceiptCollector.Analytics.Migrations/MigrationRunner.cs`) применяет все `*.sql` из `Scripts/` по порядку имени, однократно (история в `migration_scripts_history`) — пригоден и для data-fix скриптов.

### Бизнес-требования (из задачи)

1. Детализация продуктов: `Food = 1` остаётся в enum, отображаемое имя меняется на **«Прочая еда»** (запасная категория); добавляются 13 подкатегорий (коды 18–30).
2. Транспорт (коды 31–37): Платные дороги, Общественный транспорт, Ж/Д билеты, Авиабилеты, Такси, Каршеринг, Парковка.
3. Прочие пробелы (коды 38–41): Табак, Связь и интернет, ЖКХ и коммунальные услуги, Развлечения и досуг.
4. Проверить допущение заказчика: существующие товары **не распределены** по категориям (нет строк с `category_id = 1` / старым `category_name = 'Продукты питания'`).
5. Рассмотреть группировку в UI (`<optgroup>` по разделам Продукты / Транспорт / Прочее) при ~43 значениях.
6. Оценить влияние на промт ИИ (ADR 009) при 42 категориях (без `Undefined`) и необходимость перевалидации плана `auto-commodity-categorization.md`.

## Рассмотренные варианты

### A. Нумерация новых значений

- **A1 (выбрано):** новые коды **18–41** ровно по предложению заказчика. Диапазон 18–41 свободен (заняты 0–17 и 255), коллизий нет (проверено программно: 19 существующих + 24 новых = **43 значения, 0 коллизий**).
- A2: переиспользовать свободные коды из «дыр» внутри 0–17 — не требуется, диапазон 18–41 предпочтительнее: сохраняет читаемость соответствия кодов блокам (продукты / транспорт / прочие).

### B. Переименование `Food`

- **B1 (выбрано):** менять **только отображаемое имя** в `DisplayNames` хелпера («Продукты питания» → «Прочая еда»). Значение enum `Food = 1` и числовые коды не меняются — обратная совместимость данных.
- B2: заводить новое значение enum под «Прочую еду» и переносить данные — не требуется и опасно (перекодировка `category_id` в БД без нужды, ломает смысл кода 1).

### C. Проверка и обработка допущения о данных (п. 4 задачи)

- **C1 (выбрано):** перед деплоем выполнить проверочный SQL; при наличии строк с `category_id = 1` — выполнить **одноразовый data-fix** (`UPDATE commodities SET category_name = ...`), поскольку frontend отображает denormalized `commodity.categoryName`, и расхождение было бы видно в UI.
- C2: принять расхождение без правки данных — **отклонено**: UI показывает `categoryName` из строки товара; старые имена остались бы в интерфейсе до ручной перекатегоризации.

### D. Группировка в UI

- **D1 (рекомендовано):** группировку задаёт backend — поле `Group` в `CategoryDto` (источник истины — хелпер). Frontend строит `<optgroup>` по этому полю. Коды не само-документирующие, хардкод диапазонов на фронте хрупок.
- D2: группировка на фронте по диапазонам кодов — **хуже**: дублирует знание о справочнике, ломается при будущих расширениях.

### E. Промт ИИ при 42 категориях

- **E1 (выбрано):** точечная перевалидация ADR 009 и плана — обновить количество значений, добавить требования к промту (few-shot примеры, эвристики кофе/чай, разграничение схожих категорий). Каркас решения (JSON `{"category": "Name"}`, валидация `Enum.TryParse` по имени, генерация из `GetAll()`) **не меняется**.

- **Отсутствие коллизий**: диапазон 18–41 свободен (заняты 0–17 и 255); проверено программно (19 + 24 = 43 уникальных кода).
- **Обратная совместимость**: существующие коды не меняются; `Other = 255` сохранён; `Food = 1` сохранён (меняется только отображаемое имя).
- **Имена enum-членов уникальны** — важно для формата ИИ `{"category": "<имя>"}` и `Enum.TryParse` (ADR 009).
- Максимальная длина нового отображаемого имени — «ЖКХ и коммунальные услуги» (23 символа) < `varchar(128)` — схема БД не меняется.

### 2. Оценка влияния на существующий код

**Изменяется (минимально):**
- `Analytics/src/.../Domain/Modules/Commodities/CommodityCategory.cs` — добавить 24 значения enum + 24 записи в `DisplayNames`; изменить значение `Food` на «Прочая еда».
- *(Опционально)* `CategoryDto` + хелпер — поле группы для UI (решение D1); `CommodityTable.tsx` — группировка `<optgroup>`.

**Не требуется изменений (проверено по коду):**
- `CommodityEndpoints.cs` — `ListCategories` читает `GetAll()`; `UpdateCategory` использует `Enum.IsDefined` — новый состав подхватится автоматически, контракты API не меняются.
- `CommodityRepository.UpdateCategoryAsync` — пишет `category_name` через `GetDisplayName()` — корректно для новых категорий.
- Схема PostgreSQL, Go-backend, Telegram-бот, nginx — **не затрагиваются** (изменение только в Analytics).
- `MerchantCategory` / `MerchantEndpoints` / `MerchantEndpointsTests` — не затрагиваются (отдельный справочник, ADR 008).

**Тесты:** проверено — **ни один существующий тест не зависит от состава/количества `CommodityCategory`**:
- `MerchantEndpointsTests.GetMerchantCategories_ReturnsAllCategories` проверяет `Enum.GetValues<MerchantCategory>().Length` (21) — к commodities не относится.
- Тестов на `CommodityEndpoints` в репозитории нет; `grep` по `CommodityCategory` в `tests/` не даёт совпадений (кроме использования доменной сущности `Commodity` в fixture).
- **Рекомендуется добавить** тест по образцу `GetMerchantCategories_ReturnsAllCategories` (assert: `Enum.GetValues<CommodityCategory>().Length`, каждый член имеет отображаемое имя через `GetDisplayName`, `Undefined` присутствует) — зафиксирует консистентность словаря и защитит от регрессий при будущих расширениях. Это соответствует критерию приёмки 4 задачи.

### 3. Влияние на автокатегоризацию (ADR 009) и перевалидация плана

Промт ИИ генерируется из `GetAll()` без `Undefined` — новые 24 категории попадут в промт автоматически. При 42 категориях требуется:

1. **Перевалидация ADR 009 и плана `auto-commodity-categorization.md`** (точечная):
   - обновить упоминания «19 значений + `Other = 255`» на актуальный состав (42 категории без `Undefined`);
   - в ADR 009 (п. 4 «Промт») зафиксировать требование **few-shot примеров** в промте (несколько пар «название товара → категория») для устойчивости качества;
   - в план (задача 4 «ИИ-клиент») добавить пункт о few-shot и эвристиках; обновить пример промта (сейчас в ADR 009 промт содержит хардкод списка категорий).
2. **Эвристики в промте** (требование заказчика):
   - «Кофе в зёрнах / молотый / растворимый / капсулы», «Чай в пакетиках / листовой» → `Бакалея`; «Капучино», «Латте», «Американо», «Кофе с собой» → `Напитки`;
   - разграничение схожих категорий: `Meat` vs `Poultry`; `Vegetables` vs `Fruits`; `Bakery` vs `Confectionery`; `ReadyMeals` vs `FastFood`; `Groceries` vs `Food` (запасная) — проговорить в промте, чтобы не было дедупликации смыслов.
3. **Осознанный компромисс**: неидеальная точность разграничения «продукт vs готовый напиток» допустима — компенсируется ручной категоризацией администратора (п. 4 задачи, ADR 009). Не блокирует задачу.
4. Валидация ответа ИИ (`Enum.TryParse` по имени + `Enum.IsDefined`) — не меняется; новые имена членов уникальны.

## Обоснование

1. **Единственный источник истины**: справочник и его отображаемые имена остаются в `CommodityCategoryHelper` (ADR 005) — эндпоинт `GET /api/commodities/categories`, UI и будущий промт ИИ автоматически получают новый состав без правок контрактов.
2. **Обратная совместимость и минимальность**: только добавление значений + правка одного отображаемого имени; существующие коды не трогаем → не требуется перекодировка `commodities.category_id`, миграции схемы нет, Go-backend и бот не затрагиваются.
3. **Согласованность denormalized данных**: поскольку UI отображает `commodity.categoryName`, переименование требует либо подтверждения «0 строк», либо идемпотентного data-fix (решение C1) — это устраняет единственный реальный риск задачи.
4. **KISS/YAGNI**: группировка UI делается только при необходимости (не блокирует); перевалидация ADR 009 — точечная, без изменения каркаса решения.
5. **Следование паттернам проекта**: нумерация enum, хелпер с `DisplayNames`, DTO-контракты, миграционный раннер для data-fix — всё в существующем стиле.

## Компромиссы

- **Denormalized `category_name` vs централизованный словарь**: оставляем denormalized (ADR 005) ради производительности и простоты; цена — необходимость data-fix при переименованиях (компенсируется идемпотентным скриптом). Альтернатива (выводить имя всегда из словаря на клиенте) — более крупная переработка UI, отложена.
- **43 значения в плоском селекте**: без группировки UI ухудшается; группировка (D1) — дополнительная работа, не блокирует задачу.
- **Качество ИИ при 42 категориях**: выше риск смешения близких категорий; компенсируется few-shot примерами, эвристиками в промте и ручной коррекцией (компромисс заказчика, п. 4 задачи).
- **Нумерация кодов**: коды 18–41 не имеют «запаса» между блоками — при будущих расширениях блок «Продукты» займёт 18–30+; при переполнении блока новые коды продолжат серию без конфликтов (коды не используются для группировки UI — группировка отдана backend-полю `Group`).

## Последствия

### Положительные

- Детализированная аналитика расходов (питание по подкатегориям, транспорт, ЖКХ и т.д.).
- Автокатегоризация (ADR 009) получит рабочий справочник и требования к промту (few-shot, эвристики) на момент реализации.
- Ноль изменений схемы PostgreSQL, Go-backend, Telegram-бота, nginx; обратная совместимость существующих данных и кодов.
- Существующие тесты не ломаются.

### Отрицательные

- Рост справочника до 43 значений усложняет ручной выбор категории без группировки (митигируется D1).
- Промт ИИ при 42 категориях требует few-shot примеров и эвристик — чуть более объёмный промт и подготовка примеров (затрагивает план ADR 009).
- Расхождение между ADR 005 (исторический состав enum: `ClothingAndFootwear = 2`, `Other = 14`) и фактическим кодом (`Clothing = 2`, `Footwear = 17`, `Other = 255`) сохраняется — актуальным источником истины является код; при желании ADR 005 стоит актуализировать отдельно (вне этой задачи).

### Риски

- **Допущение о данных не подтвердится** (строки с `category_id = 1` есть). **Митигация:** проверочный SQL до деплоя + идемпотентный data-fix (решение C1); результат зафиксировать.
- **UI покажет старое имя** при расхождении denormalized `category_name`. **Митигация:** та же (data-fix). Долгосрочно — рассмотреть вывод имени из списка категорий на клиенте.
- **Смешение близких категорий в ИИ** (Meat/Poultry, Groceries/Food и т.д.). **Митигация:** few-shot + эвристики в промте; ручная категоризация.
- **Пропуск записи в `DisplayNames`** для нового члена enum → `GetDisplayName()` вернёт fallback «Не указана». **Митигация:** тест на консистентность словаря (рекомендуемый тест, см. «Решение» п. 3).
