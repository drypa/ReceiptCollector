# ADR-026: Второй, переключаемый провайдер AI-категоризации товаров (движок типизированных решений)

## Статус

Принято (проект). Основание — задача
[rlcd-commodity-categorization-provider](../tasks/rlcd-commodity-categorization-provider.md)
(требования FR-1…FR-4, критерии приёмки, edge cases).

> **Состояние: решение подготовлено, код не реализован.** Приоритет задачи — `low`, сроков нет;
> задача лежит в бэклоге. Документация (`AGENTS.md`, `.env.example`, `docker-compose.yml`),
> тесты и само переключение появятся на этапе реализации. До этого момента действующая
> конфигурация — прежняя, по ADR 009 и ADR 019.

Цель решения — измерить ускорение/удешевление категоризации, дав оператору
**второй, опциональный** движок, переключаемый конфигурацией. Существующий
OpenAI-совместимый клиент **не удаляется и не заменяется** (FR-1.1) — это
принципиальная позиция задачи, а не деталь реализации.

**Дополняет, ничего не отменяет:** [ADR 009](009-auto-commodity-categorization.md)
(вызов ИИ, алгоритм «existing → cache → ai», контракты эндпоинтов, таблица опций
`AI:*` — см. amend-заметку в его «Статусе»), [ADR 019](019-in-memory-commodity-category-cache.md)
(in-memory кэш, поведение `503`), [ADR 021](021-env-vars-passthrough-docker-compose.md)
(проброс env в `docker-compose.yml`), [ADR 022](022-commodity-categories-food-detailing.md)
(эвристики разграничения категорий в промте OpenAI-клиента).

> **Вне области:** развёртывание/обслуживание самого движка (внешний сервис,
> адрес/ключ/модель — только через конфигурацию), валидация качества
> категоризации в цифрах, калибровка порога, авто-откат между провайдерами,
> кэширование ответов ИИ, схема БД, Go-сервисы, бот, nginx, фронтенд.

## Контекст

### Проблема и цель (из задачи)

- Категоризация чека выполняется **последовательным потоком запросов к LLM**: на чек
  десятки позиций → десятки запросов; суммарное время ответа растёт пропорционально
  числу позиций, стоимость — пропорционально числу запросов и объёму промта.
- Ответ LLM — свободный текст, поэтому его приходится разбирать и чистить
  (обёртки ```, лишний текст, числа вместо имён категорий) — хрупкая и недешёвая
  часть решения.
- Сравнить варианты между собой **нечем**: ни времени, ни стоимости отдельного
  запроса к ИИ сейчас не измеряется.
- Цель: **опционально** переключить AI-категоризацию на «движок типизированных
  решений» (далее — *SystemOne*), который отдаёт готовую категорию из закрытого
  множества без генерации текста; снизить время и/или стоимость и **иметь
  возможность это измерить**; переключение — только через env/конфигурацию, без
  пересборки и правок кода.

## Рассмотренные варианты

### A. Форма порта `IAiClient`

#### Вариант A1: оставить порт как есть (`productName` + `IReadOnlyCollection<string> categoryNames`) — **выбран**

**Описание.** Ничего в `Application` не меняем. Адаптер SystemOne получает те же
имена значений реестра и **сам** строит из них всё, что нужно его протоколу.

**Плюсы:**
- Ноль изменений в `Application` и `Api` → тест архитектуры
  `ProjectDependencyTests` остаётся зелёным по построению, существующие тесты
  (`CommodityCategorizationServiceTests`, `ReceiptCategorizationEndpointsTests`)
  не требуют правок ожидаемого поведения (критерий приёмки №1).
- Имена значений enum — **уже** устойчивый идентификатор категории: он же является
  форматом wire-контракта API (ADR 009, решение B1). Адаптер может обогатить
  список через `CommodityCategoryHelper` (`GetDisplayName`, `GetGroup`, числовой код
  enum) **внутри себя** — порт при этом не меняется.
- Нет утечки требований одного провайдера в общий контракт (ISP/DIP), минимум
  изменений (KISS/YAGNI).

**Минусы:**
- Если протокол SystemOne потребует описаний категорий/объяснений, адаптер должен
  их взять из `CommodityCategoryHelper`; если описаний не хватит — правка в
  `Domain` (см. B2), порт при этом всё равно не меняется.

#### Вариант A2: обогатить порт моделью таксономии (`AiCategoryOption { Name, DisplayName, Code, Group, Description? }`)

**Плюсы:** один контракт на любые нужды; «описания» доступны обоим провайдерам.
**Минусы:** ломает единственную существующую реализацию и ~10 тестовых мест;
вынуждает OpenAI-промт присоединить поля, которые ему не нужны (YAGNI); по сути
проектирует таксономию под ещё не утверждённый протокол SystemOne.
**Причина отклонения:** требований к таким полям нет ни в одном FR; типичный
движок типизированных решений принимает закрытый список меток, а описания
категорий для этого не требуются.

#### Вариант A3: порт с per-request параметрами (`AiSuggestionRequest { ProductName, Categories, Parameters }`)

**Плюсы:** точка расширения под параметры уровня запроса.
**Минусы:** требования нет — FR-2.3 говорит о **конфигурации**; изменение сигнатуры
ломает существующего провайдера и тесты; лишняя абстракция (YAGNI).
**Причина отклонения:** оставляем как эволюционный путь (см. решение 8), а не как
текущее решение.

#### Вариант A4: рядом с `IAiClient` завести второй порт `IClassificationEngine`, выбор провайдера — в оркестраторе

**Плюсы:** типы не «смешиваются».
**Минусы:** выбор провайдера (конфигурационная политика) проникает в
`Infrastructure/Modules/Commodities` и в `Api`; дублирование ветвления в двух
слоях; `Application` снова меняется. **Причина отклонения:** нарушает единственную
точку истины о выборе провайдера (решение 1).

### B. Где живёт таксономия категорий

#### Вариант B1: реестр — в `Domain`, его протокольное представление — в адаптере (`Infrastructure`) — **выбран**

`CommodityCategory` + `CommodityCategoryHelper` остаются единственным источником
истины (ADR 005/009/010/022). Адаптер SystemOne получает имена и при необходимости
обогащает их локально. Ничего в `Domain` не меняется.

#### Вариант B2: перенести/расширить описание категорий в `Domain` (коды, `Description`, `IsTerminal`)

**Плюсы:** если движку понадобится описание категории, оно живёт рядом с реестром.
**Минусы:** правки `Domain` и фронтовых/UI-тестов ради ещё не утверждённого
протокола; риск «зашить» одно частное описание в общую модель.
**Решение:** отложить (решение 8, открытый вопрос). Если описания понадобятся,
добавляются в `CommodityCategoryHelper` как данные — порт и провайдер не меняются.

### C. Схема конфигурации и обратная совместимость

#### Вариант C1: селектор `AI:Provider` + вложенные секции `AI:OpenAi`, `AI:SystemOne`, легаси-ключи как fallback по факту присутствия — **выбран**

(детально — решение 2). Сохраняет `AI__BaseUrl` и т.д. рабочими, даёт
provider-aware схему и не требует синхронного переезда конфигурации у оператора.

#### Вариант C2: плоские ключи `AI:OpenAiBaseUrl`, `AI:SystemOneBaseUrl`

**Плюсы:** без вложенности. **Минусы:** не группируется по провайдеру, «расползается»
префикс, `env`-имена (`AI__OpenAi__BaseUrl` vs `AI__SystemOne__BaseUrl`)
несимметричны с любым будущим вложенным вариантом. **Отклонён:** FR-2.1 требует
*секций*.

#### Вариант C3: две независимые секции верхнего уровня — старая `AI` (OpenAI) и новая `AI:SystemOne`

**Плюсы:** ноль правок в `AiOptions`/эндпоинте/оркестраторе (секция `AI` = OpenAI
по определению). **Минусы:** нарушает FR-2.1 («настройки провайдеров **разделены**
по секциям»); легаси-ключи становятся вечными, а не совместимостью; третий
провайдер не влезает в схему. **Отклонён** требованием.

#### Вариант C4: новая схема без легаси (`AI__BaseUrl` больше не работает)

**Плюсы:** чисто. **Минусы:** «тихая поломка» текущих установок — прямо запрещена
задачей. **Отклонён.**

### D. Стратегия регистрации в DI

#### Вариант D1: разветвление на этапе конфигурации контейнера, fail-fast — **выбран**

`AddInfrastructure` читает `AI:Provider` напрямую из `IConfiguration`, парсит
общим статическим парсером и регистрирует **ровно одну** реализацию
`IAiClient` (typed `HttpClient`). Неизвестное/пустое значение → исключение при
сборке контейнера, т.е. до `app.Run()`. Второй парсерный вызов (в post-configure)
идёт через **тот же** статический метод — логика правил одна.

**Плюсы:** ошибка конфигурации = падение процесса на старте (не 500-ка на первом
запросе, не «тихий» откат); ноль «лишних» зарегистрированных зависимостей;
инвариант «`IAiClient` — одна реализация» сохраняется.
**Минусы:** выбор «зашит» в код регистрации (третий провайдер = ещё одна ветка);
парсинг значения в двух точках (устранено общим хелпером).

#### Вариант D2: регистрация обоих клиентов + диспетчер, переключение на вызове

**Плюсы:** добавление провайдера не трогает DI. **Минусы:** обе конфигурации
проверяются/создаются всегда; ошибка «плохой» конфигурации несекретного провайдера
мешает работать активному; на каждый вызов — лишняя ветка; **FR-1.4 не выполнен** в
строгой форме (ошибка всплыла бы на первом запросе). **Отклонён.**

#### Вариант D3: отложенная фабрика (`AddScoped<IAiClient>(sp => …)`)

**Плюсы:** выбор откладывается до первого вызова. **Минусы:** ровно тот же
дефект, что у D2, но менее заметный: ошибка конфигурации «едет» до первого
запроса. **Отклонён** требованием FR-1.4.

### E. Как «эффективные» параметры активного провайдера попадают к потребителям

#### Вариант E1: `IPostConfigureOptions<AiOptions>` — снимок активного провайдера в существующий тип `AiOptions` — **выбран**

`AiOptions` после слияния содержит: `Provider` (канонический id активного
провайдера) + пять параметров **активного** провайдера + `MinConfidence`.
Потребители не меняются: `ReceiptCategorizationEndpoints` (503-гейт по
`BaseUrl`), `CommodityCategorizationService` (`Concurrency`), оба клиента
(`BaseUrl/Model/Timeout/ApiKey`).

**Плюсы:** ноль изменений в `Api`/`Application`/существующем клиенте и в их тестах;
503-гейт и лимит параллелизма становятся provider-aware автоматически; правила
приоритета реализованы ровно в одном месте.
**Минусы (осознанный):** тип `AiOptions` совмещает три роли — корневая секция с
селектором, легаси-ключи и снимок активного провайдера; компенсируется
XML-документацией класса, стартовым логом и тестами резолвера.

#### Вариант E2: новый тип `AiProviderSettings` + новый порт в `Application`

**Плюсы:** типы чище. **Минусы:** меняет конструкторы клиента, сервиса и эндпоинта,
то есть и `Api`, и `Application` → больше диффа и риска без выигрыша для
FR-1/FR-3. **Отклонён** (см. также риск E1 в «Компромиссах»).

#### Вариант E3: отдельные типизированные секции + ручное «сведение» в каждом потребителе

**Отклонён:** правило приоритета размножается по коду (4 потребителя) →
гарантированный дрейф «а кто тут настроен».

### F. Наблюдаемость: что и где измеряем

#### Вариант F1: структурированные логи из адаптера, без новых зависимостей — **выбран**

Одна запись на **логический вызов** (после всех попыток) с полями
`ai.provider`, `ai.model`, `ai.outcome`, `ai.duration_ms`, `ai.attempts`,
`ai.request_bytes`, `ai.response_bytes` + провайдер-специфичные
(`ai.prompt_tokens`/`ai.completion_tokens` для OpenAI, `ai.confidence` для
SystemOne). Детализация/снижение уровня — конфигурацией `Logging:LogLevel`.

**Плюсы:** ровно то, что просит FR-4.1/4.2 и чего нет в репозитории; ноль новых
пакетов; логи уже единственный канал эксплуатации. **Минусы:** агрегации по
histogram/квантилям без внешнего сборщика не будет; денежная стоимость не считается
кодом.

#### Вариант F2: `System.Diagnostics.Metrics` / OpenTelemetry

**Плюсы:** готовые агрегации и экспорт. **Минусы:** новая зависимость и инфраструктура
экспорта, которых в проекте нет; ради двух полей (время, объём) — YAGNI.
**Решение:** отклонено; схема логов спроектирована так, чтобы позже переехать на
метрики без изменения полей.

#### Вариант F3: считать деньги в коде (`Cost` по прайсу из конфигурации)

**Плюсы:** «стоимость» сразу в логах. **Минусы:** прайс вендора нам неизвестен,
меняется, и его хранение в коде/конфигурации создаёт иллюзию точности; у нового
движка единица «стоимости» не определена вовсе. **Решение:** считаем **измеримые
величины** (время, попытки, байты, токены, уверенность) — этого достаточно, чтобы
оператор домножил на свой прайс; это же требование FR-4.2 («какие данные
фиксируются…» — состав определён).

### G. Ретраи, таймаут, деградация

#### Вариант G1: общий транспортный слой `AiHttpTransport` + общий валидатор имён категорий — **выбран**

Таймаут, ретрай ×1 (сеть/таймаут/5xx), маппинг исключений в
`AiTransientException`/`AiClientException`, измерение длительности и размеров —
один класс, используемый обоими адаптерами. Разбор тела ответа и построение
запроса — у каждого провайдера свои.

**Плюсы:** «поведение при таймауте и повторах совпадает с текущим» обеспечено
**структурно**, а не обещанием; нет дублирования ~60 строк; тесты таймаутов/ретраев
пишутся один раз.
**Минусы:** трогается проверенный код `OpenAiCompatibleAiClient` (покрыт 14
тестами через stub-`HttpMessageHandler` — регрессии будут замечены).

#### Вариант G2: продублировать логику в новом клиенте

**Плюсы:** ноль изменений в существующем клиенте. **Минусы:** две копии политики
ретраев/таймаутов, расхождение при правке; DRY-нарушение. **Отклонён.**

#### Вариант G3: общий абстрактный базовый класс `AiClientBase`

**Плюсы:** переиспользование через наследование. **Минусы:** наследование ради
переиспользования; базовый класс вынужден знать о подписях тела/ответа;
абстракция сложнее, чем делегирование. **Отклонён** (SOLID: предпочитаем
композицию).

### H. «Уверенность ниже порога» и ошибки

#### Вариант H1: не-транзиентный `AiClientException` + `reason` в логе, без новых типов — **выбран**

Ответ с уверенностью ниже порога — это **детерминированный** исход, а не
временная ошибка, поэтому бросается обычный `AiClientException` (не
`AiTransientException`) → существующий цикл ретраев его не повторяет, существующий
`catch (AiClientException)` в оркестраторе даёт ровно текущее поведение
(`source = "undefined"`, текст «AI категория не определена.»). Точная причина
(`low_confidence` / `invalid_response` / `timeout` / `http_5xx` / `network` /
`not_configured`) пишется в лог адаптером в момент обнаружения — там, где она
известна.

**Плюсы:** ноль изменений в контракте и в оркестраторе; пользовательский текст не
меняется (FR-3.1/3.4 «как сейчас»); оператор получает причину в логах.
**Минусы:** причина недоступна в API-ответе (осознанно — контракт не меняем).

#### Вариант H2: новый тип исключения + особый текст в `error`

**Плюсы:** точнее для пользователя/отладки. **Минусы:** новая ветка в оркестраторе,
изменение пользовательских строк, риск для тестов/фронта. **Отклонён.**

#### Вариант H3: клиент возвращает «неопределено» флагом, а не исключением

**Плюсы:** нет исключений на штатный исход. **Минусы:** меняет форму результата
порта и логику оркестратора; смешивает «не смогли» и «определили как
неопределённое». **Отклонён** — расходится с текущей семантикой порта.

## Решение

### 1. Переключение провайдера: селектор `AI:Provider`, разветвление в DI, fail-fast

- Нейтральные (без вендора) идентификаторы: `OpenAi` (`openai`) и `SystemOne`
  (`systemone`). Разбор — **регистронезависимый**, результат нормализуется в
  канонический lower-case id; этот же id используется во всех логах (единая
  метка для сравнения провайдеров).
- Канонические id живут константами в одном месте (`AiProviderIds` в
  `Infrastructure/Configuration`), регистронезависимое имя конфигурации
  отображается в id общим статическим парсером `AiProviderSelector.Parse(...)`.
- `AddInfrastructure` читает `AI:Provider` и регистрирует **ровно одну**
  реализацию:
  - `OpenAi` → `AddHttpClient<IAiClient, OpenAiCompatibleAiClient>()`
  - `SystemOne` → `AddHttpClient<IAiClient, SystemOneAiClient>()`
- Переключение применяется **при старте** процесса (смена env + рестарт), что
  прямо соответствует FR-1.3 и текущей семантике `IOptions` (снимок).
- **Строгая трактовка селектора (FR-1.4 vs FR-1.5).** Задача требует и «пустое
  значение → ошибка», и «провайдер не задан → текущее поведение». Разрешение задаёт
  таблица ниже; сообщение об ошибке перечисляет допустимые значения
  (`AI:Provider '…' is not a valid value. Allowed: OpenAi, SystemOne.`).
  Основание: молчаливый откат на дефолт сделал бы переключение «невидимым» —
  ровно то, чего задача не хочет. Компенсация эксплуатационная — см. ниже.

  | Состояние `AI:Provider` | Результат |
  |---|---|
  | Ключ **отсутствует** во всех источниках | `openai` (FR-1.5 — дефолт) |
  | Ключ присутствует, значение не распознано | **ошибка конфигурации на старте** (FR-1.4) |
  | Ключ присутствует, значение пустое/пробелы | **ошибка конфигурации на старте** (FR-1.4) |

- **Компенсация в развёртывании:** в `docker-compose.yml` переменная обязана иметь
  дефолт — `AI__Provider=${AI__Provider:-OpenAi}`. Передача без дефолта
  (`AI__Provider=${AI__Provider}`) при незаданной переменной даст пустое значение и
  **падение старта** — это осознанно, но требует правила в файле развёртывания.
- Точка расширения на третий движок: новое значение селектора + одна ветка в
  регистрации + новая секция. Схема `IConfiguration` и порт не меняются.

### 2. Схема конфигурации

```jsonc
{
  "AI": {
    "Provider": "OpenAi",                       // селектор; отсутствие ключа = OpenAi
    "OpenAi":   { "BaseUrl": "", "Model": "qwen", "Timeout": "00:00:10", "Concurrency": 3, "ApiKey": "" },
    "SystemOne": { "BaseUrl": "", "Model": "",  "Timeout": "00:00:10", "Concurrency": 1, "ApiKey": "",
                   "MinConfidence": 0.0 }
  }
}
```

| Опция (appsettings) | env | По умолчанию | Назначение |
|---|---|---|---|
| `AI:Provider` | `AI__Provider` | `OpenAi` (если ключ **отсутствует**) | Активный провайдер; неизвестное/пустое → падение старта |
| `AI:OpenAi:BaseUrl` | `AI__OpenAi__BaseUrl` | `AI:BaseUrl`, иначе пусто | База OpenAI-совместимого API (`{BaseUrl}/chat/completions`); пусто = провайдер не настроен → `503` |
| `AI:OpenAi:Model` | `AI__OpenAi__Model` | `AI:Model`, иначе `qwen` | Имя модели в теле запроса |
| `AI:OpenAi:Timeout` | `AI__OpenAi__Timeout` | `AI:Timeout`, иначе `00:00:10` | Таймаут одного вызова |
| `AI:OpenAi:Concurrency` | `AI__OpenAi__Concurrency` | `AI:Concurrency`, иначе `3` | Параллельные вызовы на один suggest |
| `AI:OpenAi:ApiKey` | `AI__OpenAi__ApiKey` | `AI:ApiKey`, иначе пусто | `Authorization: Bearer` |
| `AI:SystemOne:BaseUrl` | `AI__SystemOne__BaseUrl` | пусто | **Полный URL эндпоинта** движка (см. ниже); пусто → `503` |
| `AI:SystemOne:Model` | `AI__SystemOne__Model` | пусто | Имя модели/сущности; пусто → поле не отправляется |
| `AI:SystemOne:Timeout` | `AI__SystemOne__Timeout` | `00:00:10` | Таймаут одного вызова |
| `AI:SystemOne:Concurrency` | `AI__SystemOne__Concurrency` | `1` | См. обоснование ниже |
| `AI:SystemOne:ApiKey` | `AI__SystemOne__ApiKey` | пусто | `Authorization: Bearer` |
| `AI:SystemOne:MinConfidence` | `AI__SystemOne__MinConfidence` | `0` (порог **выключен**) | Порог уверенности, диапазон `0..1` |
| `AI:BaseUrl/Model/Timeout/Concurrency/ApiKey` | `AI__*` | — | **Легаси** (текущие настройки OpenAI); работают, но помечаются предупреждением |

**Правило приоритета (детерминированное, «присутствие ключа важнее значения»):**
для каждого из пяти параметров провайдера `X`:
1. если `AI:<X>:<Key>` **присутствует** в конфигурации (любой источник: json/env) →
   используется оно (в том числе явно пустое значение);
2. иначе, если `AI:<Key>` (легаси) присутствует → используется оно;
3. иначе — значение по умолчанию из таблицы.

**Особые (не легаси) ключи:** `AI:SystemOne:*` не имеют легаси-эквивалента; селектор
`AI:Provider` трактуется строго (решение 1).

**Основание именно такого правила (проверка на «тихую поломку»):**
- Прод сегодня выключает AI **пустым** `AI__BaseUrl` (`docker-compose.yml:118`
  без дефолта) — и это единственный «выключатель». При правиле «присутствие
  важнее» пустой env-ключ перекрывает `appsettings.json` → `503` сохраняется.
  Правило «непустое значение приоритетно» **сломало бы этот сценарий** (пустой env
  перестал бы перекрывать непустое значение из файла, и AI «включился бы» сам
  себя) — поэтому оно отклонено, несмотря на привлекательность.
- Обратный риск правила «присутствие важнее» — наивное добавление в
  `docker-compose.yml` строки `AI__OpenAi__BaseUrl=${AI__OpenAi__BaseUrl}`:
  незаданная переменная даст пустое значение и перекроет легаси `AI__BaseUrl`,
  молча выключив AI. Поэтому:
  1. **в `docker-compose.yml` строки `AI__OpenAi__*` не добавляются вовсе** —
     OpenAI-провайдер по-прежнему настраивается существующими `AI__*`;
  2. на такой конфликт (новый ключ присутствует и пуст, легаси — непуст) при старте
     пишется `Warning` с перечислением конфликтующих ключей.
- Правило выбирается один раз и только в резолвере → одинаково для всех
  потребителей (решение E3 отклонён).

**`Concurrency` для SystemOne = 1 по умолчанию.** Edge case задачи указывает, что
движок обрабатывает запросы последовательно: при значении 3 клиент создаёт очередь,
которая на дешёвом движке даёт таймауты и массовые `Undefined` (то есть выглядит как
поломка, а не как измерение). Значение конфигурируемо, и его подбор — ровно тот
эксперимент, ради которого задача и заводится. Компромисс: если движок параллельный,
первый запуск будет медленнее потенциального — это измеряется (FR-4.1) и правится
одной переменной.

**`BaseUrl` для SystemOne = полный URL эндпоинта** (без жёстко зашитого пути), в
отличие от OpenAI (`{BaseUrl}/chat/completions`). Основание: протокол движка не
утверждён, и любая зашитая часть пути стала бы блокером, требующим правки кода.
Разделение «база + путь» при необходимости — один новый параметр в резолвере, без
изменений порта и клиента.

**Валидация на старте:**

| Условие | Реакция |
|---|---|
| `AI:Provider` присутствует, но неизвестен/пуст | Падение старта (решение 1) |
| `AI:SystemOne:MinConfidence` вне `0..1` или не число | Падение старта, сообщение с ключом и значением |
| `AI:*:Timeout` не парсится как `TimeSpan` | Падение старта, сообщение с ключом и значением |
| `AI:*:Concurrency` не парсится как `int` | Падение старта |
| `Concurrency < 1` | Значение приводится к `1` (поведение текущего кода сохраняется, новых отказов не вводим) |
| `Timeout <= 0` | Используется 10 с (текущее поведение клиента сохраняется) |
| Неизвестный ключ в `AI`, `AI:OpenAi`, `AI:SystemOne` | `Warning` при старте со **списком имён ключей** (значения не логируются — `ApiKey` секрет) |
| Используется легаси-ключ | `Warning` «перенесите в `AI:OpenAi:*`» |
| `AI:SystemOne:*` задан, но провайдер `openai` | `Warning` «секция не используется» |

Предупреждения выдаёт post-configure, который при `ValidateOnStart()` выполняется
**ровно один раз при старте** — отдельный hosted-service не нужен.

### 3. Слияние конфигурации: `IPostConfigureOptions<AiOptions>`

- `AiOptions` (секция `AI`) получает два свойства: `Provider` (после слияния —
  канонический id активного провайдера) и `MinConfidence` (используется только
  провайдером `systemone`; для `openai` — `0`).
- Резолвер (`IPostConfigureOptions<AiOptions>` + `IConfiguration`) при разрешении
  `IOptions<AiOptions>.Value`:
  1. парсит селектор **тем же** статическим методом, что и DI;
  2. для каждого параметра применяет правило приоритета (решение 2);
  3. **перезаписывает** `BaseUrl/Model/Timeout/Concurrency/ApiKey` значениями
     активного провайдера, `MinConfidence` — значением активного провайдера;
  4. пишет стартовый лог: `id`, `model`, `timeout`, `concurrency`,
     `min_confidence`, `configured=true|false` (**без** `ApiKey` и без полного
     `BaseUrl` — только признак наличия);
  5. выдаёт предупреждения (легаси/неизвестные ключи/конфликт/неиспользуемая
     секция).
- Значения читаются **напрямую из `IConfiguration`**, а не через биндинг отдельных
  секций: требуется различать «ключ отсутствует» и «ключ присутствует с пустым
  значением», а биндинг это различие теряет. Ошибки парсинга — единообразные, с
  указанием ключа.
- Регистрация: `AddOptions<AiOptions>().Bind(…).PostConfigure(…).Validate(…).ValidateOnStart()`
  (`ValidateOnStart` доступен в Infrastructure — пакет `Microsoft.Extensions.Options`
  9.0.9 уже подключён).
- **Следствие (важно для понимания):** все четыре существующих потребителя
  `AiOptions` (клиент, оркестратор, эндпоинт `suggest`, регистрация) получают
  параметры активного провайдера без единой правки кода. Поэтому:
  - `503`-гейт (`ReceiptCategorizationEndpoints.cs:42-47`) автоматически становится
    provider-aware: проверяется `BaseUrl` активного провайдера (FR-2.4);
  - лимит параллелизма семафора — `Concurrency` активного провайдера;
  - пустой `BaseUrl` активного провайдера ⇒ `503` и при `systemone`.

### 4. Новый провайдер: адаптер SystemOne

- Класс `SystemOneAiClient : IAiClient` в `Infrastructure/AI/`, регистрируется
  только при `AI:Provider=SystemOne` (решение 1).
- Конструктор симметричен существующему: `(HttpClient, IOptions<AiOptions>, ILogger<…>)` —
  «снимок активного провайдера» (решение E1).
- Запрос: `POST` на `AI:SystemOne:BaseUrl` (полный URL, решение 2),
  `Content-Type: application/json`, `Authorization: Bearer` при непустом `ApiKey`.
  Тело (**PROVISIONAL** — уточняется при взятии задачи в работу):
  `{"model": "…", "text": "<название товара>", "classes": ["Food", …]}`.
  Порог уверенности **не передаётся** движку и применяется на нашей стороне
  (решение 6).
- Ответ (**PROVISIONAL**): `{"category": "Food", "confidence": 0.87}`.
  Разбор: значение категории проходит **тот же** валидатор, что и в OpenAI-клиенте
  (вынесен в общий `CommodityCategoryParser`): не число, имя из реестра
  (`Enum.TryParse` ignoreCase + `Enum.IsDefined`), не `Undefined`. Иначе —
  `AiClientException` без ретрая → позиция неопределённая (FR-3.3).
- Уверенность: извлекается, если поле есть; применяется по решению 6.
- `MinConfidence` не применяется (дефолт 0) ⇒ поведение при любом корректном
  ответе максимально близко к текущему; «порог не задан» = edge case задачи
  закрыт явно.
- Защита от ненастроенного провайдера повторяет текущую: пустой `BaseUrl` →
  `InvalidOperationException` (страховка; эндпоинт уже отдал `503`).
- Ошибки: сеть/таймаут/`5xx` — временные (ретрай ×1, задержка 300 мс, как сейчас);
  `4xx`, нераспознанный payload, значение вне реестра, низкая уверенность —
  детерминированные (без ретрая, квоту не тратим).

### 5. Общий транспорт и схема наблюдаемости

- `AiHttpTransport` (общий): таймаут из конфигурации, ретрай ×1 на
  сеть/таймаут/`5xx` без ретрая на заведомо неверном ответе, маппинг исключений в
  существующую таксономию (`AiTransientException` → повтор, `AiClientException` →
  без повтора), измерение длительности и размеров. `AiTransientException`
  переносится из `OpenAiCompatibleAiClient.cs` в отдельный файл (сейчас он там по
  инерции).
- Обе реализации используют **одну** схему логов (метрики), одна запись на
  логический вызов:

| Поле | Тип | Источник | Примечание |
|---|---|---|---|
| `ai.provider` | string | константа адаптера | `openai` / `systemone` — единая метка для A/B-сравнения |
| `ai.model` | string | конфигурация | |
| `ai.outcome` | string | результат | `ok` / `failed` |
| `ai.reason` | string | результат | `network` / `timeout` / `http_5xx` / `http_4xx` / `invalid_response` / `low_confidence` / `not_configured` |
| `ai.duration_ms` | int | замер | суммарно, включая повторы |
| `ai.attempts` | int | счётчик | `1` или `2` |
| `ai.request_bytes` | int | размер тела | база оценки стоимости для SystemOne |
| `ai.response_bytes` | int | размер тела | |
| `ai.prompt_tokens` | int? | `usage` в ответе | OpenAI-совместимые; `null`, если провайдер не отдаёт |
| `ai.completion_tokens` | int? | `usage` в ответе | то же |
| `ai.confidence` | double? | ответ SystemOne | то же |

Пояснения к схеме:
- **FR-4.3 соблюдается:** в записи телеметрии нет имени товара, тела запроса и
  ключа. Имя товара по-прежнему пишется только в существующих предупреждениях
  (ретрай/ошибка) — не больше, чем сегодня.
- Уровень: успех — `Information` (иначе метрики не соберутся при дефолтном
  `Logging:LogLevel=Information`), сбой — `Warning`; при необходимости снижается
  конфигурацией, без правок кода.
- **Оценка стоимости (FR-4.2):** оператор получает для обоих провайдеров
  сопоставимые величины — время на запрос, число запросов, объём входа/выхода
  (байты; токены — когда провайдер их отдаёт). Денежная оценка получается
  умножением на прайс оператора; **код стоимость не считает** (см. F3).
- Оркестратор (`CommodityCategorizationService.cs:187`) добавляет в своё
  существующее предупреждение `{Provider}` — чтобы по логу позиции было видно,
  какой провайдер её обрабатывал.

### 6. Порог уверенности

| `MinConfidence` | Поведение |
|---|---|
| `0` (дефолт) | Порог **выключен**: корректный ответ принимается как есть (edge case «порог не задан») |
| `0 < t ≤ 1` | `confidence ≥ t` → категория предлагается; `confidence < t` → позиция неопределённая (`Undefined` + «AI категория не определена.») |
| Вне `0..1` / не число | Ошибка конфигурации на старте |

- Ответ **без** поля уверенности при `t > 0` трактуется как «недостаточно
  уверенно» (fail-closed): оператор явно попросил порог — игнорировать его молча
  нельзя. Условие громко проявится в логах (`reason = low_confidence` +
  `confidence = null`) и устраняется одним действием: `MinConfidence = 0`.
- Порог по умолчанию равен 0 сознательно: значения движка не откалиброваны под наши
  данные (edge case задачи), ненулевой дефолт рискует массово выдавать `Undefined`,
  что выглядело бы как поломка. Калибровка — в Бэклоге задачи; логи дают для неё
  распределение `ai.confidence`.
- Точность границы: «порог включительно» — `confidence == t` считается предложением.

### 7. Деградация: как сейчас, без авто-отката

- Недоступность движка (не поднят, таймаут, `5xx`, некорректный payload, слишком
  длинное название/лимит движка) ведёт к тому же результату, что и сегодня: общий
  ответ `200`, незакрытые позиции — `source = "undefined"` с пояснением, остальные
  позиции обработаны. Механизм не меняется: `catch (AiClientException)` в
  оркестраторе.
- **Автоматического отката на другой провайдер нет** (FR-3.5): переключение — только
  конфигурацией при старте. Основание: составной откат делает результат
  категоризации смесью двух движков, который нельзя интерпретировать ни
  пользователю, ни при сравнении метрик (главная цель задачи). Авто-откат — в
  Бэклоге задачи.
- Согласованно с этим: **не меняем** и предел параллелизма — семафор остаётся
  per-request (как сейчас), т.е. глобального лимита параллельности к движку нет.
  Если понадобится — отдельная задача.

### 8. Точки расширения (задел под п. 7 задачи)

Перечень параметров движка уточняется позже; решение закладывает расширение
**без изменения порта и без правок существующего провайдера**:

1. **Новые параметры уровня конфигурации** (`AI:SystemOne:*`): резолвер читает
   секцию по ключам — добавление поля = +1 строка в резолвере, +1 env в
   `docker-compose.yml`, +1 строка в документации. Ни порт, ни DI, ни клиент
   меняться не должны.
2. **Более богатая таксономия** (описания категорий, коды, группы): собирается внутри
   адаптера из `CommodityCategoryHelper` (решение B1); если не хватит данных — они
   добавляются в `Domain` как данные (решение B2), порт не меняется.
3. **Формат тела/ответа**: единственное место, требующее правки при уточнении
   протокола, — построение запроса и разбор ответа в `SystemOneAiClient`; общий
   транспорт, порт, оркестратор, эндпоинт и фронтенд не затрагиваются.
4. **Per-request параметры**, если протокол их потребует: порт получает
   необязательный параметр/объект запроса (изменение с исходной совместимостью) —
   осознанно **не делается сейчас** (A3, YAGNI); фиксируется как известный
   эволюционный шаг.
5. **Единицы потребления движка** (если он их сообщает): в схему логов добавляется
   одно поле; схема построена аддитивно, обратная совместимость не нарушается.

## Компромиссы

- **Снимок активного провайдера в `AiOptions` (E1) вместо нового типа (E2).** Плюс —
  ноль правок в `Api`/`Application`/клиенте и в их тестах. Минус — тип совмещает три
  роли (селектор/легаси/снимок), и отладчик, читающий `AiOptions`, должен знать, что
  значения принадлежат **активному** провайдеру. Компенсация: XML-документация
  класса, стартовый лог, тесты резолвера, эволюционный путь — при появлении третьего
  типа настроек перейти на `AiProviderSettings` (правка 3–4 сигнатур конструкторов).
- **Легаси-ключи живут бессрочно, но предупреждают.** Плюс — нулевой риск для
  текущих установок. Минус — две схемы в конфигурации. Выбор миграции (перенос
  `AI__*` → `AI__OpenAi__*`) делается оператором по warning'у; удалять легаси —
  отдельная задача с объявлением.
- **Правило «присутствие ключа важнее значения».** Плюс — сохраняет существующий
  выключатель «пустой `AI__BaseUrl`» (это и было причиной отклонить
  «непустое-приоритетно»). Минус — наивное добавление `AI__OpenAi__*` в compose
  молча выключит AI; закрыто запретом добавлять эти строки + предупреждением о
  конфликте.
- **Дефолт `MinConfidence = 0`.** Плюс — нет риска массового `Undefined` на
  некалиброванных значениях, поведение «как сейчас». Минус — из коробки порог не
  работает, т.е. FR-3.4 включается только явной настройкой. Альтернатива
  (ненулевой дефолт) отклонена: неоткалиброванная уверенность сделала бы
  неопределённым значительную долю позиций и выглядела бы как дефект внедрения.
- **Дефолт `AI:SystemOne:Concurrency = 1`.** Плюс — безопасность для
  последовательного движка (нет очереди и таймаутов). Минус — на параллельном
  движке первая проверка медленнее потенциального. Правится одной переменной,
  измеряется по FR-4.1.
- **Логи вместо метрик (F1).** Плюс — ноль новых зависимостей, ровно то, что
  требует FR-4.1/4.2. Минус — нет перцентилей и агрегаций без внешнего сборщика;
  схема полей при этом спроектирована для последующего переезда на метрики.
- **Провенантный минимум по протоколу SystemOne.** Тело/ответ запроса — единственное
  место, зависящее от неутверждённого контракта движка. Изоляция этого места —
  сознательная цена за то, что переключение и всё остальное не меняется при
  уточнении протокола.
- **Предел параллелизма остаётся per-request.** Плюс — ноль изменений поведения и
  тестов. Минус — глобальной защиты движка от перегрузки нет; при multi-request
  нагрузке ограничение ослаблено. Осознанно (вне scope задачи).

## Последствия

### Положительные

- Оператор может переключить категоризацию между двумя движками конфигурацией и
  **измерить** разницу: по логам видно время на запрос, число попыток, объём
  входа/выхода (и токены, когда провайдер их отдаёт) по метке `ai.provider`.
- Инфраструктурная часть решения (схема конфигурации, транспорт, телеметрия,
  валидация) сделана провайдер-независимой: третий движок = секция + ветка
  регистрации + адаптер, без изменений порта, API-контрактов, БД и фронтенда.
- Время и стоимость отдельного запроса к ИИ впервые измеримы — закрывается
  исходная претензия задачи «сравнить нечем».
- Ноль изменений в `Domain`, `Application`, `Api` и в ожиданиях существующих тестов.

### Отрицательные

- Конфигурация `AI` усложняется: селектор + две вложенные секции + легаси-слой
  (5 ключей) с правилом приоритета. Требуется аккуратная документация (ADR, README,
  `.env.example`, `AGENTS.md`) и дисциплина в `docker-compose.yml`.
- `AiOptions` приобретает неочевидную семантику «снимок активного провайдера»
  (компромисс E1) — риск неверного понимания при чтении кода.
- Тип `AiOptions` получает поле `MinConfidence`, осмысленное только для одного
  провайдера (следствие единого снимка).
- Каждая категоризация чека добавляет одну запись телеметрии на позицию (рост
  объёма логов при `Information`); снижается конфигурацией.
- Падение старта при опечатке в `AI__Provider` — намеренная строгость (FR-1.4),
  но в проде это рестарт-цикл, а не «мягкая» ошибка.

### Риски

| Риск | Митигация |
|---|---|
| Опечатка в `AI__Provider` → падение старта, рестарт-цикл | Дефолт `${AI__Provider:-OpenAi}` в `docker-compose.yml`; сообщение об ошибке перечисляет допустимые значения; тест резолвера |
| Наивное добавление `AI__OpenAi__*` в compose перекроет легаси `AI__BaseUrl` пустым значением и молча выключит AI | Строки `AI__OpenAi__*` в compose не добавляются (решение 2); конфликт «новый пустой vs легаси непустой» → `Warning` при старте |
| `AI:Provider=SystemOne`, но `AI:SystemOne:BaseUrl` пуст → `503` | Ожидаемое поведение (FR-2.4); причина видна в ответе и в стартовом логе |
| Протокол движка уточнится и не совпадёт с provisional-форматом | Правка локализована в `SystemOneAiClient` (построение запроса/разбор ответа); порт, API, БД, фронт не затрагиваются; схема логов аддитивна |
| Уверенность движка некалибрована → либо массовый `Undefined`, либо мусор | Дефолт 0 (порог выключен); порог настраивается; логи `ai.confidence` дают данные для калибровки (в Бэклоге задачи) |
| Кэш категорий общий для обоих провайдеров → сравнение A/B «засорено» данными, полученными от предыдущего провайдера | Это поведение ADR 019, не меняется. Для честного замера: замерять на «холодном» кэше (`CommodityCategoryCache__MaxSize=0`) либо на позициях с уникальными названиями; зафиксировать в инструкции замера |
| Перегрузка движка (последовательная обработка) → долгий ответ `suggest` | Поведение для пользователя прежнее (частичный результат, `200`); `Concurrency` и `Timeout` конфигурируемы; дефолт `Concurrency=1` не создаёт очередь |
| Правка проверенного `OpenAiCompatibleAiClient` (вынос транспорта/валидатора) → регрессия | Покрыт 14 тестами через stub-handler; `dotnet test` — критерий приёмки; поведение сознательно не меняется |
| Новые зависимости не добавляются | Метрики — логами; внешние SDK — нет (ADR 009, решение F1); проверяется ревью |

## Открытые вопросы

1. **Перечень параметров движка (п. 7 / FR-2.3 задачи)** — будет уточняться при
   взятии задачи в работу. Сейчас обязательны `BaseUrl`, `Model`, `Timeout`,
   `Concurrency`, `ApiKey`, `MinConfidence`; точка расширения — решение 8 (1).
   Вероятные кандидаты: лимиты длины входа, `top-k`/температура, языки, версия
   схемы — ни один не спроектирован заранее.
2. **Формат `confidence`**: приходит ли в шкале `0..1` или в процентах `0..100`?
   Сейчас предполагается `0..1`; значение вне диапазона при включённом пороге
   трактуется как нераспознанный ответ. Уточнить вместе с протоколом.
3. **Точная схема запроса/ответа** (имена полей, наличие `model`, обязательность
   `confidence`, формат ошибок) — provisional, см. решение 4.
4. **Совпадает ли `BaseUrl` движка с полным URL эндпоинта** (решение 2) — если у
   движка есть корневой адрес и фиксированный путь, добавляется один параметр
   (`Path`) в резолвере; порт и клиент не меняются.
5. **Сообщает ли движок свою единицу потребления** (кредиты/вызовы/символы) — если
   да, добавляется одно поле в схему логов (аддитивно).
6. **Нужен ли авто-откат между провайдерами** — сейчас сознательно нет (FR-3.5),
   вопрос в Бэклоге задачи.
7. **Когда удалять легаси-ключи `AI__*`** — после того, как оператор переведёт их в
   `AI:OpenAi:*`; отдельная задача с объявлением в README/`.env.example`.
8. **Реализация плана** — декомпозиция ADR-026 на задачи для разработчиков с

   `docs/plans/` при взятии задачи в работу.
