# ADR-030: Рабочее окно фоновой предкатегоризации товаров

## Статус

Принято (проект). Основание — требование заказчика от 2026-10-26: фоновая ИИ-категоризация
должна работать только в наиболее свободное время, заданное в конфигурации; вне этого окна
активность не проверяется и сессии не запускаются.

**Дополняет, ничего не отменяет:** [ADR-027](027-background-commodity-precategorization.md)
(сам фоновый сервис, очередь `precategorized_commodities`, условие простоя, `Precategorization:*`),
[ADR 009](009-auto-commodity-categorization.md) и
[ADR 026](026-switchable-commodity-categorization-provider.md) (контракт `IAiClient` — не меняются),
[ADR 021](021-env-vars-passthrough-docker-compose.md) (проброс env в `docker-compose.yml`).

> **Вне области:** изменения расписания синхронизации чеков и других фоновых сервисов; несколько
> экземпляров Analytics и распределённая блокировка; изменения БД/схемы, API и webUI; рабочий
> календарь (выходные, праздники) и несколько окон в сутки.

## Контекст

### Проблема

По ADR-027 сервис `PrecategorizationBackgroundService` каждые `IdleCheckInterval` (по умолчанию
30 с) проверяет простой Analytics API и при отсутствии HTTP-запросов в течение `IdleTimeout`
запускает сессию ИИ-категоризации. Проверка и запуск выполняются **круглосуточно**: даже при
рабочем дне пользователи могут застать ИИ-нагрузку, а администратор не может сказать «фон
работает только ночью».

Требуется:

1. Задать в конфигурации **время начала и время окончания** ежедневного окна.
2. Проверять активность и запускать сессии **только внутри** окна.
3. Не терять уже оплаченный результат ИИ, если окно закрылось во время сессии.

### Текущее состояние кода (факты, проверены по коду 2026-10-26)

## Решение

Сводка:

1. **D1.** Три новые опции: `WorkWindowStart`, `WorkWindowEnd` (время суток, `TimeSpan?`) и
   `WorkWindowTimeZone` (IANA/Windows id, `string?`; пусто — локальное время сервера).
2. **D2.** Окно задаётся **обеими** границами или не задаётся вовсе. Не задано — фон работает
   круглосуточно, как до ADR-030 (обратная совместимость по умолчанию в коде).
3. **D3.** Семантика — полуинтервал `[Start, End)`; `Start > End` — окно через полночь;
   `Start == End` — ошибка старта (для 24/7 нужно не задавать окно).
4. **D4.** Вне окна `IApiActivityMonitor.IsIdle` не вызывается и сессия не стартует. Внутри —
   прежнее условие `IsIdle(IdleTimeout)`.
5. **D5.** Сессия проверяет окно перед каждой позицией и после обработки текущей. Если окно
   закрылось, сессия завершается с причиной `window_closed` после сохранения результата текущей
   позиции; незавершённые кандидаты остаются на следующий день.
6. **D6.** Часовой пояс разрешается один раз при старте; невалидный id — ошибка запуска.
   Внутри окна используется `TimeZoneInfo.ConvertTime(utcNow, zone)`, при пустом поясе —
   `TimeProvider.GetLocalNow()`.
7. **D7.** Валидация на старте: только одна граница, граница вне `[00:00, 24:00)`, равные
   границы, невалидный часовой пояс — `OptionsValidationException` (NFR-7).
8. **D8.** Конфигурация пробрасывается по ADR-021: `appsettings.json`, env
   `Precategorization__*`, `docker-compose.yml` (с `:-`-дефолтами), `.env.example`, `AGENTS.md`.
   В `appsettings.json`/`docker-compose.yml` дефолт — `02:00:00`–`06:00:00` `Europe/Moscow`.
9. **D9.** Логирование: стартовый лог содержит описание окна (или `not configured`); выход за
   окно логируется на уровне `Debug` (без спама каждые 30 с); завершение сессии по окну —
   `Reason: window_closed` в существующем итоговом логе.

### D1–D3. Модель окна и границы

```jsonc
"Precategorization": {
  "WorkWindowStart": "02:00:00",       // локальное время в WorkWindowTimeZone
  "WorkWindowEnd":   "06:00:00",       // не включается
  "WorkWindowTimeZone": "Europe/Moscow"
}
```

- Обе границы — **время суток**, а не длительность; формат `TimeSpan` выбран потому, что он уже
  используется для всех таймаутов секции и одинаково биндится из JSON/env без дополнительных
  конвертеров.
- `TimeZone` важен: контейнер Analytics живёт в UTC, поэтому без явного пояса «ночное» окно
  заказчика сместилось бы на 3 часа. Пустое значение сохраняет поведение «локальное время
  сервера» для не-контейнерных запусков, но в Docker пояс следует задавать явно.
- Окно через полночь (`23:00`–`06:00`) поддерживается: сравнение идёт по `TimeOfDay`, а не по
  абсолютной дате.

### D4–D5. Влияние на жизненный цикл сервиса

```
while (!stopping) {
    if (window open) {
        if (IsIdle(IdleTimeout)) RunSession();   // внутри сессии окно проверяется ещё раз
    }
    await Delay(IdleCheckInterval);
}
```

- Вне окна монитор активности не опрашивается — это буквальное исполнение требования «только в
  это время проверяется наличие активности».
- Внутри сессии окно проверяется до вызова ИИ и после сохранения позиции. Проверка после
  обработки не даёт «съесть» остаток лимита, если окно закрылось во время долгого вызова ИИ;
  проверка перед позицией закрывает разрыв, возникший за время `IntervalBetweenCalls`.
- Курсор (`CandidateCursor`) и `BatchLimit` не меняются: незавершённые кандидаты будут взяты в
  следующую ночь, начиная с последнего обработанного.
- Если окно закрылось, `stopReason = "window_closed"` попадает в существующий лог
  `Precategorization session finished` — диагностика без новых метрик.

### D6–D7. Часовой пояс и валидация

- `WorkWindowTimeZone` разрешается в конструкторе сервиса; повторное разрешение на каждом цикле
  не требуется (`IOptions`, не `IOptionsMonitor`). Ошибка id — `InvalidOperationException` с
  именем параметра (обычно срабатывает раньше как `OptionsValidationException`).
- Валидация (`ValidateOnStart`) не даёт тихо деградировать: без неё опечатка в поясе означала бы
  падение фонового сервиса уже после старта API, а `Start == End` — неопределённое окно.
- При пустом поясе используется `TimeProvider.GetLocalNow()` — источник времени остаётся
  внедряемым (NFR-9), тесты не зависят от часов машины.

### D8. Конфигурация

| Параметр | Дефолт в коде | Дефолт в `appsettings.json` | Смысл |
|---|---|---|---|
| `Precategorization:WorkWindowStart` | не задан | `02:00:00` | начало окна (включительно) |
| `Precategorization:WorkWindowEnd` | не задан | `06:00:00` | конец окна (не включается) |
| `Precategorization:WorkWindowTimeZone` | не задан | `Europe/Moscow` | пояс границ; пусто — локальное время сервера |

Env-переменные: `Precategorization__WorkWindowStart`, `Precategorization__WorkWindowEnd`,
`Precategorization__WorkWindowTimeZone`; в `docker-compose.yml` — с теми же `:-`-дефолтами.

### D9. Наблюдаемость

- Старт: `... WorkWindow: 02:00:00–06:00:00 (Europe/Moscow)` или
  `... WorkWindow: not configured (around the clock)`.
- Вне окна: `Debug`-сообщение (по умолчанию не видно) — нет спама в `Information`.
- Закрытие окна во время сессии: `Reason: window_closed` в итоговой строке сессии; уже
  сохранённые предложения не откатываются.

## Последствия

### Положительные

- Заказчик управляет временем ИИ-нагрузки без пересборки; окно можно менять через `.env`.
- Результат оплаченного вызова ИИ сохраняется даже при закрытии окна или остановке хоста.
- Поведение по умолчанию в коде не меняется: без новых параметров фон работает как раньше.
- Часовой пояс задаётся явно — окно не «плывёт» из-за UTC в контейнере.

### Отрицательные / компромиссы

- Одно окно в сутки; несколько интервалов, выходные и праздники не поддерживаются (вне области).
- В `appsettings.json` и `docker-compose.yml` появился конкретный дефолт `02:00–06:00`
  `Europe/Moscow`: при развёртывании в другом регионе его нужно переопределить.
- Пустой `WorkWindowTimeZone` в Docker означает UTC — это задокументировано; валидация не может
  отличить «осознанно UTC» от «забыли пояс».
- Между закрытием окна и завершением сессии возможен ещё один вызов ИИ (текущая позиция) —
  сознательный выбор в пользу сохранения уже начатой работы.

## Рассмотренные альтернативы

### A. `TimeOnly` вместо `TimeSpan?`

Семантически точнее, но биндинг `TimeOnly` из конфигурации менее предсказуем, а вся секция уже
использует `TimeSpan`. Отклонено ради единообразия и отсутствия новых конвертеров.

### B. Окно в UTC без часового пояса

Проще, но заказчик мыслит местным временем; в контейнере UTC ошибка была бы незаметной.
Отклонено.

### C. Глобальный `TZ=Europe/Moscow` у контейнера вместо отдельной опции

Меняет все логи и другие фоновые сервисы, а не только окно; для локализованного решения слишком
широко. Отклонено.

### D. Немедленное прерывание текущего вызова ИИ при закрытии окна

Экономит один вызов, но отменяет уже оплаченный запрос и теряет результат. Отклонено в пользу
«завершить текущую позицию».
