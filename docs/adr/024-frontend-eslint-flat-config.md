# ADR-024: Починка ESLint-конфига фронтенда (flat-пресет) и ворота линтинга в CI

## Статус

Принято

## Контекст

`npm run lint` в `Analytics/frontend` завершается с **exit 2** (код внутренней
ошибки конфигурации, а не код нарушения правил) до анализа какого-либо файла —
воспроизводится в том числе на нетронутых файлах.

Проверенные факты (локально, `Analytics/frontend`):

| Компонент | Установленная версия |
|-----------|----------------------|
| `eslint` | 10.9.0 |
| `eslint-plugin-react-hooks` | 7.1.1 |
| `eslint-plugin-react-refresh` | 0.4.24 |
| `typescript-eslint` | 8.67.0 |
| `package-lock.json` | lockfileVersion 3 |
| Node.js локально / в `Analytics/Dockerfile:2` | v22.23.2 / `node:22-alpine` |

`npm run lint` не выполняется ни в одном workflow `.github/workflows/`: Node
появляется в пайплайне исключительно внутри стадии `frontend` файла
`Analytics/Dockerfile` (`RUN npm run build`). Поэтому правила фронтенда не
проверялись никогда, а поломка конфига осталась незамеченной.

## Корневая причина

`Analytics/frontend/eslint.config.js:15` подключает
`reactHooks.configs['recommended-latest']`. Это **legacy (eslintrc)-форма**
пресета — в плагине ветке `configs` (без `flat`):

```js
{ plugins: ['react-hooks'], rules: { /* ... */ } }
```

Flat-конфиг ESLint требует, чтобы `plugins` был **объектом**
(`{ 'react-hooks': pluginObject }`). Массив строк ESLint 10 отвергает жёстко, без
деградации и без частичного применения конфига — отсюда `exit 2` на любом входе.

Плагин поддерживает оба формата: в нём присутствует ветка `configs.flat`, где тот
же пресет лежит в корректной flat-форме.

`reactRefresh.configs.vite` у `eslint-plugin-react-refresh@0.4.24` уже
flat-совместим (`plugins` — объект) и правки не требует.

## Решение

### R1. Переключить пресет react-hooks на flat-вариант

```diff
-      reactHooks.configs['recommended-latest'],
+      reactHooks.configs.flat['recommended-latest'],
```

**Обоснование выбора между доступными flat-вариантами.** В `configs.flat` есть
`recommended-latest` (17 правил) и `recommended` (те же 16 правил, но **без**
`react-hooks/void-use-memo`). Единственное различие — `void-use-memo`. Автор
исходного конфига осознанно выбрал `recommended-latest`; flat-вариант с тем же
именем сохраняет этот выбор и не теряет ни одного правила. Вариант
`flat.recommended` — шаг назад по строгости без выигрыша.

**Почему не `FlatCompat`.** `FlatCompat` — адаптер для чужих eslintrc-конфигов,
недоступных в flat-форме. Здесь конфиг доступен нативно в том же пакете.
Адаптер добавил бы зависимость `@eslint/eslintrc` и лишнюю трансформацию без
какой-либо выгоды — нарушало бы FR-4.

### R2. Не трогать зависимости и `package-lock.json` (FR-4)

1. Корневая запись `packages[""]` в `package-lock.json` фиксирует только
   `name`, `version`, `dependencies`, `devDependencies`. Секция `scripts` в
   lockfile **не записывается**, поэтому правка скрипта `lint` структурно не
   может рассинхронизировать lock.
2. `npm ci` по спецификации никогда не пишет `package-lock.json` (в отличие от
   `npm install`).
3. Проблема локализована в одной строке конфига. Обновление `eslint` /
   `eslint-plugin-*` — самостоятельное решение с собственным риском (новые
   правила, изменения peer-требований) и в объём задачи не входит.

### R3. Сделать строгость одинаковой локально и в CI

`package.json`: `"lint": "eslint . --max-warnings 0"`.

Пресет `recommended-latest` содержит три правила уровня `warn`
(`exhaustive-deps`, `incompatible-library`, `unsupported-syntax`). Без
`--max-warnings 0` предупреждение не блокирует ни PR, ни коммит — ворота были бы
дырявыми. Флаг переносит правило «предупреждение = провал» из дисциплины автора
workflow в сам скрипт, то есть в единственное место, откуда его читают и
разработчик, и CI.

### R4. Встроить линтинг в существующий workflow, а не создавать новый

Триггеры `build-analytics-image.yml` уже покрывают фронтенд (`paths:
'Analytics/**'`), поэтому отдельный workflow не даёт ничего.

Отдельный job с `services:` вместо общего `build` не нужен: ESLint не требует
внешних сервисов, а `dotnet test` в этом же job'е поднимает postgres/mongo
контейнерами. Отдельный job потребовал бы второго `checkout` и дублирования
установки, но при этом **не** изолировал бы .NET-тесты от Node-шага: изоляция
job'ов означала бы, что .NET-тесты не запустятся вовсе, если setup-node упал
(шаг без `continue-on-error` валит весь job). Шаг Node вставляется инлайн в
существующий `build` — до `Setup .NET`, до поднятия контейнеров.

## Чем подтверждается работоспособность правил (FR-3)

Положительный `exit 0` сам по себе не доказывает, что правила активны: конфиг
мог бы молча ничего не применять. Поэтому контрольная проверка (FR-3) построена
на **двухконтрольной** схеме, выполняемой без единой записи в рабочее дерево:

- **Позитивный контроль** — во временный каталог вне репозитория пишется
  `.tsx`-файл с тремя намеренными нарушениями (по одному на семейство правил
  `react-hooks`, `react-refresh`, `typescript-eslint`), и подаётся в ESLint через
  `eslint --stdin --stdin-filename src/<probe>.tsx`. Ожидание: **exit 1** и
  три конкретных ID правил в выводе.
- **Негативный контроль** — тем же каналом подаётся заведомо чистый `.tsx`.
  Ожидание: **exit 0**. Это отсекает ситуацию «харнесс всегда красный», то есть
  ложноотрицательный результат проверки.

Почему `--stdin`, а не временный файл в `src/`:

- ESLint игнорирует `--config` в режиме `--stdin` и всегда загружает реальный
  `eslint.config.js` из cwd (проверено). Значит контрольная проверка по определению
  проверяет **коммитируемый** конфиг, а не подставную копию.
- В репозиторий не попадает ни одного байта: нечего забыть удалить, нечего
  случайно закоммитить, `git status` остаётся чистым.
- Временный `.tsx` внутри `src/` был бы включён в `tsc -b` (`tsconfig.app.json`
  содержит `"include": ["src"]` и `noUnusedLocals: true`) и мог бы сломать
  `npm run build`, если останется по ошибке.
- Проба обязана быть `.ts`/`.tsx`: конфиг объявляет `files: ['**/*.{ts,tsx}']`.

## Последствия

**Чинится.** `npm run lint` начинает работать. На текущем коде — 0 ошибок и
0 предупреждений, поэтому FR-6 не требует правок исходников.

**Новое покрытие отсутствует.** Из-за `files: ['**/*.{ts,tsx}']` файлы
`.js`/`.mjs` (включая сам `eslint.config.js`) не покрыты ни одним правилом:
ESLint их обходит, но ни один config-объект с правилами к ним не применяется.
Это не регрессия (было так же), но и не улучшение — и это отдельный предмет для
будущей задачи, а не для FR-4.

**Риски.** Правка локальна и обратима. Регрессионный риск для .NET-части нулевой
— .NET-шаги не меняются. Единственный новый риск — фронтенд-зависимости
устанавливаются в CI дополнительным `npm ci`; риск покрыт зеркальной проверкой
`npm ci` в `Analytics/Dockerfile:5` (тот же lock, та же команда).

**Остаточная точка тихой поломки.** Если кто-то снова подключит legacy-пресет,
это увидит только что-то. Единственная защита — CI-шаг линтинга, который падает
с `exit 2`. Автоматическая защита (тест конфига) в объём задачи не входит.
