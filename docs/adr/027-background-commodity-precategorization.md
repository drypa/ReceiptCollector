## Контекст

### Проблема

- Категоризация товаров выполняется только по действию пользователя на странице чека: пока чек
  не открыт и не нажата «Категоризировать», товары остаются без категории, аналитика неполная.
- ИИ-категоризация — платная и небыстрая операция. Её логично выполнять, когда Analytics простаивает
  (нет HTTP-запросов), чтобы не мешать пользователям и не конкурировать за ИИ.
- Результат фоновой ИИ-категоризации нельзя сразу писать в `commodities`: ошибки модели нужно
  отфильтровать человеком. Нужен промежуточный слой «предложенные категории» и админский раздел,
  где предложения подтверждаются, исправляются или отклоняются.
- Подтверждение должно применяться массово ко всем некатегоризированным товарам с **точно таким же**
  наименованием у **всех** пользователей — вручную это сделать невозможно.
- In-memory кэш (ADR 019) предотвращает повторные вызовы ИИ, но наполняется только из уже
  категоризированных товаров; фоновый процесс не должен обходить кэш и существующие приоритеты.

## Решение

Сводка принятых решений:

1. Простой — глобальный, по последней HTTP-активности с исключённым `/health` (middleware + монитор).
2. Фон и админский API работают с товарами **всех** пользователей (`IgnoreQueryFilters()`, без query-filter на новой сущности).
3. Новая таблица `precategorized_commodities` — очередь предложений; индексы только на ней, индексы на `commodities` — отложенное решение.
4. Статусы `proposed`/`applied`; подтверждение — транзакция с массовым обновлением `commodities` и записью в кэш; отклонение — физическое удаление.
5. Единый порядок проверок: ручной путь — `existing → cache → precategorized → ai`; фон — глобальный existing-запрос → cache → ai.
6. Курсор сессий по последнему обработанному кандидату (in-memory, сброс при рестарте).
7. Стиль ошибок API — эталон `MerchantEndpoints` (текстовые тела, без ProblemDetails).
8. Конфигурация `Precategorization:*` без пересборки; внедряемое время (`TimeProvider`/`FakeTimeProvider`).
9. Single instance; при смене провайдера ИИ (ADR-026) фон не ломается — работа через `IAiClient`.

### 1. Детектирование простоя: `RequestActivityMiddleware` + `IApiActivityMonitor` (C1, D3, FR-1)

- Новый контракт в Application: `IApiActivityMonitor { void Touch(); DateTimeOffset LastActivityUtc { get; } bool IsIdle(TimeSpan threshold); }`.
  Реализация `ApiActivityMonitor` — потокобезопасный Singleton (`Interlocked`/`Volatile` на timestamp, O(1), без I/O и блокировок — FR-1.4).
- Новый `Api/Middleware/RequestActivityMiddleware.cs` обновляет монитор (`Touch`) на **каждом**
  HTTP-запросе, проходящем через pipeline, кроме исключённых путей. Регистрация в `Program.cs`
  **до `UseStaticFiles()`** (сразу после `UseHttpsRedirection()`): активностью считаются и статика,
  и загрузка SPA, и API-запросы — включая неаутентифицированные (D3: мониторинг инфраструктуры и
  open-пробники не должны выглядеть как «тишина», если пришёл любой реальный трафик).
- Исключённый путь — `/health` (D3): health-пробник мониторинга не сбрасывает таймер простоя,
  иначе фон никогда не запустится. Список исключений реализуется расширяемым предикатом по
  `HttpContext.Request.Path` (без переписывания логики при добавлении новых пробников — FR-1.2,
  риск 8: пробники, приходящие не на `/health`, продолжат блокировать фон, и это ожидаемо).
- «Простой» = с последней активности прошло ≥ `Precategorization:IdleTimeout` (по умолчанию 5 минут);
  если запросов не было с момента старта — отсчёт от старта сервиса (FR-1.3).
- При `Precategorization:Enabled = false` фоновый сервис не запускает сессии и не пишет в таблицу,
  но middleware, монитор и админский раздел работают — накопленные строки обрабатываются (FR-1.5, FR-9.7).

### 2. Глобальный доступ к данным: `IgnoreQueryFilters()` на `ReceiptEntity`-запросах (C2, D8, NFR-5)

- Фоновая выборка кандидатов и админский confirm обновляют товары **всех** пользователей.
  Реализация: отдельные репозиторные методы (`PrecategorizedCommodityRepository` + запросы
  existing-шага фона) используют `IgnoreQueryFilters()` на `ReceiptDbContext.Receipts` с явным
  комментарием вида «доступ вне owner-scoping намеренный: фоновая предкатегоризация и админский
  workflow обрабатывают данные всех пользователей (ADR-027, D8)».
- Существующий query-filter остаётся на `ReceiptEntity`, существующие owner-scoped запросы
  (`ReceiptRepository`, `CommodityReadService`) **не меняются** (NFR-5); Architecture-тесты
  (`ProjectDependencyTests`) проходят без ослабления правил.
- Техническая деталь: фильтр `CurrentUserId == null || r.UserId == CurrentUserId` при
  неустановленном пользователе и так пропускает все строки (глобальные read-запросы вне контекста
  запроса, например наполнение кэша в ADR-019, работают без `IgnoreQueryFilters`). Тем не менее
  новые **фоново-админские** методы обязаны использовать `IgnoreQueryFilters()` явно: это
  самодокументируемый маркер намерения, устойчивый к будущему изменению семантики фильтра, и
  видимая точка для ревью (grep `IgnoreQueryFilters` → ровно места глобального доступа).
- Query-filter на новую сущность `PrecategorizedCommodityEntity` **не ставится**: очередь общая для
  всех пользователей; фильтрация — только по статусу/поиску в самих запросах.

### 3. Таблица `precategorized_commodities` и миграция (C3, D2, D9, FR-4.1, NFR-6)

Миграция — SQL-скрипт `20261023120000_add_precategorized_commodities.sql` в
`ReceiptCollector.Analytics.Migrations/Scripts`, применяется `MigrationRunner`
(транзакция на скрипт, учёт в `migration_scripts_history` — повторный запуск идемпотентен).

```sql
CREATE TABLE precategorized_commodities
(
    id                    uuid PRIMARY KEY,
    name                  varchar(256) NOT NULL,           -- точное наименование, как commodities.name
    merchant_id           uuid         NOT NULL,           -- магазин для контекста админу
    proposed_category_id  integer      NOT NULL,           -- CommodityCategory, != 0 (Undefined)
    status                smallint     NOT NULL DEFAULT 0, -- 0 = proposed, 1 = applied
    created_at            timestamptz  NOT NULL DEFAULT now(),
    applied_at            timestamptz,
    CONSTRAINT fk_precategorized_commodities_merchants
        FOREIGN KEY (merchant_id) REFERENCES merchants (id) ON DELETE CASCADE,
    CONSTRAINT ck_precategorized_commodities_status CHECK (status IN (0, 1))
);

-- Уникальность пары (точное наименование, магазин) — C3.
CREATE UNIQUE INDEX ux_precategorized_commodities_name_merchant
    ON precategorized_commodities (name, merchant_id);

-- Индекс по статусу — выборка очереди админа и исключения FR-3.2/3.4.
CREATE INDEX ix_precategorized_commodities_status
    ON precategorized_commodities (status, created_at);
```

- Уникальность строки — пара **(точное наименование, магазин)** (C3): магазин хранится для контекста
  админу, подтверждение применяется по наименованию. Запрет дублей по имени при разных магазинах —
  на уровне сервиса (D7, FR-3.4), не в БД.
- **`ON DELETE CASCADE` для магазина — сознательно иначе, чем `RESTRICT` у `receipts`**
  (в `20241019160000_initial_create.sql` — `fk_receipts_merchants ON DELETE RESTRICT`): строка
  предложения — производная данных, а не первичный бизнес-объект; удаление магазина не должно
  блокироваться зависимыми предложениями. При удалении магазина его `proposed`-строки исчезают
  безвозвратно — и это корректно: ИИ предложит их заново в следующем простое.
- `status` — `smallint` + `CHECK`, отображается на enum
  `PrecategorizedCommodityStatus { Proposed = 0, Applied = 1 }`; wire-имена в API — `proposed`/`applied`.
- **Денормализованное имя категории не хранится** (D9): отображаемое имя вычисляется через
  `CommodityCategoryHelper.GetDisplayName` — иначе оно устареет при переименовании категорий
  (прецедент — миграция `20260807135439_fix_commodity_category_food_name.sql`).
- EF: `PrecategorizedCommodityEntity` + `PrecategorizedCommodityConfiguration` в
  `Infrastructure/Persistence/Postgres`, `DbSet` + `ApplyConfiguration` в `ReceiptDbContext`
  (snake_case уже настроен `UseSnakeCaseNamingConvention`).

**Индексы на `commodities` НЕ создаются — отложенное решение.** Выборка кандидатов требует
DISTINCT `(name, merchant_id)` через join `commodities → receipts → merchants` (прямой ссылки
commodity → merchant нет), поэтому состав индексов заранее не очевиден: и `(name, category_id)`,
и `receipt_id`-варианты дают лишь частичное ускорение. Зафиксировано обязательство: по результатам
эксплуатации замерить фактические планы запросов выборки кандидатов и подтверждения и выбрать
применимые индексы **отдельным решением/ADR** (бэклог задачи, риск 6). Текущее ожидание —
Seq Scan по отфильтрованному множеству (`category_id IS NULL OR 0`); это осознанное ограничение,
митигируемое выключателем `Precategorization:Enabled` (деградация → фон отключается без релиза).

### 4. Статусы и workflow предложений (C4, D2, D10, D11, FR-5, FR-6)

Жизненный цикл строки: `proposed` (создано фоном при валидном предложении) → `applied`
(подтверждено админом) либо **удалено** (отклонено админом). Промежуточных/возвратных статусов нет.

- **Подтверждение (`POST .../{id}/confirm`) — одна транзакция БД** (D10, FR-6.5):
  1. обновление `commodities`: **все пользователи**, `name = :name` (точное сравнение БД, без
     нормализации/`lower`), только `category_id IS NULL OR category_id = 0` (содержательные
     категории не перезаписываются; `0`/`Undefined` трактуется как «категории нет», D11);
     записываются `category_id` **и** `category_name` (`CommodityCategoryHelper.GetDisplayName`) —
     как в `CommodityRepository.UpdateCategoryAsync` (FR-6.2);
  2. перевод строки в `applied` (`status = 1`, `applied_at = now()`);
  3. удаление «сестринских» `proposed`-строк с тем же точным наименованием;
  4. `ICommodityCategoryCache.TryAdd(normalizedName, category)` — после фиксации транзакции;
     first-wins/no-op при «замороженном» кэше — существующая семантика ADR-019 (FR-6.4).
  Откат при ошибке — строка остаётся `proposed`. Ответ содержит `updatedCommodities`, которое
  может быть `0` (все товары с таким именем уже категоризированы) — строка всё равно переводится
  в `applied` (D10).
- **Подтверждённые строки (`applied`) хранятся бессрочно** (D2): (а) журнал действий админа,
  (б) защита от повторного предложения той же пары (пара из таблицы в любом статусе — не кандидат,
  **приоритет FR-3.2 над FR-3.3** — иначе вставка упрётся в unique-индекс), (в) основание индекса
  по статусу. Обратная сторона — пара с `applied`-строкой навсегда исключена из фоновой
  категоризации, даже если категорию позже сбросили вручную (риск 7, принят заказчиком;
  повторное применение — бэклог).
- **Отклонение (`DELETE .../{id}`) — физическое удаление** строки (C4); `commodities` не меняются.
  При следующем простое ИИ может снова предложить категорию для этого наименования.
- **Валидация категории** (FR-5.6, D11): `Enum.IsDefined(CommodityCategory)` и значение ≠
  `Undefined`; иначе `400`. Изменение предложения на `Undefined` запрещено.
- Операции над строкой в статусе `applied` → `409 Conflict`; над несуществующей → `404` (FR-5.7);
  повторный `confirm` идемпотентен по данным (вторая попытка → `409`, FR-5.8).
- Изменение предложенной категории (`PUT .../{id}/category`) не трогает `commodities` (UC-3).

### 5. Единый порядок проверок: existing → cache → precategorized → ai (D1, D13, FR-3, FR-9)

- **Ручной путь** (`CommodityCategorizationService.SuggestForReceiptAsync`) — порядок становится:
  `existing` (категория **самого товара**, без изменений) → `cache` (ADR-019, без изменений) →
  `precategorized` (**новый шаг**) → `ai` (без изменений). Единственное изменение контракта —
  аддитивное значение `source = "precategorized"` в `CategorizationSource`/`CategorizationSourceNames`
  (wire-имя `precategorized`, FR-9.4).
- Поиск по очереди — по **точному** наименованию (`name = :name`, без нормализации) в **любом**
  статусе строки (`proposed`/`applied`); при нескольких строках с одним наименованием берётся
  самая свежая (по `created_at`/`applied_at`); категория строки дополнительно проверяется
  `Enum.IsDefined` (защита от значения, удалённого из реестра — ср.
  `fix_commodity_category_food_name`): если не определена, позиция идёт дальше по обычному
  порядку без ошибки запроса (FR-9.2). Магазин не учитывается — подтверждение применяется по имени.
- Поиск по очереди — **один batch-запрос** на чек по множеству различных наименований, которым не
  нашлось категории на `existing`/`cache`; N+1 запрещён (FR-9.3). `suggest` остаётся read-only
  (FR-9.5); ошибка чтения очереди — Warning + деградация к ИИ вместо `500` (FR-9.6). Строка очереди
  от пользовательского сохранения не меняется — судьбу решает админ (UC-6).
- **Фоновый путь**: шаг `existing` — **новый глобальный запрос** по точному наименованию среди
  товаров **всех** пользователей (`IgnoreQueryFilters()`, п. 2), а не переиспользование existing-шага
  ручного пути (тот смотрит категорию самого товара). Затем in-memory кэш
  (`CommodityNameNormalizer`), только потом ИИ (D1). При попадании в existing/кэш строка создаётся
  с этой категорией **без вызова ИИ** (FR-4.3) — предложение всё равно проходит через админский
  workflow, ИИ не расходуется.
- Приоритеты внутри выборки кандидатов фона: `FR-3.2` (пара в таблице в любом статусе → исключена)
  выше `FR-3.3` (имя с категоризированным товаром у другого магазина → кандидат с известной
  категорией без вызова ИИ)
  выше `FR-3.4` (есть `proposed` у другого магазина → исключена) выше `FR-3.6` (кэш) выше ИИ.

### 6. Фоновый сервис: сессия, лимиты, курсор (C5, D4–D7, D12, D14, FR-2, FR-3, FR-4, FR-8)

`PrecategorizationBackgroundService` (`BackgroundService`, Infrastructure) — по паттерну
`ReceiptSynchronizationHostedService` (scope на цикл, ошибки не валят процесс, graceful shutdown;
FR-2.7, FR-2.8). Схема сессии:

1. Цикл проверяет простое с периодом `IdleCheckInterval` (30 с), без busy-loop (FR-2.1).
2. При простое ≥ `IdleTimeout` начинается сессия: выборка кандидатов — различные пары
   `(name, merchant_id)` по товарам всех пользователей с `category_id IS NULL OR 0`, с исключениями
   FR-3.2–FR-3.4, детерминированный порядок (например, `name`, `merchant_id` — FR-3.5), начиная
   **после курсора последнего обработанного кандидата** предыдущей сессии (D14).
3. Обработка строго последовательная, по одной позиции (D4, FR-2.2): existing-запрос → кэш → ИИ;
   пауза `IntervalBetweenCalls` после каждого **вызова ИИ** (для позиций, обслуженных existing/кэшем,
   пауза не нужна — FR-2.4).
4. Перед каждой следующей позицией — проверка активности: появился HTTP-запрос → сессия
   завершается **после текущей позиции** (начатый вызов ИИ доводится до конца, результат
   сохраняется; новые позиции не берутся — FR-2.5, C5). Максимальная задержка остановки =
   длительность текущего вызова ИИ (≤ `AI:Timeout`, в `appsettings.json` фактически 80 с — риск 1;
   отмена текущего вызова по сигналу активности возможна как будущее ужесточение, по умолчанию —
   «дойти до конца текущей позиции»).
5. Лимит сессии — `BatchLimit` позиций (5 по умолчанию; FR-2.3).
6. `Undefined`/ошибки ИИ строку **не создают** (D6, FR-4.4) — только лог; кандидат остаётся
   необработанным, но двигает курсор (см. ниже). Конфликт unique `(name, merchant_id)`
   (параллельная вставка) игнорируется — сессия не падает (FR-4.5). `commodities` в фоне не
   изменяются (FR-4.6). Наименования длиннее `varchar(256)`/пустые — пропуск с предупреждением (FR-4.7).
7. Если ИИ не настроен (`AI:BaseUrl` пуст) — фон не вызывает ИИ, но создаёт предложения из
   кэша/глобального existing-запроса; факт — Warning (D5).
8. Наблюдаемость (FR-8): старт/стоп сессии с причиной (лимит/активность/нет кандидатов/остановка
   хоста), число кандидатов/созданных предложений/ошибок ИИ, длительность сессии; по каждому вызову
   ИИ — длительность и результат; без ПД пользователей (userId в фоновых логах не используется).

**Курсор сессий (D14).** Сессия выставляет курсор на **последнего обработанного кандидата** —
включая кандидата, для которого строка не создалась (`Undefined`, ошибка ИИ, пропуск по FR-4.7).
Иначе такой кандидат не попадает в исключения FR-3.2/3.4, остаётся первым в детерминированном
порядке, и каждая сессия упирается в него же (head-of-line blocking). Курсор хранится в памяти
фонового сервиса; при рестарте Analytics сбрасывается — порядок перебирается заново, дублей строк
не появляется (FR-3.2/3.4 + unique-индекс), а `Undefined`-кандидаты перепроходят ИИ не более
одного раза за запуск.

**Single instance (D12).** Фон рассчитан на один экземпляр Analytics (текущее развёртывание — один
контейнер `receipt-analytics`). Распределённой блокировки нет; при горизонтальном масштабировании
каждый экземпляр запустит свой фон (дубли вызовов ИИ, гонки вставок — частично спасает unique-индекс).
Ограничение фиксируется здесь, распределённая координация — отдельное решение, вне объёма.

### 7. Админский API и webUI (FR-5, FR-7)

Группа `/api/precategorized-commodities` (модуль `Api/Modules/PrecategorizedCommodities/`,
регистрация `MapPrecategorizedCommodityEndpoints()` в `Program.cs`):

| Метод и путь | Назначение | Коды |
|---|---|---|
| `GET /api/precategorized-commodities?limit=50&offset=0&search=` | постраничный список **только `proposed`**, поиск по наименованию/магазину, `X-Total-Count` | `200`, `400`, `401`, `403` |
| `PUT /api/precategorized-commodities/{id:guid}/category` | изменение предложенной категории (без применения к товарам) | `200`, `400`, `404`, `409`, `401`, `403` |
| `POST /api/precategorized-commodities/{id:guid}/confirm` | подтверждение (транзакция п. 4; ответ содержит `updatedCommodities`) | `200`, `404`, `409`, `401`, `403` |
| `DELETE /api/precategorized-commodities/{id:guid}` | отклонение (физическое удаление) | `204`, `404`, `409`, `401`, `403` |

- **Проверки прав — эталон `MerchantEndpoints`** (FR-5.5): `UserContext.UserId` пуст → `401`;
  `IUserRepository.GetByIdAsync(...).IsAdmin = false` → `403`; проверка — на сервере, независимо от
  скрытия раздела в навигации.
- **Стиль ошибок — текстовые тела, как в `MerchantEndpoints`** (FR-5.9): `Results.BadRequest("...")`,
  `Results.NotFound("...")`, `Results.Unauthorized()`. **ProblemDetails не
  используется.** Факт по коду: в `Program.cs` `AddProblemDetails()` зарегистрирован, но
  `UseProblemDetails()` в pipeline явно не вызывается — стандартный механизм сейчас не активирован,
  поэтому существующие эндпоинты живут в текстовом стиле; новый модуль следует этому стилю.
  Переход на ProblemDetails — отдельное сквозное решение (открытый вопрос 5 задачи), а не попутное
  изменение в этой задаче.
- **Уточнение при реализации (2026-10-24): 403 отдаётся явно — `Results.StatusCode(403)`, а не
  `Results.Forbid()`.** В приложении не зарегистрирована схема аутентификации (`AddAuthentication`
  отсутствует), и `ForbidHttpResult.ExecuteAsync` в рантайме бросает
  `InvalidOperationException: No authenticationScheme was specified` → 500 вместо 403. Тот же
  дефект есть у эталонных `MerchantEndpoints` — вынесен в бэклог задачи как отдельное
  сквозное исправление (регистрация `DefaultForbidScheme` либо явный 403). Тесты нового модуля
  проверяют код статуса исполнением результата на `HttpContext`, а не тип `IResult`, —
  именно это и поймал расхождение.
- `limit` (1..200, по умолчанию 50), `offset` (≥ 0) — иначе `400` (как `limit`/`offset` проверки
  в `MerchantEndpoints.GetAll`).
- webUI: маршрут `/precategorized` (`routes.ts` в стиле ADR-023), раздел виден в навигации только
  админу (`Sidebar.tsx`, условие `{isAdmin && (...)}`); при прямом заходе не-админом страница рендерит
  «нет доступа»/`NotFoundPage` и не запрашивает данные (сервер всё равно отвечает `403`). Таблица —
  по образцу `MerchantTable`/`CommodityTable`, пагинация и поиск — по образцу `MerchantsPage`/`useMerchants`
  (`Pagination` на уровне страницы, `X-Total-Count`), диалог «Отклонить» и toast — по образцу
  `ReceiptDetails.tsx` (`CustomDialog` + `Toasts`). Ошибки API (401/403/409) показываются понятным
  сообщением без падения страницы (FR-7.6).

### 8. Изменение существующего контракта suggest (NFR-8, FR-9)

Структура ответа `POST /api/receipts/{id}/categories/suggest` и поведение
`PUT /api/receipts/{id}/categories` не меняются; единственное аддитивное изменение — значение

### 9. Конфигурация и тестируемость (NFR-7, NFR-9)

Новая секция `Precategorization` в `appsettings.json`, переопределение env `Precategorization__*`
(стиль `AI__*`/`CommodityCategoryCache__*`, ADR-021), проброс в `docker-compose.yml` (с `:-`-дефолтами
по образцу `CommodityCategoryCache__MaxSize`), `.env.example`, таблица настроек в `AGENTS.md`.

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `Precategorization:Enabled` | `true` | Фоновый сервис работает; `false` отключает **только фон**, админский раздел и поиск по очереди в ручном suggest продолжают работать на накопленных строках (FR-1.5, FR-9.7) |
| `Precategorization:IdleTimeout` | `00:05:00` | Простой, после которого запускается сессия |
| `Precategorization:IdleCheckInterval` | `00:00:30` | Период проверки простоя |
| `Precategorization:BatchLimit` | `5` | Максимум позиций за сессию |
| `Precategorization:IntervalBetweenCalls` | `00:00:02` | Пауза между вызовами ИИ |

- Валидация опций (NFR-7): `BatchLimit < 1`, отрицательные таймауты → явная ошибка валидации на
  старте или безопасные дефолты; финальный выбор способа — за реализацией, поведение фиксируется
  тестами (подход с невалидными значениями не должен «тихо деградировать»).
- **Тестируемость времени (NFR-9):** внедряемый источник времени/задержки — `TimeProvider`/`FakeTimeProvider`
  (или собственный `IClock`/`IDelay`) + пакет `Microsoft.Extensions.TimeProvider.Testing`.
  В проекте такой инфраструктуры сейчас нет (существующие тесты hosted-сервисов используют реальные
  `Task.Delay`), она создаётся **в рамках этой задачи**; логика простоя и пауз тестируется без реальных
  `Task.Delay`/системных часов.

### 10. Связь с переключаемым провайдером ИИ (ADR-026)

Фоновый сервис вызывает ИИ **только через контракт `IAiClient`** (Application) — той же точкой,
что и ручной путь. При реализации ADR-026 (второй провайдер через `AI:Provider`) **никакие
изменения фона не требуются**: селектор провайдера живёт в DI-регистрации `IAiClient`, фон получает
то, что сконфигурировано. Смена провайдера не ломает фон, и наоборот — фон не блокирует
переключение провайдера. Отсутствие `AI:BaseUrl` активного провайдера обрабатывается как D5
(предложения из кэша без ИИ).

## Рассмотренные варианты (отклонённые альтернативы)

### A. Прямое применение категории сразу в `commodities`, без очереди — **отклонено**

Фон сразу пишет ИИ-категорию в `commodities` всех товаров с тем же именем.
**Минусы:** ошибки модели попадают к пользователям молча (нет фильтрации человеком), требуемая
задачей проверка админом отсутствует; перезапись содержательных категорий при конфликте. Исходное
требование задачи — «результат фоновой ИИ-категоризации нельзя сразу писать в commodities».

### B. Запись предложений в `commodities` без подтверждения админом — **отклонено**

Хранить предложения как «черновик» в существующей таблице товаров со служебным флагом.
**Минусы:** смешение двух стадий в одном состоянии (категория одновременно «есть» и «не подтверждена»)
— ломает семантику аналитики по категориям; служебный флаг пришлось бы распространить на все
существующие запросы/фильтры; массовое «применить к товарам всех пользователей по имени» всё равно
потребовало бы отдельной транзакции — и очередь по сути всё равно нужна, а `commodities` перед этим
успевает «замусориться» недоверенными данными.

**Итог:** выбрана отдельная таблица-очередь: она изолирует непроверенные данные, позволяет отозвать
предложение без последствий для `commodities` и даёт журнал действий админа (D2).

### C. Очередь предложений вне PostgreSQL (in-memory очередь / Redis) — **отклонено**

**Минусы:** предложения теряются при рестарте до обработки админом (недоверенные данные обязаны
переживать деплой); Redis — новая инфраструктура ради одного инстанса (KISS/YAGNI, ср. A-вариант
ADR-019); in-memory не даёт пагинации/поиска и истории. PostgreSQL-таблица согласована с паттерном
проекта (миграции, EF, репозитории) и бесплатно даёт durable-очередь + индексы.

### D. Распределённая блокировка фонового процесса — **отклонено (вне объёма)**

Распределённая координация нескольких экземпляров Analytics — фиксируется как путь эволюции:
если появится горизонтальное масштабирование, потребуется отдельное решение (advisory lock
PostgreSQL или выбор лидера). YAGNI при текущем одном контейнере; unique-индекс частично спасает
от гонок вставок уже сейчас.

### E. Нормализованный матчинг при подтверждении (регистр/пробелы, нижний регистр) — **отклонено**

Сравнивать нормализованные имена, а не точные. **Минусы:** подтверждение «Молоко» затронет «молоко»
и другие написания — риск неверного массового присвоения; требование заказчика прямо говорит
о **точно таком же** наименовании. Кэш при этом нормализует ключ и может обслуживать оба варианта
после подтверждения — это уже даёт значительную часть эффекта без риска неверного массового
присвоения.
Нормализованный матчинг — бэклог, если на практике точное совпадение окажется слишком узким.

### F. ProblemDetails для ошибок админского API — **отклонено**

`AddProblemDetails` зарегистрирован, но `UseProblemDetails` в pipeline не активирован — существующий
функционал отвечает текстовыми телами (`MerchantEndpoints`). Переключение формата для одного нового
модуля дало бы несогласованность, для всего API — расширение объёма задачи. Эталон текстового стиля
фиксируется; переход на RFC 7807 — отдельное сквозное решение.

### G. Индексы на `commodities` в этой миграции — **отложено (не отклонено)**

Состав индексов под DISTINCT-выборку кандидатов (join через `receipts`) не очевиден заранее;
преждевременная переиндексация большой таблицы без замеров — риск без выгоды. Обязательство:
замерить планы запросов кандидатов/подтверждения по результатам эксплуатации, выбрать индексы
отдельным решением (см. п. 3 и «Компромиссы»).

### H. Параллельные вызовы ИИ из фона — **отклонено**

Параллельные вызовы из фона усложняют контроль лимитов, пауз и поведение «остановка после текущей
позиции» (гонки с проверкой активности) — при малой ожидаемой нагрузке последовательность дешевле и
предсказуемее (D4). Пользовательский путь сохраняет параллелизм `AI:Concurrency` (ADR-009).
Суммарная параллельность: фон — 1, пользовательский путь — до `AI:Concurrency` (NFR-3).

## Последствия

### Положительные

- Категоризация выполняется в простое: ИИ-нагрузка не конкурирует с пользовательскими запросами,
  категории наполняются без участия пользователей.
- Ничто не пишет в `commodities` без решения человека: ошибки модели фильтруются админом (UC-2/UC-3).
- Подтверждение даёт массовый эффект по всем пользователям одним действием + мгновенное
  распространение через кэш (`source = cache` без ИИ).
- Единый порядок проверок (existing → cache → precategorized → ai) остаётся интактным по
  семантике; фон не обходит кэш; существующий ручной сценарий меняется только аддитивно.
- Курсор сессий исключает head-of-line blocking на `Undefined`-кандидатах; unique-индекс даёт
  идемпотентность рестартов.
- Глобальный доступ — явный и узкий (маркер `IgnoreQueryFilters` только в новых методах),
  owner-scoping остального кода не затронут.
- Конфигурация без пересборки; фон отключается переключателем при деградации.

### Отрицательные / компромиссы

- **Человек в цикле:** категории применяются только после подтверждения — очередь админа может
  расти; побочное следствие: пользователь может получить предложение из очереди **до** подтверждения
  (`source = "precategorized"`, FR-9) — качество равно качеству ИИ, но сохранение остаётся осознанным
  действием пользователя, данные не портятся молча (риск 10, принят).
- **Индексы на `commodities` отложены:** выборка кандидатов и подтверждение — осознанный Seq Scan
  по отфильтрованному множеству; при накоплении данных обязательны замеры и отдельное решение по
  индексам (риск 6). Митигация — `Precategorization:Enabled = false` без релиза.
- **Точный матчинг:** «Молоко» и «молоко» — разные строки; кэш нивелирует
  часть эффекта по итогу подтверждения, но массовое подтверждение узковато — бэклог (риск 4).
- **`applied`-строки хранятся бессрочно:** рост ограничен числом уникальных пар, но ретенция не
  определена; пара с `applied` навсегда блокирует фоновое повторное предложение (риск 3, риск 7).
- **Single instance:** масштабирование требует распределённой блокировки — отдельное решение (D12).
- **Остановка сессии не мгновенная:** до конца текущего вызова ИИ (≤ `AI:Timeout = 80 с` в
  appsettings; расхождение дефолтов уже в бэклоге) — риск 1.
- **«Замороженный» кэш:** при `MaxSize` исчерпан `TryAdd` после подтверждения — no-op; новые товары
  с тем же названием снова пойдут в ИИ — унаследованное поведение ADR-019, не регрессия (риск 5).
- **Пробники не на `/health`** блокируют фон — список исключений расширяем, но требует сверки с
  фактическим мониторингом при приёмке (риск 8).

### Риски (сводка обязательств)

| № | Риск | Обязательство |
|---|---|---|
| 1 | Задержка остановки сессии до конца вызова ИИ (80 с) | Принято «дойти до конца текущей позиции»; ужесточение (отмена вызова) — решение архитектора при эксплуатации |
| 2 | Multi-instance Analytics → дубли фона | Ограничение зафиксировано; блокировка — отдельное решение при масштабировании |
| 3 | Рост `applied`-строк | Ретенция — бэклог; рост ограничен числом уникальных пар |
| 4 | Точный матчинг узок | Кэш смягчает; нормализованный матчинг — бэклог |
| 5 | Замороженный кэш не принимает подтверждения | Унаследовано из ADR-019; зафиксировано как известное поведение |
| 6 | Seq Scan кандидатов/подтверждения | **Замерить планы по результатам эксплуатации и выбрать индексы отдельным решением** |
| 7 | Товары, синхронизированные после `applied`, фоном не категоризируются | Принято заказчиком; повторное применение — бэклог; ручной suggest по очереди (любой статус) и ручная категоризация обслуживают их |
| 8 | Пробники не на `/health` блокируют фон | Явно документированный список исключений, расширяемый предикатом |
| 9 | Долгие сессии (50 × (2 с + ответ ИИ)) | Нормально для фона; дефолты согласовать при приёмке |

## Ограничения решения

1. Фон — только один экземпляр Analytics; горизонтальное масштабирование без дополнительной
   координации недопустимо.
2. Подтверждение матчит **точное** наименование (без нормализации) и не перезаписывает содержательные
   категории.
3. `suggest` остаётся read-only; сохранение категорий пользователем — только через существующий
   `PUT /api/receipts/{id}/categories`.
4. Формат ошибок admin-модуля — текстовый; переход на ProblemDetails — вне этого решения.
5. Список исключений активности: `/health`; любые инфраструктурные пробники на других путях
   считаются активностью — их перечень контролируется эксплуатацией.

## Приёмка (сводка ключевых критериев)

Полный список — в задаче («Критерии приёмки»). Архитектурно значимые:

- Миграция создаёт таблицу с unique `(name, merchant_id)` и индексом `(status, created_at)`;
  индексы на `commodities` в миграции отсутствуют.
- Простой: сессия стартует после `IdleTimeout`; `/health` не сбрасывает таймер, `/api/*` — сбрасывает.
- Появление HTTP-запроса останавливает сессию после текущей позиции; результат сохраняется.
- `BatchLimit`/`IntervalBetweenCalls` соблюдаются; обработка последовательна.
- Кандидаты — по товарам всех пользователей, исключения FR-3.2–3.4 работают; known-existing/кэш —
  без вызова ИИ.
- Курсор: кандидат с `Undefined`/ошибкой двигает курсор — нет head-of-line blocking.
- Ручной suggest: порядок `existing → cache → precategorized → ai`, `source = "precategorized"`,
  batch-запрос, read-only, деградация при ошибке очереди.
- Подтверждение: все пользователи, точное имя, только без категории, транзакция, `applied`,
  удаление сестринских `proposed`, `TryAdd` в кэш, `updatedCommodities`.
- Отклонение: удаление, `commodities` не меняются.
- Права: 401/403 по эталону `MerchantEndpoints`; 400/404/409 — как в FR-5.
- Глобальный запрос возвращает данные всех пользователей при установленном `CurrentUserId`
  (проверка `IgnoreQueryFilters`).
- `Enabled = false` отключает только фон; раздел админа и поиск по очереди работают.
- Architecture-тесты и `dotnet test` проходят без ослабления правил.

## Связь с другими ADR

- **ADR 009** — обоснован amend-заметкой: алгоритм приоритетов уточняется до
  `existing → cache → precategorized → ai` (добавляется шаг очереди перед ИИ; `source` расширяется
  значением `precategorized`). Существующие шаги и контракты suggest/apply не меняются.
- **ADR 019** — подтверждается целиком: `TryAdd` при подтверждении админом использует ту же семантику
  (first-wins, no-op при замороженном кэше); кэш предшествует очереди и ИИ; сквозной масштаб кэша
  соответствует глобальному масштабу фона.
- **ADR 021** — подключение новых env-переменных `Precategorization__*` выполняется по его паттерну.
- **ADR 023** — новый маршрут `/precategorized` добавляется в `routes.ts` по его правилам (плоский
  маршрут, catch-all, админ-гейт внутри компонента).
- **ADR 026** — фон не вводит новых зависимостей от конкретного провайдера: работа через `IAiClient`
  делает переключение провайдера (когда оно будет реализовано) прозрачным для фонового режима.
