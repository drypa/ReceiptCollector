# 7. Флаг пропуска синхронизации чеков при старте Analytics

## Статус

Принято

## Контекст

Сервис Analytics (`ReceiptCollector.Analytics.Api`) содержит `ReceiptSynchronizationHostedService`, реализующий `IHostedService`. При старте сервиса он синхронизирует данные из MongoDB в PostgreSQL. В production это необходимый этап, но в режиме разработки (debug) синхронизация занимает значительное время (десятки секунд), замедляя цикл отладки.

Разработчику приходится ждать завершения синхронизации при каждом запуске, даже если база уже актуальна. Требуется механизм, позволяющий пропускать синхронизацию без изменения кода.

### Бизнес-требования

1. **Ускорение цикла разработки** — возможность запустить Analytics без синхронизации
2. **Гибкость конфигурации** — флаг должен устанавливаться через `appsettings` или переменную окружения
3. **Сохранение поведения по умолчанию** — в production синхронизация работает как раньше
4. **Безопасность** — флаг не должен влиять на работу в production при стандартной конфигурации (opt-in механизм)

## Рассмотренные варианты

### Вариант 1: Проверка флага внутри `StartAsync` у `ReceiptSynchronizationHostedService`

**Описание:** Добавить флаг `Skip` в `ReceiptSynchronizationOptions`. Внедрить `IOptions<ReceiptSynchronizationOptions>` в `ReceiptSynchronizationHostedService` и проверять перед запуском синхронизации.

**Плюсы:**
- Минимальные изменения — затрагивается только 2 файла
- Сохраняется единый pipeline регистрации сервисов
- Возможность залогировать факт пропуска синхронизации
- Флаг можно изменить через конфигурацию без перекомпиляции
- Поведение по умолчанию (`false`) не меняет существующую логику
- Сервис остаётся зарегистрированным в DI, что упрощает тестирование

**Минусы:**
- Сервис всё равно создаётся и регистрируется (незначительные накладные расходы)
- Требуется внедрение `IOptions<T>` в класс, который его ранее не использовал

### Вариант 2: Условная регистрация сервиса в `DependencyInjectionExtensions`

**Описание:** В `DependencyInjectionExtensions` читать флаг из `IConfiguration` и не регистрировать `ReceiptSynchronizationHostedService`, если флаг установлен.

**Плюсы:**
- Сервис не создаётся вовсе при пропуске синхронизации

**Минусы:**
- Логика конфигурации смешивается с логикой регистрации зависимостей
- Нельзя включить синхронизацию без перезапуска (флаг читается однократно при старте)
- Невозможно залогировать причину пропуска синхронизации
- Разные вариации поведения в зависимости от конфигурации — сложнее тестировать

### Вариант 3: Профили запуска (Launch Profiles) + условная компиляция

**Описание:** Использовать директивы препроцессора (`#if DEBUG`) или отдельные профили запуска.

**Плюсы:**
- Простота реализации
- Не требует конфигурации

**Минусы:**
- Требует перекомпиляции для изменения поведения
- Невозможно настроить через docker-compose или CI
- Нарушает принцип единообразия конфигурации
- Легко забыть переключить при merge в production

### Вариант 4: Отдельный сервис-прокси с декоратором

**Описание:** Создать декоратор для `IHostedService`, который проверяет флаг и делегирует вызов.

**Плюсы:**
- Не меняет существующий `ReceiptSynchronizationHostedService`
- Можно переиспользовать для других hosted services

**Минусы:**
- Избыточная сложность для одной задачи (over-engineering)
- Дополнительный класс и регистрация
- Усложняет понимание потока выполнения

## Решение

Выбран **Вариант 1: Проверка флага внутри `StartAsync`**.

### Обоснование

1. **Минимальность изменений** — затрагивается только 2 файла: `ReceiptSynchronizationOptions.cs` и `ReceiptSynchronizationHostedService.cs`.
2. **Сохранение архитектуры** — все hosted services продолжают регистрироваться единообразно в `AddInfrastructure`.
3. **Логирование** — возможность залогировать пропуск синхронизации, что упрощает диагностику.
4. **Opt-in по умолчанию** — `Skip = false`, синхронизация работает как раньше без каких-либо изменений конфигурации.
5. **Расширяемость** — аналогичный паттерн можно применить к другим hosted services (например, `AdminUserHostedService`).
6. **Соответствие текущей архитектуре** — проект использует .NET Options pattern, и внедрение `IOptions<T>` является стандартной практикой.

### Детали решения

1. В `ReceiptSynchronizationOptions` добавить свойство `Skip` со значением по умолчанию `false`.
2. В `ReceiptSynchronizationHostedService` внедрить `IOptions<ReceiptSynchronizationOptions>`.
3. В методе `StartAsync` проверить `_options.Value.Skip`:
   - `true` → залогировать и вернуть `Task.CompletedTask`
   - `false` → выполнить синхронизацию как обычно
4. Флаг конфигурируется через стандартный .NET механизм:
   - `appsettings.json` / `appsettings.Development.json`
   - Переменные окружения (через `__`-нотацию)
   - Любой другой конфигурационный провайдер

## Последствия

### Положительные

- Разработчик может пропустить синхронизацию, установив `Infrastructure:Receipts:Synchronization:Skip = true` в `appsettings.Development.json`
- В production (где `appsettings.Development.json` не используется) синхронизация работает без изменений
- Решение reusable для других hosted services

### Отрицательные

- `ReceiptSynchronizationHostedService` всегда регистрируется и создаётся, даже при пропуске синхронизации
- Необходимо поддерживать консистентность конфигурации между `appsettings` и переменными окружения

### Компромиссы

- Некоторый оверхед на создание сервиса (пренебрежимо мал по сравнению со временем синхронизации)
- Принят trade-off в пользу простоты и поддерживаемости против полного отсутствия создания сервиса

### Риски

- Разработчик может случайно оставить `Skip = true` в коммите для `appsettings.json` (решается code review)
- **Митигация:** флаг добавляется только в `appsettings.Development.json`, который не применяется в production
