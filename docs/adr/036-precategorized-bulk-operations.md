## Контекст

### Проблема

Админская страница `/precategorized` показывает очередь AI-предложений категорий. Сегодня
решение принимается **только поштучно**: подтвердить (`POST /{id}/confirm` — категория
применяется ко всем товарам всех пользователей с этим названием и пишется в кэш), отклонить
(`DELETE /{id}` — строка удаляется) или сначала исправить категорию (`PUT /{id}/category`).
При очереди в десятки–сотни строк админ кликает по каждой строке; при разборе бэклога
(в ADR-027 оценивался как ~4000+ строк) это нерабочая рутина.

Нужны две операции «на весь экран» — **«Подтвердить все»** и **«Отклонить все»** — на строки
**текущей видимой страницы**. Операции обязаны быть безопасными (диалог) и устойчивыми
к частичным сбоям (часть строк уже обработана параллельно), при этом **логический конфликт
не должен откатывать операцию и мешать применению остальных строк**, а технический сбой
не должен оставлять применённой ни одной строки.

### Решения заказчика (обязательны к исполнению; редакция 2026-11-13)

| # | Решение | Следствие для архитектуры |
|---|---|---|
| 1 | Массовость — **две кнопки на всю страницу**, без чекбоксов | Нет состояния выделения: область действия = ровно тот список строк, который отрисован |
| 2 | Область — **строки текущей страницы пагинации**, поиск учитывается только в её пределах | Область задаёт **клиент** (id отрисованных строк), а не сервер (см. §1.4) |
| 3 | Перед каждой операцией — **диалог подтверждения** с количеством строк | Счётчик диалога = `items.length` (строк страницы), не `X-Total-Count` |
| 4 | **Вся видимая страница — один запрос**, без порций и подгрузки, и **одна транзакция** на всю страницу | Один HTTP-запрос = одна транзакция = единица атомарности; порционность и «строка = транзакция» отменены |
| 5 | **Прогресс-счётчик не нужен**: кнопки заблокированы, по завершении — сводка и автообновление | UX — только busy-состояние без чисел; никаких чанков, шагов и промежуточных счётчиков |
| 6 | **Логические конфликты** (already-applied, not-found) не откатывают операцию: пропуск + причина в сводке; **технический сбой БД/сети** — полный откат, ничего не применено | `NotFound`/`Conflict` — результат строки при HTTP `200`; любое исключение/таймаут/отмена — abort всей транзакции |
| 7 | Приёмка — **автотесты на новые массовые API-операции** + ручной прогон на dev-стенде | Массовая операция должна быть серверной и проверяемой автотестами |

### Пересмотр 2026-11-13: что было отклонено

Первая редакция этого ADR выбирала иные решения. Они **не удалены** из «Рассмотренных
вариантов», а переведены в отклонённые с новым обоснованием — чтобы история решения
и причина отказа были зафиксированы.

| Прежнее решение | Прежний смысл | Почему отклонено сейчас |
|---|---|---|
| **A1** | пакетный эндпоинт (≤ 50 id) + **клиентская порционность** по 10 id с прогрессом «выполнено X из N» | Решение заказчика 4: вся страница **одним** запросом, без порций. Решение 5: прогресс-счётчик не нужен. Порционность также не даёт атомарности всей страницы (каждая порция — отдельный commit), что противоречит решению 6 в части технического сбоя |
| **B1** | **строка = транзакция** (N независимых commit'ов), частичный успех — свойство реализации | Решение заказчика 4/6: одна транзакция на всю страницу; технический сбой — полный откат. N commit'ов оставляли бы применённую часть страницы после сбоя посреди операции |
| **Прогресс-счётчик** в UX (inline «Подтверждаем 12 из 50…») | постепенная обратная связь за счёт порций | Решение 5: счётчик убран полностью; на время операции — заблокированные кнопки, по завершении — сводка |
| **F1 (прежний)** | предел 50 id/запрос, выведенный из порционности | Предел должен покрывать **любую страницу, которую может вернуть `GET`** (`MaxLimit = 200`), иначе инвариант «одна страница — один запрос» ломается (см. §1.4, F1) |

Отклонение A1/B1 не отменяет их прежних достоинств (тестируемость на сервере, отсутствие
серверного состояния, устойчивость к устаревшей странице) — эти свойства сохранены в выбранном
варианте A3/B2. Отменена именно **форма**: один запрос вместо порций и одна транзакция вместо
транзакции на строку.

### Ключевые ограничения

1. **Единица атомарности массовой операции — весь запрос** (решение заказчика 4/6). Это
   осознанное отличие от поштучного пути (ADR-027, D10), где единица — строка: массовый путь
   не может переиспользовать поштучную транзакцию, иначе технический сбой посреди страницы
   оставил бы часть строк применёнными.
2. **Логический конфликт — не ошибка транзакции** (решение 6): `already-applied` и `not-found`
   не прерывают работу, а классифицируются **до** применения изменений и попадают в сводку.
   Отсюда требование к механизму классификации: нужен снимок строк под блокировкой, а не
   реакция на исключение.
3. **Журнал решений** (ADR-033) требует **одно событие на применённую строку** и запись строго
   после commit; recorder обязан быть последней БД-операцией запроса. При одной транзакции это
   означает накопление draft'ов и **один** вызов recorder'а после commit.
4. **Прогресс из одного ответа не выводится, и он не требуется** (решение 5): сервер молчит
   до конца; UX обязан быть корректным в этом режиме (busy-state, блокировки, сводка).
5. **Понятия «страница» на сервере нет и не должно появиться** (ADR-028 §1.3): реконструкция
   страницы по `limit/offset/search` создаёт связность и гонки; поиск/пагинация остаются в `GET`.
6. **Стоимость строки не константна** (Seq Scan по `commodities` без индекса на `name`) —
   размер батча ограничен и обоснован, длительность ограничена дедлайном, отказ — полный откат.
7. **Изоляция должна допускать ожидание блокировки с последующей классификацией строки**
   (см. §2): это определяет выбор `READ COMMITTED` и делает недопустимым `REPEATABLE READ`/
   `SERIALIZABLE` для этого сценария (там конкурентное обновление дало бы ошибку сериализации
   и, по решению 6, полный откат вместо пропуска).

## Рассмотренные варианты

### Ключевое решение A: форма контракта массовой операции

#### Вариант A1: один пакетный эндпоинт с массивом id + порционность на клиенте — **отклонён пересмотром 2026-11-13**

Историческая формулировка: два stateless-эндпоинта принимают `{ "ids": [ … ] }` (≤ 50), сервер
выполняет пошаговую операцию для каждого id, клиент режет страницу на порции по 10 id и вызывает
эндпоинт последовательно, показывая прогресс «выполнено X из N».

**Что в варианте было сильным:** серверная (тестируемая) операция, отсутствие серверного
состояния, ограниченная длительность одного запроса, реальная обратная связь.

**Почему отклонён:**

- Решение заказчика 4 прямо запрещает порции: «вся видимая страница отправляется одним запросом».
- Решение заказчика 5 убирает счётчик прогресса — главный аргумент в пользу порционности
  исчезает.
- Каждая порция — отдельный commit: технический сбой после первой порции оставляет страницу
  применённой частично, что противоречит решению 6 («технический сбой — полный откат, ничего
  не применено»).
- До 20 запросов на максимальную страницу вместо одного; сводка собирается из нескольких
  ответов, а «атомарность всей страницы» недостижима в принципе.

#### Вариант A2: N последовательных вызовов существующих поштучных эндпоинтов (клиентский цикл) — **отклонён**

Клиент перебирает id и вызывает `POST /{id}/confirm` / `DELETE /{id}`, считает успехи и ошибки сам.

**Минусы:**
- **Нет новой API-операции** → критерий приёмки «новые массовые API-операции покрыты тестами
  (успех, частичный успех, границы страницы, права доступа)» невыполним на сервере, а вся
  оркестрация уезжает в фронтенд, где **тестовой инфраструктуры нет** (ADR-011 E1).
- Область действия и лимиты негде проверить: сервер видит одиночные операции, дубликаты id
  и размер «пачки» не валидируются, агрегированная сводка считается только в браузере.
- N round-trip'ов и N проверок прав (по запросу в `users` на строку): для страницы 50–200 строк —
  50–200 запросов на один клик.
- N независимых транзакций: технический сбой посреди цикла оставляет применённую часть
  (противоречит решению 6), а клиент обязан реализовывать машину состояний «что уже сделано».
- HTTP-статусы смешиваются с бизнес-семантикой: `409`/`404` приходят как ошибки транспорта,
  хотя по требованию это **успех-с-пропуском**.

#### Вариант A3: один пакетный запрос на всю страницу, без порционности — **выбран**

Два новых stateless-эндпоинта (`POST …/batch/confirm`, `POST …/batch/decline`) принимают
`{ "ids": [ … ] }` (не более `MaxBulkIds = 200`) и обрабатывают **весь список в одной транзакции**,
возвращая агрегированные счётчики и результат по каждой строке.

**Плюсы:**
- Буквально исполняет решения заказчика 4–5: один запрос, одна транзакция, никакой оркестрации
  и никакого прогресса на клиенте.
- Массовая операция — **серверная и тестируемая**: «успех», «частичный успех по конфликтам»,
  «границы страницы», «права доступа» и **атомарность при техническом сбое** проверяются
  юнит- и сквозными тестами (решение 7), а не только руками.
- Правила валидации (пусто, лимит, дубликаты, `Guid.Empty`) и учёт «пропущено» — в одном месте.
- Одна аутентификация/авторизация и один scope `DbContext` на всю страницу.
- Клиент предельно прост: один `fetch`, busy-state, сводка, `refresh()`. Frontend без автотестов
  (ADR-011 E1) перестаёт быть риском — там нет логики, которую надо покрывать.
- Нет серверного состояния (job'ов, сессий, TTL), нет распределённой координации.

**Минусы (приняты осознанно):**
- Длительность запроса равна длительности всей страницы: до 200 × (Seq Scan + `UPDATE`)
  под удержанием блокировок; ограничивается дедлайном и полным откатом (§2, F1).
- Обратной связи до конца операции нет — только busy-state (решение 5).
- Любой технический сбой откатывает всю страницу, включая 199 «хороших» строк (решение 6).

#### Вариант A4: серверная job-модель (`202 + jobId`, клиент поллит статус) — **отклонён**

**Минусы:** job-модель существует ради прогресса и фонового выполнения; решение 5 прогресс
исключает, а операция остаётся синхронной пользовательской командой. Добавляет серверное
состояние, TTL, идемпотентность, поведение при рестарте и при нескольких экземплярах
(ADR-027, D12 — single instance). Прецедент отказа — ADR-028 вариант C.

#### Вариант A5: серверный стриминг результатов (SSE/NDJSON) — **отклонён**

**Минусы:** потоковый разбор на клиенте, буферизация в nginx, отдельная обработка отмены
и ошибок стрима, сложность тестирования minimal API — и всё это ради постепенности, которая
заказчику не нужна (решение 5). Стриминг несовместим и с одной транзакцией: результат строки
становится известен до commit, то есть до того, как он станет правдой.

#### Вариант A6: серверное понятие «страницы» (`limit/offset/search` в теле запроса) — **отклонён**

Сервер сам повторяет выборку страницы и обрабатывает её.

**Минусы:** дублирование пагинации/поиска из `GET`; между отрисовкой и кликом страница уже
изменилась — сервер обработал бы **другой** набор строк, чем видел админ (прямое расхождение
с edge case «список изменился между показом страницы и запуском операции»); связность контракта
с UI-понятиями. Отклонено тем же аргументом, что ADR-028 §1.3.

### Ключевое решение B: транзакционность

#### Вариант B1: каждая строка — своя транзакция (как в поштучной операции), конфликты — результат строки — **отклонён пересмотром 2026-11-13**

Историческая формулировка: массовая операция = цикл по id, для каждого вызывается существующая
транзакция подтверждения (ADR-027, D10) или `DELETE` строки; конфликты возвращаются как результат
строки.

**Что в варианте было сильным:** частичный успех — свойство реализации; блокировки на
`commodities` держатся миллисекунды на строку; повторный запуск естественно идемпотентен;
поштучные эндпоинты работают параллельно без новых блокировок.

**Почему отклонён:**

- Решение заказчика 4: «вся операция обрабатывается в одной транзакции»; прежняя схема
  «строка = транзакция» отменена явно.
- Решение 6: технический сбой должен откатывать **всё**. При N commit'ах откат невозможен
  физически: применённая часть страницы остаётся, а сводка «выполнено N» перестаёт быть
  атомарной.
- Промежуточное состояние страницы видно другим читателям и второму окну — при массовой
  операции это выглядит как «частично применённая страница», что заказчик исключил.

#### Вариант B2: одна транзакция на весь батч — **выбран**

```text
BEGIN (READ COMMITTED)
  SELECT … WHERE id = ANY(@ids) ORDER BY normalized_name, merchant_id, id FOR UPDATE
  → классификация: proposed | applied → already-applied | нет строки → not-found
  для каждого proposed (в том же детерминированном порядке):
      confirm → UPDATE commodities … WHERE name = @name AND (category_id IS NULL OR 0)
      decline → (изменений в commodities нет)
  confirm → UPDATE precategorized_commodities SET status = applied, applied_at = @now WHERE id = ANY(@appliedIds)
  decline → DELETE FROM precategorized_commodities WHERE id = ANY(@appliedIds)
COMMIT
после commit: cache.TryAdd(...) по каждой applied-строке
после commit: recorder.RecordAsync(drafts) — последняя БД-операция запроса
```

**Плюсы:**
- Технический сбой (исключение, таймаут, отмена, deadlock) откатывает всё: ни одна строка
  не остаётся применённой (решение 6).
- Логические конфликты разрешаются **до** изменений, одним снимком под блокировкой: строка,
  обработанная параллельно, не вызывает ошибки и не мешает применить остальные.
- Один commit вместо N: нет «полуприменённой» страницы, наблюдаемой извне.
- Классификация и применение видят одно и то же значение `proposed_category_id` и
  `original_proposed_category_id` — журнал не может разойтись с тем, что применено.

**Минусы:** блокировки строк очереди и затронутых товаров удерживаются от первого `SELECT`
до commit (до 200 Seq Scan-`UPDATE`); длительность ограничена дедлайном и `CommandTimeout`;
при техническом сбое теряется работа по всем строкам (принято).

#### Вариант B3: одна транзакция на порцию (10 строк) — **отклонён**

**Минусы:** порционность отклонена (решение 4); появляется третий режим атомарности; сбой
посреди порции откатывает уже применённые строки порции, и счётчики, показанные клиенту,
перестают быть правдой; «полный откат при техническом сбое» не выполняется для предыдущих порций.

#### Вариант B4: savepoint на каждую строку внутри одной транзакции — **отклонён**

Идея: при ошибке строки откатываться к savepoint и продолжать остальные, оставаясь в одной
транзакции.

**Минусы:** логические конфликты — не ошибки БД, а проверка статуса, поэтому savepoint'ы для них
не нужны; техническая ошибка БД (включая deadlock и таймаут) по решению 6 обязана откатывать всё,
а не «спасать» остальные строки; savepoint на 200 строк — лишние round-trip'ы внутри и без того
длинной транзакции и ложное ощущение частичного успеха.

#### Вариант B5: `pg_advisory_xact_lock` для сериализации массовых операций — **отклонён**

**Минусы:** не устраняет главную проблему (блокировки `commodities` и конкурентные
пользовательские пути), но добавляет глобальный bottleneck и новый механизм координации;
Analytics по-прежнему single-instance (ADR-027, D12), а bulk-vs-bulk уже разрешается
детерминированным порядком блокировок (§2.3). Advisory lock маскировал бы риск, не убирая его.

#### Вариант B6: предварительное чтение без блокировки + условный `UPDATE … WHERE status = 0` — **отклонён**

Идея: прочитать статусы обычным `SELECT`, затем для каждой строки выполнить
`UPDATE … WHERE id = @id AND status = 0`; `0` строк означает «уже обработана».

**Минусы:** между чтением и обновлением остаётся окно; `0` строк не различает «уже applied»
и «удалена» → нельзя отдать корректную причину `already-applied`/`not-found`; снимок категории
и `original_proposed_category_id` может разойтись с фактически применённым (журнал станет
недостоверным). `SELECT … FOR UPDATE` даёт и блокировку, и снимок, и однозначную классификацию.

### Ключевое решение C: поведение при конфликтах (409) и отсутствии строки (404)

#### Вариант C1: `NotFound`/`Conflict` — результат строки (`skipped` + причина), HTTP `200` — **выбран**

`not-found` (строку уже отклонили) и `already-applied` (строку уже подтвердили) не прерывают
операцию и **не откатывают транзакцию**: строка попадает в «пропущено» с причиной, остальные
строки применяются и коммитятся вместе, агрегат возвращается с `200`.

**Плюсы:** буквальное исполнение решения 6 и edge case «строки страницы обработаны
параллельно»; одна устаревшая строка не ломает страницу из 50–200; повторный запуск безопасен;
`skipped`-причины дают диагностику без чтения логов.

**Механика:** классификация выполняется по результату `SELECT … FOR UPDATE` в `READ COMMITTED`:
если параллельная транзакция изменила строку и зафиксировала изменение (в том числе пока мы
ждали блокировку), PostgreSQL возвращает **актуальную** версию → `already-applied`; если строку
удалили и зафиксировали удаление — она не возвращается → `not-found`. Ошибки и отката нет.

#### Вариант C2: агрегированный `409`, если хотя бы одна строка уже обработана (или остановка на первой) — **отклонён**

**Минусы:** противоречит решению 6; в реальном сценарии второго окна операция на 50 строк
падала бы целиком из-за одной строки; клиенту пришлось бы вручную исключать обработанные id
и повторять — то есть реализовывать ту самую логику, которую задача требует от сервера.

#### Вариант C3: предварительная блокировка `SELECT … FOR UPDATE` до обработки — **выбран (в составе B2; пересмотрено 2026-11-13)**

В первой редакции вариант был отклонён — но **для схемы B1** («строка = транзакция»), где
единственной надёжной точкой решения была транзакция самой строки, а предварительный `SELECT`
лишь маскировал гонку.

В схеме B2 (одна транзакция) `SELECT … FOR UPDATE` перестаёт быть «предфильтрацией» и становится
**единственным корректным механизмом**: он одновременно (а) фиксирует снимок строк для
классификации, (б) удерживает строки от конкурентных изменений до commit, (в) задаёт
детерминированный порядок взятия блокировок. Без него между классификацией и применением
возникает окно, и «пропуск» перестаёт быть достоверным.

#### Вариант C4: прервать транзакцию и вернуть ошибку при первом конфликте — **отклонён**

Прямо противоречит решению 6 («логические конфликты не откатывают операцию; остальные строки
применяются в той же транзакции»). При устаревшей странице админ не смог бы разобрать очередь
вовсе.

#### Вариант C5: `FOR UPDATE SKIP LOCKED` вместо ожидания блокировки — **отклонён**

**Минусы:** пропускались бы строки, которые **ещё не обработаны**, а только заняты параллельной
операцией; причина «пропущено» стала бы ложной (`already-applied`/`not-found` не подходят),
пришлось бы вводить новый исход (`locked`), которого нет в модели заказчика. Ожидание
блокировки ограничено (таймаут команды/дедлайн) и даёт достоверную классификацию после него.

### Ключевое решение D: откуда берётся применяемая категория

#### Вариант D1: только `ids`; категория читается из строки очереди в снимке транзакции — **выбран**

**Обоснование:** это поштучная семантика (`ConfirmAsync` читает `proposed_category_id` из БД);
правки администратора в UI сохраняются немедленно (`PUT /{id}/category` вызывается на
`onChange` селекта), поэтому «категория, показанная в строке» и значение в БД совпадают
в штатном сценарии. В массовом пути категория читается **в том же снимке**, что и блокировка,
поэтому «что применили» и «что записали в журнал» не могут разойтись. Это строже поштучного
пути, где категория берётся предварительным чтением **вне** транзакции: при гонке с
`PUT /{id}/category` поштучный путь теоретически может применить значение, прочитанное до
правки. Массовое присвоение выбранной категории — вне объёма задачи.

#### Вариант D2: клиент присылает снимок `[{ id, categoryId }]` — **отклонён**

**Минусы:** позволяет массово присвоить произвольную категорию (то, что задача явно исключает);
появляется второй источник истины рядом с `PUT /{id}/category`; клиентский снимок может
разойтись с БД (второе окно) — пришлось бы вводить политику разрешения конфликта, которой
у поштучной операции нет; расхождение «что применилось» и «что показано» стало бы
недиагностируемым.

### Ключевое решение E: журнал решений (ADR-033) внутри батча

#### Вариант E1: накопление draft'ов по применённым строкам и **один** вызов recorder'а после commit — **выбран**

**Плюсы:**
- Сохраняется инвариант поштучного пути: журнал — **последняя БД-операция** запроса, его сбой
  не может «отравить» change tracker (факт по коду `PrecategorizedCommodityService`: после
  неудачного `SaveChangesAsync` сущности остаются `Added` и были бы повторно вставлены следующим
  сохранением).
- Один батч-INSERT вместо N round-trip'ов; при одной транзакции это единственно возможная форма
  «после commit»: до commit события писать нельзя, после — все draft'ы уже известны.
- ADR-033 соблюдается поштучно: **одно событие на применённую строку** (`suggested` =
  `original_proposed_category_id`, `final` = применённая категория), события не агрегируются;
  пропущенные строки событий не дают (как и в поштучном пути).
- Атомарность согласована с данными: применённых строк без draft'а быть не может (draft
  формируется из того же снимка), откат транзакции не даёт ни данных, ни событий.

**Минусы:** сбой журнала теряет сразу всю пачку событий батча (best-effort, NFR-3 ADR-033 —
принято, но потеря масштабируется до N); recorder вызывается с `CancellationToken.None`
(данные уже зафиксированы — события не должны теряться из-за ухода администратора со страницы).

#### Вариант E2: вызов recorder'а на каждой строке — **отклонён**

**Минусы:** N INSERT-ов; внутри одной транзакции это ещё и удлинение времени удержания
блокировок; при сбое журнала оставшиеся в трекере `Added`-сущности попадают в следующее
сохранение, то есть сбой журнала начал бы откатывать **пользовательские подтверждения**
(нарушение NFR-3 ADR-033 по существу). После commit N вызовов бессмысленны — батч-INSERT дешевле
и атомарнее по форме.

#### Вариант E3: писать журнал **внутри** той же транзакции — **отклонён**

**Минусы:** «наблюдаемость» становится частью бизнес-атомарности: сбой журнала откатывал бы
подтверждённые категории, что противоречит NFR-3 ADR-033 (recorder не блокирует решение);
кроме того, INSERT'ы в журнал удлиняли бы транзакцию и удержание блокировок `commodities`.
Transactional outbox — возможное будущее решение, но не в объёме этой задачи.

### Ключевое решение F: пределы, изоляция, таймауты, отмена

#### Вариант F1: `MaxBulkIds = 200`, `READ COMMITTED`, серверный дедлайн на операцию, без новых настроек — **выбран**

- **`MaxBulkIds = 200`** — константа эндпоинта (по образцу `MaxLimit = 200` в `GET` и
  `MaxCommodityIds = 200` в ADR-028). Обоснование: `GET` не может вернуть страницу больше 200
  строк, значит **любая страница, которую видит админ, обязана обрабатываться одним запросом**;
  меньший предел сломал бы этот инвариант для API-клиентов с `limit > 100`. UI ограничен
  размерами 5/10/20/50/100 (дефолт 10), то есть реальный худший случай — 100 строк; 200 —
  верхняя страховка, а не рабочий сценарий. Инвариант «`MaxBulkIds` = `GET MaxLimit`»
  фиксируется комментарием в коде и тестом; при будущем изменении `MaxLimit` их надо менять
  вместе.
- **`READ COMMITTED`** (явно указывается при `BeginTransaction`) — обязательное условие
  семантики пропуска: после ожидания блокировки строка перечитывается в актуальной версии
  и классифицируется как `already-applied`/`not-found`. В `REPEATABLE READ`/`SERIALIZABLE`
  конкурентное обновление дало бы `40001` (ошибку сериализации) → по решению 6 это был бы
  технический сбой с полным откатом вместо пропуска, то есть требование заказчика не выполнялось
  бы. Остальные чтения транзакции — однократные и по заблокированным строкам, поэтому
  «несогласованный снимок» не создаёт проблем.
- **Дедлайн операции** — кодовая константа `BulkOperationTimeout = 90 s`, применяемая через
  `CancellationTokenSource.CreateLinkedTokenSource(requestAborted, deadline)` на входе
  эндпоинта. Вывод значения: `proxy_read_timeout 120 s` минус ~30 с запаса на авторизацию,
  ответ, сериализацию и сеть. Дедлайн **меньше** прокси-таймаута, поэтому при исчерпании
  бюджета сервер успевает откатить транзакцию и вернуть понятный `500` с текстом, вместо
  «обрыва» nginx без тела. `CommandTimeout` Npgsql (30 с на команду) остаётся вторым,
  более ранним предохранителем для отдельного «тяжёлого» `UPDATE`/ожидания блокировки.
- **Новых опций конфигурации нет** (KISS/YAGNI): внешних вызовов (ИИ) в операции нет, значение
  лимита диктуется `GET`, значение дедлайна — прокси-таймаутом; менять их в эксплуатации
  без изменения кода не требуется. Если замеры на dev/прод покажут иную стоимость строки,
  меняются две константы — контракт не меняется.

#### Вариант F2: новая опция `PrecategorizedBulk:MaxIds` / `RequestTimeout` — **отклонён**

**Минусы:** настройка ради константы, которую нельзя осмысленно варьировать в эксплуатации;
усложняет `appsettings.json`, `docker-compose.yml`, `.env.example`, `AGENTS.md` и валидацию
старта. Отложено до появления реальной потребности.

#### Вариант F3: не вводить серверный дедлайн, положиться на nginx и Npgsql — **отклонён**

**Минусы:** `CommandTimeout` ограничивает команду, а не транзакцию: 200 команд по 29 с дают
почти произвольную длительность. `proxy_read_timeout` обрывает соединение, но сервер в этот
момент может ещё выполнять работу; клиент гарантированно не получает понятного текста, а
момент отката зависит от того, когда ASP.NET заметит разрыв. Собственный дедлайн делает исход
детерминированным: откат + `500` с текстом. Остаточная неопределённость возможна только если
дедлайн/разрыв пришёлся ровно на `COMMIT` (см. §9).

#### Вариант F4: автоматический retry при deadlock/ошибке сериализации — **отклонён (отложен)**

**Минусы:** операция идемпотентна и безопасна для повтора (обработанные строки станут
`skipped`), поэтому повтор — одно действие администратора; автоматический retry внутри запроса
удваивал бы худшую длительность, мог бы усилить конкуренцию и потребовал бы политики
«сколько раз и с какой паузой». YAGNI до появления статистики deadlock'ов.

#### Вариант F5: `REPEATABLE READ` или `SERIALIZABLE` — **отклонён**

См. F1: конкурентное обновление заблокированной строки в этих уровнях даёт ошибку сериализации,
то есть **технический сбой вместо пропуска** — прямое нарушение решения 6. `SERIALIZABLE`
дополнительно потребовал бы retry-политики (F4). Для схемы «прочитать под блокировкой →
классифицировать → изменить» `READ COMMITTED` — не компромисс, а необходимое условие семантики.

## Решение

Сводка принятых решений: **A3** (два stateless-эндпоинта, вся страница одним запросом),
**B2** (одна транзакция на весь батч, `READ COMMITTED`, `SELECT … FOR UPDATE`),
**C1/C3** (`NotFound`/`Conflict` → `skipped` с причиной, HTTP `200`; классификация под
блокировкой), **D1** (только `ids`, категория — из снимка строки), **E1** (накопление draft'ов,
один вызов recorder'а после commit), **F1** (`MaxBulkIds = 200`, дедлайн 90 с, без новых
настроек).

### Обоснование

1. **Контракт должен быть серверным, а не клиентским циклом** (A3 против A2): только так
   «частичный успех», «границы страницы», «права доступа» и **атомарность при техническом
   сбое** становятся проверяемыми автотестами (решение 7), а бизнес-итоги считает сервер.
2. **Один запрос и одна транзакция — требование заказчика, а не оптимизация** (решения 4–5):
   архитектура обязана сделать эту форму корректной, а не обходить её.
3. **Логический конфликт — это результат, а не ошибка запроса** (C1): при одной транзакции
   единственный способ не откатывать страницу из-за чужого окна — классифицировать строки
   **до** изменений, под блокировкой (`SELECT … FOR UPDATE` в `READ COMMITTED`).
4. **Технический сбой — это откат всего** (B2): commit ровно один и он последний; любое
   исключение/таймаут/отмена до него не оставляет применённых строк.
5. **Журнал остаётся наблюдательным** (E1, NFR-3/ADR-033): один вызов после commit, best-effort,
   по событию на применённую строку; сбой журнала не влияет ни на коды, ни на счётчики, ни на кэш.
6. **Стоимость батча ограничена сверху и по времени** (F1): предел 200 id (инвариант с `GET`),
   дедлайн 90 с (ниже прокси-таймаута), детерминированный порядок блокировок; всё остальное —
   документированный риск и отдельное решение об индексе (ADR-027, риск 6).

### 1. Контракты API

Оба эндпоинта добавляются в существующий модуль
`Api/Modules/PrecategorizedCommodities/PrecategorizedCommodityEndpoints.cs` (группа
`/api/precategorized-commodities`, тег `PrecategorizedCommodities`), регистрация — в уже
существующем `MapPrecategorizedCommodityEndpoints()`. Стиль ошибок — текстовые тела, без
ProblemDetails (ADR-027 п. 7).

| Метод и путь | Назначение | Коды |
|---|---|---|
| `POST /api/precategorized-commodities/batch/confirm` | массовое подтверждение строк текущей страницы | `200`, `400`, `401`, `403`, `500` |
| `POST /api/precategorized-commodities/batch/decline` | массовое отклонение строк текущей страницы | `200`, `400`, `401`, `403`, `500` |

- `POST`, а не `DELETE` с телом: тело у `DELETE` не гарантированно доходит через прокси/клиентов;
  поштучный `DELETE /{id}` (без тела) остаётся без изменений.
- Литеральный сегмент `batch` не конфликтует с `{id:guid}` (ограничение маршрута), порядок
  маппинга в группе значения не имеет.
- Порядок проверок — как в существующих эндпоинтах и ADR-028: `401` (нет пользователя) →
  `403` (не админ, явный `Results.StatusCode(403)`) → валидация `400` → сервис. Проверка прав
  выполняется **до** разбора тела: не-админ с некорректным телом получает `403`, а не `400`.
- `404`/`409` на уровне всего запроса не используются: отсутствие строки и уже применённая
  строка — это `skipped`-результат при `200` (решение 6).

#### 1.1 `POST …/batch/confirm`

Запрос (до 200 id; на практике — ровно `items` текущей страницы):

```json
{ "ids": ["3f1c…", "9a02…"] }
```

Ответ `200`:

```json
{
  "requested": 50,
  "applied": 48,
  "skipped": 2,
  "updatedCommodities": 312,
  "results": [
    { "id": "3f1c…", "outcome": "applied", "categoryId": 23,
      "categoryName": "Молочные продукты", "updatedCommodities": 12 },
    { "id": "9a02…", "outcome": "skipped", "reason": "already-applied" }
  ]
}
```

- `results` — по одной записи на каждый id **в порядке запроса** (не в порядке блокировок);
  `outcome` ∈ `applied` | `skipped`; `reason` ∈ `already-applied` | `not-found` (только
  у `skipped`). Wire-имена — lowercase (стиль статусов/источников проекта).
- `results` — **послеоперационный отчёт**, а не прогресс: он формируется один раз после commit
  и не выдаётся частями (решение 5).
- `updatedCommodities` в агрегате — сумма по `applied`-строкам; в строке — значение, которое
  вернул `UPDATE` (может быть `0` — D10 ADR-027, решение всё равно состоялось).
- `categoryId`/`categoryName` — фактически применённая категория из снимка строки (D1);
  в `skipped`-строках отсутствуют.
- `requested` = число id в запросе (самодокументируемость сводки и тестов).
- `applied + skipped = requested` — инвариант ответа (проверяется тестом).

#### 1.2 `POST …/batch/decline`

Запрос — тот же (`{ "ids": [ … ] }`). Ответ `200`:

```json
{
  "requested": 50,
  "declined": 49,
  "skipped": 1,
  "results": [
    { "id": "3f1c…", "outcome": "declined" },
    { "id": "9a02…", "outcome": "skipped", "reason": "already-applied" }
  ]
}
```

- `outcome` ∈ `declined` | `skipped`; `reason` ∈ `already-applied` | `not-found`.
- `updatedCommodities` отсутствует: отклонение не меняет `commodities` (ADR-027, C4).
- Асимметрия имён полей (`applied`/`updatedCommodities` против `declined`) намеренная: она
  повторяет асимметрию существующих поштучных контрактов (`confirm` возвращает счётчик
  обновлённых товаров, `decline` — `204` без тела) и делает код и тесты самодокументируемыми.

#### 1.3 Валидация (`400`)

Правила — зеркально `CommodityBatchCategorizationEndpoints` (ADR-028 п. 1.2):

| Условие | Тело |
|---|---|
| `ids` отсутствует/`null`/пуст | `"ids must not be empty."` |
| `ids` содержит больше `MaxBulkIds` (200) | `"ids must contain at most 200 items."` |
| `ids[i] == Guid.Empty` | `"ids[i] is not a valid GUID."` |
| дубликат id | `"ids contains duplicate id '…'."` |

Дубликаты отклоняются, а не «схлопываются»: повтор id — ошибка клиента, и её надо ловить
(иначе один и тот же товар/событие журнала могли бы обработаться дважды). Правило согласовано
с ADR-028. Пустой список отклоняется на API, хотя UI не даёт отправить его (кнопки неактивны
на пустой странице): контракт не должен зависеть от дисциплины клиента.

#### 1.4 Почему «страница» — не понятие сервера, и почему предел равен 200

Сервер принимает произвольный список id и не знает ни о пагинации, ни о поиске. Область
«ровно текущая страница» обеспечивает клиент: он отправляет **снимок отрисованных строк**,
зафиксированный в момент подтверждения диалога (тот же массив `items`, что видит админ).
Следствия, которые принимаются явно:

- при активном поиске затрагиваются только строки страницы (критерий приёмки);
- строки других страниц (`X-Total-Count > items.length`) не затрагиваются;
- строки, исчезнувшие между отрисовкой и кликом, попадают в `skipped` (`not-found`);
- строки, появившиеся после отрисовки, не затрагиваются (их не было в снимке);
- серверная реконструкция страницы отклонена (вариант A6) — она обработала бы **не тот** набор.

**Предел и инвариант.** `MaxBulkIds = 200` равен `MaxLimit = 200` у `GET`. Это не совпадение,
а инвариант: «любая страница, которую `GET` способен вернуть, обрабатывается одним запросом».
Если предел сделать меньше (например, 50 или 100), то клиент с `limit = 200` получит страницу,
которую нельзя обработать массово без нарушения решения 4. UI-размеры (5/10/20/50/100, дефолт
10) — это фактический рабочий диапазон; 200 — верхняя граница API, а не рекомендуемый размер
страницы. Инвариант фиксируется тестом («страница максимального размера проходит валидацию»)
и комментарием рядом с константой: менять `MaxLimit` и `MaxBulkIds` можно только вместе.

#### 1.5 Технические ошибки (`500`)

| Ситуация | Ответ |
|---|---|
| Дедлайн операции исчерпан (сработал внутренний CTS, запрос клиента жив) | `500`, текст: `"Bulk operation timed out and was rolled back; no rows were applied."` |
| Исключение БД/сети (constraint, deadlock `40P01`, `CommandTimeout`, разрыв соединения) | `500`, текст: `"Bulk operation failed and was rolled back; no rows were applied."` |
| Клиент разорвал соединение (`RequestAborted`) | ответ не отправляется; сервер откатывает транзакцию |

- Различение «наш дедлайн» и «клиент ушёл» — по `HttpContext.RequestAborted`: если отменён
  именно запрос клиента, ответ писать некому (и не нужно). Иначе — `500` с текстом. `503`
  не используется (это не «сервис недоступен», а конкретная операция, которая откатилась),
  `504` остаётся за nginx.
- Во всех случаях **ни одна строка не применена**: commit ровно один, и он последний.
- Если разрыв/таймаут произошёл ровно на `COMMIT`, клиент не может знать, прошёл ли commit;
  состояние всё равно консистентно (либо вся страница, либо ничего), а `refresh()` показывает
  правду. Повторный запуск безопасен (§9).
- `504` от nginx возможен только если серверный дедлайн по какой-то причине не сработал;
  это не отдельная семантика, а тот же сценарий «исход неизвестен → обновить список».
- Тексты `500` — английские, как и остальные ошибки API (ADR-027 п. 7), и служат диагностике.
  Клиент для `5xx` показывает локализованное сообщение «Операция не выполнена, изменения
  не применены» (и не подставляет серверный текст в тост), чтобы админ видел понятную причину,
  а не техническую строку.

### 2. Транзакция: порядок операций, изоляция и блокировки

#### 2.1 Точный порядок

```text
BEGIN;  -- READ COMMITTED (указывается явно)

-- 1. Блокировка + снимок + классификация (один запрос, порядок детерминирован)
SELECT id, name, normalized_name, merchant_id, proposed_category_id,
       original_proposed_category_id, status
FROM precategorized_commodities
WHERE id = ANY(@ids)
ORDER BY normalized_name, merchant_id, id
FOR UPDATE;

-- 2. Применение (только для строк, классифицированных как proposed),
--    в том же детерминированном порядке:
--    confirm:  UPDATE commodities SET category_id = @cat, category_name = @name
--              WHERE name = @exactName AND (category_id IS NULL OR category_id = 0);
--    decline:  изменений в commodities нет.

-- 3. Одна set-based операция по очереди для всех applied-строк:
--    confirm:  UPDATE precategorized_commodities
--              SET status = 1, applied_at = @now
--              WHERE id = ANY(@appliedIds);
--    decline:  DELETE FROM precategorized_commodities WHERE id = ANY(@appliedIds);

COMMIT;

-- 4. После commit, вне транзакции:
--    cache.TryAdd(normalized_name, applied_category) — по каждой applied-строке confirm;
--    recorder.RecordAsync(drafts) — один вызов, последняя БД-операция запроса.
```

Ключевые свойства:

- **Классификация и снимок — один запрос.** `status = applied` → `already-applied`;
  отсутствие id в результате → `not-found`; остальные → `proposed`. Никаких отдельных
  «проверок перед транзакцией»: они бы создали окно. `ORDER BY` задан в самом SQL: PostgreSQL
  размещает узел `LockRows` над `Sort`, поэтому блокировки берутся именно в этом порядке,
  а не в порядке индекса/сканирования.
- **Порядок строк в результате `SELECT` не определяет порядок ответа.** Результаты
  сопоставляются по id и отдаются в порядке запроса (§1.1), а обрабатываются — в порядке
  `(normalized_name, merchant_id, id)`.
- **Set-based обновление очереди вместо 200 `SaveChanges`.** Строки читаются проекцией
  (без change tracking), статус меняется одним `UPDATE … WHERE id = ANY(...)`; это короче
  транзакцию и не накапливает 200 tracked-сущностей. `applied_at` — одно значение `@now`
  на весь батч (одно чтение `TimeProvider`); отличие от поштучного пути (там время читается
  на строку) не влияет на бизнес-смысл: `AppliedAt` — отметка решения, а не очередь событий.
- **`commodities` обновляется по одному имени за statement, а не одним `UPDATE … FROM unnest`.**
  Это осознанный выбор в пользу детерминированного порядка блокировок: один set-based `UPDATE`
  блокировал бы строки в порядке сканирования, который мы не контролируем. Плата — N statement'ов
  (N ≤ 200) в одной транзакции. Предикат `category_id IS NULL OR = 0` сохраняется дословно
  (NFR-1 ADR-027: массового применения по очищенному ключу нет).
- **`IgnoreQueryFilters()` обязателен** для `commodities` (глобальный доступ вне owner-scoping —
  ADR-027, D8/NFR-5), как и в поштучном `ConfirmAsync`.
- **Поштучные методы репозитория в batch не вызываются.** `ConfirmAsync`/`DeleteProposedAsync`
  открывают собственную транзакцию (или сохраняют изменения самостоятельно) — вызов в цикле
  сломал бы B2 и породил бы вложенные транзакции. Batch-путь работает только с новыми
  batch-методами; общим с поштучным путём остаётся **приватный шаг обновления `commodities`
  по имени** (предикат и сеттеры не дублируются).
- **`SELECT … FOR UPDATE` выполняется raw SQL без LINQ-композиции** (`FromSqlRaw`/`SqlQueryRaw`
  + `ToListAsync`), чтобы `FOR UPDATE` не оказался во вложенном запросе и порядок блокировок
  оставался предсказуемым.
- **Отклонение** не трогает `commodities` и не пишет событий журнала: удаляются только
  классифицированные `proposed`-строки.

#### 2.2 Изоляция `READ COMMITTED` — почему это часть решения

`SELECT … FOR UPDATE` в `READ COMMITTED` ведёт себя так, как требует решение 6:

- если параллельная транзакция уже **зафиксировала** изменение строки, `FOR UPDATE` берёт
  блокировку и возвращает **актуальную (перечитанную) версию** строки → `status = applied` →
  `already-applied` (пропуск, без ошибки);
- если строку **удалили** и зафиксировали удаление, она не возвращается → `not-found` (пропуск);
- если параллельная транзакция **ещё не завершилась**, мы ждём (ограниченно `CommandTimeout`
  и дедлайном) и после её commit получаем актуальную версию (пропуск или применение),
  после rollback — прежнюю.

В `REPEATABLE READ`/`SERIALIZABLE` первый сценарий дал бы `40001 could not serialize access due
to concurrent update`: это техническая ошибка, то есть полный откат вместо пропуска — нарушение
решения 6. Поэтому уровень изоляции фиксируется явно, а не оставляется «по умолчанию сервера».

`READ COMMITTED` также означает, что `UPDATE commodities` перепроверяет предикат
`category_id IS NULL OR = 0` на актуальной версии строки после ожидания блокировки: товар,
которому категорию только что присвоил пользователь, не будет перезаписан. Это ровно поведение
поштучного пути.

#### 2.3 Блокировки, порядок и deadlock-риски

**Что и как долго удерживается.** Строки очереди (`FOR UPDATE`) и строки `commodities`,
затронутые `UPDATE`, удерживаются от первого `SELECT` до `COMMIT` — то есть на всю операцию,
включая до 200 Seq Scan-`UPDATE`. Это главный компромисс одной транзакции (§«Последствия»).

**Порядок взятия блокировок (митигация deadlock'ов):**

| Пара путей | Порядок | Риск цикла |
|---|---|---|
| bulk vs bulk | оба: строки очереди по `(normalized_name, merchant_id, id)` → затем `commodities` по `normalized_name` | цикла нет: один и тот же глобальный порядок |
| bulk vs `POST /{id}/confirm` | поштучный: строка очереди → `commodities` одного имени; bulk: строки очереди → `commodities` по возрастанию `normalized_name` | цикла нет: поштучный держит ровно одно имя и не берёт новых блокировок очереди |
| bulk vs `PUT /{id}/category`, `DELETE /{id}` | эти пути берут только блокировку строки очереди (плюс FK-проверки) | цикла нет; возможны только ожидания |
| bulk vs пакетное сохранение категорий на странице «Товары» (несколько имён в request-порядке) | два многоимённых пути с разным порядком имён | **теоретически возможен**; митигация — детерминированный порядок в bulk, полный откат и безопасный повтор; выравнивание порядка в batch-пути «Товаров» — отдельная задача |

**Что происходит при deadlock.** PostgreSQL обнаруживает цикл и прерывает одну из транзакций
(`40P01`). Если прерван bulk — исключение → транзакция откатывается целиком → `500` с текстом
(§1.5); ничего не применено, повтор безопасен. Автоматический retry не вводится (F4).

**Чего решение не делает:** не вводит advisory-локи (B5), не сериализует операции глобально,
не меняет схему и индексы. Риск конкуренции принимается и документируется; «лечение» стоимости
`UPDATE` — индекс на `commodities(name)` — остаётся отдельным решением ADR-027 (риск 6)
и в объём этой задачи не входит.

#### 2.4 Стоимость и оценка длительности

- Один `UPDATE commodities` по точному имени — Seq Scan по таблице всех пользователей
  (индекса на `name` нет). Стоимость строки растёт с объёмом `commodities`, а не с размером
  очереди.
- Худший случай: 200 строк × (Seq Scan + `UPDATE` + WAL) в одной транзакции. Это **не**
  «секунды по определению»: на реальном объёме таблицы время надо замерить на dev-стенде
  (входит в ручную приёмку). Именно поэтому вводятся предел 200, дедлайн 90 с и полный откат,
  а не «надежда на быстрый диск».
- `CommandTimeout` Npgsql (30 с) ограничивает отдельный statement, включая ожидание блокировки;
  дедлайн 90 с ограничивает всю операцию. Что сработает раньше — то и откатит (оба варианта
  дают «ничего не применено»).
- Если замеры покажут, что 100 строк (реальный максимум UI) не укладываются в бюджет,
  решение не меняется на порционность: уменьшается **размер страницы** (UI-настройка,
  эксплуатационный рычаг) или принимается отдельное решение об индексе. Порционность
  и прогресс запрещены решением заказчика.

### 3. Кэш и журнал после commit

**Кэш (ADR-019).**

- `TryAdd(CommodityNameNormalizer.NormalizeName(name), appliedCategory)` — по каждой
  **applied**-строке confirm, строго **после** `COMMIT`.
- `TryAdd` first-wins/no-op сохраняется дословно: существующая запись не перезаписывается,
  «замороженный» кэш (ADR-019, `MaxSize`) молча игнорирует новые записи.
- При откате транзакции записей в кэш нет вообще (кода после `COMMIT` не достигаем).
- Отклонение кэш не трогает.

**Журнал (ADR-033).**

- Draft'ы формируются **из снимка** для каждой applied-строки: `CommodityName = name`,
  `SuggestionSource = precategorized`, `SuggestedCategory = original_proposed_category_id`,
  `FinalCategory = proposed_category_id` (применённая), `AcceptedByUserId = UserContext.UserId`
  (серверное значение, ADR-033 F1), `AcceptedByAdmin = true`.
- Пропущенные строки draft'ов не дают (как `NotFound`/`Conflict` в поштучном пути).
- **Один** вызов `ICategorizationDecisionRecorder.RecordAsync(drafts)` после `COMMIT` —
  последняя БД-операция запроса. Recorder по контракту не бросает; защитный `catch` с `Error`
  гарантирует NFR-3 и при нарушении контракта.
- Вызов выполняется с `CancellationToken.None`: данные уже зафиксированы, и уход администратора
  со страницы (отмена HTTP-запроса) не должен уничтожать события. Это осознанное отличие
  от поштучного пути (там токен передаётся как есть) и кандидат на выравнивание отдельным
  решением.
- Сбой журнала не влияет на HTTP-код, счётчики и кэш: операция уже состоялась.
- Потеря при сбое журнала масштабируется до N событий (весь батч) — принято как best-effort
  (NFR-3), но фиксируется в наблюдаемости (`Warning` со счётчиком).

**Change tracker.** Строки очереди читаются проекцией (не tracked), `commodities` и статусы
меняются set-based. В трекере не накапливается 200 сущностей, и «отравление» трекера после
неудачного `SaveChangesAsync` невозможно по конструкции; журнал всё равно остаётся последней
БД-операцией (инвариант ADR-033).

### 5. UX-контракт

**Расположение и доступность.** Две кнопки — «Подтвердить все» и «Отклонить все» — в шапке
страницы `PrecategorizedCommoditiesPage` (рядом с «Обновить»), не в таблице. Кнопки не
рендерятся для не-админа (гейт страницы уже возвращает «Доступ запрещён»; сервер всё равно
ответит `403`). Кнопки `disabled`, когда список пуст, идёт загрузка/ошибка или уже выполняется
массовая операция (обе кнопки блокируются одновременно — вторая операция невозможна).

**Диалог подтверждения** — существующий `CustomDialog`, один экземпляр с состоянием
`{ action: 'confirm' | 'decline' }`:

- подтверждение: «Подтвердить все N предложений на этой странице? Категории будут применены
  ко всем товарам с этими названиями у всех пользователей.»;
- отклонение: «Отклонить все N предложений на этой странице? Предложения будут удалены
  безвозвратно. Категории товаров не изменятся.»;
- `N` = `items.length` (**строки текущей страницы**, не `X-Total-Count`);
- «Отмена»/закрытие диалога — никаких запросов, ничего не меняется (критерий приёмки);
- диалог закрывается сразу при подтверждении; состояние выполнения живёт в хуке
  (у `CustomDialog` нет busy-режима, и он не добавляется — YAGNI).

**Снимок страницы и один запрос.** В момент подтверждения диалога массив `items` фиксируется
в состоянии хука; из него берутся **id** и отправляются **одним** `POST` в `batch/confirm`
или `batch/decline`. Список во время операции не перезапрашивается, повторных запросов нет;
обрабатываются ровно те строки, которые видел администратор.

**Busy-состояние (без прогресса и без чисел).** Пока идёт запрос — inline-строка в шапке
с `role="status"` и `aria-live="polite"`: «Подтверждаем предложения…» / «Отклоняем
предложения…» и индетерминированный спиннер. **Никакого счётчика, процентов, «X из N»,
шага или порций нет** (решение 5). На это время блокируются: обе массовые кнопки, поштучные
кнопки строк, «Обновить», размер страницы, поиск, пагинация (с `title`-подсказкой о причине) —
чтобы сводка относилась к тому набору строк, который на экране (паттерн блокировок ADR-028, C5).

**Итоговая сводка.** По завершении:

- успех: «Подтверждено: 48, пропущено: 2» (+ для подтверждения «обновлено товаров: 312») /
  «Отклонено: 49, пропущено: 1»; показывается inline в `role="status"` (не исчезает сама) **и**
  дублируется тостом по конвенции ADR-020; сводка сохраняется до следующего действия или смены
  страницы;
- если пропуски есть — рядом со сводкой причина(ы) в человекочитаемом виде: «уже обработаны
  в другом окне» (`already-applied`) и/или «больше не существуют» (`not-found`). Причины
  агрегируются по счётчикам, без списка id (детали есть в `results`, если понадобится
  диагностика);
- ошибка (`5xx`, сеть): тост с текстом ошибки (`toast.error`, конвенция ADR-020) + inline
  сообщение «Операция не выполнена, изменения не применены» — по решению 6 при техническом
  сбое не применено **ничего**; кнопки разблокируются, список перезагружается, повторный запуск
  обработает всю страницу заново (безопасен);
- после успеха и после ошибки — автообновление списка (`refresh()` текущей страницы).

**Опустевшая страница.** Если после операции страница опустела и это не первая страница —
хук перезапрашивает последнюю доступную (исправление существующего дефекта нормализации,
ADR-028 §6); пустое состояние показывается штатно, без ошибки; массовые кнопки становятся
неактивными.

**Клиентская логика (полный псевдокод, без порций):**

```text
onClick(action):
    open dialog(action, count = items.length)
onConfirm:
    ids = snapshot(items).map(i => i.id)
    isRunning = true; summary = null; error = null
    try:
        response = POST batch/<action> { ids }          // один запрос, одна транзакция
        summary = { applied|declined: response.applied|declined,
                    skipped: response.skipped,
                    updated: response.updatedCommodities,
                    reasons: groupReasons(response.results) }
        toast(summary)
    catch e:
        error = e.message                                 // «изменения не применены»
        toast.error(error)
    finally:
        isRunning = false
        refresh()                                         // автообновление списка
```

### 7. Наблюдаемость

- `Information` — одна строка на операцию: действие (`bulk-confirm`/`bulk-decline`), `requested`,
  `applied|declined`, `skipped` (с разбивкой по причинам), `updatedCommodities`, длительность
  в миллисекундах, признак «дедлайн исчерпан».
- `Warning` — операция, где все строки пропущены (обычно — чужое окно/устаревший снимок);
  прерывание по дедлайну с числом классифицированных строк; длительность выше порога
  (константа, например 30 с) — раннее предупреждение о деградации; сбой журнала (счётчик
  потерянных событий).
- `Error` — исключение при выполнении транзакции (тип исключения, `SqlState` при наличии),
  сбой recorder'а.
- Наименования товаров — только `Debug` (практика «без ПД» ADR-027/028/033), ids — `Debug`.
- Метрик/телеметрии не добавляется: проект живёт на структурных логах (прецеденты ADR-027/033).

| Frontend | сборка и линт (тестовой инфраструктуры нет — ADR-011 E1); ручной прогон | `npm run build`, `npm run lint` |
| Ручной прогон (dev-стенд) | массовое подтверждение и отклонение на странице с несколькими страницами пагинации; при активном поиске (затрагивается только страница); строка, подтверждённая во втором окне (попадает в «пропущено», операция не падает); пустая страница (кнопки неактивны); последняя страница опустела (переход на предыдущую); последняя страница без предыдущей (пустое состояние); обрыв сети (сообщение «изменения не применены», список консистентен, повтор безопасен); **100 строк** (busy-state без счётчика, UI не «висит», длительность замерена); двойной клик по кнопке (второй запрос не уходит) | чек-лист приёмки задачи |

Соответствие критериям приёмки (сводка): кнопки/область/диалог/пустая страница/busy-состояние —
UI-часть + ручной прогон; «только строки страницы», «одна транзакция», «полный откат при
техническом сбое», «пропуск при конфликте» — сквозные тесты на Testcontainers; «идентично
поштучному» (категория из строки, кэш, журнал) — unit + сквозные; «не-админы» — тесты
эндпоинтов; «автотесты проходят» — `cd Analytics && dotnet test`.

### 9. Явно зафиксированные семантики

| Вопрос | Решение |
|---|---|
| Область действия | Ровно `ids`, присланные клиентом = строки, отрисованные в момент подтверждения диалога |
| Форма запроса | Один `POST` на всю страницу; порций и повторных запросов нет |
| Транзакционность | Одна транзакция на весь батч, `READ COMMITTED`, commit ровно один и последний |
| Счётчик в диалоге | `items.length` (строки страницы), не `X-Total-Count` |
| Поиск | Учитывается косвенно: страница отрисована с фильтром, значит в снимке только отфильтрованные строки |
| Применяемая категория | `proposed_category_id` строки в снимке транзакции (правки через `PUT /{id}/category`, зафиксированные до блокировки, уже видны) |
| Кэш | `TryAdd` по нормализованному имени, только для `applied`, после commit (ADR-019) |
| Журнал | Одно событие на `applied`-строку, источник `precategorized`, после commit, один вызов recorder'а, best-effort |
| Уже подтверждённая строка | `skipped` / `already-applied`, без ошибки, без отката и без второго события |
| Удалённая/несуществующая строка | `skipped` / `not-found`, без ошибки и без отката |
| Все строки пропущены | `200`, `applied = 0`, `skipped = N` (не ошибка) |
| Технический сбой (исключение, дедлайн, deadlock, разрыв) | Полный откат: ни одна строка не применена; `500` с текстом (если есть кому ответить) |
| Повторный запуск | Идемпотентен по строкам: обработанные → `skipped`, оставшиеся обрабатываются |
| Отмена запроса клиентом | Транзакция откатывается целиком; ответ не отправляется |
| Разрыв/таймаут ровно на `COMMIT` | Исход неизвестен клиенту, но состояние консистентно (вся страница или ничего); `refresh()` показывает правду, повтор безопасен |
| Дубликаты id в запросе | `400` |
| Больше 200 id в запросе | `400` |
| Пустой `ids` | `400` |
| Не-админ | `403` (сервер), кнопки не отрисованы (UI) |
| Пустая страница | Массовые операции недоступны (кнопки `disabled`) |
| Две массовые операции одновременно (одно окно) | Невозможны: обе кнопки блокируются на время выполнения |
| Две массовые операции одновременно (два администратора) | Вторая ждёт блокировки строк, затем пропускает уже обработанные; ожидание ограничено `CommandTimeout`/дедлайном, при исчерпании — полный откат второй операции |
| Поштучные действия во время массовой | Заблокированы (вместе с пагинацией/поиском/размером/«Обновить») |
| Обновление списка | Только после завершения (успех или ошибка), во время операции список не перезапрашивается |
| Опустевшая последняя страница | Переход на предыдущую доступную (исправление нормализации хука) |
| Существующие поштучные контракты | Без изменений (пути, тела, коды, транзакция на строку) |
| `MaxBulkIds` | 200 = `GET MaxLimit` (инвариант); UI-размеры 5/10/20/50/100 |
| Дедлайн операции | 90 с (константа), ниже `proxy_read_timeout 120 s`; при исчерпании — полный откат |

## Последствия

### Положительные

- Администратор разбирает очередь страницами: один диалог и один клик вместо десятков.
- Атомарность технического сбоя — свойство серверной транзакции, а не аккуратности UI: либо вся
  страница, либо ничего; состояние после ошибки всегда консистентно.
- Логический конфликт (второе окно, устаревшая страница) не ломает операцию и не заставляет
  администратора вычищать id вручную: строки пропускаются с причиной.
- Клиент предельно прост (один запрос, busy-state, сводка, `refresh`) — критично при отсутствии
  frontend-автотестов (ADR-011 E1).
- Нет нового серверного состояния (job'ов, сессий, TTL), нет распределённых блокировок,
  нет изменений схемы БД, миграций, индексов, конфигурации, nginx и Go-сервисов.
- Поштучный путь не рефакторится по транзакции: риск регрессии ограничен общим приватным
  helper'ом обновления `commodities` и закрывается существующими тестами.
- Повторный запуск безопасен при любом исходе, включая неизвестный (обрыв на commit).

### Отрицательные / компромиссы

- **Длинная транзакция — главная плата.** Блокировки строк очереди и затронутых товаров
  удерживаются на всю операцию: до 200 × (Seq Scan по `commodities` без индекса на `name`).
  Параллельные поштучные подтверждения/отклонения этих же строк и пользовательские сохранения
  категорий этих же товаров ждут (ограниченно `CommandTimeout`/дедлайном).
- **Нет промежуточной обратной связи.** До 200 строк администратор видит только спиннер;
  при медленной БД операция выглядит «зависшей». Принято заказчиком (решение 5) и смягчено
  дедлайном и понятной ошибкой.
- **Технический сбой откатывает всю страницу**, включая 199 корректных строк. Принято
  (решение 6): альтернатива — частично применённая страница, что заказчик исключил.
- **Потеря журнала масштабируется до N событий** при сбое recorder'а (best-effort, ADR-033),
  хотя данные и кэш уже зафиксированы.
- **Возможен deadlock с многоимённым пользовательским путём** (пакетное сохранение категорий
  на странице «Товары»), если порядок имён там отличается. Митигация — детерминированный
  порядок в bulk, полный откат, безопасный повтор; выравнивание порядка — отдельная задача.
- **Риск регрессии поштучного подтверждения** из-за общего helper'а обновления `commodities`:
  митигация — существующие `PrecategorizedCommodityServiceTests` и
  `PrecategorizedCommodityWorkflowTests` остаются без изменений и должны быть зелёными.
- **Фронтенд без автотестов** (унаследованное ограничение): проверяется `build` + `lint` +
  ручным прогоном; поэтому вся бизнес-логика вынесена на сервер.

### Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Длительность операции превышает `proxy_read_timeout` (накопление данных, Seq Scan по `commodities`) | Низкая–средняя (зависит от объёма `commodities`) | `MaxBulkIds = 200`, UI-максимум 100, дедлайн 90 с < 120 с, полный откат и понятный `500`; замер на dev-стенде входит в приёмку; долгосрочное лечение — индекс на `commodities(name)` (ADR-027, риск 6, отдельное решение) |
| `CommandTimeout` Npgsql (30 с) срабатывает на одном «тяжёлом» `UPDATE` или ожидании блокировки | Низкая | Это технический сбой → полный откат, ничего не применено, повтор безопасен; диагностируется по `SqlState`/типу исключения в логе |
| Lock-контеншн: пользовательские сохранения ждут массовую операцию | Средняя (при активной работе) | Детерминированный порядок блокировок; ограниченная длительность (дедлайн); администратор может уменьшить размер страницы (5/10/20) как эксплуатационный рычаг |
| Deadlock с параллельным многоимённым путём | Низкая | Детерминированный порядок в bulk; PostgreSQL прерывает одну транзакцию; bulk откатывается целиком, повтор безопасен; автоматический retry не вводится (F4) |
| Два администратора запускают массовую операцию одновременно | Низкая | Вторая ждёт блокировки и пропускает обработанные; при исчерпании таймаута — полный откат и `500`; повтор безопасен |
| Журнал теряет до N событий при сбое recorder'а | Низкая | Best-effort по ADR-033 (NFR-3); `Warning` со счётчиком; события только наблюдательные |
| Один и тот же товар/событие обработаны дважды | Низкая | Дубликаты id → `400`; статус под блокировкой переводится в `applied`; повторный проход → `skipped/already-applied`; unique-индексы очереди неизменны |
| Двойной клик / две вкладки запускают операцию дважды | Низкая | Кнопки блокируются на время выполнения; на сервере повтор безопасен (`skipped`) |
| Клиент «завис» на спиннере при сетевом обрыве или медленной операции | Низкая | Серверный дедлайн; обработка ошибки: тост + «изменения не применены», разблокировка, обновление списка |
| Устаревшая страница: строки уже удалены/подтверждены | Средняя (штатно) | `skipped` с причиной, без ошибки и без отката |
| `MaxLimit` у `GET` и `MaxBulkIds` разойдутся при будущей правке | Низкая | Инвариант зафиксирован тестом и комментарием; менять только вместе |
| Неизвестный исход при обрыве ровно на `COMMIT` | Очень низкая | Состояние консистентно (вся страница или ничего); `refresh()` показывает правду; повтор безопасен |

### Ограничения решения

1. Область массовой операции — только присланные клиентом id; «вся очередь», «все под фильтром»
   и выборочное выделение не поддерживаются (вне объёма задачи).
2. Применяется категория строки, а не присланная клиентом: массовое присвоение категории —
   отдельная задача, требующая своего контракта.
3. **Прогресса нет** (решение 5): ни счётчика, ни порций, ни промежуточных результатов;
   обратная связь — только busy-state и финальная сводка.
4. **Одна транзакция на страницу** (решение 4): операция не масштабируется на «всю очередь»
   без нового решения заказчика; при техническом сбое теряется работа по всей странице.
5. Analytics по-прежнему рассчитан на один экземпляр (ADR-027, D12); операция не вводит
   распределённых блокировок. Конкурентные операции двух администраторов разрешаются
   блокировками строк и классификацией, а не координацией.
6. Стоимость строки остаётся прежней (Seq Scan без индекса на `name`); массовость увеличивает
   число таких `UPDATE`, но не их стоимость. Индексы — отдельное решение ADR-027, риск 6.
7. Frontend-автотестов нет (ADR-011 E1): регрессионный барьер — `build` + `lint` + ручной прогон.
8. Известное (не исправляемое здесь) узкое место: `PUT /{id}/category` делает обычное чтение
   и последующую запись без условного предиката — при гонке с подтверждением категория строки
   может измениться уже после применения. Массовый путь этот риск не увеличивает (он читает
   под блокировкой); исправление — отдельным решением.

## Связь с другими ADR

- **[ADR 027](027-background-commodity-precategorization.md)** — дополняется: админский API
  получает два пакетных эндпоинта; поштучная транзакция подтверждения (D10), отклонение (C4),
  стиль ошибок и `401/403` не меняются. Для массового пути вводится **своя** единица
  атомарности — запрос (B2), что не отменяет D10 для поштучного пути. Риск 6 (отложенные
  индексы на `commodities`) остаётся в силе и становится заметнее: Seq Scan выполняется
  на каждую строку батча, поэтому вводятся предел 200 и дедлайн.
- **[ADR 028](028-commodities-page-categorization.md)** — переиспользуются: пакетный
  stateless-эндпоинт, правила валидации (`400`, дубликаты, `Guid.Empty`, верхний предел),
  `AdminAuthorization`, блокировка контролов на время операции (C5), §1.3 «страница — не
  понятие сервера». **Не переиспользуется** клиентская порционность: она была прецедентом
  для первой редакции ADR-036 и отклонена заказчиком (решение 4).
- **[ADR 030](030-precategorization-work-window.md)** — без изменений: массовые операции —
  ручные действия администратора, окно ограничивает только фон.
- **[ADR 033](033-categorization-decision-log.md)** — подтверждается: одно событие на строку
  очереди, `suggested` = `original_proposed_category_id`, после commit, recorder не бросает.
  Меняется только группировка вызовов (один вызов на батч, E1), что усиливает инвариант
  «журнал — последняя БД-операция» и делает набор событий атомарным по отношению к данным.
- **[ADR 034](034-commodity-name-normalization.md)** — используется: partial unique
  `proposed` по `normalized_name` исключает две применяемые строки с одним очищенным ключом
  в батче и делает порядок `(normalized_name, merchant_id, id)` детерминированным.
- **[ADR 019](019-in-memory-commodity-category-cache.md)** — `TryAdd` first-wins/no-op
  сохраняется дословно; новых путей записи в кэш нет, запись только после commit.
- **[ADR 020](020-toast-after-categorization-save.md)** — сводка использует тосты как конвенцию,
  дополняясь inline-строкой `role="status"` (тост автоскрывается через 5 с, а сводку нужно
  прочитать).
- **[ADR 023](023-analytics-url-routing.md)**, **[ADR 011](011-merchant-name-editing.md)** —
  маршруты не добавляются; ограничение «frontend-тестов нет» (E1) учтено в плане тестирования.
