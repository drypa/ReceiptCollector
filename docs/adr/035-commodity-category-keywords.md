# ADR-035: Ключевые слова категоризации товаров (админское управление boost/exclude-списками)

## Статус

Принято (проектирование). Основание — задача
[commodity-categories](../tasks/commodity-categories.md) (статус Draft, автор user, дата 2026-11-12;
FR-1…FR-10, NFR-1…NFR-4, UC-1…UC-5, критерии приёмки и edge cases обязательны к исполнению).
Реализация — по плану (декомпозиция задачи в `docs/plans/`).

**Дополняет, ничего не отменяет:** [ADR 009](009-auto-commodity-categorization.md) (контракты
suggest/apply чека, промт и `IAiClient`), [ADR 022](022-commodity-categories-food-detailing.md)
(откуда появился хардкод «Разграничения схожих категорий»), [ADR 019](019-in-memory-commodity-category-cache.md)
(in-memory кэш и его инвалидация/«заморозка»), [ADR 027](027-background-commodity-precategorization.md)
(фоновая прекатегоризация, single instance D12, стиль админских эндпоинтов, `MigrationRunner`),
[ADR 028](028-commodities-page-categorization.md) (общий resolver, страница «Товары»),
[ADR 032](032-merchant-default-commodity-category.md) (безопасное чтение кодов категорий),
[ADR 033](033-categorization-decision-log.md) (журнал решений — **не** затрагивается),
[ADR 034](034-commodity-name-normalization.md) (источник нормализованного названия).

> **Вне области (зафиксировано задачей и этим ADR):**
>
> - **ретроактивный пересчёт** — изменения влияют только на будущие запросы; уже проставленные
>   категории в `commodities`, строки `precategorized_commodities` и события
>   `categorization_decisions` не пересматриваются и не удаляются;
> - **аудит правок** слов (кто/когда добавил или удалил, история изменений) — не ведётся;
> - **телеметрия срабатываний** слов (сколько раз подсказка повлияла на ответ ИИ) — в
>   `categorization_decisions` не пишется, формат журнала не меняется;
> - **справочник категорий в БД** — не создаётся (ADR 005: категории — enum в коде);
> - **per-user / per-merchant** ключевые слова, приоритеты/веса слов, синонимы, стемминг,
>   морфология, regex/границы слов, импорт/экспорт;
> - **автопроставление категорий** (слова — только подсказки в промте, решение всегда за ИИ);
> - **редактируемые настройки ИИ** (промт, модель, лимиты) — в системе их нет и эта задача не вводит;
> - **синхронизация кэша между инстансами** (Redis/pub-sub/`LISTEN/NOTIFY`) — Analytics один;
> - изменения Go-сервисов (`backend/`, `bot/`), MongoDB, nginx, `docker-compose.yml`, `.env.example`,
>   `AGENTS.md`.

## Контекст

### Проблема

Всё, что уточняет ответы ИИ при категоризации, захардкожено в
`OpenAiCompatibleAiClient.BuildPayload` — блок «Разграничения схожих категорий» (11 строк с
примерами товаров, появился по ADR 022). Администратор видит ошибки категоризации в «Журнале
категоризации», но не может ни добавить слово, ведущее к категории, ни исключить слово, тянущее
товар в чужую категорию: любое изменение — правка кода и релиз.

Требуется раздел «Категории товаров» с двумя списками слов на категорию (**boost** —
«вероятно эта категория», **exclude** — «скорее не эта категория»), хранение в PostgreSQL,
мёрж только совпавших подсказок в промт ИИ и применение во **всех** точках категоризации.

### Требования (из задачи, сводка)

- **FR-1** — хранение «категория + тип списка (boost|exclude) + слово», категория — int-код enum.
- **FR-2** — хардкоженный блок «Разграничения…» → сид в БД, в коде отсутствует.
- **FR-3/FR-4** — API чтения (все категории, оба списка) и изменения (добавить/удалить слово).
- **FR-5** — слово 2–64 символа после trim, пустое/пробельное отклоняется, дубликат в рамках
  одного списка одной категории (case-insensitive) отклоняется, ≤ 200 слов на список, регистр
  введённого сохраняется.
- **FR-6** — матчинг по `CommodityNameNormalizer.NormalizeName(name)`:
  `normalized.Contains(word.ToLowerInvariant())`.
- **FR-7** — в промт попадают только совпавшие подсказки, формулировки «вероятно …» / «скорее не …»,
  формат ответа ИИ остаётся строгим JSON.
- **FR-8** — одна и та же логика в ручном suggest (чек, «Товары») и в фоне, без дублирования.
- **FR-9/FR-10** — админская страница с группами и чипами; не-админ не видит пункт, прямой заход и
  API → `403`.
- **NFR-1** — поиск совпадений без похода в БД на каждый товар (in-memory кэш + инвалидация).
- **NFR-2** — промт не растёт с числом слов в БД (только совпавшие).
- **NFR-3** — контракты существующих suggest/categories не меняются.
- **NFR-4** — изменение применяется к следующим запросам без рестарта.

## Рассмотренные варианты

### Ключевое решение A: модель хранения слов

#### Вариант A1: одна таблица `commodity_category_keywords` (+ колонка `normalized_word`) — **выбран**

Строка = одно слово в одном списке одной категории: `(category_id, list_type, word, normalized_word)`.
`normalized_word` — детерминированная производная от `word` (`trim + lowercase + collapse пробелов`),
заполняется приложением; уникальность — уникальный индекс по
`(category_id, list_type, normalized_word)`.

**Плюсы:**
- Уникальность case-insensitive гарантируется **БД** (не только проверкой в коде) — FR-5 и edge
  case «конкурентное редактирование с двух вкладок» выполняются структурно.
- `normalized_word` — обычная колонка: EF-модель выражает и колонку, и индекс, значит инвариант
  существует и в тестовой схеме (`EnsureCreatedAsync`) — прецедент ADR 034 (B1).
- Индекс `(category_id, list_type, normalized_word)` обслуживает и per-category чтение, и проверку
  дубликата; таблица крошечная (см. оценку объёма), отдельного индекса не требуется.
- Простая модель «строка = слово» даёт атомарные add/remove по `id`, честные коды ошибок и
  тривиальную сортировку чипов.

**Минусы:** при удалении/добавлении — по одной строке (не «список целиком»), значит нет
«сохранения всей формы одной кнопкой» (см. G).

#### Вариант A2: JSONB-колонка на категорию (`{boost: [...], exclude: [...]}`) — **отклонено**

**Минусы:** уникальность внутри массива БД не гарантирует (нужен триггер или всегда
read-modify-write → lost update при двух вкладках); нельзя адресно удалить слово по `id`
(только перезапись массива); уникальный индекс по элементам массива невозможен; EF-модель и тесты
усложняются. Выигрыш (одна строка на категорию) при объёме в сотни строк несущественен.

#### Вариант A3: `text[]` / `hstore`-колонки `boost_words`/`exclude_words` в строке категории — **отклонено**

Те же проблемы, что A2, плюс денормализация «категория как строка таблицы», при том что
справочника категорий в БД нет (ADR 005) и создавать его задача запрещает.

#### Вариант A4: уникальность через `citext` или выражение `lower(word)` — **отклонено**

**Минусы:** `citext` — новое расширение PostgreSQL; индекс по выражению не выражается EF-моделью,
поэтому в тестовой схеме (`EnsureCreatedAsync` из EF-модели) уникальности бы **не было** — тесты
проверяли бы нерелевантную схему (прямой прецедент отказа ADR 034, A2/B2). Колонка
`normalized_word` даёт тот же эффект без SQL-специфики.

#### Вариант A5: считать лимит 200 ограничением БД (триггер/EXCLUDE-констрейнт) — **отклонено**

**Минусы:** триггеры в проекте не используются; лимит — продуктовое правило, а не целостность
данных. Проверка в сервисе (count перед вставкой) достаточна: админ один, инстанс один, а
«перелёт» на единицы при гонке безвреден и сам себя останавливает (следующая вставка снова
увидит ≥ 200). Прецедент допущения о гонке — ADR 019 (`MaxSize` кэша «переоценивается» на
единицы).

#### Тип списка и кодирование категории

- `list_type varchar(16) NOT NULL` + `CHECK (list_type IN ('boost','exclude'))`, C# enum
  `KeywordListType { Boost, Exclude }` + `KeywordListTypeNames` (wire-имена, прецедент
  `CategorizationSourceNames`). В отличие от `suggestion_source` (ADR 033: открытое множество
  источников, CHECK сознательно не ставился), здесь множество **закрыто требованием FR-1**
  («два списка»): CHECK защищает от опечаток в ручном SQL и делает схему самодокументируемой;
  добавление третьего типа — продуктовое изменение, при котором правка констрейнта — одна строка.
- `category_id integer NOT NULL` + `CHECK (category_id <> 0)`, **без FK**: справочника категорий
  в БД нет (ADR 005), имена/группы считаются из `CommodityCategoryHelper` на чтении (прецеденты
  `proposed_category_id` ADR 027, `suggested_category_id` ADR 033, ADR 032 «безопасное чтение»).
  `Undefined` запрещён констрейнтом; `Other = 255` допустим (реальная категория).

### Ключевое решение B: механизм сида хардкоженного блока

#### Вариант B1: одноразовый `INSERT … ON CONFLICT DO NOTHING` в SQL-миграции, без маркера «сид» — **выбран**

Скрипт миграции создаёт таблицу и вставляет слова блока. Повторно он **не выполняется**:
`MigrationRunner` пишет имя скрипта в `migration_scripts_history`. Значит удалённое админом слово
не воскресает ни при рестарте, ни при деплое, ни при повторном запуске миграций. `ON CONFLICT
DO NOTHING` — страховка для ручного/частичного повторного выполнения того же скрипта (и для
случая, когда два слова блока нормализуются в один ключ).

**Плюсы:** «единственный источник правды — БД» (FR-2) выполняется буквально; нет фонового
upsert'а, который бы затирал работу админа; нет новых сущностей/колонок; откат — обычный SQL.

**Минусы:** «пустая» БД после ручного `TRUNCATE` не восстанавливается автоматически (нужен явный
повтор `INSERT`-блока из файла миграции) — фиксируется как эксплуатационная процедура, а не как
поведение приложения.

#### Вариант B2: идемпотентный upsert «недостающих» слов при каждом старте (hosted service) — **отклонено**

**Минусы:** прямо нарушает «удалённое слово не должно воскресать» — удалённый сид-слово
возвращался бы после каждого рестарта; чтобы этого избежать, понадобилась бы таблица-надгробий
или флаг «уже сидировали», то есть ровно та сложность, которую B1 получает бесплатно от
`migration_scripts_history`.

#### Вариант B3: колонка `is_seed` / `seeded_at` + кнопка «восстановить примеры» — **отклонено (YAGNI)**

**Минусы:** атрибут «сид» не нужен ни одному сценарию задачи (аудит правок вне области), а кнопка
восстановления — новая продуктовая функция, которой нет в требованиях. Появится потребность —
это аддитивная колонка + отдельный эндпоинт, не меняющий модель.

#### Вариант B4: слова в JSON-ресурсе, загружаемом сервисом при старте — **отклонено**

**Минусы:** источник правды снова в коде/образе (нарушает FR-2 «в коде этого блока нет»);
плюс та же проблема воскрешения удалённых слов, что B2.

### Ключевое решение C: где и как строится набор подсказок

#### Вариант C1: отдельный Application-порт `ICommodityCategoryHintProvider` + чистый матчер, подсказки передаются в `IAiClient` параметром — **выбран**

- `CategoryKeywordMatcher` (Domain, чистая функция): на вход — снимок слов и **уже нормализованное**
  название товара, на выход — упорядоченный список совпавших подсказок.
- `ICommodityCategoryHintProvider.GetHints(normalizedName)` (Application-контракт,
  Infrastructure-реализация поверх кэша) — единственная точка, откуда подсказки берут оба
  вызывающих.
- `CommodityCategoryResolver` (шаг 5) и `PrecategorizationBackgroundService` вызывают провайдер
  и передают результат в `IAiClient.SuggestCategoryAsync(…, hints, ct)`.

**Плюсы:**
- FR-8 выполняется буквально: логика матчинга существует в одном месте (Domain), доставка — в
  одном месте (провайдер); оба call site делают ровно один вызов.
- Промт остаётся ответственностью `IAiClient`: клиент по-прежнему единственный, кто знает формат
  запроса; тестируется юнит-тестом без БД и без кэша (подсказки передаются аргументом).
- Провайдер не знает про БД (только кэш) — NFR-1 выполняется по построению.

**Минусы:** сигнатура порта ИИ расширяется (см. D).

#### Вариант C2: `OpenAiCompatibleAiClient` сам читает кэш/провайдер по названию товара — **отклонено**

**Минусы:** скрытая зависимость внутри «транспортного» клиента; промт перестаёт быть функцией
своих аргументов (тесты потребуют мок кэша); нарушение слоёв (клиент ИИ начинает зависеть от
модуля категоризации); нельзя проверить «подсказки собраны провайдером» на уровне resolver'а.

#### Вариант C3: продублировать матчинг в resolver'е и в фоне — **отклонено**

**Минусы:** прямо запрещено FR-8; два источника истины для порядка/фильтрации/лимита подсказок
неизбежно разойдутся (прецедент «одна нормализация», ADR 019/027/034).

#### Вариант C4: новый порт «промт-билдер» в Application (клиент получает готовую строку) — **отклонено**

**Минусы:** перекладывание форматирования промта из `Infrastructure.AI` в Application — больший
diff без выгоды: шаблон диктуется требованиями конкретного HTTP-API (роль/формат ответа), а
чистоту тестируемости уже даёт C1 (подсказки — аргумент функции).

### Ключевое решение D: изменение контракта `IAiClient`

#### Вариант D1: обязательный параметр `hints` (без значения по умолчанию) — **выбран**

```csharp
Task<AiSuggestionResult> SuggestCategoryAsync(
    string productName,
    IReadOnlyCollection<string> categoryNames,
    IReadOnlyCollection<CommodityCategoryKeywordHint> hints,   // пустая коллекция = подсказок нет
    CancellationToken cancellationToken = default);
```

**Плюсы:** «подсказки применяются везде» проверяется **компилятором**: новый/забытый вызов не
соберётся, пока не решит, что передать (пустая коллекция — осознанное «совпадений нет»).
Семантика «подсказок нет» = пустая коллекция, а не `null` — нет двух представлений одного
состояния (прецедент стиля проекта: пустые словари-заглушки в resolver'е).

**Минусы:** ломается сигнатура порта → правятся resolver, фон и существующие тесты (внутренний
контракт; HTTP-контракты не затрагиваются — NFR-3 задачи).

#### Вариант D2: необязательный параметр `hints = null` — **отклонено**

**Минусы:** пропущенный call site тихо теряет подсказки — ровно тот класс регрессии, который
требуется исключить (FR-8/UC-4). Компилятор здесь бесплатный тест.

#### Вариант D3: второй интерфейс `IAiClientWithHints` / перегрузка — **отклонено**

**Минусы:** два порта с одинаковой ответственностью, два DI-разрешения, ветвление в потребителях;
KISS.

### Ключевое решение E: кэш списков и инвалидация (NFR-1, NFR-4)

#### Вариант E1: singleton-кэш с неизменяемым снимком, атомарная подмена, reload после мутации + «грязный» флаг — **выбран**

- Снимок (`CommodityCategoryKeywordSnapshot`: неизменяемый список записей) публикуется через
  `Volatile.Write`/`Volatile.Read`; читатели работают без блокировок.
- Наполнение при старте — `CommodityCategoryKeywordCacheInitializationHostedService` (прецедент
  `CommodityCategoryCacheInitializationHostedService`).
- После успешной записи в БД сервис вызывает `RefreshAsync()`: **перечитывает таблицу целиком**
  (одна `SELECT`, сотни строк) под `SemaphoreSlim(1,1)` и подменяет ссылку. Чтение из БД, а не
  «патч в памяти», устраняет расхождение «память vs БД» при конкурентных правках.
- Если перечитывание не удалось (БД недоступна), мутация всё равно успешна (данные уже
  зафиксированы), кэш помечается «грязным» (`volatile bool`), и **следующее чтение** выполняет
  перечитывание (double-check под тем же семафором). Так NFR-4 восстанавливается сам, без рестарта.

**Плюсы:** lock-free чтения на горячем пути (матчинг на каждый товар); один формат доступа к
данным; простота и предсказуемость; инвалидация «после commit» повторяет порядок `cache.TryAdd`
(ADR 019/027/032).

**Минусы:** на каждое изменение — один полный `SELECT` (сотни строк, десятки микросекунд);
кэш живёт в памяти процесса (рестарт — перечитывание, потери нет).

#### Вариант E2: инкрементальная правка `ConcurrentDictionary` (add/remove по ключу) — **отклонено**

**Минусы:** параллельные add/remove в двух вкладках дают разные порядки применения; удаление
последнего слова категории/списка требует «пустых» записей; согласованность с БД после частичного
сбоя приходится восстанавливать вручную. Полное перечитывание — тот же результат дешевле.

#### Вариант E3: читать таблицу на каждый запрос категоризации — **отклонено**

**Минусы:** нарушает NFR-1 (лишний round-trip на каждый suggest, включая пакетные порции и фон);
таблица нужна целиком для подстрочного поиска, индексировать её под `Contains` нельзя.

#### Вариант E4: распределённый кэш / pub-sub инвалидация (Redis, `LISTEN/NOTIFY`) — **отклонено**

**Минусы:** новая инфраструктура и новый отказ-режим ради ограничения, которое сейчас не
действует: Analytics — один экземпляр (D12 ADR 027). Зафиксировано как открытый вопрос 5.

#### Мультиэкземплярность (зафиксированное ограничение)

Если Analytics когда-нибудь запустят в нескольких экземплярах, правка на инстансе A **не**
инвалидирует кэш инстанса B: подсказки там останутся прежними до рестарта/перечитывания. БД —
источник правды, поэтому расхождение ограничено подсказками (не категориями) и лечится рестартом.
Это осознанное ограничение текущего single-instance развёртывания, а не дефект реализации.

### Ключевое решение F: формат мёржа подсказок в промт (FR-7, edge cases)

#### Вариант F1: текстовый блок подсказок в user-сообщении; экранирование управляющих символов; детерминированный порядок; лимит 50 — **выбран**

Шаблон user-сообщения (изменения — только вставка блока, выделенного `[...]`):

```text
Товар: "<productName>"
Выбери ОДНУ наиболее подходящую категорию из реестра: <catalog>.
[Подсказки по ключевым словам (совпали в названии; это только подсказки, решение принимай сам):
- в названии есть «<word>» → скорее не <DisplayName> (<EnumName>)
- в названии есть «<word>» → вероятно <DisplayName> (<EnumName>)]
Ответь строго в формате JSON: {"category": "НазваниеКатегории"} без пояснений.
```

- Блок отсутствует целиком, если совпадений нет: промт при пустых подсказках = сегодняшний промт
  **без** удалённого хардкода (NFR-2 задачи: объём не зависит от числа слов в БД).
- **Порядок детерминирован**: сначала все exclude-подсказки, затем все boost; внутри группы — по
  `category_id` asc, затем по `normalized_word` (ordinal asc). Исключения идут первыми, потому что
  UC-5 объявляет их сильнее: при усечении по лимиту boost-подсказки отбрасываются первыми.
- **Лимит** `MaxPromptHints = 50` — константа в `OpenAiCompatibleAiClient` (edge case «все 200 слов
  совпали»). Новых настроек не вводим (см. открытый вопрос 2).
- **Экранирование**: `word` проходит `EscapeHintWord` — все управляющие символы
  (`char.IsControl`: `\r`, `\n`, `\t`, …) заменяются пробелом, пробелы схлопываются, результат
  обрезается до 64 символов. Так слово не может создать новую строку/подсказку и «дописать»
  инструкцию. Кавычки (`«»`/`"`) **не** нейтрализуются: JSON-тело защищено сериализатором
  (`"` → `\"`, переводы строк → `\n`), а строку блока кавычка разорвать не может.
- **Формат ответа** остаётся строгим JSON и остаётся **последней** инструкцией сообщения (модели
  лучше следуют последней инструкции); парсер ответа (`TryExtractCategory`) не меняется.
- Хранение слова не меняется (FR-5: «как введено»); санитайзинг — только на рендеринг промта.

**Плюсы:** KISS; полный контроль над форматом; тестируется прямым чтением тела запроса
(существующая практика `OpenAiCompatibleAiClientTests`).

#### Вариант F2: отдельное поле/структура в JSON сообщения (например, `hints: [...]`) — **отклонено**

**Минусы:** содержимое `content` — единственный канал, который модель гарантированно прочитает;
структурированные поля вне `content` не специфицированы OpenAI-совместимым API (поведение зависит
от бэкенда). Формат ответа всё равно остаётся текстовой инструкцией.

#### Вариант F3: подсказки в system-сообщении — **отклонено**

**Минусы:** system-сообщение статично для всех запросов; подсказки зависят от названия товара,
то есть динамичны. Плюс смешение «роли» и «данных запроса» ухудшает управляемость промта.

### Ключевое решение G: форма API изменения

#### Вариант G1: `GET` всего снимка + `POST` одного слова + `DELETE` по `id` — **выбран**

Одна строка = одно слово: валидация и ошибки адресны (FR-5), конкурентные правки двух вкладок не
теряются (уникальный индекс + 409), удаление идемпотентно по `id`, кэш инвалидируется после каждой
операции.

#### Вариант G2: `PUT` со всем списком категории (`{boost: [...], exclude: [...]}`) — **отклонено**

**Минусы:** last-write-wins: вторая вкладка затирает правки первой (прямой конфликт с edge case
«конкурентное редактирование»); сервер не может объяснить, какое именно слово невалидно или
является дубликатом; клиенту нужно присылать весь список на каждое нажатие чипа.

#### Вариант G3: `DELETE` по `(categoryId, listType, word)` вместо `id` — **отклонено**

**Минусы:** слово в URL/query нужно нормализовать и кодировать (регистр/пробелы/юникод), ответ
«не найдено» неоднозначен при дубликатах регистра; `id` уже есть в выдаче `GET` и однозначен.

### Ключевое решение H: состояние UI после мутации

#### Вариант H1: рефетч `GET` после каждой успешной мутации (с сохранением текущих данных на экране) — **выбран**

**Плюсы:** единственный источник истины — сервер (порядок слов, реальные значения после
trim/normalize, счётчики); нет дублирования правил сортировки на клиенте; ошибки БД не
маскируются оптимистичным состоянием.

#### Вариант H2: оптимистичное добавление/удаление чипа — **отклонено**

**Минусы:** нужно воспроизводить на клиенте сортировку, нормализацию и лимит 200, чтобы не
показывать состояние, которого нет на сервере; при 409/400 придётся откатывать вставку. Страница
админская и низкочастотная — рефетч дешевле.

## Решение

Сводка: **A1** (таблица `commodity_category_keywords` + `normalized_word` + уникальный индекс),
**B1** (одноразовый сид в миграции, `ON CONFLICT DO NOTHING`, без маркера и без ресида),
**C1** (`CategoryKeywordMatcher` в Domain + `ICommodityCategoryHintProvider` — одна точка для
resolver'а и фона), **D1** (обязательный параметр `hints` в `IAiClient`), **E1** (singleton-кэш с
неизменяемым снимком, атомарная подмена, reload после мутации + «грязный» флаг),
**F1** (текстовый блок подсказок, exclude-first, лимит 50, санитайзинг управляющих символов,
неизменный строгий JSON-ответ), **G1** (GET/POST/DELETE), **H1** (рефетч после мутации).

### Обоснование

1. **Инварианты — в БД, проверки — в коде** (A1): case-insensitive дубликат и «нет `Undefined`»
   держит схема, поэтому edge case конкурентного редактирования не зависит от аккуратности
   приложения. EF-модель выражает всё, что объявлено в SQL, — тестовая схема идентична проду.
2. **Никакого воскрешения сида** (B1): гарантия берётся у существующего механизма
   `migration_scripts_history`, а не у новой логики; в коде нет ни файла с примерами, ни стартового
   upsert'а — FR-2 выполняется буквально.
3. **Одна логика, оба входа** (C1+D1): матчинг — чистая функция Domain, доставка — один провайдер,
   обязательный параметр порта превращает «забыли применить подсказки» в ошибку компиляции.
4. **Дешёвый горячий путь** (E1): на каждый товар — проход по снимку в памяти, без БД; на каждое
   изменение — одно перечитывание крошечной таблицы; NFR-4 достигается без рестарта, NFR-1 — без
   обращения к БД.
5. **Промт остаётся промтом** (F1): блок добавляется только при совпадениях, порядок
   детерминирован, исключения приоритетнее при усечении, инструкция формата ответа не меняется;
   JSON-валидность тела обеспечивает сериализатор, а не ручное экранирование.
6. **Минимальный радиус поражения** (G1, вне области): существующие HTTP-контракты
   (`suggest`, `categories`, `/precategorized`, журнал) не меняются; новых настроек, таблиц-справочников,
   фоновых сервисов и зависимостей нет.

### 1. Схема PostgreSQL и миграция

Скрипт `Analytics/src/ReceiptCollector.Analytics.Migrations/Scripts/20261112120000_add_commodity_category_keywords.sql`
(транзакция на скрипт, учёт в `migration_scripts_history`):

```sql
-- Ключевые слова категоризации (ADR-035): boost- и exclude-списки на категорию.
-- Категория — код enum CommodityCategory (ADR 005: справочника в БД нет), FK отсутствует.
-- Слово хранится как введено (кроме trim); normalized_word — ключ case-insensitive
-- уникальности и вход подстрочного матчинга (FR-6): trim + lowercase + collapse пробелов.
-- Лимит 200 слов на список — правило приложения (проверка перед вставкой), не целостность данных.

CREATE TABLE commodity_category_keywords
(
    id              uuid        PRIMARY KEY,
    category_id     integer     NOT NULL,
    list_type       varchar(16) NOT NULL,
    word            varchar(64) NOT NULL,
    normalized_word varchar(64) NOT NULL,
    CONSTRAINT ck_commodity_category_keywords_category_not_undefined
        CHECK (category_id <> 0),
    CONSTRAINT ck_commodity_category_keywords_list_type
        CHECK (list_type IN ('boost', 'exclude')),
    CONSTRAINT ck_commodity_category_keywords_word_length
        CHECK (char_length(word) BETWEEN 2 AND 64)
);

-- Дубликат в рамках «одна категория + один список» (регистр не важен) — FR-5.
-- Индекс же обслуживает per-category чтение (префикс category_id, list_type).
CREATE UNIQUE INDEX ux_commodity_category_keywords_category_list_word
    ON commodity_category_keywords (category_id, list_type, normalized_word);

-- Сид: содержимое блока «Разграничения схожих категорий» (ADR-022) из BuildPayload (FR-2).
-- ON CONFLICT DO NOTHING — страховка повторного/частичного выполнения; штатная идемпотентность —
-- migration_scripts_history. Маркера «сид» нет: удалённое админом слово не воскресает.
INSERT INTO commodity_category_keywords (id, category_id, list_type, word, normalized_word) VALUES
    (gen_random_uuid(), 42, 'boost',   'изюм',   'изюм'),
    (gen_random_uuid(), 42, 'boost',   'курага', 'курага'),
    (gen_random_uuid(), 26, 'exclude', 'изюм',   'изюм'),
    (gen_random_uuid(), 19, 'boost',   'соль',   'соль'),
    -- … полный список — в таблице п. 2
    (gen_random_uuid(), 52, 'exclude', 'абонемент', 'абонемент')
ON CONFLICT DO NOTHING;
```

- **Порядок развёртывания.** Миграция аддитивна: существующие таблицы, колонки и индексы не
  затрагиваются, поэтому старый образ продолжает работать с новой таблицей (он её просто не
  использует). `analytics` уже зависит от `analytics-migrations` через
  `service_completed_successfully`, так что «новая схема раньше нового кода» обеспечена
  компоузом; простоя не требуется.
- **Объём.** Верхняя граница — 53 категории × 2 списка × 200 слов ≈ 21 200 строк; реалистично —
  сотни. Полное чтение таблицы (для снимка) и её индексация тривиальны.
- **Имена и типы.** snake_case, `uuid` PK, `timestamptz` не нужен (см. «Явно зафиксированные
  семантики»: времени создания у слова нет — аудита нет).
- **EF-конфигурация** (`Persistence/Postgres/Configurations/CommodityCategoryKeywordConfiguration.cs`)
  повторяет миграцию: имя таблицы, длины, три CHECK, уникальный индекс — иначе тестовая схема
  (`EnsureCreatedAsync` из EF-модели) не содержит инвариантов, которые проверяют тесты.

### 2. Сид: содержимое (FR-2)

Правило раскладки блока на слова:

1. Каждая строка блока — «категория(и)-субъект со словами — не категория-цель (пояснение)».
2. Слова субъекта → **boost** соответствующих категорий (слово уходит в ту категорию, которую оно
   называет; дубли внутри одной категории не создаются).
3. Те же слова → **exclude** каждой категории-цели из «не …» (формулировка «не X» сохраняется
   ровно так, как в промте сегодня: UC-5 «исключение сильнее boost»).
4. Пояснения в скобках — это положительное определение категории-цели, поэтому их перечисления
   → **boost** этой категории (иначе из промта пропала бы информация «бакалея — крупы, мука,
   макароны, сахар, соль, масло, чай/кофе»; наличие «соль» в списке объясняет edge case задачи
   «соль в фасоль»).
5. Словоформы: слово приводится к форме, которая **входит подстрокой** в исходную форму блока
   (единственное число: `холодильники → холодильник`, `финики → финик`; `столы → стол`).
   Смысловые дубли («рыбные, мясные, овощные консервы» → `консервы`) не размножаются, если ведут
   в одну категорию. Морфология/стемминг — вне области.

| Строка блока (ADR 022) | boost | exclude |
|---|---|---|
| Сухофрукты (DriedFruits): изюм, курага, чернослив, финики — не Fruits (свежие фрукты/ягоды) | `DriedFruits`: изюм, курага, чернослив, финик; `Fruits`: фрукты, ягоды | `Fruits`: изюм, курага, чернослив, финик |

### 4. Сборка подсказок: единственная точка (FR-6, FR-8, NFR-1, NFR-2)

#### 4.1. Матчер (Domain, чистая функция)

```text
GetHints(snapshot, normalizedProductName):
  1. если normalizedProductName пуст или не содержит ни одной буквы → пустой список
     (edge case «название пустое/из цифр» — совпадений не ищем)
  2. matched = [ e for e in snapshot if normalizedProductName.Contains(e.NormalizedWord) ]
  3. порядок: exclude-подсказки первыми, затем boost; внутри группы — category_id asc,
     normalized_word (ordinal) asc
  4. вернуть matched целиком (усечение — на рендере промта, п. 5)
```

- Совпадение — простая подстрока по обеим сторонам, приведённым к нижнему регистру: `соль`
  сработает в `фасоль` (edge case задачи; документируется подсказкой в UI).
- Никаких границ слов, regex, стемминга.
- Матчер — `static`-функция над снимком: тестируется без DI и без БД; порядок детерминирован
  независимо от порядка вставки строк.

#### 4.2. Провайдер (Application-порт, Infrastructure-реализация)

`ICommodityCategoryHintProvider.GetHints(string normalizedName)` → `IReadOnlyList<CommodityCategoryKeywordHint>`:
берёт снимок из singleton-кэша (при «грязном» флаге — перечитывает) и вызывает матчер. Кэш не
знает про БД на горячем пути; провайдер не знает про промт.

#### 4.3. Точки применения (ровно две, обе — за одним провайдером)

| Точка | Изменение |
|---|---|
| `CommodityCategoryResolver` (шаг 5, ручной suggest чека и страницы «Товары») | в `SuggestByAiAsync` для каждого уникального ключа: `var hints = _hintProvider.GetHints(item.Key);` → `_aiClient.SuggestCategoryAsync(item.Key, CategoryNames, hints, aiCancellationToken)`. Один расчёт на уникальное очищенное имя (дедупликация ADR 034 сохраняется) |
| `PrecategorizationBackgroundService.ProcessCandidateAsync` | `var hints = _hintProvider.GetHints(normalized);` → `aiClient.SuggestCategoryAsync(normalized, CategoryNames, hints, cancellationToken)` |

Приоритеты конвейера (`existing → merchant-default → cache → precategorized → ai`), коды ответов,
`503`/`aiAvailable = false` при пустом `AI:BaseUrl`, бюджет `SuggestTimeout` и частичный `200` —
**без изменений**: подсказки влияют только на содержимое промта, а не на маршрутизацию запроса.

### 5. Формат промта, экранирование и строгий JSON (FR-7)

- Из `BuildPayload` удаляется блок «Разграничения схожих категорий» (заголовок + 11 строк
  примеров). Остаются: system-сообщение (без изменений), user-сообщение: товар,
  реестр категорий, **опциональный блок подсказок**, инструкция формата ответа.
- Блок подсказок (только при `hints.Count > 0`), см. F1. Формулировки: exclude — «скорее не
  <DisplayName> (<EnumName>)», boost — «вероятно <DisplayName> (<EnumName>)». Имя enum в скобках —
  потому что ответ модели обязан быть именем enum (парсер принимает только его); DisplayName —
  потому что он объясняет смысл категории (как в удалённом блоке).
- `MaxPromptHints = 50`, усечение после сортировки (exclude первыми) → при переполнении
  отбрасываются только boost-подсказки.
- `EscapeHintWord`: `char.IsControl(c)` → пробел; схлопывание пробелов; обрезка до 64 символов.
  Так слово с `\n`/`\r`/`\t` не создаёт новую строку блока и не «переписывает» инструкции.
- JSON-контракт запроса и ответа: тело сериализуется/парсится как раньше (`JsonSerializer`,
  `JsonDocument`); никакого ручного склеивания JSON нет. Ответ модели по-прежнему
  `{"category": "<EnumName>"}`; `TryExtractCategory` и `ParseCategoryName` не меняются.
- Реестр категорий (`CategoryNames`) и порядок сообщений не меняются → поведение ИИ без
  совпадений идентично сегодняшнему за вычетом удалённого статического блока (его содержание
  теперь приходит подсказками из БД).

### 6. Кэш и инвалидация (NFR-1, NFR-4)

- `ICommodityCategoryKeywordCache` (singleton):
  - `GetSnapshot()` — `Volatile.Read` ссылки на неизменяемый `CommodityCategoryKeywordSnapshot`;
    если выставлен «грязный» флаг — перечитывание (double-check под `SemaphoreSlim(1,1)`).
  - `RefreshAsync(ct)` — полное перечитывание таблицы и атомарная подмена ссылки
    (`Volatile.Write`); при ошибке — `LogWarning`, флаг «грязный» остаётся, старое снимок
    продолжает использоваться (деградация без исключения на горячем пути).
- Прогрев при старте — `CommodityCategoryKeywordCacheInitializationHostedService` (стиль
  `CommodityCategoryCacheInitializationHostedService`); ошибка прогрева не валит процесс:
  кэш остаётся «грязным» и перечитается на первом чтении.
- Инвалидация — **после** commit изменения (`AddAsync`/`DeleteAsync` → `RefreshAsync`); порядок
  совпадает с `cache.TryAdd` (ADR 019/027/032). Мутация возвращает успех независимо от результата
  перечитывания (БД — источник правды).
- Потокобезопасность: читатели без блокировок (неизменяемый снимок), писатели сериализованы
  семафором; гонка «два админа одновременно» приводит к двум перечитываниям, оба снимка валидны
  (побеждает последний — данные одинаковы).
- Мультиэкземплярность: см. E — ограничение зафиксировано, координация вне области.

### 7. API-контракты (FR-3, FR-4, FR-5, FR-10)

Все три эндпоинта — под `AdminAuthorization.AuthorizeAsync` (пустой `UserContext.UserId` → `401`,
не админ → `403`), текстовые тела ошибок (без ProblemDetails), группа
`/api/commodity-category-keywords` (`WithTags`), стиль — как у
`PrecategorizedCommodityEndpoints`/`CategorizationDecisionEndpoints`.

#### `GET /api/commodity-category-keywords`

Возвращает **все** определённые категории (кроме `Undefined`), включая пустые списки (UC-1 п. 2–3:
плейсхолдеры и счётчики должны быть видны без второго запроса). Порядок категорий — как в
`CommodityCategoryHelper.GetAll()` (порядок объявления), слова — по `word` (`OrdinalIgnoreCase`,
затем `Ordinal` как разрешение ничьих) — детерминированно.

```json
[
  {
    "categoryId": 42,
    "categoryKey": "DriedFruits",
    "categoryName": "Сухофрукты",
    "group": "Продукты",
    "boost": ["изюм", "курага", "финик", "чернослив"],
    "exclude": ["изюм", "курага", "финик", "чернослив"]
  },
  {
    "categoryId": 2,
    "categoryKey": "Clothing",
    "categoryName": "Одежда",
    "group": "",
    "boost": [],
    "exclude": []
  }
]
```

`X-Total-Count` и пагинация **не вводятся**: объём ограничен (≤ 53 категории × 2 × 200, реально —
сотни слов), страница загружает снимок один раз.

#### `POST /api/commodity-category-keywords`

```json
{ "categoryId": 42, "listType": "boost", "word": "  Курага  " }
```

- `200 OK` + созданный элемент `{ "id": "…", "categoryId": 42, "listType": "boost", "word": "Курага" }`.
  Код `200`, а не `201`, — сознательно: в проекте все мутации отвечают `Results.Ok`/`NoContent`
  (см. фактическую таблицу), а ресурс «слово по id» отдельным `GET` не адресуется (`Location`
  вёл бы в 404). Контракт фронта от этого не зависит.
- Тело ответа содержит слово **после trim** и в исходном регистре (FR-5: «сохраняется как введено»,
  кроме обрамляющих пробелов).
- Ошибки (все — с текстовым телом, фронт показывает текст):

| Условие | Код | Тело |
|---|---|---|
| `categoryId` не `Enum.IsDefined` или `Undefined` | `400` | `Invalid category.` |
| `listType` не `boost`/`exclude` | `400` | `listType must be 'boost' or 'exclude'.` |
| слово после trim короче 2 или длиннее 64 | `400` | `word must be between 2 and 64 characters after trimming.` |
| дубликат в этом же списке этой же категории (case-insensitive) | `409` | `word already exists in this list.` |
| в списке уже 200 слов | `409` | `list limit of 200 words reached.` |
| не админ / нет сессии | `403` / `401` | стандартные ответы `AdminAuthorization` |

- Дубликат определяется по `normalized_word` (проверка в сервисе) и **дополнительно** ловится
  уникальным индексом (`23505` → `Duplicate`) — гонка двух вкладок даёт `409`, а не 500.
- Лимит проверяется count'ом перед вставкой; единичный «перелёт» при гонке допустим и
  самоблокируется (следующая вставка увидит ≥ 200).

#### `DELETE /api/commodity-category-keywords/{id:guid}`

- `204 NoContent` — удалено; `404 NotFound` (`word not found.`) — нет такой строки
  (в т.ч. удалено в другой вкладке); `401/403` — как выше.
- Удаление не влияет на уже проставленные категории и на очередь предкатегорий (вне области:
  ретроактивного пересчёта нет).

#### Совместимость (NFR-3 задачи)

`POST /api/receipts/{id}/categories/suggest`, `POST /api/commodities/categories/suggest`,
`PUT …/categories`, `/api/commodities/categories`, `/api/precategorized-commodities*`,
`/api/categorization-decisions` — без изменений ни в полях, ни в кодах, ни в текстах ошибок.

- Чтение и запись — только админ на сервере (`AdminAuthorization`), UI-скрытие вторично.
- Отдельного «публичного» API подсказок нет: подсказки не отдаются клиентам категоризации, только
  мёржатся в промт на сервере.
- Слова — источник потенциальной инъекции в промт: администратор доверенный, но управляющие
  символы нейтрализуются (F1), а слово ограничено 64 символами; многострочная инструкция через
  слово невозможна.
- Валидация на сервере — единственная авторитетная (клиентская — UX).
- Слова не персональные данные; в логах — только количество совпавших подсказок (не тексты слов),
  на уровне Debug (ПД-практика ADR 027/028).

### 10. Тестируемость

| Уровень | Проверки |
|---|---|
| `CategoryKeywordMatcher` | совпадение подстрокой в обе стороны регистра; слово-подстрока другого слова (`соль`/`фасоль`); пустое/цифровое название → пусто; boost двух категорий → обе подсказки; boost и exclude одной категории → обе, exclude первой; детерминированный порядок при перемешанном входе; полный набор 200×N не теряется (усечение — на рендере) |
| `CommodityCategoryKeywordRules` | trim/collapse/lowercase нормализация; 1/2/64/65 символов; пробельное слово; эмодзи/спецсимволы; регистр сохраняется в `word` и сворачивается в `normalized_word` |
| `OpenAiCompatibleAiClient` | блок подсказок отсутствует при пустой коллекции и присутствует при непустой (тело запроса читается как сейчас); формулировки «вероятно»/«скорее не»; порядок exclude→boost; лимит 50 (boost отбрасывается первым); `\n`/`\r`/`\t` в слове не создают новой строки; тело остаётся валидным JSON (`JsonDocument.Parse`), инструкция ответа — последняя; разбор ответа и ретраи не изменились. **Тест `SuggestCategoryAsync_prompt_contains_new_category_heuristics` удаляется** (он утверждает удаляемый хардкод) |
| `CommodityCategoryResolver` | в `IAiClient` уходит подсказка, собранная по нормализованному имени (mock/NSubstitute захватывает аргумент); при отсутствии совпадений — пустая коллекция; приоритеты `existing/merchant-default/cache/precategorized/ai` без регрессий; дедупликация уникальных имён сохранена |
| `PrecategorizationBackgroundService` | подсказки передаются по очищенному имени; `Undefined` по-прежнему не создаёт строку; пауза/окно/лимит без изменений |
| `CommodityCategoryKeywordService` | добавление (регистр сохраняется), дубликат case-insensitive → `Duplicate`, 200 → `LimitReached`, удаление по id/`NotFound`; `RefreshAsync` вызывается после commit; при падении refresh мутация успешна и кэш помечен «грязным» |
| Кэш | прогрев при старте; `GetSnapshot` без БД; refresh подменяет снимок; «грязный» флаг → перечитывание при следующем чтении; конкурентные чтения во время refresh не падают и не видят «полуснимок» |
| API | `401/403/400/404/409` исполнением `IResult` (практика ADR 027/028); `GET` содержит все категории (включая пустые) и не содержит `Undefined`; `POST` возвращает слово после trim; `DELETE` идемпотентен по результату (404 на повтор) |
| Миграция | на пустой БД создаёт таблицу и сид; повторный запуск runner'ом — skip; `ON CONFLICT DO NOTHING` не падает при повторе `INSERT`; удалённое слово после «рестарта» (повторного запуска миграций) не появляется — проверяется на уровне сервиса (ресида нет) + ручной смоук |
| Регрессия | `cd Analytics && dotnet test` зелёный; `npm run build`/`lint`; ручная проверка в UI на 2–3 товарах из «Журнала категоризации»: добавленное слово меняет блок подсказок в промте |

## Явно зафиксированные семантики

| Вопрос | Решение |
|---|---|
| Гранулярность строки | Одна строка = одно слово в одном списке одной категории |
| Тип списка | `boost` \| `exclude`, `varchar(16)` + CHECK; C# `KeywordListType`, wire-имена `boost`/`exclude` |
| Категория | `category_id` int (код `CommodityCategory`), FK нет, `0` запрещён CHECK; имена/группы — из `CommodityCategoryHelper` на чтении |
| Дубликат | Уникальный индекс `(category_id, list_type, normalized_word)` + проверка в сервисе; ответ `409`; при совпадении остаётся первая сохранённая форма слова |
| Case-insensitive | Через `normalized_word` (trim + lowercase + collapse), а не через `citext`/выражение |
| Хранение слова | Как введено, кроме обрамляющих пробелов (trim обязателен по FR-5); внутренние символы и регистр сохраняются |
| Нормализация слова vs названия | Слово — простая нормализация (`CommodityCategoryKeywordRules.NormalizeWord`); название товара — `CommodityNameNormalizer.NormalizeName` (ADR 034). Снятие кодов/мусора к словам **не** применяется |
| Матчинг | `normalizedProductName.Contains(normalizedWord)`, без границ слов/regex; «соль» срабатывает в «фасоль» — осознанно |
| Лимит слов | 200 на список, проверка в сервисе (count перед вставкой); гонка может дать единичный перелёт — допустимо |
| Сид | Одноразовый `INSERT … ON CONFLICT DO NOTHING` в миграции; маркера «сид» нет; удалённое админом слово не воскресает |
| Источник слов в промте | Только БД; в коде блока «Разграничения…» нет |
| Что попадает в промт | Только совпавшие подсказки; при отсутствии совпадений блока нет вовсе |
| Сила подсказок | Формулировки различаются; при конфликте/усечении приоритет у exclude (первыми в блоке и при усечении) |
| Порядок подсказок | exclude → boost; внутри — `category_id` asc, `normalized_word` ordinal asc |
| Усечение | `MaxPromptHints = 50` (константа, без новой настройки) |
| Экранирование | Управляющие символы → пробел, обрезка до 64; JSON-валидность — сериализатором |
| Формат ответа ИИ | Не меняется; инструкция — последняя строка сообщения |
| Когда подсказки не работают | Пустой `AI:BaseUrl` (`503`/`aiAvailable = false`), пустое/цифровое нормализованное название — поведение как раньше |
| Инвалидация кэша | После commit мутации, полное перечитывание; при сбое — «грязный» флаг и ленивое перечитывание |
| Мультиэкземплярность | Не поддерживается (single instance, D12 ADR 027); ограничение зафиксировано |
| Аудит/время создания слова | Не ведутся (`created_at`/`created_by` нет) — аудит вне области |
| Ретроактивность | Нет: `commodities`, `precategorized_commodities`, `categorization_decisions` не пересчитываются |
| Телеметрия подсказок | Нет: формат journal `categorization_decisions` не меняется |
| Новые настройки | Отсутствуют |

## Последствия

### Положительные

- Систематические ошибки ИИ исправляются администратором за секунды, без релиза; блок «Разграничения
  схожих категорий» перестаёт быть частью кода и становится редактируемыми данными.
- Подсказки применяются единообразно во всех точках категоризации (чек, страница «Товары», фон) —
  по построению, без дублирования логики.
- Промт не растёт с числом слов (NFR-2): в запрос уходят только совпадения; при их отсутствии
  промт короче сегодняшнего (статический блок удалён).
- Добавление новых категорий или слов не требует миграций и деплоя.
- Изменения аддитивны: старая версия кода работает с новой таблицей, откат образа не ломает схему.

### Отрицательные / компромиссы

- **Качество слов = качество подсказок.** Подстрочный матчинг без границ слов даёт ложные
  срабатывания (`соль` в `фасоль`, `стол` в `столешница`); это осознанная семантика (FR-6/edge
  cases), ответственность за формулировки — на администраторе, поведение документируется в UI.
- **Сид — снимок сегодняшнего промта.** Перенос включает пояснения в скобках как boost-слова
  (иначе информация из промта пропала бы); часть слов — общие (`мясо`, `фрукты`), что может
  добавлять подсказки там, где раньше работал только текст блока. Смягчение: подсказки не решают,
  их можно удалить в UI, приёмка — на реальных товарах из журнала.
- **Нет аудита правок** — нельзя узнать, кто и когда удалил слово (вне области); восстановление —
  только из дампа/повторного `INSERT`-блока миграции.
- **Мультиэкземплярность**: второй инстанс не увидит правку до рестарта (ограничение single
  instance).
- **Лимит 200 проверяется приложением**, поэтому при одновременной вставке возможен единичный
  перелёт; список после этого не растёт.
- **Полное перечитывание на каждую мутацию** — приемлемо для админской низкочастотной операции,
  но не подходит как паттерн для массовых правок (массовый импорт — вне области).
- **`200 OK` вместо `201`** на создание: сознательное следование стилю проекта (нет GET-by-id).

### Риски и откат

| Риск | Вероятность | Митигация |
|---|---|---|
| Ошибка/неполнота сида → деградация качества категоризации | Средняя | Таблица раскладки (п. 2) проверяется при ревью миграции; ручная приёмка на 2–3 реальных товарах из «Журнала категоризации»; правки — данными, без релиза |
| Слова с управляющими символами ломают структуру промта | Низкая | `EscapeHintWord` (F1); слова ограничены 64 символами; источник — только админ |
| Промт-инъекция через слово («игнорируй инструкции») | Низкая | Админ доверенный; слово — короткая подсказка в фиксированном шаблоне; формат ответа парсится строго (`TryExtractCategory`) |
| Раздувание промта при массовых совпадениях | Низкая | Только совпадения + `MaxPromptHints = 50`, exclude приоритетнее при усечении |
| Ложные совпадения подстроки | Средняя | Осознанная семантика (FR-6), подсказка в UI, слова редактируются админом |
| Расхождение кэша и БД | Низкая | Полное перечитывание после commit; «грязный» флаг при сбое; БД — источник правды |
| Дубликат/лимит в гонке двух вкладок | Низкая | Уникальный индекс (`23505` → `409`); count-проверка; единичный перелёт лимита некритичен |
| Замедление suggest из-за матчинга | Низкая | In-memory проход по сотням слов; при росте — замер и (при необходимости) предфильтр по первой букве (открытый вопрос 3) |
| Старый тест промта падает после удаления хардкода | Высокая (ожидаемо) | Тест удаляется в той же задаче, что и блок, и заменяется тестами блока подсказок |

**Откат.**

1. **Только код (наиболее вероятный сценарий).** Выкатить прежний образ: таблица аддитивна и
   старым кодом не читается, существующие таблицы не менялись — схему откатывать не нужно,
   приложение возвращается к хардкоженному блоку. Слова, добавленные админом, остаются в БД
   (не используются) и снова начнут действовать при повторной выкатке новой версии.
2. **Схема + код.** `DROP TABLE commodity_category_keywords;` (после выката прежнего образа).
   Данные админских слов теряются — перед откатом снять дамп:
   `pg_dump -t commodity_category_keywords` (или `./backup.sh`, в него входит дамп PostgreSQL
   Analytics). Строка в `migration_scripts_history` удаляется вместе с решением о повторном
   применении миграции (иначе раннер её пропустит).
3. **Данные без отката кода.** Вернуть сид: повторно выполнить `INSERT`-блок из файла миграции
   (`ON CONFLICT DO NOTHING`); удалить мешающие слова — через UI.
4. **Порядок деплоя.** Сначала `analytics-migrations` (создаёт таблицу и сид), затем новый образ —
   это уже гарантировано зависимостью `service_completed_successfully`; простоя не требуется.

## Открытые вопросы

1. **Словоформы сида.** Раскладка использует формы, входящие подстрокой в исходные
   (`холодильник` → `холодильники`), но без стемминга: `варенье` не найдёт `варенья`, `консервы`
   не найдёт `консервированный`. Нужен ли морфологический поиск — отдельное решение с оценкой
   ложных срабатываний; сейчас администратор добавляет нужные формы руками.
2. **Лимит подсказок в промте** (`MaxPromptHints = 50`) — константа. Делать ли его настройкой
   (новая секция конфигурации) — решать по факту эксплуатации; новых настроек задача не вводит.
3. **Производительность матчинга при росте словаря.** Сейчас — линейный проход по снимку.
   Если словарь вырастет на порядки, понадобится предфильтр (по первой букве/`Aho-Corasick`),
   но это не меняет контрактов провайдера.
4. **Ключевые слова для `Other`/служебных категорий.** `Other = 255` технически допустим, но,
   вероятно, бессмысленен; скрывать ли его в UI — UX-решение, схему не меняет.
5. **Синхронизация кэша между инстансами.** При появлении второго экземпляра Analytics понадобится
   `LISTEN/NOTIFY` или короткий TTL снимка — отдельное решение (сейчас single instance, D12 ADR 027).
6. **Телеметрия эффективности подсказок** (сколько раз слово совпало и совпал ли ответ ИИ с
   ожиданием) — сознательно отложено: потребует расширения журнала `categorization_decisions`,
   что задачей запрещено.
7. **Массовый импорт/экспорт словарей** (CSV, копирование между средами) — вне области; при
   необходимости — отдельный эндпоинт поверх той же таблицы.

## Допущения

- Analytics — один экземпляр (D12 ADR 027); распределённой инвалидации кэша не требуется.
- Таблица слов маленькая (сотни строк, верхняя граница ~21 200): полное чтение и линейный матчинг
  пренебрежимо дешевы.
- Администратор — доверенный пользователь: слова не проверяются на «смысловую безопасность»,
  только на форму.
- `ToLowerInvariant()` .NET и `lower()` PostgreSQL согласованы на реальном корпусе слов; уникальность
  сравнения обеспечивается `normalized_word`, посчитанным в C# (SQL-нормализации в runtime нет).
- Нормализация названия товара (`CommodityNameNormalizer`) остаётся единственной и не меняется.
- Существующие эндпоинты и их клиенты не требуют изменений (NFR-3 задачи).
- Миграция применяется до запуска нового образа (обеспечено компоузом), простоя не требуется.

## Связь с другими ADR

- **ADR-009**: промт получает динамический блок подсказок вместо статического блока
  «Разграничения…»; алгоритм `existing → … → ai`, контракты suggest/apply, `503` при пустом
  `AI:BaseUrl` и формат ответа — без изменений. Требуется amend-заметка (в рамках декомпозиции):
  источник уточнений промта — БД, а не код.
- **ADR-022**: статический блок, введённый этим ADR, переносится в БД сидом и удаляется из кода;
  содержимое сохраняется (таблица п. 2). Требуется amend-заметка.
- **ADR-019**: in-memory кэш категорий не меняется; новый кэш слов использует тот же паттерн
  singleton + прогрев hosted service, но с инвалидацией после мутации (в отличие от «заморозки»
  кэша категорий).
- **ADR-027**: стиль админских эндпоинтов (`AdminAuthorization`, текстовые ошибки), `MigrationRunner`,
  single-instance допущение и `TimeProvider`-практика переиспользуются; фоновая прекатегоризация
  получает подсказки в промт, её приоритеты/окно/лимиты — без изменений. Требуется amend-заметка.
- **ADR-028**: пакетный suggest страницы «Товары» получает подсказки автоматически (общий resolver);
  `SuggestTimeout`, `aiAvailable`, assign-only — без изменений. Требуется amend-заметка.
- **ADR-032**: безопасное чтение кодов категорий (`Enum.IsDefined` + `GetDisplayName`) применяется
  к словам; `merchant-default` и `commodities.category_source` не затрагиваются.
- **ADR-033**: журнал решений **не** меняется; телеметрия срабатываний подсказок в него не
  добавляется (осознанно отложено, открытый вопрос 6).
- **ADR-034**: нормализованное название товара — единственный вход матчинга; нормализация слов —
  отдельное простое правило (снятие кодов/мусора к словам не применяется).
- **ADR-005**: справочник категорий остаётся enum; слова хранят int-коды, имена/группы считаются
  на чтении.
