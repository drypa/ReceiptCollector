# Задача: Редактирование имени магазина в списке магазинов (/merchants)

## 1. Бизнес-ценность / Цель

Сейчас названия магазинов приходят из данных nalog.ru и могут быть нечитаемыми,
содержать лишние символы, сокращения или опечатки. Администратор может исправить
имя магазина только косвенно — через представление «Детали чека» (по одному чеку),
что неудобно, когда нужно навести порядок в списке магазинов целиком.

**Цель:** Дать администратору возможность редактировать имя магазина
непосредственно в списке магазинов по адресу `/merchants`, по аналогии с уже
существующим редактированием в представлении «Детали чека». Это позволит быстро
исправлять и нормализовывать названия магазинов, что напрямую улучшает качество
и читаемость всей аналитики (отчёты, списки чеков, поиск).

## 2. Пользовательские сценарии (User Stories)

1. **Администратор открывает `/merchants`**, видит таблицу магазинов. В строке
   магазина доступно действие «Редактировать» имя. При клике имя превращается в
   текстовое поле с кнопками «Сохранить» и «Отмена» (inline-редактирование).
2. После ввода нового имени и нажатия «Сохранить» имя обновляется в списке
   магазинов и во всех связанных представлениях (детали чека, список чеков, поиск).
3. При нажатии «Отмена» (или потере фокуса при отмене) изменения не сохраняются,
   строка возвращается к исходному состоянию.
4. При попытке сохранить пустое имя (или имя из одних пробелов) — сохранение
   блокируется, администратору показывается понятное сообщение об ошибке.
5. Обычный (не администратор) пользователь не видит возможности редактирования
   имени — страница `/merchants` и так доступна только администраторам.
6. При ошибке сети или сервера изменения не теряются, показывается сообщение
   об ошибке, поле остаётся в режиме редактирования (данные не сбрасываются).

## 3. Функциональные требования

- **Доступность:** редактирование имени доступно только аутентифицированным
  пользователям с правами администратора.
- **UX редактирования:** inline-редактирование в таблице по аналогии с паттерном
  редактирования категории магазина в этой же таблице (кнопка «ред.» →
  поле ввода → «Сохранить»/«Отмена»). Внешне и по поведению должно быть
  консистентно с редактированием имени в «Деталях чека».
- **Валидация:** новое имя не может быть пустым или состоять только из пробелов;
  применяется обрезка пробелов (trim) до сохранения; ограничение максимальной
  длины (согласовать с лимитом, используемым в «Деталях чека»).
- **Индикация состояния:** при сохранении показывать состояние «Сохранение...»;
  после успешного сохранения список обновляется; при ошибке — понятное сообщение.
- **Согласованность данных:** после переименования магазина новое имя должно
  отображаться во всех представлениях системы (список магазинов, детали чека,
  список чеков, поиск/фильтрация по имени магазина).

## 4. Предполагаемый вариант реализации (без технических деталей)

> Детальную техническую проработку (какие именно модули, эндпоинты, файлы
> затрагиваются) выполняет архитектор. Ниже — только ожидаемое направление.

- **Backend:** эндпоинт обновления имени магазина с проверкой прав администратора
  уже существует и используется представлением «Детали чека» (`PUT` на имя
  магазина). Архитектор должен подтвердить, что его достаточно для нового
  сценария, либо предложить вынести обновление имени в группу `/api/merchants`
  (для единообразия с управлением магазинами).
- **Frontend:** расширить таблицу магазинов на `/merchants` inline-редактированием
  имени, переиспользуя существующую функцию API для обновления имени.
  Повторно использовать готовые компоненты (диалог подтверждения, состояние
  загрузки) и существующие CSS-стили из «Деталей чека».

## 5. Критерии приёмки (Acceptance Criteria)

1. Администратор на `/merchants` может изменить имя любого магазина inline-способом
   и сохранить его; имя обновляется в таблице без перезагрузки страницы.
2. Новое имя отображается в «Деталях чека» и списке чеков для чеков этого магазина
   после обновления данных.
3. Пустое имя / имя из пробелов не сохраняется — показывается сообщение об ошибке.
4. Не-администратор не видит кнопку редактирования имени (страница недоступна).
5. Ошибка сервера/сети обрабатывается корректно: данные в поле не теряются,
   пользователь получает понятное сообщение.
6. Редактирование категории магазина и прочие существующие функции `/merchants`
   продолжают работать без регрессий.

## 6. Затрагиваемые области (что проверить при приёмке)

- Список магазинов `/merchants` (таблица, пагинация, поиск).
- Представление «Детали чека» и список чеков (консистентность имени).
- Backend-эндпоинты магазинов (проверка прав администратора).
- Существующие тесты backend/frontend — не должно быть регрессий.
