# Задача: Bash-скрипт запуска всех сервисов в режиме отладки (Debug Run Script)

## 1. Бизнес-ценность / Цель

Сегодня запуск всех сервисов проекта в режиме отладки требует ручного выполнения множества шагов из README.md: поднять docker-compose dev-контейнеры (`./up.dev.sh`), сгенерировать TLS-сертификаты, задать переменные окружения, запустить backend (`go run .`), прогнать миграции Analytics, запустить Analytics API (`dotnet run`), запустить frontend (`npm run dev`) и Telegram-бот (`go run .`). Это трудоёмко, подвержено ошибкам и сильно замедляет онбординг и ежедневную разработку.

**Цель:** Создать один bash-скрипт `dev-run.sh` в корне проекта, который запускает **все** сервисы в режиме отладки одной командой. Все переменные окружения берутся из `.env` файла (из корня проекта). Это ускоряет запуск окружения разработчика, устраняет ручные шаги и делает процесс воспроизводимым.

**Дополнительная ценность для заказчика:**
- Снижение времени и когнитивной нагрузки на разработку: одна команда вместо ~7 ручных шагов из README.
- Воспроизводимость окружения: у всех разработчиков запуск идентичен, меньше «у меня работает / у меня нет».
- Единый источник переменных — `.env`; создаётся шаблон `.env.example` со всеми необходимыми переменными.
- Учитываются изменения в `docker-compose`-файлах: скрипт перезапускает dev-контейнеры через существующий `./up.dev.sh`.

## 2. Текущее состояние (AS-IS)

Проект — трёхсервисная система (Backend Go + MongoDB, Telegram Bot Go, Analytics .NET 8/10 + PostgreSQL + frontend React/Vite + Nginx).

Запуск в режиме отладки описан в `README.md` и состоит из шагов:

1. **Инфраструктура**: `./up.dev.sh` поднимает dev-контейнеры из `docker-compose.develop.yml` (mongo на `:27017`, pg на `:5432`, nginx на `:8080`).
2. **TLS-сертификаты**: `./generate-ssl-cert.sh` — генерирует сертификаты (читает `BACKEND_GRPC_HOST` из `.env`). Backend и бот жёстко читают их из `/usr/share/receipts/ssl/certs/` (`certificate.crt`, `private.key`).
3. **Backend** (`backend/`): экспорт переменных (`MONGO_URL`, `MONGO_LOGIN`, `MONGO_SECRET`, `CLIENT_SECRET`, `OPEN_URL`, `NALOGRU_BASE_ADDR`, `TEMPLATES_PATH`, `GET_RECEIPT_WORKER_INTERVAL`) → `go run .`. Слушает `:8888` (HTTP), `:15000` и `:15001` (gRPC).
4. **Analytics Migrations**: `cd ReceiptCollector.Analytics.Migrations && dotnet run` — применяет SQL-миграции к PostgreSQL.
5. **Analytics API**: `cd ReceiptCollector.Analytics.Api && dotnet run` — API на `:5039`; в Development-конфигурации (`appsettings.Development.json`) connection strings указывают на `localhost`.
6. **Frontend**: `cd Analytics/frontend && npm install && npm run dev` — Vite dev-сервер на `:5173`, проксирует `/api` на `:5039`.
7. **Telegram Bot** (`bot/`): экспорт переменных (`BOT_TOKEN`, `BOT_DEBUG`, `HTTP_PROXY`, `ANALYTICS_URL`, `BACKEND_GRPC_ADDR`, `REPORTS_GRPC_ADDR`) → `go run .`. Подключается к backend по TLS gRPC; ждёт готовности gRPC (5 минут).

Проблемы текущего состояния:
- Все шаги выполняются вручную в разных терминалах.
- Переменные окружения захардкожены в README и в примерах могут расходиться с `.env`.
- Файла `.env.example` нет (`.env` в `.gitignore`, у каждого разработчика свой).
- Порядок запуска важен: backend gRPC должен быть готов до старта бота (бот ждёт до 5 минут), PostgreSQL — до миграций.

## 3. Решения заказчика (зафиксированы, обязательны для технического решения)

1. **Все сервисы запускаются всегда**, опциональность запуска отдельных сервисов (флаги/переменные) пока не требуется.
2. **Hot reload (`air`) не используется** — сервисы запускаются через `go run .`.
3. **Скрипт вызывает `./up.dev.sh`** (docker-compose develop). Если контейнеры уже запущены — они не будут пересозданы без необходимости, но изменения в docker-compose-файлах будут учтены.
4. **Создаётся `.env.example`** (шаблон всех переменных окружения). Скрипт при выполнении **проверяет только наличие файла `.env`** и при его отсутствии выдаёт понятную ошибку с подсказкой (например, «скопируйте `.env.example` в `.env` и заполните значения»). **Валидация наличия конкретных переменных не требуется.**
5. **Frontend запускается** в составе скрипта (`npm install` при необходимости + `npm run dev`).
6. **Повторный запуск перезапускает не-инфраструктурные сервисы.** Скрипт можно запускать повторно: если какие-либо сервисы разработки (backend, Analytics API, frontend, бот) уже запущены — скрипт **останавливает их и запускает заново** (чтобы применить новые изменения в коде). **Инфраструктурные сервисы (MongoDB, PostgreSQL, Nginx — docker-контейнеры) при повторном запуске не останавливаются** и продолжают работать.

## 4. Функциональные требования

### FR-1. Единый скрипт запуска
- FR-1.1. Скрипт `dev-run.sh` лежит в корне проекта.
- FR-1.2. Запуск одной командой: `./dev-run.sh` (или `bash dev-run.sh`).
- FR-1.3. Скрипт работает из любого каталога (определяет корень проекта относительно своего расположения).

### FR-2. Источник переменных окружения — `.env`
- FR-2.1. Скрипт подключает `.env` из корня проекта (source) и передаёт переменные запускаемым процессам.
- FR-2.2. Если `.env` отсутствует — скрипт завершается с понятным сообщением об ошибке и подсказкой (см. решение заказчика №4).
- FR-2.3. Создаётся `.env.example` в корне проекта со всеми переменными, используемыми сервисами (перечислены в разделе 7), с комментариями-подсказками и значениями по умолчанию для локальной разработки.

### FR-3. Запуск инфраструктуры
- FR-3.1. Скрипт вызывает существующий `./up.dev.sh` (поднятие dev-контейнеров mongo/pg/nginx).
- FR-3.2. При необходимости генерирует TLS-сертификаты (вызов `./generate-ssl-cert.sh` или эквивалентная логика), если они ещё не созданы.
- FR-3.3. Обеспечивает наличие путей для TLS-сертификатов и шаблонов чеков, которые сервисы читают из фиксированных путей (`/usr/share/receipts/ssl/certs/`, `TEMPLATES_PATH`).

### FR-4. Запуск Backend (Go)
- FR-4.1. Запускается `go run .` в каталоге `backend/` с переменными из `.env`: `MONGO_URL`, `MONGO_LOGIN`, `MONGO_SECRET`, `CLIENT_SECRET`, `OPEN_URL`, `NALOGRU_BASE_ADDR`, `TEMPLATES_PATH`, `GET_RECEIPT_WORKER_INTERVAL` (+ прочие, если требуются).
- FR-4.2. Значения по умолчанию для локальной разработки (если в `.env` не заданы): `MONGO_URL=mongodb://localhost:27017`, `OPEN_URL=http://localhost:5173/login`, `NALOGRU_BASE_ADDR=https://irkkt-mobile.nalog.ru:8888`, `GET_RECEIPT_WORKER_INTERVAL=1m`.

### FR-5. Запуск Analytics (.NET)
- FR-5.1. Сначала выполняются миграции: `dotnet run` в `ReceiptCollector.Analytics.Migrations`.
- FR-5.2. Затем запускается API: `dotnet run` в `ReceiptCollector.Analytics.Api` (слушает `:5039`).
- FR-5.3. Порядок «миграции → API» соблюдается строго.

### FR-6. Запуск Frontend
- FR-6.1. Запускается `npm run dev` в `Analytics/frontend` (dev-сервер на `:5173`).
- FR-6.2. При отсутствии `node_modules` выполняется `npm install`.

### FR-7. Запуск Telegram Bot (Go)
- FR-7.1. Запускается `go run .` в каталоге `bot/` с переменными из `.env`: `BOT_TOKEN`, `BOT_DEBUG`, `HTTP_PROXY`, `ANALYTICS_URL`, `BACKEND_GRPC_ADDR`, `REPORTS_GRPC_ADDR`.
- FR-7.2. Значения по умолчанию для локальной разработки: `BOT_DEBUG=true`, `ANALYTICS_URL=http://localhost:5039`, `BACKEND_GRPC_ADDR=localhost:15000`, `REPORTS_GRPC_ADDR=localhost:15001`.

### FR-8. Поведение при завершении
- FR-8.1. Все сервисы запускаются в фоне (каждый в своём процессе/терминале).
- FR-8.2. Скрипт выводит понятную сводку: какие сервисы запущены, на каких портах, куда смотреть логи.
- FR-8.3. Останавливает (Ctrl+C / trap) запущенные фоновые процессы корректно (без осиротевших процессов).

### FR-9. Повторный запуск и перезапуск сервисов (решение заказчика №6)
- FR-9.1. При повторном запуске скрипт определяет, какие не-инфраструктурные сервисы уже запущены, **останавливает их** и **запускает заново** — с актуальным кодом (перезапуск `go run .` / `dotnet run` / `npm run dev`).
- FR-9.2. К не-инфраструктурным сервисам относятся: backend (`:8888`, gRPC `:15000`/`:15001`), Analytics API (`:5039`), frontend (`:5173`), Telegram-бот (без порта — определяется по процессу/PID).
- FR-9.3. Инфраструктурные сервисы (MongoDB `:27017`, PostgreSQL `:5432`, Nginx `:8080` — docker-контейнеры) при повторном запуске **не останавливаются**; для них выполняется только `./up.dev.sh` (корректировка контейнеров при изменении docker-compose-файлов).
- FR-9.4. Остановка запущенных сервисов выполняется корректно (весь процессный дерево, включая дочерние бинарники `go run`/`dotnet run`), без осиротевших процессов.
- FR-9.5. Если не-инфраструктурный сервис был запущен **не этим экземпляром скрипта** (например, вручную в отдельном терминале) — скрипт всё равно останавливает его и забирает порт под свой запуск.

## 5. Нефункциональные требования

- NFR-1. Скрипт написан на bash (`#!/usr/bin/env bash`) с `set -euo pipefail` (или эквивалентными опциями безопасности).
- NFR-2. Повторный запуск безопасен для инфраструктуры (docker-контейнеры не пересоздаются/не останавливаются без необходимости), а сервисы разработки (backend, Analytics API, frontend, бот) при повторном запуске **перезапускаются с актуальным кодом** (см. решение заказчика №6, FR-9).
- NFR-3. Переносимость: не зависит от `cd` в текущем каталоге, корректно определяет корень проекта.
- NFR-4. Понятные сообщения об ошибках: отсутствие `.env`, отсутствие зависимостей (go/dotnet/npm/docker), сбой одного из сервисов.
- NFR-5. Не дублирует логику, которая уже есть в существующих скриптах (`up.dev.sh`, `generate-ssl-cert.sh`) — переиспользует их.
- NFR-6. Добавляется `.env.example`; `.env` остаётся в `.gitignore` (секреты не коммитим).

## 6. Критерии приёмки

1. В корне проекта появились `dev-run.sh` и `.env.example` (оба — исполняемые/читаемые, `.env.example` попадает в git).
2. При отсутствии `.env` скрипт выводит понятную ошибку с подсказкой про `.env.example` и завершается с ненулевым кодом.
3. После `cp .env.example .env` и заполнения значений одна команда `./dev-run.sh` поднимает окружение: dev-контейнеры (mongo/pg/nginx), backend (`:8888`, gRPC `:15000`/`:15001`), миграции Analytics, Analytics API (`:5039`), frontend (`:5173`), Telegram-бот.
4. Переменные для backend и бота действительно приходят из `.env` (проверяется логами/поведением сервисов).
5. Backend и бот стартуют с TLS-сертификатами (gRPC соединение бота с backend успешно).
6. Скрипт корректен при запуске из любого каталога (не только из корня проекта).
7. Повторный запуск `./dev-run.sh` останавливает и перезапускает не-инфраструктурные сервисы (backend, Analytics API, frontend, бот) — с актуальным кодом; инфраструктурные контейнеры (mongo/pg/nginx) при этом продолжают работать и не перезапускаются (FR-9, NFR-2).
8. Ctrl+C корректно останавливает все фоновые процессы, запущенные скриптом (FR-8.3).
9. `go vet`/`shellcheck` (или эквивалентная проверка) для `dev-run.sh` проходит без критических замечаний.

## 8. Предположения (сделаны PM на основе контекста проекта)

- Скрипт переиспользует существующие `./up.dev.sh` и `./generate-ssl-cert.sh`, не дублируя их логику (NFR-5).
- Сервисы запускаются фоновыми процессами с выводом логов (в терминал или в файлы логов в `.gitignore`-каталоге, например `logs/`), финальное решение — за архитектором.
- Порядок запуска: инфраструктура → сертификаты → backend → миграции → Analytics API → frontend → бот. Бот ждёт готовности gRPC backend (до 5 минут) — этот механизм уже встроен в код бота.
- При повторном запуске не-инфраструктурные сервисы перезапускаются (FR-9): механизм определения «уже запущен» (PID-файлы и/или занятость портов) и корректной остановки (процессные группы) — на усмотрение архитектора.
- Допускается добавить короткие паузы/ожидание готовности портов (`:8888`, `:5039`) перед запуском зависимых сервисов.
- Глубокие технические детали (архитектура, точная структура процессов, обработка сигналов, логирование) — на усмотрение архитектора; здесь намеренно не детализированы.

## 9. Связь с техническим решением и ожидания от команды

Техническое решение ожидается от архитектора (@software-architect): скрипт `dev-run.sh` + шаблон `.env.example`. Реализация — по ADR/плану после утверждения архитектуры.

**Ожидания от команды по реализации:**
- Разработать `dev-run.sh` строго по требованиям разделов 3–5 (без отклонений от решений заказчика).
- Создать `.env.example` со всеми переменными раздела 7 и комментариями-подсказками.
- Обеспечить критерии приёмки раздела 6, включая корректное завершение процессов по Ctrl+C.
- Обновить `README.md` (добавить раздел про `dev-run.sh` и `.env.example`), если это входит в объём.
