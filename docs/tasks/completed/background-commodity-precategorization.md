# Задача: Фоновая предкатегоризация товаров в простое + админский раздел подтверждения

> **Относится к функционалу автоматической категоризации товаров.** Базируется на ADR 009 (автокатегоризация, контракт suggest/apply), ADR 019 (in-memory кэш категорий и порядок приоритетов), ADR 021 (проброс env в docker-compose), ADR 023 (URL-схема webUI). Существующий пользовательский сценарий категоризации чека **не меняется**.
>
> **Требуется новое ADR** (предлагаемый номер — ADR-027): фоновый режим работы, глобальный (вне owner-scoping) доступ к данным всех пользователей, новая таблица с очередью предложений и админский workflow. ADR пишет @software-architect, в этой задаче он не создаётся.

## Приоритет
**medium** — сроков нет, задача из бэклога. Даёт снижение ручной работы и заранее наполняет категории для всех пользователей, но не блокирует текущий функционал: категоризация чеков по запросу пользователя работает как раньше.

## Проблема (контекст)
- Категоризация выполняется только по действию пользователя на странице чека. Пока пользователь не открыл чек и не нажал «Категоризировать», товары остаются без категории, а аналитика по категориям неполная.
- ИИ-категоризация — платная и небыстрая операция. Логично выполнять её, когда сервис простаивает (нет запросов), чтобы не мешать пользователям и не создавать конкуренцию за ИИ.
- Результат фоновой ИИ-категоризации нельзя сразу писать в `commodities`: ошибки модели нужно отфильтровать силами человека. Нужен промежуточный слой «предложенные категории» и отдельный раздел для администратора, где предложения подтверждаются, исправляются или отклоняются.
- Подтверждение админом должно применяться массово ко всем некатегоризированным товарам с **точно таким же** наименованием у **всех** пользователей — вручную это делать невозможно.
- Сейчас повторные вызовы ИИ для уже известных названий предотвращает in-memory кэш (ADR 019), но заполняется он только из уже категоризированных товаров; фоновый процесс не должен обходить этот кэш.

## Цель
- Выполнять ИИ-категоризацию товаров **в фоне, только в период простоя** Analytics (по умолчанию — 5 минут без HTTP-запросов), последовательно, с ограничениями по числу позиций и паузе между вызовами ИИ, с корректной остановкой при появлении запроса.
- Не сохранять категории в `commodities` сразу: складывать предложения в отдельную таблицу `precategorized_commodities` (наименование, магазин, предложенная категория).
- Дать администратору раздел webUI для просмотра предложений и трёх действий: подтвердить, изменить категорию, отклонить.
- При подтверждении массово присвоить выбранную категорию **всем некатегоризированным** товарам с точно таким же наименованием у всех пользователей и обновить in-memory кэш, чтобы последующие пользовательские запросы получали категорию из кэша.
- Перед вызовом ИИ использовать единый порядок проверок: список уже категоризированных товаров → in-memory кэш → очередь предкатегорий → ИИ. Тот же порядок применяется и в фоне, и в ручной категоризации чека (в ручной добавляется только новый шаг поиска по очереди; existing-шаг фона — отдельный глобальный запрос по точному наименованию, D1).

## Границы задачи

### Входит в объём (in scope)
- Монитор активности HTTP-запросов и фоновый hosted service предкатегоризации в `Analytics`.
- Новая таблица `precategorized_commodities`, SQL-миграция (индексы — только на новой таблице; индексы на `commodities` отложены, см. NFR-6/риски), EF-конфигурация.
- Админские HTTP-эндпоинты управления предложениями (список/изменение/подтверждение/отклонение).
- Новый раздел webUI, доступный только администратору (скрыт в навигации для не-админа + серверная проверка прав).
- Интеграция ручной категоризации чека с очередью предкатегорий: в `suggest` перед вызовом ИИ выполняется поиск по `precategorized_commodities`; при находке ИИ не вызывается.
- Конфигурация (`Precategorization:*`), проброс в `docker-compose.yml` и `.env.example`, обновление таблицы настроек в `AGENTS.md`.
- Тесты по слоям + Architecture-тесты.

### Не входит в объём (out of scope)
- Изменения Go-сервисов (`backend/`, `bot/`), nginx, MongoDB-схемы.
- Изменение структуры существующих контрактов `POST /api/receipts/{id}/categories/suggest` и `PUT /api/receipts/{id}/categories` (допустимо только добавление нового значения `source = "precategorized"`, FR-9).
- Изменение порядка и поведения пользовательской категоризации чека, кроме добавления шага поиска по очереди предкатегорий перед ИИ (FR-9).
- Пакетные операции над предложениями («подтвердить все», «отклонить все»), массовый импорт/экспорт.
- Автоматическое применение категорий без подтверждения админом, обучение/калибровка модели, оценка качества ИИ.
- Распределённая координация нескольких экземпляров Analytics (см. «Риски»).
- Политика ретенции/очистки подтверждённых строк (см. «Риски» и «Бэклог»).
- Отдельный ADR (пишется архитектором как зависимость, не в этой задаче).

## Пользователи
- **Администратор** (`users.is_admin = true`, проверка по паттерну `MerchantEndpoints`) — просматривает очередь предложений, подтверждает/меняет/отклоняет категории.
- **Конечный пользователь webUI** — косвенно: его некатегоризированные товары получают категорию после подтверждения админом, а на странице чека предложение приходит из кэша (`source = cache`) без вызова ИИ.
- **Оператор/DevOps** — включает/выключает фон, настраивает таймауты и лимиты через конфигурацию, наблюдает по логам.

## Принятые решения

Зафиксированы ответы заказчика и решения PM по неоднозначностям. Все они обязательны к исполнению.

| № | Решение |
|---|---------|
| C1 | **Простой определяется глобально** по всем пользователям: фоновый процесс запускается, если за последние N минут (по умолчанию 5) не было **ни одного** HTTP-запроса к Analytics API. При появлении нового запроса работа приостанавливается. |
| C2 | **Область данных — все товары всех пользователей.** Подтверждение применяется ко всем некатегоризированным товарам с точно таким же наименованием у всех пользователей. |
| C3 | **Уникальность строки таблицы — пара (точное наименование, магазин).** Магазин хранится для контекста админу; подтверждение применяется по наименованию. |
| C4 | **Отклонение = удаление строки** без запоминания. При следующем простое ИИ может снова предложить категорию для этого наименования. |
| C5 | **Ограничения:** настраиваемый лимит обработанных позиций за сессию + настраиваемая пауза между вызовами ИИ; при появлении HTTP-запроса — корректная остановка после текущей позиции. |
| D1 | **Перед ИИ — проверка уже категоризированных товаров** (список из `commodities`) и in-memory кэш, порядок концептуально тот же, что в `CommodityCategorizationService` (existing → cache → AI). Важно: в ручном пути шаг `existing` в `CommodityCategorizationService` проверяет **категорию самого товара чека** и остаётся без изменений. Фоновый процесс использует **новый репозиторный запрос** — по точному наименованию среди товаров всех пользователей (`IgnoreQueryFilters()`, D8) — это не переиспользование кода существующего existing-шага, а новая реализация, воспроизводящая его семантику глобально. Если у любого товара с таким же точным наименованием категория уже выставлена — предложение создаётся с этой категорией; иначе проверяется кэш (`CommodityNameNormalizer`); ИИ вызывается только если ни там, ни там категории нет. Строка предложения создаётся в любом случае (админ её подтверждает), ИИ при попадании в existing/кэш не вызывается. Ход проверок: новый глобальный запрос по существующим категориям → кэш → ИИ. |
| D2 | **Статусы строк:** `proposed` (показывается админу) и `applied` (подтверждена). Подтверждённые строки **не удаляются**, а переводятся в `applied`: это (а) журнал действий админа, (б) защита от повторного предложения той же пары, (в) основание для индекса по статусу. Отклонённые — удаляются (C4). |
| D3 | **Health-check не считается активностью.** Запросы к `/health` (и аналогичные пробники, если появятся) не сбрасывают таймер простоя, иначе мониторинг инфраструктуры навсегда заблокирует фон. Все остальные запросы, включая статику и загрузку SPA, считаются активностью. |
| D4 | **Порядок обработки — строго последовательный («по одному»)**, без параллельных вызовов ИИ в фоне. Пауза `IntervalBetweenCalls` выдерживается после каждого вызова ИИ; для строк из кэша пауза не нужна. |
| D5 | **Если ИИ не настроен** (`AI:BaseUrl` пуст) — фоновый процесс не вызывает ИИ, но может создавать предложения из кэша; факт фиксируется в логе уровня Warning. Фон не падает и не отключается. |
| D6 | **Ответы ИИ `Undefined` / ошибки ИИ не создают строку** — только запись в лог; кандидат останется необработанным и может быть предложен в следующей сессии. |
| D7 | **Повторные предложения не создаются:** если пара `(name, merchant_id)` уже есть в таблице в любом статусе, или для этого точного наименования уже есть строка в статусе `proposed` (у другого магазина), новая строка не создаётся. Уникальность в БД — по `(name, merchant_id)` (C3), запрет дублей по имени — на уровне сервиса. |
| D8 | **Глобальный доступ к данным** реализуется явно: отдельные репозиторные методы для фоновой/админской логики используют `IgnoreQueryFilters()` на `ReceiptDbContext.Receipts` (query-filter owner-scoped настроен только на `ReceiptEntity`) с комментарием, что доступ намеренно вне owner-scoping. Существующие owner-scoped запросы (`ReceiptRepository`, `CommodityReadService`) не меняются. |
| D9 | **Категория предложения хранится только как `proposed_category_id`**; отображаемое имя вычисляется через `CommodityCategoryHelper.GetDisplayName` (как в ADR 019), денормализованное имя в новой таблице не хранится — иначе оно устареет при переименовании категорий (ср. миграцию `20260807135439_fix_commodity_category_food_name.sql`). |
| D10 | **Подтверждение — одна транзакция**: обновление `commodities` (все пользователи, только `category_id IS NULL OR category_id = 0`), перевод строки в `applied`, удаление «сестринских» `proposed`-строк с тем же точным наименованием, `TryAdd` в in-memory кэш по нормализованному имени. Если commodities не обновились (их уже категоризировали) — строка всё равно переводится в `applied`, ответ содержит `updatedCommodities = 0`. |
| D11 | **`Undefined` (0) трактуется как «категории нет»** и в предложения не попадает; изменить предложение на `Undefined` нельзя (400). |
| D12 | **Фон работает в одном экземпляре Analytics.** Текущее развёртывание — один контейнер `receipt-analytics`; распределённой блокировки нет. При масштабировании потребуется отдельное решение (в риски). |
| D13 | **Ручная категоризация чека тоже использует очередь предкатегорий.** В `CommodityCategorizationService.SuggestForReceiptAsync` порядок становится: категория самого товара (`existing`) → in-memory кэш (`cache`) → `precategorized_commodities` (`precategorized`) → ИИ (`ai`). Приоритет кэша выше очереди, потому что кэш содержит уже подтверждённые категории, а очередь — неподтверждённые предложения. Поиск по очереди — по **точному** наименованию товара (магазин не учитывается, т.к. подтверждение применяется по наименованию), одним batch-запросом на все различные наименования чека. При находке ИИ не вызывается; результат отдаётся как предложение (`suggest` по-прежнему ничего не сохраняет) с `source = "precategorized"`. |
| D14 | **Прогресс между сессиями — курсор по последнему обработанному кандидату.** Кандидаты перебираются в детерминированном порядке (FR-3.5); сессия выставляет курсор на последнего обработанного кандидата — в том числе кандидата, для которого строка не создалась (`Undefined`, ошибка ИИ, пропуски по FR-4.7). Иначе такой кандидат не попадает в исключения FR-3.2/3.4, остаётся первым в порядке и каждая сессия будет упираться в него же (head-of-line blocking). Курсор хранится в памяти фонового сервиса; при перезапуске Analytics сбрасывается — порядок перебирается заново, повторных строк не появляется благодаря FR-3.2/3.4 и уникальному индексу, а «пройденные» `Undefined`-кандидаты перепроходят ИИ не более одного раза за запуск. |

## Пользовательские сценарии

### UC-1. Фоновая сессия предкатегоризации (happy path)
1. Пользователи не обращаются к Analytics; таймер последней активности истёк (≥ `IdleTimeout`, по умолчанию 5 минут).
2. Фоновый сервис выбирает очередную порцию кандидатов: различные пары `(наименование, магазин)` по товарам всех пользователей, у которых категория не выставлена (`NULL` или `0`), исключая пары/имена, уже присутствующие в `precategorized_commodities` (любой статус).
3. Для каждого кандидата по порядку:
   - сначала проверяется, есть ли у товара с таким же точным наименованием уже выставленная категория в `commodities`, затем in-memory кэш; при попадании в existing/кэш строка создаётся с этой категорией, ИИ не вызывается;
   - иначе — один вызов ИИ (`IAiClient.SuggestCategoryAsync`), пауза `IntervalBetweenCalls`;
   - при валидной категории (не `Undefined`) в таблицу добавляется строка `proposed`; при `Undefined`/ошибке строка не создаётся.
4. После каждой позиции проверяется активность: если пришёл HTTP-запрос — сессия завершается (новые позиции не берутся), недообработанные останутся на следующий простой.
5. Сессия также завершается при достижении `BatchLimit`.

### UC-2. Админ подтверждает предложенную ИИ категорию
1. Админ открывает раздел «Предкатегоризация» (пункт навигации виден только админу).
2. Видит таблицу предложений: наименование, магазин, предложенная категория, дата; доступны поиск и пагинация.
3. Нажимает «Подтвердить» у строки.
4. Сервис в транзакции присваивает категорию всем товарам с **точно таким же** наименованием без категории у **всех** пользователей, помечает строку `applied`, удаляет одноимённые `proposed`-строки, кладёт категорию в кэш.
5. Строка исчезает из списка; показывается уведомление с числом обновлённых товаров (`updatedCommodities`).

### UC-3. Админ меняет категорию и подтверждает
1. Админ выбирает другую категорию в выпадающем списке строки.
2. Изменение сохраняется в предложении (`PUT .../category`), после чего админ нажимает «Подтвердить» (шаги 4–5 UC-2). До подтверждения `commodities` не меняются.
3. Если админ передумал — «Отклонить» удаляет строку целиком.

### UC-4. Админ отклоняет предложение
1. Админ нажимает «Отклонить» (с подтверждением в диалоге).
2. Строка удаляется; `commodities` не меняются. При следующем простое ИИ может снова предложить категорию для этого наименования (C4).

### UC-5. Пользователь после подтверждения
1. Пользователь открывает чек с некатегоризированным товаром, чьё наименование совпало с подтверждённым.
2. Suggest отвечает предложением из кэша (`source = cache`), без вызова ИИ. Сохранение — как раньше, по кнопке.

### UC-6. Пользователь запускает категоризацию чека вручную, пока в очереди есть предложения
1. Пользователь нажимает «Категоризировать» на странице чека (`POST /api/receipts/{id}/categories/suggest`).
2. Для каждой позиции сервис проверяет: категория товара → in-memory кэш → очередь `precategorized_commodities` (поиск по точному наименованию).
3. Если наименование найдено в очереди — позиция получает предложенную там категорию с `source = "precategorized"`, ИИ для неё не вызывается.
4. Пользователь может изменить категорию и сохранить как обычно; сохранение идёт через существующий `PUT /api/receipts/{id}/categories` и кладёт категорию в кэш.
5. Строка в очереди при этом не меняется: её судьбу (подтвердить/отклонить) решает админ.

## Функциональные требования

### FR-1. Детектирование простоя
- FR-1.1. В Analytics ведётся монотонный **глобальный** признак последней активности: timestamp обновляется на каждом HTTP-запросе, проходящем через pipeline, кроме исключённых путей.
- FR-1.2. Исключённые пути: `/health`. Решение фиксируется в коде и в ADR; список исключений должен быть расширяемым без переписывания логики (например, предикат по `Path`).
- FR-1.3. Состояние «простой» = с последней активности прошло не меньше `Precategorization:IdleTimeout` (по умолчанию 5 минут). Если запросов не было с момента старта — отсчёт ведётся от старта сервиса.
- FR-1.4. Обновление timestamp не должно заметно влиять на latency запроса (O(1), без I/O, без блокировок).
- FR-1.5. При `Precategorization:Enabled = false` фоновый сервис не запускает сессии (и не пишет в таблицу), но админский раздел и API продолжают работать для уже накопленных строк.

### FR-2. Фоновая сессия и её ограничения
- FR-2.1. Фоновая обработка запускается только при состоянии «простой» (FR-1.3); ожидание проверяется периодически (`Precategorization:IdleCheckInterval`, по умолчанию 30 секунд), без busy-loop.
- FR-2.2. Обработка последовательная, по одной позиции; параллельные вызовы ИИ из фона запрещены.
- FR-2.3. За сессию обрабатывается не более `Precategorization:BatchLimit` позиций (по умолчанию 5). Достижение лимита завершает сессию; остаток обрабатывается в следующем простое.
- FR-2.4. Между вызовами ИИ выдерживается `Precategorization:IntervalBetweenCalls` (по умолчанию 2 секунды).
- FR-2.5. Перед взятием каждой следующей позиции проверяется активность: если с момента старта сессии появился хотя бы один HTTP-запрос (не исключённый по FR-1.2), сессия завершается **после текущей позиции** — начатый вызов ИИ доводится до конца и его результат сохраняется, новые позиции не берутся.
- FR-2.6. Ошибка обработки одной позиции (исключение БД/ИИ/валидации) логируется и не прерывает сессию; сервис продолжает со следующей позиции.
- FR-2.7. Ошибка уровня БД при выборке кандидатов логируется, сессия завершается, повтор — на следующем цикле; процесс Analytics не падает (паттерн `ReceiptSynchronizationHostedService`).
- FR-2.8. При остановке приложения (`CancellationToken` хоста) сессия прекращается без исключений; уже записанные строки сохраняются.

### FR-3. Выбор кандидатов
- FR-3.1. Кандидат — различные пары `(name, merchant_id)` по товарам **всех** пользователей, у которых `category_id IS NULL OR category_id = 0`.
- FR-3.2. Исключаются пары, для которых уже есть строка в `precategorized_commodities` в **любом** статусе. Эта проверка имеет приоритет над FR-3.3: пара, присутствующая в таблице (в т.ч. `applied`), кандидатом не является, даже если у наименования есть категоризированный товар у другого магазина — иначе вставка всё равно упрётся в unique-индекс (ср. FR-4.5).
- FR-3.3. Наименования, для которых у любого пользователя уже есть товар с выставленной категорией (`category_id IS NOT NULL AND category_id <> 0`), **не исключаются** из кандидатов: для них предложение формируется из этой уже известной категории без вызова ИИ (это и есть «список уже категоризированных товаров» из дополнения заказчика — проверка выполняется до ИИ). Приоритет FR-3.2 выше: пара, уже присутствующая в таблице в любом статусе, кандидатом не является независимо от этого пункта.
- FR-3.4. Исключаются наименования, для которых уже есть строка в статусе `proposed` (в т.ч. у другого магазина) — не плодим дубли в очереди админа (D7).
- FR-3.5. Выборка детерминирована (стабильный порядок, например по `name`, `merchant_id`), чтобы пагинация сессий не «зацикливалась» на одних и тех же строках. Продвижение между сессиями — по курсору последнего обработанного кандидата (D14), а не по смещению; `Undefined`/ошибочные кандидаты тоже двигают курсор, иначе каждая следующая сессия начнётся с него же.
- FR-3.6. После проверки по списку категоризированных (FR-3.3) и перед ИИ выполняется проверка in-memory кэша (`ICommodityCategoryCache.TryGet` по `CommodityNameNormalizer.NormalizeName`), как в существующем алгоритме (D1).

### FR-4. Создание предложений
- FR-4.1. Строка таблицы содержит: точное наименование товара (как в `commodities.name`), магазин, предложенную категорию, статус, дату создания.
- FR-4.2. Валидное предложение ИИ (`CommodityCategory != Undefined`, значение из реестра `CommodityCategoryHelper.GetAll()` без `Undefined`) создаёт строку `proposed`.
- FR-4.3. Наличие уже категоризированного товара с тем же точным наименованием или попадание в in-memory кэш создаёт строку `proposed` с этой категорией **без вызова ИИ** (D1).
- FR-4.4. `Undefined`, ошибки/таймауты/невалидный ответ ИИ строку не создают (D6); факт пишется в лог.
- FR-4.5. Конфликт уникальности `(name, merchant_id)` (например, параллельная вставка) не приводит к ошибке сессии: конфликт игнорируется (upsert/`ON CONFLICT DO NOTHING` или обработка `DbUpdateException`).
- FR-4.6. `commodities` в ходе фоновой обработки **не изменяются**.
- FR-4.7. Наименования, не помещающиеся в `varchar(256)`, и пустые/пробельные наименования пропускаются с предупреждением (в текущей схеме длина ограничена 256, но защита нужна).

### FR-5. Админский API управления предложениями
- FR-5.1. `GET /api/precategorized-commodities` — постраничный список строк **только в статусе `proposed`**, с поиском по наименованию/магазину; возвращает `X-Total-Count`.
- FR-5.2. `PUT /api/precategorized-commodities/{id}/category` — изменение предложенной категории без применения к товарам.
- FR-5.3. `POST /api/precategorized-commodities/{id}/confirm` — подтверждение: применение категории к товарам по точному наименованию (FR-6), перевод строки в `applied`, удаление одноимённых `proposed`-строк, обновление кэша.
- FR-5.4. `DELETE /api/precategorized-commodities/{id}` — отклонение: физическое удаление строки, `commodities` не меняются (C4).
- FR-5.5. Все методы требуют аутентификации (`UserContext.UserId`): нет пользователя → `401`; пользователь не админ (`IUserRepository` → `User.IsAdmin`) → `403`. Проверка — на сервере, независимо от видимости раздела в UI.
- FR-5.6. Валидация категории: `Enum.IsDefined(CommodityCategory)` и значение ≠ `Undefined`; иначе `400`.
- FR-5.7. Операции над строкой в статусе `applied` → `409 Conflict`; над несуществующей → `404`.
- FR-5.8. Изменение/подтверждение идемпотентно по данным: повторный `confirm` не дублирует обновления (вторая попытка → `409`).
- FR-5.9. Ошибки авторизации/валидации возвращаются в стиле существующих эндпоинтов (`Results.Unauthorized`/`Forbid`/`BadRequest`/`NotFound`); формат тела ошибки — как у `MerchantEndpoints`/`CommodityEndpoints` (текст; `ProblemDetails` — на усмотрение архитектора).

### FR-6. Применение подтверждённой категории
- FR-6.1. При подтверждении категория присваивается **всем** товарам у **всех** пользователей, у которых `name` **точно равен** наименованию строки (сравнение БД `name = :name`, без нормализации/`lower`) и `category_id IS NULL OR category_id = 0`.
- FR-6.2. Записываются и `category_id`, и `category_name` (отображаемое имя через `CommodityCategoryHelper.GetDisplayName`) — как в `CommodityRepository.UpdateCategoryAsync`.
- FR-6.3. Товары, у которых уже есть содержательная категория (`category_id NOT NULL` и `<> 0`), не затрагиваются и не перезаписываются; `category_id = 0` (`Undefined`) трактуется как отсутствие категории и обновляется (D11).
- FR-6.4. Категория добавляется в in-memory кэш по нормализованному имени (`ICommodityCategoryCache.TryAdd`), чтобы последующие suggest получали её как `source = cache`. `TryAdd` не ломает работу при «замороженном» кэше (существующая семантика ADR 019).
- FR-6.5. Вся операция выполняется в одной транзакции БД; при ошибке — откат, строка остаётся `proposed`.
- FR-6.6. Ответ содержит число фактически обновлённых товаров (`updatedCommodities`), которое может быть `0`.

### FR-7. WebUI: раздел «Предкатегоризация»
- FR-7.1. Новый маршрут `/precategorized` (имя — на усмотрение архитектора, но по стилю ADR-023 в `routes.ts`), страница доступна только админу: пункт навигации скрыт для не-админа (`useAdmin`), а при прямом заходе не-админу показывается «нет доступа»/`NotFoundPage`, данные не запрашиваются.
- FR-7.2. Таблица: наименование, магазин, предложенная категория (выпадающий список всех категорий, кроме `Undefined`), дата создания, действия.
- FR-7.3. Действия: «Подтвердить», «Отклонить» (с диалогом подтверждения), смена категории в списке с сохранением.
- FR-7.4. Пагинация и поиск по образцу `MerchantsPage`/`useMerchants` (`Pagination` на уровне страницы, `X-Total-Count`); прототип поиска по подстроке — `api/merchants.ts` (`search` → `MerchantEndpoints.GetAll`); в существующих хуках поиск не заведён, так что search-состояние реализуется по этому паттерну (limit/offset + `X-Total-Count`). Пустое состояние («Нет предложений»), состояние загрузки и ошибки.
- FR-7.5. После успешного действия — toast (паттерн `Toasts`) и обновление списка; после подтверждения — текст с числом обновлённых товаров.
- FR-7.6. Ошибки API (`401`/`403`/`409`) показываются пользователю понятным сообщением, без падения страницы.

### FR-8. Наблюдаемость
- FR-8.1. Логируются: старт/стоп сессии (с причиной: лимит/активность/нет кандидатов/остановка хоста), число кандидатов, число созданных предложений, число ошибок ИИ, длительность сессии.
- FR-8.2. Для каждого вызова ИИ — длительность и результат (категория/`Undefined`/ошибка), без содержимого чеков сверх наименования товара.
- FR-8.3. Логи не содержат персональных данных пользователей (userId в фоновых логах не обязателен; при необходимости — только агрегаты).

### FR-9. Использование очереди в ручной категоризации чека
- FR-9.1. В `CommodityCategorizationService.SuggestForReceiptAsync` между проверкой кэша и вызовом ИИ добавляется поиск по `precategorized_commodities` (D13). Порядок: `existing` → `cache` → `precategorized` → `ai`.
- FR-9.2. Поиск выполняется по **точному** наименованию товара (`name = :name`, без нормализации и `lower`) в любом статусе строки (`proposed`/`applied`); при нескольких строках с одним наименованием берётся категория самой свежей (по `created_at`/`applied_at`). Категорию строки дополнительно проверяем `Enum.IsDefined(CommodityCategory)` (маловероятное событие — значение удалено из реестра категорий, ср. миграцию `fix_commodity_category_food_name`): если не определена, позиция идёт дальше по обычному порядку (кэш/ИИ) без ошибки запроса; деталь фиксируется в ADR.
- FR-9.3. Запрос к очереди выполняется один раз на чек: по множеству различных наименований позиций, которым ещё не нашлось категории на шагах `existing`/`cache`. N+1 запросов не допускается.
- FR-9.4. Найденная категория возвращается в `suggest` с `source = "precategorized"`; ИИ для этой позиции не вызывается. Значение `precategorized` добавляется в `CategorizationSource`/`CategorizationSourceNames` (wire-имя `precategorized`).
- FR-9.5. `suggest` остаётся read-only: ни `commodities`, ни `precategorized_commodities` не изменяются; сохранение — только через существующий `PUT /api/receipts/{id}/categories`.
- FR-9.6. Ошибка чтения очереди не должна ломать категоризацию чека: логируется Warning, позиции продолжают обрабатываться через ИИ (деградация вместо `500`).
- FR-9.7. Если `Precategorization:Enabled = false`, поиск по очереди в ручном пути **не отключается** (раздел админа обязан работать с уже накопленными строками), но новых строк фон не создаёт.

## Нефункциональные требования

- **NFR-1. Не блокировать запросы.** Фоновая работа не выполняется в контексте HTTP-запроса; появление запроса останавливает сессию (FR-2.5). Максимальная задержка остановки = длительность текущего вызова ИИ (ограничена `AI:Timeout`, в `appsettings.json` по умолчанию 80 с) — см. «Риски».
- **NFR-2. Изоляция отказов.** Любая ошибка фона логируется и не приводит к падению Analytics; админские эндпоинты возвращают корректные коды, а не 500 при ожидаемых конфликтах.
- **NFR-3. Ограниченная стоимость ИИ.** Число вызовов ИИ за сессию ≤ `BatchLimit`, интервал между вызовами ≥ `IntervalBetweenCalls`; при попадании в кэш/список категоризированных/очередь предкатегорий ИИ не вызывается. Суммарная параллельность: фон — 1 вызов, пользовательский путь — до `AI:Concurrency`.
- **NFR-4. Идемпотентность.** Повторный запуск сессии/повторное подтверждение не создают дублей и не перезаписывают уже выставленные категории.
- **NFR-5. Owner-scoping не сломан.** Существующие owner-scoped запросы остаются owner-scoped; глобальный доступ реализован только в новых методах и явно (`IgnoreQueryFilters` + комментарий, D8). Architecture-тесты проходят без ослабления правил.
- **NFR-6. Производительность БД.** Список админа и исключения FR-3.2/3.4 опираются на индексы таблицы `precategorized_commodities` (unique по паре, по статусу). Индексы на `commodities` в этой задаче не создаются: выборка кандидатов (DISTINCT по парам через join `commodities → receipts → merchants`) может идти Seq Scan'ом по отфильтрованному множеству — это осознанное ограничение (решение PM); по мере накопления данных замерить планы запросов и выбрать индексы отдельным решением (см. «Риски» п. 6).
- **NFR-7. Управляемость.** Все параметры фона задаются конфигурацией (`appsettings.json` + env `Precategorization__*`), применяются без пересборки; некорректные значения (отрицательные таймауты, `BatchLimit < 1`) приводят к явной ошибке валидации на старте или к безопасным дефолтам — решение фиксирует архитектор.
- **NFR-8. Совместимость.** Go-сервисы, бот, nginx, MongoDB не затрагиваются; контракты существующих эндпоинтов не меняются, кроме аддитивного значения `source = "precategorized"` в ответе suggest (FR-9).
- **NFR-9. Тестируемость.** Логика простоя и паузы тестируется без реальных `Task.Delay`/системных часов (внедряемый источник времени/задержки).

## Схема БД и миграции

Новая таблица — очередь предложений. Миграция: SQL-скрипт в `src/ReceiptCollector.Analytics.Migrations/Scripts` (имя вида `20261023120000_add_precategorized_commodities.sql`), применяется существующим `MigrationRunner` (транзакция на скрипт, учёт в `migration_scripts_history`).

```sql
CREATE TABLE precategorized_commodities
(
    id                    uuid PRIMARY KEY,
    name                  varchar(256) NOT NULL,           -- точное наименование, как commodities.name
    merchant_id           uuid         NOT NULL,           -- магазин для контекста админу
    proposed_category_id  integer      NOT NULL,           -- CommodityCategory, != 0 (Undefined)
    status                smallint     NOT NULL DEFAULT 0, -- 0 = proposed, 1 = applied
    created_at            timestamptz  NOT NULL DEFAULT now(),
    applied_at            timestamptz,
    CONSTRAINT fk_precategorized_commodities_merchants
        FOREIGN KEY (merchant_id) REFERENCES merchants (id) ON DELETE CASCADE,
    CONSTRAINT ck_precategorized_commodities_status CHECK (status IN (0, 1))
);

-- Уникальность пары (точное наименование, магазин) — C3.
CREATE UNIQUE INDEX ux_precategorized_commodities_name_merchant
    ON precategorized_commodities (name, merchant_id);

-- Индекс по статусу — выборка очереди админа.
CREATE INDEX ix_precategorized_commodities_status
    ON precategorized_commodities (status, created_at);

-- Индекс на commodities (name, category_id) НЕ создаётся в этой задаче
-- (решение PM): состав индексов под выборку кандидатов заранее не определён —
-- нужна DISTINCT-выборка (name, merchant_id), а merchant у commodity есть
-- только через join commodities → receipts → merchants. Текущее ожидание:
-- запрос кандидатов пойдёт Seq Scan'ом по отфильтрованному множеству.
-- По результатам эксплуатации замерить планы запросов и решить применимость
-- индексов отдельным решением (см. «Риски» п. 6 и ADR-027).
```

Пояснения:
- `status` — `smallint` + `CHECK`, отображается на enum (например, `PrecategorizedCommodityStatus { Proposed = 0, Applied = 1 }`). Wire-имена в API — `proposed`/`applied`.
- Денормализованное имя категории не хранится (D9): отображается через `CommodityCategoryHelper`.
- `ON DELETE CASCADE` для магазина: предложение — производная данных, удаление магазина не должно блокироваться. (У `receipts` — `RESTRICT`, здесь сознательно иначе; зафиксировать в ADR.)
- Индекс на `commodities (name, category_id)` в миграцию **не включается** (решение PM): состав индексов под выборку кандидатов (DISTINCT `(name, merchant_id)` через join `commodities → receipts`) не выбран заранее; ограничение производительности описано в NFR-6 и рисках, замеры по результатам использования — в ADR-027 и бэклоге.
- EF: `PrecategorizedCommodityEntity` + `PrecategorizedCommodityConfiguration` в `Infrastructure/Persistence/Postgres`, `DbSet` в `ReceiptDbContext`; `ApplyConfiguration` в `OnModelCreating`. Маппинг snake_case уже настроен (`UseSnakeCaseNamingConvention`).
- Query-filter на новую сущность **не** ставится: очередь общая для всех пользователей; фильтрация — только по статусу в запросах. Это надо явно указать в ADR.

## API-контракты

- `409` — строка уже `applied`.
- `401`/`403`.
- Побочные эффекты: обновление `commodities` всех пользователей по точному имени (только без категории), `status = applied`, `applied_at = now()`, удаление других `proposed` строк с тем же `name`, `TryAdd` в кэш. Транзакция (FR-6.5).

### 4. Отклонение
`DELETE /api/precategorized-commodities/{id:guid}`

- `204` — удалено.
- `404` — не найдено.
- `409` — строка уже `applied` (нельзя «отклонить» применённую категорию; откат — через `PUT /api/commodities/{id}/category`).
- `401`/`403`.

### 5. Изменение существующего контракта suggest (FR-9)

`POST /api/receipts/{receiptId:guid}/categories/suggest` — структура ответа не меняется, в `items[].source` добавляется значение `precategorized` (наряду с `existing`, `cache`, `ai`, `undefined`).

```json
{
  "receiptId": "...",
  "items": [
    {
      "commodityId": "...",
      "name": "Молоко 3,2% 1л",
      "categoryId": 23,
      "categoryName": "Молочные продукты",
      "source": "precategorized",
      "error": null
    }
  ]
}
```

- Коды ответов не меняются (`200`/`400`/`404`).
- `PUT /api/receipts/{receiptId:guid}/categories` не меняется.

## Риски и открытые вопросы

**Риски**
1. **Задержка остановки.** Проверка активности выполняется между позициями; текущий вызов ИИ может длиться до `AI:Timeout` (в `appsettings.json` — 80 с). Пользовательский запрос в это время не блокируется (вызов в фоне), но фон продолжит занимать одно соединение с ИИ до завершения. Возможное ужесточение (отмена текущего вызова по сигналу активности) — решение архитектора; по умолчанию требуется «дойти до конца текущей позиции» (C5).
2. **Несколько экземпляров Analytics.** При горизонтальном масштабировании каждый экземпляр запустит свой фон → дубли вызовов ИИ и гонки вставок (частично спасает unique-индекс). Сейчас экземпляр один; ограничение фиксируется в ADR, распределённая блокировка — вне объёма.
3. **Рост `precategorized_commodities`.** Строки `applied` хранятся бессрочно (D2). Рост ограничен числом уникальных пар `(name, merchant)`; политика очистки — в бэклог. Обратная сторона: `applied`-строка навсегда блокирует повторное предложение этой пары, даже если категорию потом сбросили вручную.
4. **Точное сравнение наименований.** Подтверждение матчит `name = :name` (регистр и пробелы важны). «Молоко» и «молоко» — разные строки; кэш при этом нормализует ключ и может обслуживать оба варианта. Это осознанное следствие требования «точно такое наименование»; при необходимости — отдельная задача о нормализованном матчинге.
5. **«Замороженный» кэш.** При достижении `MaxSize` `TryAdd` после подтверждения — no-op (ADR 019); уже подтверждённые позиции своих чеков получат категорию из `existing`, но новые товары с тем же названием из других чеков кэш не увидят и снова пойдут в ИИ. Поведение унаследованное, не регрессия; фиксируется в ADR/бэклоге.
6. **Индексы на `commodities` отложены (решение PM).** Выборка кандидатов требует DISTINCT `(name, merchant_id)` через join `commodities → receipts → merchants` (прямой ссылки commodity→merchant нет), поэтому состав индексов заранее не очевиден: и `(name, category_id)`, и `receipt_id`-варианты дают лишь частичное ускорение. В этой задаче индекс не создаётся (Seq Scan по отфильтрованному множеству — приемлемо, включение `Precategorization:Enabled` позволяет отключить фон при деградации). В ADR-027 зафиксировать: по результатам использования замерить фактические планы запросов кандидатов/подтверждения и выбрать применимые индексы отдельным решением/задачей (бэклог).
7. **Товары, синхронизированные после подтверждения.** Подтверждение применяет категорию только к товарам, существовавшим на момент `applied`; пара `(name, merchant)` с `applied`-строкой исключается из кандидатов (FR-3.2, приоритет над FR-3.3), тем более админ не может пере-подтвердить (409, FR-5.7). Поэтому товары того же `(name, merchant)`, появившиеся позже (новые чеки), фон автоматически никогда не закатегоризирует; их обслуживают ручной suggest по очереди (FR-9.2 — поиск в любых статусах) и ручная категоризация, а `updatedCommodities` в момент подтверждения может быть впоследствии «недоучтённым». Риск заказчиком принят (решение PM); повторное применение — кандидат в бэклог (см. «Бэклог»).
8. **Пробники инфраструктуры не на `/health`.** Если мониторинг ходит на `/` или `/index.html`, фон не будет запускаться (D3). Список исключений должен быть явно описан в ADR и легко расширяем.
9. **Долгие сессии.** При `BatchLimit=5` и `IntervalBetweenCalls=2s` плюс время ответа ИИ сессия может длиться десятки минут. Это нормально (фон), но стоит согласовать дефолты при приёмке.
10. **Неподтверждённая категория попадает пользователю (FR-9).** Если пользователь запускает категоризацию чека, он может получить предложение из очереди, которое админ ещё не подтвердил; качество такого предложения равно качеству ИИ. Пользователь сохраняет его явным действием, поэтому данные не портятся молча. При этом строка очереди остаётся `proposed`: админ позже увидит её и подтвердит (тогда `updatedCommodities` может быть `0`). Автоматически помечать строку `applied` при пользовательском сохранении — вне объёма (кандидат в бэклог).

**Открытые вопросы (для архитектора/заказчика)**
1. Нужен ли отдельный эндпоинт «сохранить и подтвердить» одним запросом вместо пары `PUT` + `POST confirm` (UX админа)?
2. Нужна ли админу фильтрация очереди по магазину/категории помимо поиска (в задаче — только поиск)?
3. Нужен ли счётчик предложений (badge) в навигации — потенциально отдельная задача.
4. Требуется ли аудит «кто и когда подтвердил» (сейчас `applied_at` без `applied_by`); при необходимости — добавить `applied_by_user_id` в таблицу.
5. Формат ошибок API: сохранить текстовый (как в `MerchantEndpoints`) или перейти на `ProblemDetails` (подключён в `Program.cs`)?

## Бэклог (отдельные задачи, не входят в объём)
- Политика ретенции и очистки строк в статусе `applied` (срок хранения, job очистки, влияние на запрет повторных предложений).
- Счётчик ожидающих предложений (badge) в навигации админа.
- Пакетные операции «подтвердить все видимые» / «отклонить все видимые» с осторожной семантикой.
- Нормализованный матчинг при подтверждении (регистр/пробелы) — если на практике точное совпадение окажется слишком узким.
- Распределённая блокировка фонового процесса для нескольких экземпляров Analytics.
- Аудит «кто подтвердил» (`applied_by_user_id`) и история изменений предложений.
- Калибровка/оценка качества предложений ИИ на размеченных данных.
- Повторное применение категории после `applied` для товаров того же `(name, merchant)`, синхронизированных позже подтверждения (риск 7).
- Пересмотр индексов на `commodities` по результатам эксплуатации (риск 6): замерить планы запросов выборки кандидатов/подтверждения, выбрать состав индексов отдельным решением/ADR.
- Гармонизация дефолта `AI:Timeout` (вне объёма этой задачи): в `appsettings.json` фактически `00:01:20` (80 с), в `AGENTS.md`, docker-compose и `AiOptions` — `00:00:10`; выбрать единый дефолт и синхронизировать документацию/конфиг.
- Микро-исправление `CommodityEndpoints.GetAll`: неавторизованный запрос возвращает `400` вместо `401`; выровнять по эталону `MerchantEndpoints` (эталон фиксируется в ADR-027).
- Дефект эталона прав (найдена при реализации ADR-027): в приложении не зарегистрирована схема аутентификации (`AddAuthentication` отсутствует), поэтому `Results.Forbid()` в рантайме бросает `InvalidOperationException` → **500 вместо 403** у `MerchantEndpoints` (и у любого кода, следующий «по эталону»). Новый модуль `PrecategorizedCommodities` отдаёт 403 явно (`Results.StatusCode(403)`). Вылечить эталон: зарегистрировать аутентификацию/`DefaultForbidScheme` или заменить `Forbid()` на явный 403 во всех существующих эндпоинтах.
