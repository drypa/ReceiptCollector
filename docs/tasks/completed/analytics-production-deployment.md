# Задача: Подготовка Analytics-сервиса к продакшен-деплою через docker compose

> **Статус:** в работе (передано архитектору на подготовку технического решения).
> **Контекст:** анализ готовности выявил блокеры деплоя (см. раздел 2); задача — устранить их и обеспечить запуск всего стека через `docker compose` на продакшен-сервере одной командой.

## 1. Бизнес-ценность / Цель

Сервис Analytics (миграция данных MongoDB → PostgreSQL + аналитический webUI) разработан и работает локально, но **не может быть развёрнут в продакшен**: `docker compose` не поднимет его из-за несоответствия имён образов, отсутствия продакшен-конфигурации, незапускаемых миграций и неполадающего в образ фронтенда.

**Цель:** сделать продакшен-деплой всего стека (mongo, postgres, collector, bot, analytics, nginx) воспроизводимым одной командой `./up.sh` (docker compose) на сервере. Заказчик получает работающий аналитический webUI и актуальные данные в PostgreSQL без ручных действий на сервере (кроме формирования `.env`).

**Дополнительная ценность:**
- Аналитика (веб-интерфейс по расходам) становится доступна конечным пользователям в проде.
- Деплой автоматизирован и повторяем — снижается риск «работает только у разработчика».
- Миграции БД применяются детерминированно при каждом развёртывании (отдельный сервис в compose).

---

## 2. Текущее состояние (AS-IS) и выявленные блокеры

### 2.1 Что уже готово
- Dockerfile Analytics корректен (multi-stage, публикация .NET 10).
- CI-пайплайн для Analytics существует (`.github/workflows/build-analytics-image.yml`): тесты + сборка + push образа.
- Миграционные SQL-скрипты на месте (`Analytics/src/ReceiptCollector.Analytics.Migrations/Scripts/`, 5 скриптов).
- Фронтенд собирается локально командой `npm run build` в `wwwroot` API (задан `vite.config.ts`, `build.outDir: '../src/ReceiptCollector.Analytics.Api/wwwroot'`).
- Имена MongoDB-коллекций backend и Analytics согласованы: `receipt_collection` / `receipt_requests` / `system_users`.
- nginx-конфиг продакшена присутствует (`nginx.prod.conf`).

### 2.2 Критические блокеры (требуют устранения)

1. **Несоответствие имени Docker-образа Analytics:**
   - CI пушит `drypa/receipt-collector-analytics`, а `docker-compose.yml` ссылается на `drypa/receipt-analytics:latest` → `docker compose pull` не найдёт образ, сервис не запустится.
   - Тег `latest` публикуется только для дефолтной ветки `master`; ветка `feature/analytics` не смёржена.

2. **В `docker-compose.yml` у сервиса `analytics` нет `build:` секции** — `build.sh` (docker compose build) его не соберёт.

3. **Несоответствие портов:**
   - `nginx.prod.conf` проксирует на `analytics:5039` (API) и `analytics:5173` (dev-порт Vite).
   - В Dockerfile `EXPOSE 8080`; без `ASPNETCORE_URLS` .NET в контейнере слушает порт по умолчанию → nginx не достучится до API.
   - Порт `5173` — dev-порт Vite, которого нет в проде.

4. **Нет продакшен-конфигурации подключения к БД:**
   - `appsettings.json` (Production) не содержит ConnectionStrings для Postgres и MongoDB.
   - Подключения есть только в `appsettings.Development.json` (localhost).
   - → в проде сервис падает при старте: `Postgres connection string is not configured.`
   - **Решение заказчика:** продакшен-настройки передаются **через переменные окружения**, а не через `appsettings.json`.

5. **Миграции не запускаются:**
   - В `docker-compose.yml` нет сервиса миграций.
   - **Решение заказчика:** объявить **отдельный сервис миграций в том же docker-compose.yml**, который применяет SQL-скрипты к PostgreSQL до старта API.

6. **Фронтенд не попадает в Docker-образ:**
   - Собранные ассеты `wwwroot/assets/*` не закоммичены в git; Dockerfile не выполняет сборку фронтенда (`npm build`) → в образе будет `index.html` без JS/CSS.
   - **Решение заказчика:** собранный фронтенд **должен попадать в образ**; в продакшене **nginx отдаёт фронтенд как статику** (не проксирует на dev-сервер).

7. **Нет healthcheck'ов:**
   - У `mongo`, `postgres`, `analytics` нет healthcheck; аналитике также нужен `mongo`, но в `depends_on` он отсутствует.
   - **Решение заказчика:** healthcheck'и добавить (как минимум для БД и analytics; `depends_on` с учётом готовности зависимостей).

### 2.3 Вне области задачи (подтверждено заказчиком)
- `.env` не анализируется и не правится — файл будет формироваться вручную на продакшен-сервере (переменные из него подставляет docker compose).
- SSL-сертификаты уже развёрнуты на сервере — настройка/генерация сертификатов не требуется.

## 3. Требования

### FR-1. Согласование Docker-образа Analytics
- FR-1.1. Имя образа в `docker-compose.yml` и в CI-пайплайне должно совпадать (единый источник: `drypa/receipt-collector-analytics` или согласованное значение).
- FR-1.2. У сервиса `analytics` в `docker-compose.yml` должна быть `build:` секция (контекст `./Analytics`), чтобы локальная сборка `docker compose build` собирала образ.
- FR-1.3. Тег `latest` должен публиковаться и быть доступен для `docker compose pull` на сервере (смёржить ветку / настроить публикацию).

### FR-2. Конфигурация через переменные окружения (продакшен)
- FR-2.1. Все продакшен-настройки Analytics (строка подключения PostgreSQL, MongoDB, ключи/флаги синхронизации и т.п.) задаются **через переменные окружения** (маппинг на конфигурацию .NET: `Infrastructure__Postgres__ConnectionString`, `Infrastructure__Receipts__Mongo__*`, `Infrastructure__Receipts__Synchronization__*` и т.д.).
- FR-2.2. Значения передаются в контейнер через `environment:` в `docker-compose.yml` (с подстановкой из `.env`).
- FR-2.3. Сервис не должен требовать ручного редактирования `appsettings.json` на сервере.

### FR-3. Фронтенд в образе + статика через nginx
- FR-3.1. Собранный фронтенд (результат `npm run build` из `Analytics/frontend`) должен попадать в Docker-образ (добавить шаг сборки фронтенда в Dockerfile / CI).
- FR-3.2. В продакшене **nginx раздаёт фронтенд как статические файлы** (корень сайта), а `/api` проксирует на Analytics API.
- FR-3.3. Убрать из продакшен-nginx проксирование на dev-порт `5173` (и любые dev-серверы).

### FR-4. Миграции через docker compose
- FR-4.1. В `docker-compose.yml` объявить **отдельный сервис миграций** (проект `ReceiptCollector.Analytics.Migrations`), который применяет SQL-скрипты к PostgreSQL.
- FR-4.2. Сервис API Analytics должен стартовать **после успешного выполнения миграций** (`depends_on` с условием готовности).
- FR-4.3. Конфигурация миграций (строка подключения PostgreSQL) — через переменные окружения (FR-2).

### FR-5. Healthcheck'и и порядок запуска
- FR-5.1. Добавить healthcheck для `mongo` и `postgres`; сервисы, зависящие от БД, стартуют только после готовности БД.
- FR-5.2. Добавить healthcheck для `analytics` (эндпоинт здоровья) и использовать его в `depends_on` nginx/других потребителей.
- FR-5.3. Analytics должен корректно стартовать при доступности и PostgreSQL, и MongoDB (добавить `mongo` в зависимости/условия при необходимости).

### FR-6. Порт API
- FR-6.1. Зафиксировать согласованный порт, на котором Analytics API слушает внутри контейнера (5039), передав его через переменную окружения (`ASPNETCORE_URLS` и т.п.); он должен совпадать с upstream в nginx.
- FR-6.2. Убедиться, что `EXPOSE`/порт в Dockerfile не конфликтуют с фактическим портом прослушивания.

---

## 4. Нефункциональные требования

- **NFR-1. Детерминированность:** `docker compose up` на пустом сервере (с заполненным `.env`) поднимает весь стек без ручных шагов.
- **NFR-2. Идемпотентность миграций:** повторный запуск сервиса миграций безопасен (скрипты не ломают уже применённые изменения).
- **NFR-3. Наблюдаемость:** healthcheck'и позволяют compose/оркестратору корректно определять готовность сервисов.
- **NFR-4. Безопасность:** секреты (пароли БД, токены) — только через `.env`/переменные окружения, не хардкодятся и не коммитятся в репозиторий.
- **NFR-5. Совместимость:** изменения не ломают локальную разработку (`docker-compose.develop.yml`, `up.dev.sh`).

## 5. Критерии приёмки

1. На сервере (чистая машина) с заполненным `.env` и SSL-сертификатами команда `./up.sh` (или `docker compose up -d`) поднимает **весь стек**: mongo, postgres, collector, bot, analytics, nginx.
2. Сервис `analytics` запускается и **не падает** при старте (ранее падал с «Postgres connection string is not configured»).
3. Миграции применяются к PostgreSQL **автоматически** при старте (отдельный сервис в compose); таблицы аналитики существуют.
4. Фронтенд Analytics доступен по HTTPS: nginx отдаёт статику (собранные JS/CSS из образа), `/api/...` проксируется на Analytics API — аналитический webUI открывается и работает.
5. В nginx-конфигурации продакшена **нет** проксирования на порт `5173`.
6. Docker-образ Analytics содержит собранный фронтенд (проверка: в образе есть `wwwroot/assets/*`).
7. Healthcheck'и настроены: `docker ps` показывает healthy для mongo/postgres/analytics (где применимо); порядок запуска учитывает готовность БД.
8. Продакшен-настройки Analytics задаются переменными окружения; сервис работает без ручного редактирования `appsettings.json`.
9. `docker compose build` локально собирает образ analytics без ошибок; `docker compose pull` находит образ (имена совпадают).

---

## 6. Решения заказчика (зафиксированы, обязательны для технического решения)

1. **Продакшен-настройки передаются через переменные окружения**, а не через `appsettings.json`.
2. **В продакшене nginx не проксирует фронтенд, а отдаёт его как статику**; собранный фронтенд должен попадать в Docker-образ.
3. **Миграции запускаются через docker compose** — в том же `docker-compose.yml` объявляется отдельный сервис миграций.
4. **`.env` не анализировать и не править** — файл формируется вручную на продакшен-сервере.
5. **SSL-сертификаты уже есть на сервере** — настройкой сертификатов не заниматься.
6. **Healthcheck'и нужно добавить** (БД и сервисы).

## 7. Предположения (сделаны PM на основе контекста)

- Архитектура системы (3 сервиса: backend Go, bot Go, Analytics .NET 8/10 + PostgreSQL + MongoDB + nginx) сохраняется; задача не меняет бизнес-логику сервисов.
- Фронтенд собирается штатной командой `npm run build` из `Analytics/frontend` (outDir уже настроен в `wwwroot`).
- Итоговый образ публикуется в Docker Hub под учётной записью `drypa` (как остальные образы).
- Дефолтная ветка для публикации `latest` — `master`; для деплоя ветку `feature/analytics` необходимо смёржить (или настроить публикацию с нужной ветки) — детали на усмотрение архитектора.
- Глубокие технические детали (схема Dockerfile, порядок healthcheck, переменные окружения) — на усмотрение архитектора, фиксируются в ADR/техническом решении.
