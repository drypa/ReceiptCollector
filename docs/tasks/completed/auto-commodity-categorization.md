# Задача: Автоматическая категоризация товаров в чеке (Auto Commodity Categorization)

> **Актуальное архитектурное направление зафиксировано в [ADR 009](../adr/009-auto-commodity-categorization.md) (утверждено заказчиком), декомпозиция — в [плане](../plans/auto-commodity-categorization.md).** Данный документ описывает бизнес-требования и критерии приёмки; техническое решение — в ADR 009, шаги реализации — в плане.

> **Решения заказчика (зафиксированы, см. раздел 7):**
> 1. Категорий в MongoDB нет — переносить их не нужно.
> 2. Формат ответа ИИ — категория сериализуется **именем** enum (`{"category": "Food"}`), а не номером.
> 3. Добавляется списочное представление **всех позиций всех чеков** с серверной фильтрацией по «без категории / `CommodityCategory.Undefined`» (новые UC-6, FR-5).
> 4. Унифицировать справочники `MerchantCategory` и `CommodityCategory` **не нужно**.
> 5. Кэш ранее присвоенных категорий — **сквозной для всех пользователей** (без привязки к `user_id`).
> 6. Порт Analytics **не меняется** (остаётся `5039`, как в nginx-конфигурации).

> **Техническое решение (ADR 009 и план) запрошено на перевалидацию под эти решения — раздел 9.**

## 1. Бизнес-ценность / Цель

Сегодня категории товаров в чеке пользователь проставляет вручную (или они отсутствуют). Это трудоёмко и приводит к тому, что большая часть покупок остаётся без категории, а аналитика по расходам строится неполно.

**Цель:** Дать пользователю возможность одним действием получить предложения категорий для всех товаров в чеке, предзаполненные автоматически (на основе ранее присвоенных категорий и ИИ-модели), с обязательным подтверждением перед сохранением. Это сокращает время на ведение категорий, повышает полноту и качество данных для аналитики по категориям расходов и снижает когнитивную нагрузку на пользователя.

**Дополнительная ценность для заказчика (из ADR 009):**
- Категоризация использует **единый справочник** `CommodityCategory` (19 значений + `Other`), который уже применяется в Analytics и PostgreSQL — предложенное пользователю значение совпадает с сохранённым, без маппинга и потерь.
- Результат сохраняется в **уже существующую схему** PostgreSQL (`commodities.category_id`/`category_name`) — аналитика по категориям расходов наполняется без изменения модели данных.
- Повторное использование ранее присвоенных категорий (кэш) экономит вызовы ИИ и делает поведение стабильным для пользователя.
- Масштаб кэша — **сквозной для всех пользователей**: категория, однажды присвоенная товару, используется в предложениях всем пользователям (решение заказчика). Это повышает долю попаданий кэша и дополнительно сокращает вызовы ИИ.

## 2. Текущее состояние (AS-IS)

**Analytics (.NET 8, PostgreSQL) — место реализации задачи:**
- Чеки и позиции хранятся в PostgreSQL. Позиции (`Commodity`) уже имеют колонки `category_id`/`category_name` (миграция `20241019160000_initial_create.sql`), доменный метод `AssignCategory(Category)` и репозиторий `ICommodityRepository.UpdateCategoryAsync` — место для сохранения результата готово.
- Справочник категорий — `CommodityCategory` (enum: **19 значений + `Other = 255`**) в `Analytics/src/ReceiptCollector.Analytics.Domain/Modules/Commodities/CommodityCategory.cs` + хелпер `CommodityCategoryHelper` (русские названия, `GetAll()`). Это **единственный источник истины** для категоризации в данной задаче.
- **webUI расположен в `Analytics/frontend`** (React 19 + Vite + TypeScript): страница деталей чека `ReceiptDetails.tsx` показывает позиции чека, но без колонки категории; есть готовые API-клиенты (`src/api/`) и паттерны UI. Отдельного каталога `webapp/` в репозитории нет.
- HTTP API — minimal APIs в группах `/api/receipts`, `/api/commodities`, `/api/merchants`; авторизация через `UserContext.UserId`; доступ к чеку owner-scoped (`ReceiptDbContext` query filter + `IReceiptReadService.GetByIdAsync(userId, receiptId)` → `404` для чужого/несуществующего чека).
- Существующий эндпоинт ручной категоризации товара — `PUT /api/commodities/{id:guid}/category`; справочник категорий отдаётся `GET /api/commodities/categories`.

**Синхронизация MongoDB → PostgreSQL (read-only):**
- `MongoReceiptBatchLoader` читает MongoDB только через `Find().Skip().Limit()` (только чтение) → `MongoReceiptMapper` → `ReceiptRepository.AddAsync` в PostgreSQL. MongoDB — исключительно источник сырых данных; записей в неё Analytics не делает. Поле `categories` (7 значений backend) в `MongoReceiptDocumentDto.ReceiptItemDto` при маппинге игнорируется — категории живут только в PostgreSQL.

**Backend (Go, MongoDB) и Telegram-бот:**
- Хранят и обрабатывают чеки, но в сценарии категоризации **не участвуют**: gRPC-контракты, воркеры и HTTP API backend не изменяются; команды Telegram-бота не меняются. Поле `Purchase.Categories` (7 значений backend) в этой задаче не используется.

**Nginx:**
- Проксирует весь `/api` на Analytics, `/` — на `Analytics/frontend`. Новые эндпоинты категоризации автоматически попадают под существующий прокси — **изменения nginx не требуются**.

**Вывод:** Точка **инициации** категоризации — **webUI (`Analytics/frontend`)**. Точка категоризации (логика) — **Analytics (.NET 8)**: там данные позиций с категориями (PostgreSQL), справочник `CommodityCategory` и webUI. Точка подтверждения/изменения/сохранения категорий пользователем — **webUI (`Analytics/frontend`)**. MongoDB остаётся строго read-only (только синхронизация).

## 3. Варианты использования (Use Cases)

> **Точка входа в сценарий — webUI (`Analytics/frontend`), а не Telegram-бот.** Инициация: **webUI**. Подтверждение/редактирование/сохранение: **webUI**. Telegram-бот в сценарии не участвует. Схема потока: webUI (`Analytics/frontend`) → nginx → Analytics HTTP API (.NET) → PostgreSQL.

### UC-1: Пользователь запрашивает автоматическую категоризацию чека
1. Пользователь открывает чек в **webUI** (`Analytics/frontend`, страница деталей чека) и нажимает кнопку/действие «Категоризировать» (инициатива со стороны пользователя). webUI обращается к Analytics через HTTP API (nginx reverse-proxy проксирует запрос).
2. Система для каждой позиции чека выполняет алгоритм приоритетов:
   - **Шаг 1.** У позиции уже есть категория (`commodities.category_id` задан) — предложить её (`source = existing`), ИИ не вызывается.
   - **Шаг 2.** Если категории нет — искать в кэше ранее категоризированных позиций с точно таким же названием (нормализованным). При попадании — предложить сохранённую категорию (`source = cache`).
   - **Шаг 3.** Если совпадения нет — отправить название товара в ИИ-модель с коротким промтом и требовать ответ строго в формате JSON с категорией из `CommodityCategory` (`source = ai`).
3. Система возвращает список позиций с предложенными категориями.
4. **Категории НЕ сохраняются автоматически.** На UI предзаполняются предложенные значения.

### UC-2: Пользователь подтверждает предложенные категории
1. webUI показывает список позиций чека с предзаполненными категориями (режим редактирования).
2. Пользователь просматривает предложения.
3. Если всё корректно — нажимает «Сохранить»; система сохраняет категории в **PostgreSQL** (обновляет `commodities.category_id`/`category_name`).
4. webUI подтверждает успешное сохранение.

### UC-3: Пользователь изменяет предложенную категорию вручную перед сохранением
1. webUI показывает список позиций с предзаполненными категориями.
2. Пользователь выбирает позицию и меняет категорию на любую из доступных (свою категорию вручную).
3. Пользователь нажимает «Сохранить»; система сохраняет изменённые значения (без повторной категоризации).

### UC-4: ИИ-модель недоступна или возвращает некорректный ответ
1. Система не может получить категорию от ИИ (таймаут, ошибка сети, невалидный JSON, неизвестная категория).
2. Для таких позиций категория не предлагается; в UI они помечаются как «категория не определена».
3. Остальные позиции обрабатываются штатно. Сохранение выполняется без неопределённых позиций (они остаются без изменений, если пользователь не выбрал категорию сам).

### UC-5: Повторное использование ранее присвоенной категории
1. Позиция с названием, которое уже категоризировано ранее (кэш `commodity_category_assignments`, **сквозной для всех пользователей**), не отправляется в ИИ — берётся сохранённая категория. Это экономит вызовы ИИ и обеспечивает согласованность данных (решение заказчика).

### UC-6: Просмотр всех позиций всех чеков с фильтрацией по отсутствию категории
1. Пользователь открывает в **webUI** списочное представление **всех позиций всех своих чеков** (не отдельного чека).
2. Пользователь выбирает фильтр: «позиции **без категории**» или «позиции с категорией `CommodityCategory.Undefined`».
3. **Фильтрация выполняется на сервере** (запрос к Analytics HTTP API с параметрами фильтра); сервер возвращает только соответствующие позиции (с учётом пагинации).
4. Пользователь видит отфильтрованный список и может проставить категории позициям (вручную и/или через механизм категоризации UC-1…UC-5).

## 4. Функциональные требования

### FR-1. Алгоритм категоризации (приоритеты)
- FR-1.1. Порядок приоритетов строго соблюдается: «существующая категория позиции» → «кэш ранее присвоенных категорий» → «ИИ».
- FR-1.2. При наличии категории у позиции (`commodities.category_id` задан) используется она, без вызова ИИ.
- FR-1.3. При совпадении нормализованного названия с кэшем ранее присвоенных категорий используется сохранённая категория (без вызова ИИ).
- FR-1.4. При отсутствии совпадений вызывается ИИ-модель для определения категории.

### FR-2. Интеграция с ИИ-моделью
- FR-2.1. Название товара + короткий промт отправляются в ИИ-модель.
- FR-2.2. От ИИ требуется структурированный ответ строго в формате JSON, где категория передаётся **именем** значения enum `CommodityCategory` (например, `{"category": "Food"}`), а не числовым кодом (решение заказчика). Допустимые значения — из справочника `CommodityCategory` (19 значений + `Other = 255`, без `Undefined`).
- FR-2.3. Ответы вне заданной схемы/с неизвестной категорией считаются ошибкой и не применяются (см. UC-4).
- FR-2.4. Необходимо обрабатывать таймауты и ошибки сети (грациозное падение: позиция остаётся без категории, операция не прерывается).

### FR-3. UX / UI (КРИТИЧНО)
- FR-3.1. Автоматическая категоризация запускается **только по запросу пользователя** (кнопка/действие на странице чека в **webUI (`Analytics/frontend`)**), а не автоматически при загрузке чека.
- FR-3.2. **Запрещено автоматическое сохранение** предложенных категорий без явного действия пользователя.
- FR-3.3. Предложенные категории **предзаполняются** в UI как значения по умолчанию.
- FR-3.4. У пользователя есть возможность **изменить** категорию вручную перед сохранением (для каждой позиции).
- FR-3.5. Сохранение происходит только по явному действию «Сохранить» (UC-2, UC-3).
- FR-3.6. UI должен показывать, какая категория предложена автоматически, а какая задана вручную (минимально: понятная индикация «предложено»).

### FR-4. Сохранение
- FR-4.1. Результат сохраняется в **PostgreSQL** — в существующие колонки `commodities.category_id`/`category_name`. **Запись в MongoDB не выполняется** (MongoDB — только чтение при синхронизации). Категорий в MongoDB нет, переносить их не нужно (решение заказчика).
- FR-4.2. Для сохранённых позиций обновляется кэш «ранее присвоенных категорий» (таблица `commodity_category_assignments` в PostgreSQL, **сквозной масштаб — без привязки к пользователю**), чтобы FR-1.3 работал при следующих обращениях.

### FR-5. Списочное представление всех позиций всех чеков (решение заказчика)
- FR-5.1. webUI должен предоставлять списочное представление **всех позиций всех чеков** текущего пользователя (а не только отдельного чека).
- FR-5.2. **Фильтрация выполняется на сервере** (Analytics HTTP API с параметрами фильтра), а не на клиенте.
- FR-5.3. Обязательные фильтры: «позиции **без категории**» (`category_id` не задан) и «позиции с категорией **`CommodityCategory.Undefined`**».
- FR-5.4. Выдача ограничена позициями чеков текущего пользователя (owner-scoping) и должна поддерживать пагинацию.

## 5. Нефункциональные требования

### NFR-1. Конфигурируемость ИИ-модели
- NFR-1.1. Адрес/конфигурация ИИ-модели задаётся через конфигурационные файлы (`appsettings*.json`) или переменные окружения (`AI__BaseUrl` и т.п.). **Хардкод запрещён.**
- NFR-1.2. Как минимум конфигурируемы: адрес/эндпоинт модели, таймаут запроса.
- NFR-1.3. Изменение конфигурации не должно требовать пересборки сервиса.

### NFR-2. Производительность и отказоустойчивость
- NFR-2.1. Категоризация не должна блокировать другие операции с чеками (обработка каждой позиции не должна «подвешивать» остальные операции сервиса).
- NFR-2.2. Сбой ИИ-модели не должен ломать весь запрос (частичный успех допустим, UC-4).
- NFR-2.3. Следует предусмотреть ограничение количества одновременных вызовов ИИ (rate limiting / батчинг) — детали на усмотрение архитектора (зафиксированы в ADR 009: `AI:Concurrency`, общий таймаут).

### NFR-3. Согласованность данных
- NFR-3.1. Нормализация названий перед поиском совпадений (нижний регистр, обрезка/схлопывание пробелов) — чтобы «точно такое же название» трактовалось стабильно.
- NFR-3.2. Категория из ИИ должна принадлежать справочнику `CommodityCategory` (валидация по enum); сохранение — в `commodities.category_id`/`category_name` без маппинга.

## 6. Критерии приёмки

1. Пользователь из **webUI (`Analytics/frontend`)** может запросить категоризацию для чека (UC-1 выполняется end-to-end: webUI → nginx → Analytics HTTP API → ответ отображается в webUI).
2. Для позиций с уже заданной категорией и для позиций с совпадением названия в кэше ранее присвоенных категорий (`commodity_category_assignments`) ИИ **не** вызывается и подставляется существующая/сохранённая категория (проверяется логами/метриками и результатом).
3. Для новых названий категория определяется ИИ и приходит в формате JSON с **именем** категории из справочника `CommodityCategory` (например, `{"category": "Food"}`; 19 значений + `Other = 255`).
4. Ни одна категория не сохраняется без явного действия «Сохранить» (проверка: после запуска категоризации без сохранения **данные в PostgreSQL** (`commodities.category_id`, `commodity_category_assignments`) **и в MongoDB** не изменяются).
5. Пользователь может изменить предложенную категорию вручную; в PostgreSQL сохраняется именно его выбор (UC-3).
6. При недоступности ИИ система возвращает частичный результат: позиции без категории помечены как «не определено», остальные предложены (UC-4).
7. Адрес ИИ-модели и таймаут задаются через переменную окружения/конфиг (`AI:BaseUrl`, `AI:Timeout` / `AI__BaseUrl`, `AI__Timeout`) и работают без пересборки (NFR-1).
8. Все варианты использования UC-1…UC-6 покрыты автотестами **Analytics** (`cd Analytics && dotnet test`) и проверены вручную через webUI.
9. **MongoDB остаётся строго read-only**: ни один новый код не выполняет запись в MongoDB (только чтение при синхронизации); категории проверяются/хранятся исключительно в PostgreSQL.
10. Из webUI доступно списочное представление всех позиций всех чеков пользователя; фильтры «без категории» и «`CommodityCategory.Undefined`» применяются **на сервере** и возвращают только соответствующие позиции (UC-6, FR-5; проверяется ответом API и отображаемым списком).
11. Кэш ранее присвоенных категорий работает **сквозь всех пользователей**: категория, сохранённая одним пользователем, используется в предложениях другому (при совпадении нормализованного названия), без вызова ИИ (UC-5, проверяется логами/метриками).
12. Порт Analytics **не изменился** (остаётся `5039`, соответствует nginx-конфигурации); сервис работает без пересборки/перенастройки прокси.

## 7. Решения заказчика и открытые вопросы

### Решения заказчика (зафиксированы, обязательны для технического решения)

1. **Категорий в MongoDB нет, переносить их не нужно.** Поле `categories` (7 значений backend) в MongoDB игнорируется при синхронизации; миграция/маппинг исторических категорий в PostgreSQL **не выполняется**. Категоризация стартует с чистой базы PostgreSQL (учитываются только категории, уже проставленные в `commodities`).
2. **Формат ответа ИИ — имя enum, не номер.** Категория сериализуется именем значения `CommodityCategory` (`{"category": "Food"}`), маппинг по `Enum.TryParse` по имени. Числовой формат `{"category_id": N}` **отклонён**.
3. **Списочное представление всех позиций всех чеков** с серверной фильтрацией по «без категории» / «`CommodityCategory.Undefined`» — обязательный функционал (UC-6, FR-5).
4. **Унификация справочников `MerchantCategory` (21) и `CommodityCategory` (19) не нужна.** Выполнять не требуется; вопрос закрыт.
5. **Кэш ранее присвоенных категорий — сквозной для всех пользователей** (`commodity_category_assignments` без привязки к `user_id`, уникальность по нормализованному имени). Per-user масштаб **отклонён**.
6. **Порт Analytics не меняется.** Остаётся `5039` (как в nginx-конфигурации); `EXPOSE 8080` в Dockerfile — вне области этой задачи, вопрос закрыт.

### Открытые вопросы (для уточнения у заказчика / команды)

1. **UX отображения длинных списков позиций:** при категоризации чека — редактирование всего списка на одной странице с индикацией «предложено» vs. по одной позиции за раз; финальное подтверждение UX — на демо.
2. **Права доступа:** категоризация доступна только владельцу чека (owner-scoped, реализовано в `IReceiptReadService.GetByIdAsync` и query filter `ReceiptDbContext`). Подтвердить, что правки категорий не требуются администратору.

## 8. Предположения (сделаны PM на основе контекста проекта)

- Категоризация выполняется в **Analytics (.NET 8)**: там данные позиций с категориями (PostgreSQL), справочник `CommodityCategory` и webUI. **Go-backend, Telegram-бот и nginx не изменяются.**
- **Analytics обращается к MongoDB только для синхронизации и только в режиме чтения (read-only)** — ни записи категорий, ни других записей в MongoDB. Категорий в MongoDB нет, переносить их не нужно. Категории позиций чека проставляются **только в PostgreSQL** (`commodities.category_id`/`category_name`).
- **Инициация, подтверждение, редактирование и сохранение — webUI (`Analytics/frontend`)**. Новые HTTP API-эндпоинты категоризации добавляются в проект Analytics (группа `/api/receipts`) и автоматически покрываются существующим nginx-проксированием `/api` → Analytics. Telegram-бот в этом сценарии не участвует.
- Перечень категорий — **`CommodityCategory.cs`** (19 значений + `Other = 255`), единственный источник истины; ИИ присваивает одну из этих категорий. Формат ответа ИИ — **имя** enum (`{"category": "Food"}`), не номер.
- Взаимодействие с ИИ — по HTTP(S) к внешнему эндпоинту, настраиваемому через `appsettings`/env (`AI__*`) без пересборки.
- Пользовательские изменения категорий — это обновление уже сохранённых данных в PostgreSQL, без повторного вызова ИИ.
- Кэш ранее присвоенных категорий (для повторного использования, FR-1.3) — таблица **PostgreSQL** `commodity_category_assignments`, масштаб **сквозной для всех пользователей** (без `user_id`).
- В webUI должно появиться списочное представление **всех позиций всех чеков** с серверной фильтрацией (UC-6, FR-5); требует новых серверных эндпоинтов Analytics и доработки frontend.
- Глубокие технические детали (архитектура, протоколы, схема HTTP API, структура БД, библиотеки) зафиксированы в **ADR 009** и плане; здесь намеренно не детализированы.

## 9. Связь с техническим решением (ADR 009) и ожидания от команды

Техническое направление в целом утверждено (логика в Analytics, справочник `CommodityCategory`, PostgreSQL, MongoDB read-only, webUI `Analytics/frontend`), но **ADR 009 и план запрошены на перевалидацию** под новые решения заказчика (раздел 7): формат ответа ИИ по имени enum, сквозной кэш без `user_id`, отсутствие переноса категорий из MongoDB, списочное представление всех позиций с серверной фильтрацией (UC-6/FR-5), отсутствие унификации справочников, неизменный порт Analytics.

**Ожидания от команды по реализации (детали — в ADR 009 и плане после перевалидации):**
- Реализовать эндпоинты и логику категоризации в Analytics-проекте строго по ADR 009 и плану (без отступлений в сторону Go-backend или записи в MongoDB).
- Учесть новые решения заказчика (раздел 7) в финальной версии ADR 009/плана.
- Доработать webUI (`Analytics/frontend`): кнопка «Категоризировать» на странице чека, предзаполнение категорий, ручное редактирование, индикация «предложено», сохранение по явному действию (UC-1…UC-5, FR-3), а также списочное представление всех позиций всех чеков с серверной фильтрацией (UC-6, FR-5).
- Обеспечить критерии приёмки раздела 6, включая автотесты Analytics и ручную проверку через webUI.
- Дать ответы/комментарии по открытым вопросам раздела 7 (по части из них — решение на демо).
