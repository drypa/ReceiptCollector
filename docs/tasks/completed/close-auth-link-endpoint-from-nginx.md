# Задача: Закрыть эндпоинт генерации auth-ссылки от внешнего мира на nginx

- **Статус:** открыта (бизнес-требование сформулировано, ожидает технического решения @software-architect)
- **Автор:** менеджер проекта
- **Дата создания:** 2026-08-27
- **Приоритет:** высокий (уязвимость безопасности, перехват аккаунта)
- **Исполнитель:** @software-architect (техническое решение)

## 1. Бизнес-задача

Проблема: **«Открытый эндпоинт генерации auth-ссылки = перехват аккаунта»**.

Эндпоинт `GET /api/users/auth/link?telegramId=N` генерирует одноразовую ссылку
авторизации для пользователя с заданным `telegramId`. Переход по такой ссылке
устанавливает аутентификационную cookie для этого пользователя (см. `ConsumeAuthLink`
в Analytics). Т.е. владелец ссылки получает полный доступ к аккаунту указанного
пользователя в админ-панели Analytics.

Проблема в том, что nginx (`nginx.prod.conf`, блок `location /api { proxy_pass http://analytics_api; }`)
проксирует наружу **весь** префикс `/api` в интернет. Из-за этого эндпоинт
`/api/users/auth/link` доступен любому атакующему извне. Атакующий может **перебирать
`telegramId`** (например, `?telegramId=1`, `?telegramId=2`, ...), получать валидные
auth-ссылки для произвольных пользователей и таким образом **захватывать аккаунты**.

Требуется закрыть `/api/users/auth/link` от доступа извне (через публичный nginx),
при этом **не сломав** легитимных серверных клиентов (Telegram-бот), которым этот
эндпоинт нужен.

## 2. Ценность для заказчика

- **Устранение критической уязвимости безопасности** — перебор `telegramId` извне и
  захват учётных записей пользователей/администраторов админ-панели становится
  невозможен.
- **Защита пользовательских данных и доверия** — закрываем самый простой вектор
  несанкционированного доступа ко всей базе пользователей системы.
- **Минимальное воздействие на продукт** — легитимный сценарий (Telegram-бот выдаёт
  ссылку конкретному пользователю) продолжает работать.
- **Соблюдение принципа наименьших привилегий** — эндпоинт, предназначенный только
  для внутренних сервисов, не должен быть публичным.

## 3. Текущая ситуация (контекст)

Эндпоинт реализован в Analytics-сервисе (.NET):
- `Analytics/src/ReceiptCollector.Analytics.Api/Modules/Users/UserAuthEndpoints.cs`
  (`RequestAuthLink`) — обработчик `GET /api/users/auth/link?telegramId=...`;
- маршрутизация группы: `Endpoints.AuthGroup = "/api/users"`,
  `AuthLinkRequestPath = "/auth/link"` (итог — `/api/users/auth/link`).

Единственный легитимный вызов эндпоинта — со стороны **Telegram-бот** (серверный
сервис) в момент, когда пользователь запрашивает в боте ссылку на вход в админку:
- `bot/analytics/client.go` → `GetLoginLink(ctx, telegramId)` → `GET {ANALYTICS_URL}/api/users/auth/link?telegramId={id}`;
- вызывается из `bot/commands/login.go`.

Фронтенд админ-панели **не** использует этот эндпоинт (проверено: в `adminService.ts`
и всей frontend-части `auth/link` не встречается; браузер работает только с
`/api/users/is-admin` и `/api/users/auth?token=...`).

Сетевой слой (nignx):
- `nginx.prod.conf` (монтируется в `nginx` в `docker-compose.yml`, порты 80/443):
  `location /api { proxy_pass http://analytics_api; ... }` — открывает весь `/api`
  наружу, включая проблемный эндпоинт;
- `nginx.dev.conf` (корневой) и `docker/nginx/nginx.dev.conf` — аналогичные dev-прокси
  `location ~ ^/api`.

Открытый вопрос (важно для решения): как бот добирается до Analytics в проде.
- В `docker-compose.yml` для сервиса `bot` **не задаётся** переменная `ANALYTICS_URL`
  (есть только `BOT_TOKEN`, `BACKEND_GRPC_ADDR`, `REPORTS_GRPC_ADDR`, `HTTP_PROXY`).
  При этом `bot/options.go` требует непустой `ANALYTICS_URL` (иначе `validate()`
  падает). В локальном dev-конфиге значение `ANALYTICS_URL=http://localhost:5039`
  (README, `_.env`) указывает напрямую на порт Analytics-сервиса.
- Для безопасности необходимо, чтобы бот обращался к Analytics **по внутренней сети**
  (`http://analytics:5039` внутри `collector-net`), минуя публичный nginx. Только тогда
  публичное закрытие `/api/users/auth/link` на nginx не сломает легитимный сценарий.
  Окончательное решение по способу подключения бота — на усмотрение архитектора,
  но требование: публичный nginx не должен быть единственным/целевым путём для бота.

Backend (Go) также содержит клиента `backend/users/link/client.go`
(`GetUserAuthLink`), но в реальных flow он указывает на `OPEN_URL` (фронтенд-URL), не
на Analytics, и вызовом эндпоинта `auth/link` не является — это отдельный, вероятно
устаревший, код. Решение по нему — на усмотрение архитектора (возможная чистка вне
прямого scope данной задачи).

## 4. Объём работ (scope)

- Конфигурация публичного nginx (в первую очередь `nginx.prod.conf`): эндпоинт
  `/api/users/auth/link` не должен быть доступен извне.
- Обеспечение работы легитимного серверного клиента (Telegram-бот) через внутренний
  путь к Analytics (не через публичный nginx) — на уровне конфигурации/сети
  (`docker-compose.yml`, переменные окружения, возможно документация).
- Аналогично оценить необходимость закрытия/dev-конфигов (`nginx.dev.conf` корневой и
  `docker/nginx/nginx.dev.conf`) — в dev перебор `telegramId` тоже нежелателен, но
  приоритетный контур — **production**.
- Обновить документацию/`.env.example` в части `ANALYTICS_URL` для бота, если решение
  предполагает внутренний адрес.

## 5. Критерии приёмки

1. Снаружи (через публичный nginx, порты 80/443) запрос `GET /api/users/auth/link?telegramId=...`
   **не** возвращает валидную auth-ссылку: возвращается 4xx (например, 403/404) —
   перебор `telegramId` извне **невозможен**.
2. Другие маршруты `/api/*`, используемые фронтендом (например,
   `/api/users/auth?token=...`, `/api/users/is-admin`, API чеков/товаров/продавцов),
   продолжают работать снаружи без изменений.
3. Легитимный сценарий работы сохранён: команда бота на получение ссылки входа
   (`GetLoginLink`) успешно выдаёт ссылку пользователю в production, обращаясь к
   Analytics внутренне (минуя публичный nginx).
4. Внутренние маршруты (не только `auth/link`) не затронуты в худшую сторону.
5. Работоспособность проверена: контейнеры поднимаются (nginx без ошибок конфигурации),
   сборка/запуск бота не ломается; при наличии тестов — `cd bot && go test ./...` и
   `cd Analytics && dotnet test` проходят.

## 6. Вне объёма (out of scope)

- Изменение бизнес-логики генерации/потребления auth-ссылок в Analytics
  (`UserAuthLinkService`, обработчики) — если архитектор не выявит критичной
  необходимости вынести часть логики.
- Редизайн всей системы аутентификации (JWT, SSO и т.п.).
- Полная ревизия остальных эндпоинтов `/api` (кроме необходимости закрыть именно
  `auth/link`).

## 7. Открытые вопросы / риски

1. **Путь бота к Analytics в production.** В `docker-compose.yml` у бота не задан
   `ANALYTICS_URL`. Нужно определить/исправить внутренний адрес (`http://analytics:5039`)
   и убедиться, что бот не ходит через публичный nginx. Иначе закрытие эндпоинта сломает
   выдачу ссылок. Это ключевой вопрос для архитектора.
2. **Полнота закрытия именно на nginx.** Следует решить, достаточно ли блокировки на
   уровне nginx (`location = /api/users/auth/link { return 404/403; }` и т.п.) и какова
   семантика: точечно-точное совпадение пути или регулярное выражение по префиксу —
   чтобы не задеть `/api/users/auth?token=...` (consume-ссылка, открытая фронтенду).
3. **Backend-клиент `backend/users/link/client.go`** — устаревший/неиспользуемый код;
   решить, требуется ли его удаление или он остаётся (вне прямого scope, но стоит
   отметить в решении).
4. **Dev-конфиги** — следует ли синхронно закрывать эндпоинт в dev-nginx, чтобы
   исключить перебор в dev-окружении.
