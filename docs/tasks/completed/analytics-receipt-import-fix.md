# Починка импорта новых чеков в Analytics (Mongo → PostgreSQL)

## Приоритет
high

## Проблема
Новые чеки успешно сохраняются backend'ом в MongoDB (в логах продакшена видно `InsertRawTicket ... saved. with status 2. ticket exist`), но в UI Analytics видны только старые чеки за 2020 год. Новые покупки в аналитику не попадают.

Факты текущего состояния:
- Полный payload нового чека backend сохраняет в коллекцию **`raw_tickets`** (документ вида `id`, `qr`, `status`, `ticket.document.receipt`, `seller`, `operation`, `query`).
- Сервис Analytics синхронизирует данные из коллекции **`receipt_requests`** (классические «запросы на добавление чека»), в которой полного чека нет — там только `owner`, `query_string`, `ticket_id`.
- Старые (2020) чеки в `receipt_requests` содержат вложенный верхнеуровневый `receipt` — именно они были импортированы в PostgreSQL при первом деплое Analytics и видны в UI.
- Синхронизация в проде по умолчанию пропускается (`Skip=true`).

## Цель
Все новые чеки (и накопленная история из `raw_tickets`) появляются в UI Analytics с корректной датой покупки, суммой, продавцом и привязкой к владельцу. Синхронизация обновляет данные периодически, без необходимости рестарта сервиса, и не создаёт дубликатов уже импортированных чеков (в т.ч. за 2020 год).

## Пользователи
Владелец системы (просматривает аналитику своих чеков в веб-UI Analytics через Telegram-авторизацию).

## Сценарий использования
1. Пользователь добавляет чек (по QR/электронно). Backend сохраняет полный чек в `raw_tickets`.
2. Сервис Analytics при старте и далее периодически (раз в 5–15 минут) синхронизирует чеки из MongoDB в PostgreSQL.
3. Новый чек появляется в списке чеков UI Analytics с корректными датой, суммой, продавцом и привязкой к пользователю.
4. История (включая чеки за 2020 год, если они есть в `raw_tickets`) импортируется один раз, без задвоения уже существующих записей.

## Критерии приёмки
- [ ] Новый чек, сохранённый backend'ом в `raw_tickets`, появляется в UI Analytics (проверка на живых данных: добавить чек → дождаться цикла синхронизации → увидеть в UI)
- [ ] В синхронизации учитываются документы, где payload лежит вложенно (`ticket.document.receipt`), а не только в верхнеуровневом `receipt`
- [ ] Дата покупки, сумма, продавец (ИНН/название) и адрес импортируются корректно для новых чеков
- [ ] Чек привязан к правильному владельцу (Telegram-пользователю); если владелец не определяется — импорт пропускается с понятным логом, без падения сервиса
- [ ] Повторные запуски синхронизации не создают дубликатов ни среди вновь импортированных, ни среди ранее импортированных чеков (в т.ч. чеки 2020 года из `raw_tickets`)
- [ ] Синхронизация запускается автоматически и периодически (старт + интервал 5–15 мин), без требования ручного рестарта
- [ ] В проде включена синхронизация (`ANALYTICS_SYNC_SKIP=false` в `.env` / конфигурация `Skip=false`)
- [ ] Автотесты Analytics проходят (`cd Analytics && dotnet test`)

## Edge cases
- Документ в `raw_tickets` без payload (`ticket == null`) — пропускается, а не роняет импорт
- Документ без владельца (`owner` отсутствует в `raw_tickets`) — владелец определяется по связке с `receipt_requests`; если не найден — лог + пропуск
- Чек существует и в `raw_tickets`, и в старом формате `receipt_requests` (ситуация 2020 года) — не должен импортироваться дважды
- Один и тот же физический чек у одного пользователя — не должен дублироваться при повторных циклах синхронизации (идемпотентность)
- Отсутствие timestamp/даты в payload — пакет не импортируется либо импортируется с понятной ошибкой в логе
- Синхронизация падает (сеть, БД недоступна) — сервис не должен падать целиком, ошибки логируются, следующий цикл продолжает работу

## Зависимости
- Backend: коллекция `raw_tickets` — источник полных чеков (уже существует, меняться не должен)
- Backend: коллекция `receipt_requests` — источник привязки владельца по `query_string`/`qr`
- Analytics (`Analytics/src/ReceiptCollector.Analytics.*`): слой синхронизации, DTO для чтения Mongo, маппер в доменную модель, конфигурация MongoDB источника
- Инфраструктура: `docker-compose.yml` (переменные окружения Analytics), `.env` прода
- PostgreSQL: таблица `receipts` (дедупликация по естественному ключу)
