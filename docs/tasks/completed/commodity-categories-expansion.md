# Задача: Расширение справочника категорий товаров (Commodity Categories Expansion)

## 1. Бизнес-ценность / Цель

Текущий справочник `CommodityCategory` слишком крупнозернистый: категория **«Продукты питания»** объединяет всё (от молока до фастфуда), а транспортные расходы (платные дороги, общественный транспорт, билеты) не выделены вовсе и попадают в «Прочее».

**Цель:** Детализировать справочник категорий товаров, чтобы:
- строить осмысленную аналитику расходов на питание (мясо, рыба, овощи, бакалея, фастфуд и т.д.);
- корректно классифицировать транспортные расходы (платные дороги, общественный транспорт, Ж/Д, авиабилеты, такси, каршеринг, парковка);
- закрыть прочие заметные пробелы (табак, связь/интернет, ЖКХ, развлечения).

Это подготовительный шаг к автокатегоризации (ADR 009): расширенный справочник автоматически попадёт в промт ИИ и в UI, т.к. оба источника генерируются из `CommodityCategoryHelper.GetAll()`.

---

## 2. Текущее состояние (AS-IS)

- `CommodityCategory` — enum, 19 значений (0–17 + `Other = 255`) в `Analytics/src/ReceiptCollector.Analytics.Domain/Modules/Commodities/CommodityCategory.cs` + `CommodityCategoryHelper` (русские `DisplayNames`, `GetDisplayName()`, `GetAll()`).
- Категория товара хранится в PostgreSQL denormalized: `commodities.category_id` (int?) + `commodities.category_name` (varchar(128)).
- Справочник отдаётся `GET /api/commodities/categories` (`CategoryDto[]`); frontend (`CommodityTable.tsx`) загружает список динамически.
- Ручная категоризация — `PUT /api/commodities/{id:guid}/category` (только администратор, проверка `Enum.IsDefined`).
- Автокатегоризация через ИИ (ADR 009) **ещё не реализована**; промт генерируется из `GetAll()` — новые категории попадут в промт автоматически.

**Важно:** по информации заказчика, существующие товары **ещё не распределены по категориям** (`Food = 1` не присвоен данным), поэтому расширение справочника и переименование отображаемого имени `Food` не требуют перекатегоризации данных. Архитектору нужно **проверить это допущение** (см. раздел 6).

## 4. Ключевое бизнес-требование: разграничение «продукт» vs «готовая еда/напиток» (кофе)

Заказчик отметил: **по одному названию нельзя достоверно определить**, «Кофе» в чеке — это упаковка для приготовления (бакалея) или готовый напиток из кофейни. То же касается чая, выпечки и т.п.

Требование к логике категоризации (реализуется при автокатегоризации, ADR 009; сейчас — только зафиксировать правила):
1. Промт ИИ должен содержать **явные эвристики**: «Кофе в зёрнах / молотый / растворимый / капсулы», «Чай в пакетиках / листовой» → `Бакалея`; «Капучино», «Латте», «Американо», «Кофе с собой» → `Напитки`.
2. Допускается **неидеальная точность** такого разграничения — для исправления существует ручная категоризация администратором. Это осознанный компромисс, он не должен блокировать задачу.
3. Архитектор должен учесть, что с ростом справочника до ~44 значений промту ИИ потребуется **примеры категоризации** (несколько примеров «название товара → категория») для стабильности качества.

## 5. Требования к реализации (границы задачи)

- Изменение затрагивает **только Analytics (.NET)**: `CommodityCategory` + `CommodityCategoryHelper`. Схема PostgreSQL, Go-backend, Telegram-бот и nginx **не меняются**.
- Новые значения enum — только **добавление** (коды 18+), без переиспользования/удаления существующих значений. `Other = 255` сохраняется.
- Переименование отображаемого имени `Food` («Продукты питания» → «Прочая еда») — изменение только в `DisplayNames` словаре хелпера.
- Эндпоинт `GET /api/commodities/categories` и frontend-выпадающий список должны автоматически показывать новый состав (фактически — без изменений, т.к. список генерируется из `GetAll()`; проверить).
- **UI-удобство:** при ~44 категориях плоский `<select>` становится неудобным. Рассмотреть группировку в `<optgroup>` по разделам (Продукты / Транспорт / Прочее). Не блокирует задачу, но желательно.
- При необходимости обновить существующие тесты, зависящие от состава/количества категорий.

## 6. Ограничения и вопросы для проработки архитектором

1. **Проверка допущения о нераспределённых данных:** убедиться, что в `commodities` нет строк с `category_id = 1` (или старым `category_name = 'Продукты питания'`). Если такие строки есть — решить вопрос согласованности denormalized `category_name` при переименовании (обновить данные или принять расхождение) и согласовать с заказчиком.
2. **Нумерация enum:** предложенные коды (18–41) — ориентировочные; архитектор вправе изменить при сохранении отсутствия коллизий и обратной совместимости.
3. **Промт ИИ (ADR 009):** после расширения справочника состав промта меняется автоматически; план/ADR 009 нужно перевалидировать на предмет качества категоризации при 44 значениях (примеры в промте, дедупликация смыслов: `Meat` vs `Poultry`, `Vegetables` vs `Fruits` и т.п.).
4. **Не выполняем** унификацию `MerchantCategory`/`CommodityCategory` (решение заказчика, ADR 008) — справочники остаются независимыми.

## 7. Критерии приёмки

1. `CommodityCategory` содержит все перечисленные значения (п. 3), `Other = 255` сохранён, `Food = 1` переименован в «Прочая еда».
2. `GET /api/commodities/categories` возвращает полный список с корректными русскими именами; существующие значения не изменили коды.
3. Ручная категоризация (`PUT /api/commodities/{id}/category`) принимает новые категории; фронтенд отображает их в выпадающем списке (при наличии группировки — по разделам).
4. Проект Analytics собирается, тесты проходят; добавлены/обновлены тесты на состав справочника при необходимости.
5. Допущение о нераспределённых данных проверено, результат зафиксирован в решении архитектора.

## 8. Зависимости и связи

- **ADR 005** (`commodity-category-as-enum.md`) — решение о справочнике-перечислении; данная задача расширяет состав.
- **ADR 009** (`auto-commodity-categorization.md`) — автокатегоризация; расширение справочника влияет на промт ИИ (см. п. 6.3).
- **ADR 008** — унификация справочников не выполняется.
