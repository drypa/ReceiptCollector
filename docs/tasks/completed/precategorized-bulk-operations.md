# Массовые подтверждение и отклонение на странице «Предкатегоризация»

## Приоритет
medium

## Проблема
Админская страница «Предкатегоризация» (`/precategorized`) показывает очередь AI-предложений категорий для товаров. Сейчас каждое предложение обрабатывается **только поштучно**: подтвердить (категория применяется к товарам всех пользователей с этим названием и попадает в кэш), отклонить (строка удаляется) или изменить категорию перед подтверждением. На странице может отображаться до 200 строк (по умолчанию 50), и администратор вынужден кликать по каждой строке — при наполненной очереди это нерабочая рутина.

## Цель
Дать администратору на странице «Предкатегоризация» две массовые операции — **«Подтвердить все»** и **«Отклонить все»**, действующие на все строки текущей видимой страницы очереди. Операции должны быть безопасными (диалог подтверждения), устойчивыми к частичным сбоям и прозрачными по результату (прогресс и итоговая сводка).

## Пользователи
Администраторы Analytics — единственные, кому доступен раздел предкатегоризации (доступ уже ограничен серверной проверкой прав). Для остальных пользователей ничего не меняется.

## Решения заказчика
1. Массовость реализуется **двумя кнопками на всю страницу**, без чекбоксов и выборочного выделения строк: «Подтвердить все» / «Отклонить все».
2. Область действия — **ровно строки текущей страницы пагинации**, даже если активен поиск и под фильтр подходит больше строк на других страницах. Строки других страниц не затрагиваются.
3. Перед каждой массовой операцией — **диалог подтверждения** с указанием количества затрагиваемых строк.
4. **Вся видимая страница отправляется одним запросом** (без порций и без подгрузки) и обрабатывается **в одной транзакции**.
5. **Прогресс-счётчик не нужен**: на время выполнения кнопки заблокированы, по завершении — сводка и автообновление списка.
6. При частичном сбое — **частичный успех по логическим конфликтам**: строки, уже обработанные параллельно (второе окно браузера), пропускаются без общей ошибки и попадают в сводку (выполнено N, пропущено M); остальные строки применяются в той же транзакции. Технический сбой БД — полный откат, ничего не применяется.
7. Приёмка — **автотесты на новые API-операции** плюс ручная проверка страницы на dev-стенде.

## Сценарий использования

### Happy path (массовое подтверждение)
1. Админ открывает «Предкатегоризация»; на странице, например, 50 предложений.
2. В шапке таблицы видит кнопки «Подтвердить все» и «Отклонить все».
3. Нажимает «Подтвердить все» → диалог: «Подтвердить все 50 предложений на этой странице? Категории будут применены ко всем товарам с этими названиями у всех пользователей.»
4. Подтверждает → кнопки блокируются, страница ждёт ответа (без счётчика прогресса).
5. По завершении — сводка «Подтверждено: 50, пропущено: 0», список автоматически перезагружается (строки уходят из очереди, на их место поднимаются следующие).

### Массовое отклонение
1. Админ нажимает «Отклонить все» → диалог с явным предупреждением, что предложения будут удалены безвозвратно.
2. Подтверждает → одна транзакция → сводка «Отклонено: N, пропущено: M», список перезагружается.

### Частичный сбой
Часть строк уже обработана параллельно (другое окно/фон): массовая операция не падает, обработанные строки попадают в «пропущено», остальные применяются в той же транзакции. Сводка показывает итог; список перезагружается.

### Ошибки
- Техническая ошибка (сеть, БД) → одна транзакция → операция откатывается целиком, ничего не применено; администратор видит сообщение об ошибке; список перезагружается, состояние консистентно; повторный запуск безопасен.
- Пустая страница (нет предложений) → кнопки массовых операций неактивны/не отображаются.

## Критерии приёмки
- [ ] На странице «Предкатегоризация» для администратора отображаются кнопки «Подтвердить все» и «Отклонить все», действующие на все строки текущей страницы (без чекбоксов).
- [ ] При активном поиске массовая операция затрагивает только строки текущей страницы; строки других страниц, подходящие под фильтр, не затрагиваются.
- [ ] Перед каждой массовой операцией показывается диалог подтверждения с количеством затрагиваемых строк; для массового отклонения — предупреждение о безвозвратном удалении.
- [ ] При отказе от диалога ничего не меняется.
- [ ] Во время операции кнопки заблокированы (без счётчика прогресса); по завершении — итоговая сводка (выполнено N, пропущено M) и автообновление списка.
- [ ] Вся видимая страница отправляется одним запросом и обрабатывается в одной транзакции; технический сбой приводит к полному откату — ни одна строка не остаётся применённой.
- [ ] Массовое подтверждение применяет к товарам категорию, показанную в строке на момент запуска (включая отредактированные администратором значения), и пишет подтверждённые категории в кэш — поведение идентично поштучному подтверждению для каждой строки.
- [ ] Массовое отклонение удаляет предложения — поведение идентично поштучному отклонению для каждой строки.
- [ ] Частичный сбой по логическим конфликтам не ломает операцию: уже обработанные строки пропускаются без общей ошибки и учитываются в сводке как «пропущено»; остальные применяются в той же транзакции.
- [ ] Повторный запуск операции безопасен: уже обработанные строки пропускаются, оставшиеся обрабатываются.
- [ ] Не-администраторы не видят кнопки и не получают доступа к массовым операциям (серверная проверка прав).
- [ ] При пустой странице массовые операции недоступны (кнопки неактивны или скрыты).
- [ ] Автотесты Analytics проходят (`cd Analytics && dotnet test`); новые массовые API-операции покрыты тестами (успех, частичный успех, границы страницы, права доступа).
- [ ] Ручной прогон на dev-стенде: массовое подтверждение и отклонение на странице с несколькими страницами пагинации, с активным поиском, с параллельной обработкой строки во втором окне.

## Edge cases
- **Строки страницы обработаны параллельно** (второе окно, фоновая предкатегоризация не пишет в подтверждённые категории, но админ мог подтвердить в другой вкладке) — операция не падает, пропущенные строки считаются как «пропущено».
- **Список изменился между показом страницы и запуском операции** (новые предложения добавились, старые удалены) — операция применяется к строкам, фактически показанным на странице в момент клика; сводка честно отражает результат.
- **Последняя страница опустела после операции** — пагинация должна остаться работоспособной (переход на предыдущую доступную страницу или пустое состояние), без ошибок.
- **Операция на максимальный размер страницы (до 200 строк)** — выполняется одним запросом в одной транзакции; на время выполнения кнопки заблокированы; по завершении — сводка или ошибка.
- **Обрыв сети во время выполнения** — операция либо применилась целиком, либо нет (одна транзакция); администратор видит ошибку, после обновления страницы состояние консистентно.
- **Таймаут прокси/БД на большой странице** — транзакция откатывается целиком, администратор получает понятную ошибку; повторный запуск безопасен.
- **Повторные названия в разных строках страницы** — обрабатываются независимо, как и при поштучных операциях.
- **Одновременное нажатие двух массовых кнопок** — вторая операция невозможна, пока идёт первая (кнопки заблокированы).

## Зависимости
- Существующие API очереди предкатегоризации (`GET /api/precategorized-commodities`, `POST /{id}/confirm`, `DELETE /{id}`, `PUT /{id}/category`) и сервис `IPrecategorizedCommodityService` (ADR-027, ADR-030, ADR-033).
- Права администратора (`AdminAuthorization`) и текущая страница `/precategorized` во фронтенде.
- Существующий компонент тостов и диалогов подтверждения (`CustomDialog`).

## Не входит в объём
- Выборочное выделение строк чекбоксами (массовость — только «вся видимая страница»).
- Массовые операции на других страницах («Товары», «Детали чека», «Решения по категориям»).
- Массовые операции с выбором целевой категории (смена категории всем строкам) — только подтверждение/отклонение уже показанных предложений.
- Изменение поведения фоновой предкатегоризации (ADR-027/ADR-030).
