# Telegram-бот: keyboard с кнопкой быстрого входа в webUI для авторизованных пользователей

## Приоритет
medium

> **Архитектурное решение:** [ADR-029](../../adr/029-bot-login-reply-keyboard.md) — авторизован =
> **подтверждён кодом из SMS** (предикат по токенам device, доставка полем gRPC `User.verified`,
> бот кэширует только подтверждённых), точка централизации keyboard (`commands.Messenger`,
> политика в момент отправки), распознавание кнопки и оформление inline-ответа.

## Проблема
Сейчас Telegram-бот отвечает только текстом. Чтобы попасть в webUI (Analytics),
пользователь должен вручную ввести команду `/login`, дождаться ответа и
перейти по текстовой ссылке. Это лишние действия: пользователь уже идентифицирован
в Telegram и зарегистрирован в системе, но интерфейс не подсказывает ему
доступные действия. Затрагивает всех зарегистрированных и подтверждённых
пользователей бота.

## Цель
Зарегистрированный и подтверждённый пользователь видит постоянный
reply-keyboard с одной кнопкой **«Войти в webUI»**, нажатие которой выполняет
логику команды `/login` и приводит пользователя в webUI. Ответ на `/login`
оформляется понятной inline-кнопкой **«Открыть webUI»** вместо «голой»
текстовой ссылки.

## Пользователи
- **Основная аудитория**: пользователи Telegram, прошедшие `/register <телефон>`
  и подтвердившие аккаунт кодом из SMS (аккаунт привязан к Telegram ID).
- **Незарегистрированные пользователи**: изменений не видят — keyboard им
  не показывается, текстовая подсказка про `/register` остаётся как есть.

## Сценарий использования
1. Пользователь регистрируется: отправляет `/register +7...`, получает запрос
   кода из SMS, отправляет код, аккаунт подтверждён.
2. Сразу после успешного подтверждения регистрации бот показывает ответ
   с reply-keyboard, содержащим кнопку **«Войти в webUI»**.
3. Далее **каждый** ответ бота этому пользователю (успешный или об ошибке)
   сопровождается тем же keyboard: он постоянно виден под полем ввода.
4. Пользователь нажимает **«Войти в webUI»** — бот обрабатывает нажатие
   как команду `/login` (распознаются и текст кнопки, и сама команда `/login`).
5. Бот получает одноразовую ссылку в webUI и отвечает сообщением,
   содержащим inline-кнопку **«Открыть webUI»**, ведущую по этой ссылке.
6. Пользователь нажимает inline-кнопку и попадает в webUI.

## Критерии приёмки
- [x] Авторизованному (зарегистрированному и подтверждённому) пользователю
      бот отвечает с reply-keyboard из одной кнопки «Войти в webUI».
      (BuildLoginKeyboard + политика Messenger; messenger_test.go)
- [x] Keyboard прикладывается к каждому ответу бота авторизованному
      пользователю, включая сообщения об ошибках (неверная команда, сбой
      обработки чека, ошибка получения login-ссылки).
      (все команды, get_report и processNotifications идут через Messenger)
- [x] Keyboard показывается сразу после успешного подтверждения регистрации.
      (/code отвечает; lazy-политика + read-after-write backend'а)
- [x] Незарегистрированный пользователь keyboard не получает; поведение
      для него не меняется. (markup nil; тексты команд не менялись)
- [x] Нажатие кнопки «Войти в webUI» выполняет логику `/login`; команда
      `/login`, введённая вручную, продолжает работать как раньше.
      (Accepted в login.go; login_test.go)
- [x] Ответ со ссылкой содержит inline-кнопку «Открыть webUI», ведущую
      по полученной одноразовой ссылке; поведение `/login` для незарегистрированных
      не сломано. (BuildLoginLinkMessage; Analytics остаётся источником истины)
- [x] Юнит-тесты в `bot/` покрывают: определение авторизованности для показа
      keyboard, распознавание текста кнопки как `/login`, формирование keyboard
      и inline-кнопки. (24 новых теста: keyboard/login/messenger/provider/processor)
- [x] `cd bot && go test ./...` — все тесты проходят. (проверено 2026-10-26,
      также `go test -race ./...` в bot и `go test ./...` в backend — все ok)
- [ ] Ручная проверка в Telegram пройдена: регистрация → keyboard появился →
      нажатие кнопки → сообщение с inline-кнопкой → переход в webUI.
      (ожидает проверки заказчиком; требует деплоя в порядке backend → bot)

## Edge cases
- **Статус регистрации устарел** (аккаунт отвязали/удалили): пользователь
  может ещё видеть keyboard; `/login` в этом случае честно отвечает ошибкой.
  Это допустимая деградация — специальной синхронизации не требуется.
- **Ошибка получения ссылки** (Analytics недоступен): пользователь получает
  сообщение об ошибке, но keyboard при нём остаётся.
- **Сервис определения статуса недоступен**: бот не должен из-за этого ломать
  обработку прочих сообщений (пользователь может временно не получить keyboard —
  допустимо).
- Незарегистрированный пользователь по-прежнему может ввести `/login` вручную —
  ответ бота не должен измениться по смыслу (ошибка/отказ, как сейчас).
- Повторные нажатия кнопки допустимы: на каждое — новая одноразовая ссылка.

## Зависимости
- Analytics-сервис: существующий механизм получения одноразовой login-ссылки
  (используется командой `/login` сегодня).
- Backend: возможность определить, что пользователь зарегистрирован и
  подтверждён по Telegram ID — **решено архитектором (ADR-029, ред. 2)**: предикат
  «подтверждён кодом из SMS» вычисляется backend'ом по состоянию device (непустые
  `SessionId`/`RefreshToken` — побочный эффект только успешного `VerifyPhone`) и доставляется
  в бота аддитивным полем gRPC `User.verified`; миграции/backfill не требуются
  (см. [ADR-029, D1](../../adr/029-bot-login-reply-keyboard.md)).
- Никаких миграций данных не ожидается.
