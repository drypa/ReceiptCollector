# Ссылки на «Чеки по магазину» из списка магазинов + URL-роутинг состояния аналитики

## Приоритет
high

## Проблема
Экран «Чеки по магазину» уже существует, но включается внутренним стейтом `Analytics/frontend/src/components/ReceiptsPage.tsx:16` (`selectedMerchantId`) и доступен только кликом по магазину в таблице чеков. Из списка магазинов (`/merchants`, админский раздел) в него попасть нельзя — хотя это самый очевидный путь: увидел магазин, захотел его чеки.

Состояние не отражено в адресе страницы: перезагрузка (F5), открытие ссылки в новой вкладке, закладка и кнопка браузера «Назад» теряют выбранный магазин или чек. Дополнительно параметр `receiptId` после загрузки чека actively удаляется из адреса (`ReceiptsPage.tsx:88-94`), что ломает даже частичную сохраняемость ссылки.

## Цель
Любое место в аналитике — открытый раздел, выбранный магазин, открытый чек — отражается в URL. По ссылке можно вернуться в ту же точку, ссылка переживает перезагрузку и переносится между вкладками/устройствами. Из списка магазинов можно в один клик попасть к чекам конкретного магазина.

## Пользователи
- Администратор — работает со списком магазинов (раздел `/merchants` доступен только ему, `Sidebar.tsx:22-28`) и с чеками по магазину.
- Обычный пользователь — смотрит чеки и переходит к чекам магазина из таблицы чеков. Экран «Чеки по магазину» должен быть доступен и ему.

## Сценарий использования
**Основной (из списка магазинов):**
1. Пользователь открывает раздел «Магазины» (`/merchants`).
2. Кликает по названию магазина в таблице — открывается экран «Чеки по магазину».
3. В адресной строке — путь, соответствующий разделу «Чеки» и конкретному магазину.
4. Администратор нажимает F5 — открывается тот же экран, а не список всех чеков.
5. Нажимает «Назад» в браузере — возвращается к списку магазинов.
6. Копирует адрес из адресной строки и отправляет коллеге — коллега видит те же чеки этого магазина.
7. Кликает по чеку в таблице — открывается карточка чека, адрес содержит id чека; F5 сохраняет открытый чек.

**Из таблицы чеков:**
1. Пользователь на «Чеках» (`/receipts`) кликает по магазину в строке чека.
2. Открывается тот же экран «Чеки по магазину» с соответствующим маршрутом.
3. Кнопка «Все чеки» возвращает к общему списку чеков.

**Ошибки:**
1. Пользователь открывает ссылку с несуществующим id магазина или чека — видит экран «Не найдено» и возможность вернуться к списку чеков, а не пустой список.
2. Пользователь открывает неизвестный/мусорный путь — видит экран «Не найдено».

## Маршруты
Только сегменты пути. Query-параметры не используются.

| URL | Экран |
|---|---|
| `/receipts` | Все чеки (прежний `/` редиректит сюда) |
| `/receipts/{receiptId}` | Карточка чека |
| `/merchants` | Список магазинов (только администратор) |
| `/merchants/{merchantId}/receipts` | Чеки по магазину |
| `/commodities` | Товары (без изменений) |
| любой другой путь | «Не найдено» + возможность вернуться в «Чеки» |

## Требования к поведению
- URL — единственный источник состояния: открытый раздел, выбранный магазин, открытый чек. Внутренние стейты, дублирующие состояние из URL, не используются.
- В адрес попадают только идентификаторы. Номер страницы пагинации, размер страницы, режим редактирования, сортировка в URL **не** сохраняются.
- Состояние восстанавливается при перезагрузке страницы (F5) и при открытии ссылки в новой вкладке.
- Кнопки браузера «Назад»/«Вперёд» работают штатно, история переходов соответствует переходам между экранами.
- Адрес не «чистится» после загрузки чека (сейчас это делается в `ReceiptsPage.tsx:88-94`).
- Ссылки рабочие: правый клик / Ctrl+клик / средняя кнопка открывают в новой вкладке.
- Ссылка на название магазина в таблице «Магазины» ведёт на экран «Чеки по магазину». Ссылка присутствует всегда; когда администратор открыл инлайн-редактирование имени («ред.»), вместо ссылки отображается поле ввода, после «Сохранить»/«Отмена» — снова ссылка.
- Кнопка «Магазин» в таблице чеков ведёт на тот же маршрут (остаётся кнопкой, а не ссылкой).
- Экран «Чеки по магазину»: заголовок без имени магазина, кнопка «Все чеки» возвращает к общему списку. Больше ничего на этом экране не меняем.
- Экран «Чеки по магазину» доступен всем пользователям, включая не-администраторов. Сообщение «Доступ запрещён» применяется только к списку магазинов `/merchants`.
- Старые ссылки не ломаются: `/` редиректит на `/receipts`, `/?receiptId={id}` редиректит на `/receipts/{id}`.

## Критерии приёмки
- [ ] Название магазина в таблице раздела «Магазины» кликабельно и открывает «Чеки по магазину»
- [ ] Клик по магазину из таблицы чеков открывает тот же экран
- [ ] Ссылка на магазин сохраняется при копировании из адресной строки и открывается в новой вкладке/у другого пользователя
- [ ] Перезагрузка страницы (F5) на любом маршруте восстанавливает тот же экран
- [ ] Кнопка браузера «Назад» возвращает на предыдущий экран, «Вперёд» — вперёд
- [ ] В адресной строке находятся только идентификаторы (id магазина, id чека), без параметров фильтрации/сортировки, номера и размера страницы
- [ ] Клик по чеку открывает карточку чека, её адрес содержит id чека и переживает перезагрузку
- [ ] Несуществующий id магазина или чека → экран «Не найдено», а не пустой список и не «Доступ запрещён»
- [ ] Магазин существует, но чеков нет → пустое состояние «Чеки не найдены» (отличается от «Не найдено»)
- [ ] Неизвестный путь → экран «Не найдено»
- [ ] Не-администратор может открыть экран «Чеки по магазину» по прямой ссылке, но не список магазинов
- [ ] Ссылки `/` и `/?receiptId={id}` из старых закладок продолжают работать
- [ ] `npm run build` (tsc + vite build) в `Analytics/frontend` проходит без ошибок
- [ ] `npm run lint` в `Analytics/frontend` проходит без ошибок

## Edge cases
- Несуществующий или удалённый id магазина в URL → «Не найдено» + ссылка на общий список чеков
- Несуществующий id чека в URL → «Не найдено» + возможность вернуться к списку
- Магазин существует, чеков 0 → пустое состояние, а не «Не найдено»
- Мусорный путь (`/чеки`, `/receipts/abc/def`, пустой id) → «Не найдено»
- Быстрое переключение маршрутов / возврат «Назад» во время загрузки — не должно приводить к гонкам и отображению данных предыдущего экрана
- Администратор переименовал магазин: ранее выданная ссылка на «Чеки по магазину» продолжает работать (в адресе id, а не имя)
- Раздел «Магазины» — админский: не-админ не должен видеть его в меню и должен получать отказ при прямом заходе на `/merchants`
- Прямой заход на `/merchants` не-админом → «Доступ запрещён» (текущее поведение сохраняется)

## Открытый вопрос для архитектора
`GET /api/receipts/by-merchant/{merchantId}` должен различать два случая: магазина нет (нужен «Не найдено») и магазин есть, но чеков нет (нужно пустое состояние). Если сейчас в обоих случаях приходит пустой список, задача может потребовать минимального изменения на бэкенде (например, 404 для неизвестного магазина). Решение — на усмотрение архитектора; поломка существующих контрактов API недопустима.

## Вне объёма задачи
- Имя магазина в заголовке экрана «Чеки по магазину» (соответственно не нужен `GET /api/merchants/{id}`)
- Хлебные крошки и ссылка «назад к списку магазинов» на экране «Чеки по магазину»
- Фильтрация, сортировка, поиск, экспорт
- Настройка автотестов фронтенда (Vitest и т.п.) — сейчас во фронтенде тестов нет, приёмка ручная
- Изменение раздела «Товары» (`/commodities`), кроме сохранения его маршрута
