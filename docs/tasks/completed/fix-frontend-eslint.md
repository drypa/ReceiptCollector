# Починка ESLint фронтенда и включение линтинга в CI

## Приоритет
medium

## Проблема
`npm run lint` в `Analytics/frontend` падает с `exit 2` на любом файле, включая нетронутые (проверено на `src/components/CommodityTable.tsx`). Причина: `eslint.config.js:15` подключает `reactHooks.configs['recommended-latest']` — это legacy-конфиг (`plugins: ["react-hooks"]`, массив строк), который ESLint 10 в flat-режиме не принимает. Корректный flat-вариант (`reactHooks.configs.flat['recommended-latest']`) есть в том же плагине.

Остальное содержимое конфига корректно: `reactRefresh.configs.vite` уже использует объектные `plugins` и flat-формат применим.

Линт не запускается и в CI: ни один workflow в `.github/workflows/` не выполняет `npm run lint` (`build-analytics-image.yml` запускает только `dotnet test` и Docker-сборку, а Node появляется исключительно внутри `Analytics/Dockerfile`). Поэтому поломка осталась незамеченной, а правила фронтенда фактически не проверялись никогда — ошибки и предупреждения копились без проверки.

## Цель
`npm run lint` работает, реально проверяет код по правилам проекта (react-hooks, react-refresh, typescript-eslint) и служит воротами в CI. Правила одинаково строги локально и в CI: предупреждение равно провалу.

## Пользователи
- Frontend-разработчики — локальный запуск `npm run lint` должен давать достоверный результат.
- Ревьюеры — статусная проверка PR должна подтверждать, что правила соблюдены.
- Косвенно — пользователи аналитики: код перестаёт накапливаться непроверенным.

## Сценарий использования
1. Разработчик вносит изменения в `Analytics/frontend/src` и запускает `npm run lint` локально — команда отрабатывает, а не падает на конфигурации, и выдаёт осмысленный список нарушений.
2. Разработчик открывает PR с изменениями фронтенда — в статусных проверках появляется шаг линтинга.
3. Если в коде есть нарушение — шаг падает, PR не проходит проверку.
4. Если нарушений нет — шаг зелёный, PR проходит.

## Требования
- **FR-1.** Линтер запускается без ошибок конфигурации; на текущем коде — 0 ошибок, 0 предупреждений.
- **FR-2.** `npm run lint` = `eslint . --max-warnings 0` — одинаково строго локально и в CI, предупреждение равно провалу.
- **FR-3.** Работоспособность проверки должна быть доказана, а не ограничена «exit 0»: в задачу входит контрольная проверка — внести искусственное нарушение в `Analytics/frontend/src/...`, убедиться, что линтер его находит, и откатить. Это подтверждает, что правила `react-hooks`, `react-refresh` и `typescript-eslint` действительно активны, а не молча отключены.
- **FR-4.** Зависимости не меняются: `package.json` меняется только в части скрипта `lint`, `package-lock.json` не трогается.
- **FR-5.** CI: шаг `setup-node` (Node 22 — как в `Analytics/Dockerfile:2`) + `npm ci` + `npm run lint` добавляется в существующий `.github/workflows/build-analytics-image.yml` сразу после `checkout`, до установки .NET. Блок `on:` (триггеры) не изменяется — фронтенд уже подпадает под `Analytics/**`. Новый workflow не создаётся.
- **FR-6.** Реальные ошибки/предупреждения, вскрытые включением настоящего пресета, исправляются в этой же задаче.
- **FR-7.** .NET-часть не трогается, включая предупреждения NU1902/NU1903 об уязвимостях пакетов.

## Критерии приёмки
- [ ] `cd Analytics/frontend && npm run lint` → `exit 0`, пустой вывод
- [ ] Контрольная проверка: искусственное нарушение правила даёт ошибку в выводе линтера, после отката — снова чисто
- [ ] `cd Analytics/frontend && npm run build` (tsc + vite) по-прежнему проходит без ошибок
- [ ] `git status` не показывает изменений в `Analytics/frontend/package-lock.json`; в `package.json` изменён только скрипт `lint`
- [ ] В `.github/workflows/build-analytics-image.yml` шаг линтинга расположен после `checkout` и до .NET; блок `on:` не изменён; workflow принимается GitHub Actions
- [ ] Линт реально исполняется в CI: на PR с изменением в `Analytics/frontend/src` виден зелёный шаг; при искусственном нарушении PR падает именно на нём
- [ ] `cd Analytics && dotnet test` по-прежнему зелёный (194 теста) — регрессия не внесена

## Edge cases
- `npm ci` падает при рассинхронизации `package-lock.json` с `package.json` — нужно подтвердить, что они в порядке
- Расхождение локальной версии Node и CI-версии 22 может давать разные результаты линтинга — версия в CI фиксируется явно
- Конфиг линтера остаётся точкой тихой поломки: автоматической защиты от его регресса в объём задачи не входит, страховкой служит CI
- `eslint .` проходит по всему каталогу `Analytics/frontend`, включая сам `eslint.config.js` и конфиги Vite — нужно убедиться, что это не даёт новых нарушений
- `eslint-plugin-react-refresh@0.4.24` в flat-режиме применим (`plugins` — объект); если чинить придётся именно его — это тоже в объёме задачи
- Возможные реальные нарушения в существующем коде (например, новые compiler-правила `react-hooks@7`) исправляются в этой же задаче, а не откладываются

## Зависимости
- `Analytics/frontend/eslint.config.js` — нерабочий пресет `reactHooks.configs['recommended-latest']`
- `Analytics/frontend/package.json` — скрипт `lint`
- `.github/workflows/build-analytics-image.yml` — существующий workflow, триггеры неприкосновенны
- `Analytics/Dockerfile:2` — источник версии Node (22)
- `Analytics/frontend/package-lock.json` — неприкосновенна (FR-4)

## Вне объёма
- Обновление ESLint и пин-плагинов, правка `package-lock.json`
- Исправление предупреждений NU1902/NU1903 (уязвимости .NET-пакетов) — отдельная задача
- Автотесты конфига линтера
- Новый workflow и изменение триггеров существующих workflow
- Дублирование `npm run build` в CI — уже покрыто Dockerfile-стадией `Analytics/Dockerfile:9` внутри `build-analytics-image.yml`
- Контрольные проверки (FR-3) ручные, автоматизация не требуется

## Решения заказчика
- `actions/setup-node@v4` — оставляем как есть, обновление major-версий actions выносится на потом отдельной задачей. Сознательный размен: единообразие пиннинга в workflow против актуальности версии.
- `.js`-файлы остаются вне покрытия правил (`files: ['**/*.{ts,tsx}']`). Для фронтенда безобидно: единственный `.js` — сам `eslint.config.js`, нарушений он не даёт. Расширение покрытия — отдельная задача при необходимости.
