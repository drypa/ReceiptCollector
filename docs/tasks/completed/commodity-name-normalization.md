# Усиление нормализации названий товаров (снятие артикулов/штрихкодов и мусорных префиксов)

## Приоритет
high

## Проблема
Общая нормализация названий (`CommodityNameNormalizer`) выполняет только
`lowercase + trim + схлопывание пробелов`. В продакшене названия товаров из чеков
содержат технические артикулы и штрихкоды в начале и в конце, а также ведущие
мусорные знаки:

- `2417268000006 ПИРОГ С ВИШНЕЙ ПО РЕ` — ведущий EAN-13;
- `2444436000001 СЕТ ДУЭТ 256г` — ведущий EAN-13;
- `*3455614 РЖ.КРАЙ Хлеб нар.300г` — ведущая звёздочка + артикул;
- `2195738 Туалетная бумага "СВАЁ" (3сл, 4р) 4810981001530` — артикул в начале
  и EAN-13 в конце.

Последствия:
1. **Загрязнение запроса к ИИ.** В `CommodityCategoryResolver` в ИИ уходит
   **сырое** имя — артикулы/штрихкоды не несут смысла для категоризации и
   искажают промпт.
2. **Один товар — разные ключи.** Кэш, дедупликация пакетного suggest, журнал и
   поиск по очереди предкатегоризации используют нормализованное или точное имя;
   из-за кодов один и тот же товар считается разными товарами, повторно
   уходит в ИИ и дублируется в очереди `precategorized_commodities` (4000+
   записей).
3. **Очередь ищется по точному сырому имени** (`GetCategoriesByExactNamesAsync`:
   `nameList.Contains(p.Name)`) — поэтому очистка кэша без изменения поиска по
   очереди не даёт эффекта.

## Цель
Очищать технические дополнения в названиях товаров по единому правилу и применять
очищенное имя во всех местах, где оно используется как ключ или уходит в ИИ:
запрос к ИИ, кэш, дедупликация, поиск по очереди, `normalized_name` новых событий
журнала. Очистить неподтверждённую очередь предкатегоризации, чтобы она
пересобралась по новым правилам. Интерфейс и пользовательский поток не меняются,
автопроставления категорий нет.

## Пользователи
- **Администратор** — опосредованно: чище журнал (меньше «дублей» одного товара),
  меньше повторных предложений в `/precategorized`, меньше ручной разметки.
- **Обычные пользователи** — изменений в интерфейсе не замечают; получают более
  релевантные предложения и меньше повторов.

## Сценарий использования
1. Пользователь открывает чек с позицией `2417268000006 ПИРОГ С ВИШНЕЙ ПО РЕ`,
   нажимает «предложить категории» → в ИИ уходит очищенное имя
   `пирог с вишней по ре`; полученное предложение сохраняется в кэш под очищенным
   ключом.
2. В другом чеке позиция `ПИРОГ С ВИШНЕЙ ПО РЕ` (без кода) → категория берётся из
   кэша (или очереди), ИИ не вызывается.
3. На странице «Товары» варианты `2195738 Туалетная бумага "СВАЁ" ... 4810981001530`
   и `Туалетная бумага "СВАЁ" ...` схлопываются в одно уникальное название при
   пакетном suggest.
4. Фон предкатегоризации заново собирает предложения для безкатегорийных товаров
   с очищенными именами; админ видит их в `/precategorized` как раньше (в UI —
   исходные названия из чеков).
5. Журнал категоризации для новых событий хранит сырое `commodity_name` и
   очищенный `normalized_name`; накопленная история не пересчитывается.

## Функциональные требования
- **FR-1. Правило очистки.** При нормализации:
  - снимать непрерывные последовательности цифр **от 6 знаков** в начале и в
    конце названия (артикулы/SKU/EAN);
  - снимать ведущие знаки пунктуации `*`, `#`, `№` (возможно повторные и в
    комбинации с пробелами);
  - **не трогать** прочие цифры и фрагменты: `256г`, `нар.300г`, `(3сл, 4р)`,
    бренд `РЖ.КРАЙ`, короткие числа (`АИ-95`, `1000 ЛЕПЕСТКОВ`);
  - сохранять текущие правила: приведение к нижнему регистру, trim, схлопывание
    повторных пробелов;
  - если после очистки от имени ничего не осталось (пустая строка/одни пробелы) —
    использовать исходное название (не возвращать пустой ключ).
- **FR-2. ИИ получает очищенное имя** во всех suggest-сценариях (чек, страница
  «Товары», фон предкатегоризации), где формируется промпт по имени товара.
- **FR-3. Очищенное имя — единый ключ** в: кэше категорий, дедупликации пакетного
  suggest, поиске по очереди `precategorized_commodities` (вместо поиска по
  точному сырому имени), ключе группировки в resolver, `normalized_name` новых
  событий журнала.
- **FR-4. Сырые данные не теряются:** `commodity_name` в журнале и отображение
  названий в UI остаются исходными; накопленные события журнала не
  пересчитываются.
- **FR-5. Миграция данных:** удалить из `precategorized_commodities` строки в
  статусе `proposed` (неподтверждённые), чтобы фон пересобрал их по новым
  правилам. Строки в статусе `applied` **сохраняются** (история действий админа,
  защита от повторных предложений). Миграция безопасна на пустой таблице и
  идемпотентна.

## Нефункциональные требования
- **NFR-1.** Автопроставление категорий по-прежнему запрещено: задача меняет
  только качество имени/ключа, не поведение подтверждения.
- **NFR-2.** Интерфейс и контракты API не меняются (кроме качества данных);
  пользовательский поток не замечает изменений.
- **NFR-3.** Нормализация детерминирована и без побочных эффектов; накладные
  расходы на сохранение/предложение несущественны (регулярные выражения
  ограниченной сложности).
- **NFR-4.** Существующий набор тестов Analytics (`dotnet test`) остаётся зелёным;
  поведение при некорректных/пустых названиях не ухудшается.

      `*3455614 РЖ.КРАЙ Хлеб нар.300г` → `рж.край хлеб нар.300г` (звёздочка и
      артикул сняты, бренд и `нар.300г` сохранены);

      имя, состоящее только из кода (`2417268000006`, буквально `*3455614`),

## Edge cases
- Название состоит только из кода/пунктуации (`2417268000006`, `*345`) → возвращается
  исходное (непустой ключ).
- Осмысленные короткие числа в начале/конце (`АИ-95`, `1000 ЛЕПЕСТКОВ`, `256г`)
  не снимаются.
- Код в середине названия (не на краю) — не снимается (вне правила).
- Несколько ведущих звёздочек/решёток/знаков `№` и пробелов между ними — снимаются
  все.
- Снятие кода обнажило лишние пробелы/пунктуацию (`*3455614 ...`) → финальный
  trim и схлопывание пробелов.
- Очень длинное название после очистки — контроль длины колонок журнала/очереди
  остаётся как есть (очистка только сокращает).
- Очередь содержит дубли одного очищенного ключа — после удаления `proposed`
  фон пишет заново; конфликтов нет (в `applied` остаются прежние строки).

## Зависимости
- `CommodityNameNormalizer` (Domain) — общая нормализация, используется кэшем,
  resolver, пакетным suggest, журналом.
- `CommodityCategoryResolver` (Инфраструктура) — порядок `existing → cache →
  precategorized → ai` и промпт ИИ.
- `PrecategorizedCommodityRepository.GetCategoriesByExactNamesAsync` — поиск по
  имени (сейчас точное).
- Фон `PrecategorizationBackgroundService` — сбор кандидатов и запись в очередь.
- Журнал решений категоризации (ADR-033) — `normalized_name` событий.
- Миграции `ReceiptCollector.Analytics.Migrations` (`Scripts/*.sql`).
- ADR-009 (нормализация, NFR-3.1), ADR-019 (кэш), ADR-027 (очередь), ADR-028
  (пакетный suggest), ADR-033 (журнал).

## Вне объёма
- Пересчёт истории журнала (старые `normalized_name` остаются).
- Унификация `ё → е` и иные лингвистические правила (пунктуация, опечатки).
- Снятие кодов в середине названия и любые эвристики выше описанного правила.
- Изменение UI, экспорт, счётчики, агрегаты.
- Автопроставление категорий; ретеншен журнала.
