# Задача: Альтернативный провайдер категоризации товаров (RLCD / SystemOne)

> **Относится к функционалу автоматической категоризации товаров (см. [auto-commodity-categorization.md](completed/auto-commodity-categorization.md), ADR 009; кэш категорий — [in-memory-commodity-category-cache.md](completed/in-memory-commodity-category-cache.md), ADR 019).** Задача **не заменяет** существующего OpenAI-совместимого клиента, а добавляет второй, подключаемый по конфигурации.

> **Именование.** Подход к категоризации — экспериментальный; конкретная модель/движок на момент реализации может быть другой. В коде, конфигурации и тексте задачи **не привязываемся к вендору**: используются обобщённые имена «RLCD» / «SystemOne» / «движок типизированных решений». Конкретные названия полей, адресов и протокола уточняются при взятии задачи в работу.

## Приоритет
**low** — сроков нет, задача живёт в бэклоге. Ценность зафиксирована (ускорение и снижение стоимости), но текущий провайдер работает и задачу не блокирует.

## Проблема
- Категоризация товаров выполняется последовательным потоком запросов к LLM (OpenAI-совместимый эндпоинт). На чеке десятки позиций → десятки запросов: **суммарное время ответа растёт** пропорционально числу позиций, а **стоимость** пропорциональна числу запросов и объёму промпта.
- Ответ LLM — свободный текст, поэтому его приходится разбирать и чистить (обёртки ``` , лишний текст, числовые значения вместо имени категории) — это хрупкая и недешёвая часть решения.
- Сравнить провайдеров между собой по факту нечем: **нет измерений** ни времени, ни стоимости отдельного запроса к ИИ.

## Цель
- Получить возможность **опционально** переключить AI-категоризацию на движок типизированных решений (RLCD / SystemOne), который отдаёт готовую категорию из закрытого множества без генерации текста.
- Снизить время категоризации чека и/или стоимость одного запроса к ИИ — и **иметь возможность это измерить**.
- Сохранить работоспособность и поведение текущего провайдера: переключение туда-обратно — через переменные окружения, без пересборки и без правок кода.

## Пользователи
- Конечный пользователь webUI `Analytics/frontend` (страница чека) — получает тот же функционал категоризации, но с меньшим временем ожидания (цель задачи).
- Оператор/администратор сервиса — переключает провайдер через конфигурацию (`docker-compose` / env), может сравнить время и стоимость двух вариантов.
- DevOps — разворачивает сам движок **вне** нашего репозитория (в область ответственности заказчика); со стороны Analytics требуется только корректно обращаться к нему по настроенному адресу.

## Вне области задачи
- Развёртывание, обслуживание и дообучение самого движка (модели) — выполняется вне этого репозитория.
- Валидация качества категоризации в цифрах (точность, доля верных категорий) — см. «Бэклог».
- Миграции данных, изменения схемы БД, изменения API-контрактов и фронтенда.
- Go-сервисы (backend, bot), nginx.

## Сценарий использования
1. Оператор задаёт в окружении, какой провайдер использовать (например, переключает с OpenAI-совместимого на RLCD/SystemOne), и перезапускает Analytics.
2. Пользователь открывает чек в webUI и нажимает «Категоризировать».
3. Сервис проходит прежние шаги приоритета: «категория позиции уже есть» → «совпадение в кэше категорий» → **AI-провайдер** (для обоих провайдеров поведение одинаково, `source = ai`).
4. RLCD/SystemOne-провайдер отвечает готовой категорией из реестра; ответ сохраняется в предложение для пользователя, **не** сохраняется в БД (сохранение — только после подтверждения пользователем, как сейчас).
5. Пользователь подтверждает/исправляет предложения и сохраняет — как в текущей функциональности.
6. Для оценки ускорения/удешевления оператор сравнивает зафиксированные в логах метрики по обоим провайдерам (см. FR-4).

## Функциональные требования

### FR-1. Переключение провайдера
- FR-1.1. В Analytics появляется **второй, альтернативный** провайдер категоризации (движок типизированных решений, далее — «новый провайдер»). Существующий OpenAI-совместимый клиент **не удаляется и не заменяется**.
- FR-1.2. Активный провайдер задаётся конфигурацией (`AI:Provider`), значения: `OpenAi` (по умолчанию, текущее поведение) и `SystemOne`. Имена значений — на усмотрение архитектора, при условии нейтральности (без упоминания конкретного вендора/продукта).
- FR-1.3. Переключение выполняется **только через переменные окружения / конфигурацию**, без изменения кода и без пересборки; применяется при старте сервиса.
- FR-1.4. Некорректное/пустое значение `AI:Provider` приводит к явной ошибке конфигурации на старте сервиса, а не к откату на «молчаливый» провайдер по умолчанию.
- FR-1.5. Поведение по умолчанию (провайдер не задан / старые настройки) полностью совпадает с текущим: работает OpenAI-совместимый клиент.

### FR-2. Конфигурация провайдеров
- FR-2.1. Настройки провайдеров **разделены** по секциям: `AI:OpenAi:*` и `AI:SystemOne:*` (оба движка развёрнуты снаружи и могут иметь разные адреса/ключи).
- FR-2.2. Минимальный состав каждой секции: `BaseUrl`, `Model`, `Timeout`, `Concurrency`, `ApiKey` (по аналогии с текущей секцией `AI`; способ сохранения обратной совместимости существующих переменных — на усмотрение архитектора, но без «тихой» поломки текущих установок).
- FR-2.3. Для нового провайдера дополнительно задаётся **порог уверенности** через конфигурацию/переменную окружения: ответ с уверенностью ниже порога считается неопределённым (см. FR-3.4). Полный перечень параметров нового провайдера (например, лимиты длины входа) **уточняется при взятии задачи в работу**; сейчас обязательны только перечисленные.
- FR-2.4. Существующий признак «AI не настроен» (пустой `BaseUrl`) сохраняет поведение: `POST /api/receipts/{id}/categories/suggest` отвечает `503` (ADR 019).

### FR-3. Поведение нового провайдера
- FR-3.1. Внешний контракт и поведение для пользователя **такие же**, как у текущего провайдера: предложение категории по позиции чека, ответ `200` со списком позиций, сохранение — после подтверждения пользователем (контракт `POST .../categories/suggest` / `PUT .../categories` не меняется, значения `CategorizationSource` не меняются).
- FR-3.2. Приоритет источников сохраняется: категория позиции → кэш категорий → AI-провайдер (кэш и его политика — ADR 019, без изменений).
- FR-3.3. Категория приходит из закрытого множества существующих категорий реестра; категории `Undefined` и несуществующие значения не должны приводиться к предложению.
- FR-3.4. **Порог уверенности:** если ответ нового провайдера несёт оценку уверенности ниже настроенного порога — позиция считается неопределённой (`Undefined` + пояснение для пользователя, как сейчас при «ИИ категорию не определила»).
- FR-3.5. **Деградация при недоступности нового провайдера** (сервис не поднят, таймаут, 5xx, некорректный ответ) — **ровно как сейчас**: общий ответ `200`, по незакрытым позициям `Undefined` + пояснение; автоматического отката на другой провайдер нет.

### FR-4. Наблюдаемость: время и стоимость
- FR-4.1. Каждый запрос к AI-провайдеру логируется с **измерением длительности**, с указанием активного провайдера; по логам можно сравнить время ответа двух провайдеров на одинаковых данных (цель — ускорение/замедление).
- FR-4.2. Предусматривается **способ оценки стоимости** одного запроса к AI: определить и реализовать, какие данные фиксируются в логах/метриках, позволяющие оценить стоимость (для нового провайдера — например, по объёму входа/выхода и числу запросов; для существующего — по числу запросов и объёму отправленных/принятых токенов, если провайдер это позволяет). Конкретный состав полей и способ расчёта — на усмотрение архитектора, но **оценка должна быть доступна оператору по логам/метрикам**.
- FR-4.3. Никаких персональных данных/содержимого чека в метриках не логируется сверх того, что уже логируется.

## Критерии приёмки
- [ ] Автотест: при стандартной конфигурации (провайдер не задан) Analytics работает ровно как до задачи — используется OpenAI-совместимый клиент, его тесты проходят без правок ожидаемого поведения.
- [ ] Автотест: при `AI:Provider=SystemOne` (и корректной секции `AI:SystemOne:*`) вызывается новый провайдер, а не OpenAI-совместимый; при обратном переключении — наоборот.
- [ ] Автотест: неизвестное/пустое значение `AI:Provider` → явная ошибка конфигурации на старте.
- [ ] Автотест: корректный ответ нового провайдера приводится к категории из реестра; недопустимое значение (в т.ч. `Undefined`, числовое) — к неопределённой позиции, а не к «случайной» категории.
- [ ] Автотест: уверенность ниже порога → позиция неопределённая (`Undefined` + пояснение); выше порога — категория предлагается.
- [ ] Автотест: недоступность нового провайдера (сеть/таймаут/5xx) — общий ответ `200`, незакрытые позиции неопределённые; **без** автоматического отката на другой провайдер.
- [ ] Автотест: пустой `BaseUrl` активного провайдера → `503` на suggest (прежний контракт сохранён).
- [ ] Автотест: существующий кэш категорий (ADR 019) не обходится: при попадании в кэш новый провайдер не вызывается (тесты кэша и `CommodityCategorizationService` проходят).
- [ ] Автотест: в логи попадают длительность и идентификатор провайдера для каждого запроса к AI; состав данных для оценки стоимости зафиксирован и проверяем тестом/ручным примером записи лога.
- [ ] `cd Analytics && dotnet test` — все тесты проходят.
- [ ] Ручная проверка (внешний движок поднят отдельно): с каждым из двух провайдеров на одном и том же чеке suggest отрабатывает и предлагает категории; переключение через env туда-обратно работает без правок кода; при недоступном движке — частичный результат без падения.
- [ ] Ручная проверка: по логам двух провайдеров можно сопоставить время и оценку стоимости категоризации одного и того же чека.

## Edge cases
- **Движок не развёрнут / адрес не задан** — `503` на suggest (как сейчас при пустом `BaseUrl`); другие сценарии Analytics не затрагиваются.
- **Движок отвечает некорректным payload'ом** (нет ответа/поля, значение вне реестра) — позиция неопределённая, чек обрабатывается целиком, ошибка фиксируется в логах.
- **Движок перегружен** (отказ в обслуживании/лимит параллельности) — позиция неопределённая, ответ `200`; отдельный прогон приводит к тому, что категоризация чека может занять заметное время (движок обрабатывает запросы последовательно) — поведение для пользователя остаётся прежним.
- **Очень длинное название товара** или превышение лимитов на стороне движка — позиция неопределённая, чек обрабатывается целиком.
- **Порог уверенности не задан** — поведение по умолчанию (для нового провайдера — категория используется как есть; см. FR-3.4) и наличие явного порога фиксирует архитектор.
- **Уверенность «завышена» движком** — значения нельзя считать откалиброванными без проверки на своих данных; порог по умолчанию не должен приводить к массовому `Undefined` (в Бэклог — калибровка).
- **Переключение провайдера при незакрытом in-memory кэше** — кэш общий для обоих провайдеров; поведение не меняется, переключение не требует перезапуска сверх смены конфигурации.
- **Опечатка в env-имени параметра** — приводит к молчаливому применению значения по умолчанию; желательно предупреждение в лог при старте о неизвестных ключах секции (на усмотрение архитектора).
- **Таймаут/ретраи** — поведение при таймауте и повторах совпадает с текущим (ретрай на сетевых ошибках/таймауте/5xx, без ретрая на заведомо некорректном ответе); конкретные значения — через конфигурацию.

## Зависимости
- **Внешний RLCD/SystemOne-движок**, развёрнутый вне репозитория (адрес, ключ, имя модели — через конфигурацию). Со стороны Analytics — только обращение к нему.
- Текущая функциональность категоризации: ADR 009 (вызов ИИ, контракт эндпоинтов), ADR 019 (in-memory кэш, поведение `503`), ADR 021 (проброс env в docker-compose) — **не отменяются**, при необходимости дополняются amend-заметкой.
- Актуализируются: `docker-compose.yml` (проброс новых переменных, ADR 021), `.env.example`, таблица настроек в `AGENTS.md`.
- Оформляется **новое ADR** (архитектура второго провайдера: порт, конфигурация, переключение, наблюдаемость, обработка ошибок) — на усмотрение архитектора.
- Схема БД, миграции, Go-сервисы, бот, nginx, фронтенд — **не затрагиваются**.

## Бэклог (отдельные задачи)
- Проверка качества и производительности нового провайдера на реальных чеках (доля верных категорий, время, стоимость) — в объём этой задачи не входит, критерий приёмки — ручная работоспособность.
- Калибровка порога уверенности на собственных размеченных данных.
- Возможность автоматического отката на второй провайдер при недоступности основного.
- Кэширование ответов AI (а не только подтверждённых категорий) для сокращения числа запросов.
