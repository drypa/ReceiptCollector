# Журнал решений категоризации товаров (предложено → принято)

## Приоритет
high

## Проблема
Категоризация товаров требует большой ручной разметки: в продакшене накоплен
бэклог (4000+ пре-категоризованных позиций, несколько тысяч в очереди) и
одновременно идёт большой поток новых чеков. Предложения ИИ часто не
соответствуют действительности, и их приходится переназначать вручную.

При этом система **не сохраняет историю решений**: «ИИ предложил X — человек
выбрал Y» нигде не фиксируется. Невозможно понять, где именно ИИ ошибается,
какие категории путаются, какие названия исправляются снова и снова. Качество
предложений правится «на глазок», а каждое подтверждённое человеком решение
оказывается безвозвратно потеряно для анализа уже в момент сохранения.

## Цель
Завести журнал «предложено → принято»: при каждом подтверждении человеком
категории, для которой ранее выдавалось предложение, фиксировать событие.
Администратору дать страницу просмотра этого журнала с фильтрами (в первую
очередь — «только расхождения»). Это первый шаг к управлению качеством
категоризации: копить фактические данные об ошибках ИИ, не меняя текущий
пользовательский поток.

## Пользователи
- **Администратор** — просмотр и фильтрация журнала.
- Обычные пользователи — участников процесса подтверждения остаются как есть,
  нового интерфейса не получают и изменений не замечают.

## Сценарий использования
1. Пользователь открывает чек, нажимает «предложить категории» (источники
   предложений — `ai`, `precategorized`, `cache`, `merchant_default`), правит
   часть категорий и сохраняет → по каждой позиции с предложением в журнал
   попадает событие: исходное название товара (как в чеке), нормализованное
   название, источник предложения, предложенная категория, итоговая категория,
   кто принял.
2. Аналогично на странице «Товары» (пакетный suggest + сохранение).
3. Администратор в `/precategorized` подтверждает или исправляет предложение —
   событие также попадает в журнал.
4. Администратор открывает страницу журнала, фильтрует «только расхождения»,
   видит, какие названия и категории ИИ портит чаще всего; выгружать/считать
   проценты в этой задаче не нужно — список для просмотра.

## Функциональные требования
- **FR-1.** Событие журнала содержит: исходное название товара (как в чеке),
  нормализованное название, источник предложения (`ai` / `precategorized` /
  `cache` / `merchant_default`), предложенную категорию, итоговую категорию,
  принявшего (флаг «админ» + имя пользователя, если оно известно).
- **FR-2.** Фиксируются предложения **всех** источников, не только «чистый ИИ».
- **FR-3.** Фиксируются и согласия (предложено = принято), и исправления —
  иначе невозможно оценить долю ошибок.
- **FR-4.** Точки фиксации — все места подтверждения ранее предложенной
  категории: страница чека, страница «Товары», подтверждение админом в
  `/precategorized`.
- **FR-5.** НЕ фиксируется: (а) предложение показали, но не сохранили;
  (б) человек проставил категорию вручную, не запрашивая предложений
  (предложения не было — фиксировать нечего).
- **FR-6.** Страница журнала доступна только администратору. Колонки: исходное
  название, нормализованное название, предложено (категория + источник),
  принято (итоговая категория), кто принял. Фильтры: только расхождения,
  источник, предложенная категория, итоговая категория, поиск по названию,
  период. Пагинация.
- **FR-7.** В выдаче отображаются **только уникальные сочетания** (одинаковые
  «название + источник + предложено + принято» показываются одной строкой;
  «кто принял» — от последнего события). Счётчики, группировки и агрегаты в
  UI не нужны.
- **FR-8.** Хранение — сырое, по событию на каждое подтверждение (без дедупли
  на уровне хранения): журнал является историческими данными, дедупликация —
  только на уровне отображения.

## Нефункциональные требования
- **NFR-1. Автопроставление категорий запрещено** (заказчик: категорическое
  «нет» при текущем качестве ИИ). Журнал только наблюдает: поведение suggest /
  сохранения / подтверждения не меняется, любое присвоение категории по-прежнему
  только после подтверждения человеком.
- **NFR-2.** Для обычных пользователей изменения в интерфейсе незаметны;
  существующие контракты suggest/apply не ломаются.
- **NFR-3.** Запись в журнал не должна заметно замедлять сохранение категорий
  и не может сделать сохранение неуспешным из-за собственных ошибок (ошибочная
  запись журнала не должна «ронять» пользовательское действие; детали — за
  архитектором).

## Критерии приёмки
- [ ] Подтверждение предложенной категории на странице чека добавляет событие
      журнала со всеми полями FR-1.
- [ ] То же для страницы «Товары» и для `/precategorized`.
- [ ] Согласия и исправления различимы фильтром «только расхождения».
- [ ] Фильтры по источнику, предложенной/итоговой категории, названию, периоду
      работают; есть пагинация.
- [ ] Одинаковые сочетания в выдаче схлопнуты в одну строку, «кто принял» — от
      последнего события; счётчиков и группировок нет.
- [ ] Сохранение категории без предложения и неподтверждённое предложение в
      журнал не попадают.
- [ ] Страница журнала недоступна не-администраторам.
- [ ] Текущий поток пользователя (включая обязательность подтверждения) не
      изменился; автопроставления не появилось.
- [ ] `cd Analytics && dotnet test` проходит; покрыто unit-тестами; ручная
      проверка через UI.

## Edge cases
- Предложение выдавалось, но пользователь ушёл без сохранения → события нет.
- Пользователь сбросил категорию («Не указана») после предложения на странице
  чека → это решение по предложению: событие фиксируется с итогом `Undefined`.
- Один сохранённый чек с многократно повторяющимся названием → события пишутся
  по каждой позиции (сырой журнал), в выдаче схлопываются.
- Разные исходные названия дают одинаковое нормализованное («Хлеб» / «ХЛЕБ») →
  в выдаче это разные строки, т.к. исходное название входит в сочетание.
- Имя пользователя недоступно → фиксируется идентификатор принявшего, имя в UI
  остаётся пустым; флаг «админ» заполняется всегда.
- ИИ/предложение по позиции отсутствовало (ошибка вызова, пустой ответ) и
  человек заполнил категорию сам → события нет (нет предложения).
- Не-администратор пытается открыть страницу журнала/API → отказ доступа на
 равне с существующей защитой админ-разделов.

## Зависимости
- Существующий конвейер категоризации Analytics: suggest/save страницы чека и
  «Товары», очередь `precategorized_commodities`, in-memory кэш, дефолты
  мерчантов (ADR 009, 019, 026*, 027, 028, 030, 032).
- Нормализация названия товара (уже используется кэшем/очередью) — журнал
  использует то же нормализованное имя.
- Авторизация админ-разделов Analytics и фронтенд-раздел для новой страницы.

## Вне объёма (не в этой задаче)
- Персистентная память «имя → подтверждённая категория» (следующий вероятный
  шаг, опирающийся на данные этого журнала).
- Любое автопроставление категорий (NFR-1).
- Проценты точности, графики, матрицы путаницы, счётчики в UI.
- Восстановление истории задним числом (предложения ранее не сохранялись —
  журнал начинается с момента внедрения).
- Реализация второго провайдера ADR 026.
