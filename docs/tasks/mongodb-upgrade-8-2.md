# Задача: Обновление MongoDB до версии 8.2.3 с миграцией данных

## 1. Бизнес-ценность / Цель

Проект использует устаревшую версию MongoDB (`mongo:4.1` в `docker-compose.yml`), которая давно не получает обновлений безопасности и не поддерживается вендором. Это создаёт риски:

- **Безопасность**: известные уязвимости в MongoDB 4.x не исправляются;
- **Поддерживаемость**: при проблемах с СУБД получить официальную поддержку невозможно;
- **Совместимость**: новые версии драйверов и инструментов постепенно перестают гарантировать работу со старыми серверами (драйвер `go.mongodb.org/mongo-driver` в backend уже заметно отстаёт от актуального);
- **Надёжность и производительность**: современные версии MongoDB содержат многолетние улучшения движка хранения (WiredTiger), репликации и диагностики.

**Цель:** Перевести продакшн-хранилище чеков на актуальную версию **MongoDB 8.2.3**, сохранив все данные без потерь, через проверенный механизм выгрузки/восстановления `mongodump → mongorestore`, с возможностью быстрого отката на предыдущую версию в случае проблем.

---

## 2. Текущее состояние (AS-IS)

- Версия MongoDB: **4.1** — `image: mongo:4.1` в `docker-compose.yml`, контейнер `receipt-mongo`.
- Данные хранятся на volume `${MONGO_DATA}` (по умолчанию `/home/drypa/receipts/backup`).
- Аутентификация: `MONGO_LOGIN` / `MONGO_SECRET` из `.env` (`admin` / пароль), healthcheck использует команду `mongo --eval "db.adminCommand('ping')"` — в новых образах shell называется `mongosh`, healthcheck потребует обновления.
- Пользователи БД:
  - **Backend (Go)** — основной потребитель: базы `receipt-data` / `receipt_collection`, коллекции `receipt_requests`, `system_users` и др.; драйвер `go.mongodb.org/mongo-driver v1.11.3`; подключение через `MONGO_URL=mongodb://mongo:27017`.
  - **Analytics (.NET)** — читает MongoDB для миграции данных в PostgreSQL (строка подключения в `appsettings.*.json`, `authSource=admin`); запись в MongoDB не делает.
  - **Bot** — к MongoDB напрямую не подключается.
- Уже есть вспомогательный скрипт `restore.sh` с `mongorestore --drop --gzip` — можно опереться на него при разработке процедуры миграции.
- Запуск сервисов: `./build.sh`, `./up.sh` / `up.dev.sh` / `down.sh`; есть скрипт локальной разработки `dev-run.sh`, который поднимает mongo как docker-контейнер.
- CI собирает образы backend и bot; сборка образов от MongoDB напрямую не зависит, но интеграционные тесты (`*_test.go`) требуют запущенного MongoDB с корректными кредами.

## 3. Требования (FR — функциональные требования)

### FR-1. Целевая версия
Все окружения, использующие MongoDB из docker-compose (продакшн, develop, локальная разработка через `dev-run.sh`), должны работать на MongoDB **8.2.3**.

### FR-2. Сохранность данных
Миграция выполняется по схеме **mongodump → mongorestore**:
1. Полный дамп всех баз данных перед остановкой старого контейнера (`--gzip`);
2. Восстановление дампа в новый контейнер с MongoDB 8.2.3;
3. Пользователь `admin` и права доступа должны быть восстановлены/пересозданы так, чтобы все сервисы продолжили подключаться без изменения строк подключения (параметры `MONGO_URL`, connection strings Analytics остаются прежними).

### FR-3. Возможность отката
До начала миграции должна существовать проверенная точка отката:
- Дамп данных + сохранённый образ/конфигурация старой версии позволяют вернуть систему на MongoDB 4.1 с исходными данными за ограниченное время.

### FR-4. Совместимость клиентов
После обновления должны корректно работать:
- Backend: чтение/запись чеков, users, reports, waste — весь текущий функционал;
- Analytics: миграция MongoDB → PostgreSQL проходит полностью, количество перенесённых чеков совпадает;
- Интеграционные тесты backend проходят против новой версии БД.

При необходимости допускается обновление Go-драйвера `mongo-driver` до версии, официально совместимой с сервером 8.x (техническая деталь — на усмотрение архитектора).

### FR-5. Актуализация сопутствующих конфигураций
- Healthcheck в docker-compose должен использовать инструменты, доступные в новом образе (`mongosh` вместо `mongo`);
- Скрипты резервного копирования/восстановления (`restore.sh` и аналогичные) должны использовать инструменты версии 8.2.3;
- Инструкция по эксплуатации (AGENTS.md или README) должна быть обновлена: новая версия, изменённая процедура бэкапа/восстановления, порядок миграции для будущих развёртываний.

### FR-6. Процедура миграции
Должна быть задокументирована пошаговая процедура выполнения миграции на проде:
- Предварительный полный дамп и его проверка (восстановимость);
- Окно простоя (сервисы останавливаются, данные не теряются);
- Порядок действий: down → замена образа/данных → restore → up → проверки;
- Чек-лист послемиграционных проверок (сервисы поднялись, воркеры опрашивают nalog.ru, чеки создаются, аналитика видит данные).

## 4. Нефункциональные требования

| № | Требование |
|---|------------|
| NFR-1 | Простое время миграции — минимально достаточное; простой сервиса сбора чеков допустим, но должен быть ограничен и заранее спланирован |
| NFR-2 | Потеря данных недопустима: после миграции количество документов во всех коллекциях совпадает с дампом |
| NFR-3 | Строки подключения приложений не меняются |
| NFR-4 | Откат на 4.1 возможен без потери данных, накопленных после миграции — не требуется (окно простоя закрывает вопрос), но дамп до миграции обязателен |

## 5. Критерии приёмки

1. `docker-compose.yml` (и связанные compose-файлы / dev-скрипты) используют образ `mongo:8.2.3`.
2. Выполнена миграция по схеме mongodump → mongorestore; все коллекции восстановлены (проверка счётчиков документов до/после).
3. Backend работает: регистрация пользователей, получение чеков, отчёты — без ошибок в логах.
4. Analytics успешно выполняет миграцию MongoDB → PostgreSQL.
5. Healthcheck mongo в compose зелёный.
6. Задокументированная процедура миграции и отката присутствует в репозитории; AGENTS.md обновлён.
7. Тесты backend (`go test ./...`) проходят против новой версии БД.
8. Подготовлен отдельный документ-инструкция для персонала с ручными действиями по обновлению (FR-7): пошаговые команды, точки принятия решений, процедура отката, чек-лист проверок.

## 6. Решения заказчика (зафиксированы)

1. **Окно простоя**: допустимо до нескольких часов (объём данных небольшой, времени должно хватить).
2. **Схема миграции**: только одношаговая — 4.1 → 8.2.3 сразу через mongodump → mongorestore.
3. **Исправление `backup.sh`** (база `receipt-data` не попадала в бэкапы): выполняется в рамках этой задачи.
4. **Инструкция для персонала**: подготовить отдельный документ с инструкцией по ручным действиям персонала при выполнении обновления (см. FR-7).

---

## 7. Требования к документации для персонала

### FR-7. Операционная инструкция для персонала
Подготовить **отдельный самостоятельный документ** с пошаговой инструкцией ручных действий персонала при обновлении:
- Подготовительный этап: проверки перед началом (свободное место, доступы, наличие дампов);
- Пошаговые команды в порядке выполнения с ожидаемыми результатами каждого шага;
- Точки принятия решений: что проверять и как интерпретировать результат перед переходом к следующему шагу;
- Действия при проблемах: критерии остановки, процедура отката на MongoDB 4.1;
- Чек-лист финальных проверок и порядок запуска сервисов.

Документ должен позволить выполнить миграцию оператору без знания внутренней архитектуры проекта — только следуя инструкции.

## 8. Ограничения и замечания

- MongoDB 4.1 — не LTS-версия; прямая in-place репликация данных между 4.1 и 8.x невозможна, поэтому выбран путь dump/restore (решение заказчика).
- Volume `${MONGO_DATA}` содержит данные старой версии; формат файлов движка несовместим между мажорными версиями — новый контейнер должен либо получать чистый volume с последующим restore, либо отдельный volume.
- Не забыть про `depends_on: - mongo` и порядок старта сервисов после миграции.
