# Задача: In-memory кэш категорий товаров для сокращения вызовов ИИ

> **Относится к функционалу автоматической категоризации товаров (см. [auto-commodity-categorization.md](completed/auto-commodity-categorization.md), ADR 009).** Данная задача уточняет/заменяет реализацию кэша ранее присвоенных категорий (FR-1.3, FR-4.2, UC-5 исходной задачи): вместо таблицы PostgreSQL `commodity_category_assignments` вводится **in-memory кэш в Analytics**, таблица удаляется миграцией.

## Приоритет
**high** — вызовы ИИ дорогие, каждое повторное совпадение названия товара должно обслуживаться без обращений к ИИ.

## Проблема
- При категоризации чека в webUI система вызывает ИИ для названий товаров, для которых категория **уже известна** (на примере «АИ-95-К5»: запись с категорией в таблице `commodity_category_assignments` есть, но запрос к ИИ всё равно уходит).
- Кэш хранится в PostgreSQL (`commodity_category_assignments`), накопились дубликаты, что усложняет работу с ним (непонятно, какую запись обновлять).
- Каждый вызов ИИ — прямые денежные затраты; повторные вызовы для одинаковых названий неоправданны.

## Цель
- Сократить количество вызовов ИИ при категоризации: если для нормализованного названия товара уже известна категория — использовать её, ИИ не вызывать.
- Перевести кэш категорий в память сервиса Analytics (быстрый доступ, без дубликатов и без расходов на запись в БД), наполняемый из уже категоризированных товаров PostgreSQL.

## Пользователи
- Конечный пользователь webUI `Analytics/frontend` (страница чека, массовая категоризация) — получает те же предложения категорий, но быстрее и без расходов на ИИ для известных названий.
- Заказчик/оператор сервиса — снижение затрат на ИИ.

## Сценарий использования

1. Пользователь открывает чек в webUI и нажимает «Категоризировать».
2. Для каждой позиции без собственной категории система ищет нормализованное название в in-memory кэше (сценарий с эталонным «АИ-95-К5»):
   - **шаг 1** — у позиции уже есть категория → предложить её (`source = existing`), ИИ не вызывается;
   - **шаг 2** — совпадение в in-memory кэше → предложить сохранённую категорию (`source = cache`), ИИ **не вызывается**;
   - **шаг 3** — нет совпадения → вызов ИИ (`source = ai`).
3. Пользователь подтверждает/правит предложения и сохраняет (UC-2/UC-3 исходной задачи).
4. При сохранении (в т.ч. ручном `PUT /api/commodities/{id}/category`) кэш обновляется, чтобы FR-1.3 работал для последующих обращений.

## Функциональные требования

### FR-1. In-memory кэш
- FR-1.1. Кэш — in-memory структура ключ-значение в сервисе Analytics: ключ — **нормализованное** название товара, значение — категория `CommodityCategory`.
- FR-1.2. **Наполнение при старте сервиса**: при запуске Analytics кэш заполняется из всех позиций `commodities`, у которых заполнена категория, **отличная от `Undefined`** (неизвестные категории в кэш не попадают).
- FR-1.3. **Обновление при изменении категории**: и при ручном присвоении (`PUT /api/commodities/{id}/category`), и при сохранении после категоризации новое значение добавляется в кэш.
- FR-1.4. **Дубликаты допустимы**: при изменении категории для названия, которое уже есть в кэше, добавляется новая запись (устаревшее значение остаётся). Разрешение конфликтов — в бэклог (см. раздел «Бэклог»).
- FR-1.5. **Лимит размера кэша**: максимальное число записей (по умолчанию **1000**) задаётся через конфигурацию (`appsettings` / переменная окружения, в стиле существующих `AI__*`, имя опции — на усмотрение архитектора). При достижении лимита кэш **замерзает**: новые записи не добавляются, ничего не вытесняется (стратегия вытеснения не выбирается — нет обоснованного решения).
- FR-1.6. Таблица **`commodity_category_assignments` удаляется миграцией** (её данные/дубликаты больше не актуальны; при необходимости миграция переносит актуальные значения на усмотрение архитектора, но это не обязательно — см. FR-1.7). При удалении таблицы прекращается вся запись/чтение в неё.
- FR-1.7. Источник истины для наполнения кэша — таблица `commodities` (позиции с заполненной категорией).

### FR-2. Использование кэша при категоризации
- FR-2.1. Приоритеты строго соблюдаются: «существующая категория позиции» → «in-memory кэш» → «ИИ» (как в FR-1.1 исходной задачи).
- FR-2.2. При совпадении нормализованного названия с кэшем ИИ **не вызывается**, используется значение из кэша (это и есть устранение наблюдаемой проблемы «запись есть, а ИИ вызывается»).
- FR-2.3. Нормализация названий: нижний регистр, обрезка/схлопывание пробелов (как в NFR-3.1 исходной задачи; правило подтверждено).
- FR-2.4. Масштаб кэша — **сквозной для всех пользователей** (без привязки к `user_id`), как и в исходном решении заказчика.

## Критерии приёмки
- [ ] Автотест: при старте сервиса кэш наполняется из `commodities` (позиции с заполненной категорией ≠ `Undefined` попадают в кэш; позиции без категории и с `Undefined` — нет).
- [ ] Автотест: при совпадении нормализованного названия с кэшем ИИ не вызывается, значение берётся из кэша (фиксируется и сценарий «АИ-95-К5»).
- [ ] Автотест: при отсутствии совпадения вызывается ИИ (поведение не сломалось).
- [ ] Автотест: при упоре в лимит (по умолчанию 1000) кэш перестаёт обновляться (новые записи не добавляются), ничего не вытесняется.
- [ ] Автотест: лимит размера кэша настраивается через конфигурацию/переменную окружения и применяется без пересборки.
- [ ] Миграция удаления таблицы `commodity_category_assignments` применяется без ошибок; код больше не обращается к этой таблице.
- [ ] Ручной сценарий: категоризация чека с «АИ-95-К5» на странице чека в webUI больше не вызывает ИИ, если значение есть в кэше.
- [ ] `cd Analytics && dotnet test` — все тесты проходят.

## Edge cases
- **Конфликт значений**: одно и то же нормализованное название встречается с разными категориями — берётся первое подходящее значение; разрешение конфликтов — отдельная задача в бэклог (сейчас не рассматривается).
- **Лимит достигнут**: кэш «замерзает» — новые записи игнорируются, старые не вытесняются; ИИ продолжает вызываться для новых/неизвестных названий (функционал не ломается, просто перестаёт наполняться).
- **Рестарт сервиса**: кэш пуст и наполняется заново при старте из актуальных данных `commodities`.
- **Изменение категории после заполнения кэша**: добавляется новая запись (дубликат), поведение поиска не меняется.
- **Категория `Undefined`/отсутствующая**: в кэш не попадает; при поиске не используется.

## Зависимости
- Сервис **Analytics (.NET 8, PostgreSQL)** — место реализации; webUI `Analytics/frontend` и существующие эндпоинты категоризации не меняются по сценариям (кроме факта работы кэша).
- Миграции — в проекте `ReceiptCollector.Analytics.Migrations`.
- Исходные решения заказчика (раздел 7 `auto-commodity-categorization.md`) сохраняются: формат ответа ИИ по имени enum, сквозной масштаб кэша, MongoDB read-only, порт 5039.
- Требуется обновление ADR 009 (замена хранилища кэша с PostgreSQL на in-memory) — на усмотрение архитектора.
