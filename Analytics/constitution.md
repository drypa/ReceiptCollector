# Constitution — Проект «Управление тратами"

**Версия:** 1.0  
**Дата:** 2025-10-05

## 1. Введение

Этот документ — официальная "конституция" проекта «Управление тратами» (далее — Проект). Он описывает цели, область ответственности, архитектурные решения, требования к качеству, процесс разработки, деплоймента и эксплуатации. Цель документа — обеспечить единое понимание архитектуры и правил работы для разработчиков, админов и заинтересованных лиц.

## 2. Цели проекта

- Преобразование и нормализация чеков покупок, хранящихся в сторонней MongoDB, в реляционную базу данных (Postgres).
- Автоматическое и ручное (через админ-интерфейс) присвоение категорий товарам в чеках.
- Предоставление пользователям аналитики по тратам через веб-интерфейс (React).
- Аутентификация и вход через Telegram.
- Развертывание приложения в Docker-контейнерах на Linux-окружении.
- Обеспечение масштабируемости, безопасности и удобства администрирования.

## 3. Область и ограничения

**Включено:**
- Сервис для чтения чеков из MongoDB и миграции в Postgres.
- Сервис категоризации позиций (автоматический + админ-редактирование).
- REST/HTTP API для frontend.
- Admin UI для ручной корректировки категорий и мониторинга.
- Пользовательский Web UI (React) с аналитикой и конструктором запросов.
- Аутентификация через Telegram OAuth / бот.
- Логирование, мониторинг, бэкапы базы данных.

**Исключено:**
- Хранение/обработка изображений чеков (если не требуется отдельно).
- Полноценная OCR-пайплайн (если чек приходит уже распарсенным в MongoDB).

## 4. Технологический стек

- Backend: ASP.NET (C#) на .NET 7/8 (в зависимости от совместимости), EF Core.
- БД (реляционная): PostgreSQL.
- Источник чеков: MongoDB (сторонняя система).
- Frontend: React (TypeScript рекомендуется).
- Аутентификация: Telegram (бот + OAuth/Telegram Login Widget) + JWT для сессий.
- Контейнеризация: Docker, Docker Compose / Kubernetes (опционально для прод).
- CI/CD: GitHub Actions / GitLab CI или выбранный инструмент.
- Логирование/мониторинг: Serilog, Prometheus/Grafana (рекомендация).
- Message broker (опционально): RabbitMQ / Kafka — для асинхронной обработки и масштабирования.

## 5. Высокоуровневая архитектура

Архитектурный стиль — модульный монолит: все сервисы собираются в единое приложение с чёткими функциональными границами между модулями и возможностью последующего выделения в отдельные сервисы при необходимости.

1. **Ingest Service** — читает новые чеки из MongoDB (pull/poll или подписка), валидирует и публикует события в очередь задач (или сразу вызывает миграцию).
2. **ETL / Migration Service** — отвечает за трансформацию документов чеков в нормализованные сущности и сохранение в Postgres.
3. **Categorization Service** — сопоставляет позиции с категориями: сначала применяет автоматические правила/машинное обучение, затем сохраняет результат; если неудачно — помечает для ручной классификации.
4. **API Service (ASP.NET)** — основной backend: CRUD, аналитические эндпоинты, авторизация, фронт.
5. **Admin UI (React)** — интерфейс для правки категорий, просмотра необработанных позиций, управления правилами категоризации.
6. **User UI (React)** — аналитика, настройки, построение пользовательских запросов.
7. **Auth Gateway** — интеграция с Telegram: обмен данными, выдача JWT.
8. **Data Warehouse / OLAP (опционально)** — для тяжёлой аналитики и построения агрегатов (например, ClickHouse, Postgres-materialized views).

## 6. Важные доменные сущности (high-level)

- User: id, telegram_id, email (опционально), display_name, role, settings.
- Receipt (чек): id, user_id, source_id, raw_document_reference, total, currency, timestamp, merchant.
- ReceiptItem: id, receipt_id, name, quantity, unit_price, total_price, parsed_attributes (brand, barcode), category_id (nullable), confidence_score.
- Category: id, name, parent_id, metadata.
- CategorizationRule: id, pattern, category_id, priority, created_by.
- AuditLog: событие, кто, когда, что изменено.

## 7. Схема данных — ориентиры

> Приведено в сокращённом виде. Конечную схему детализируем в миграциях EF Core.

**Receipts** (table)
- id (UUID, PK)
- user_id (UUID, FK)
- source_id (string) — идентификатор в MongoDB
- merchant (string)
- total_amount (decimal)
- currency (string)
- purchased_at (timestamp)
- raw (jsonb) — исходный документ (опционально)
- created_at, updated_at

**ReceiptItems** (table)
- id (UUID, PK)
- receipt_id (UUID, FK)
- name (text)
- quantity (decimal)
- unit_price (decimal)
- total_price (decimal)
- category_id (UUID, FK nullable)
- confidence_score (float nullable)
- normalized_name (text)

**Categories** (table)
- id (UUID, PK)
- name (string)
- parent_id (UUID nullable)
- synonyms (text[])

## 8. Поток данных и логика категоризации

1. Ingest Service получает новый документ чека из MongoDB.
2. ETL нормализует поля, сохраняет Receipt и ReceiptItems в Postgres.
3. Categorization Service выполняет попытку автоматической классификации по правилам:
   - Правила (keyword matching, regex), словарь (synonyms), ML-модель (опционально).
   - Если confidence_score < threshold => пометка для ручной проверки.
4. Admin UI показывает необработанные/низкоквалифицированные позиции для ручной категоризации.
5. После ручного назначения категория применяется к похожим позициям (возможно, создание/обновление правила).

## 9. Админ-интерфейс

Функции:
- Просмотр позиций с низкой уверенностью.
- Быстрая массовая категорияция (bulk edit).
- Управление категориями и синонимами.
- Просмотр истории изменений и audit log.
- Управление правилами автоматической категоризации.

UX:
- Таблица с фильтрами (merchant, дата, пользователь, confidence).
- Быстрый доступ к похожим названиям и предложенным категориям.

## 10. Аутентификация и безопасность

- Вход через Telegram (Login Widget или OAuth flow), в результате пользователь получает JWT (short-lived) и refresh token (если нужно).
- Роли: User, Admin, SuperAdmin — контроль доступа на уровне API и UI.
- Все API должны требовать HTTPS.
- Хранение секретов: использовать Vault / Kubernetes Secrets / docker-secret.
- Пароли/токены в БД не хранить в явном виде; хранить только Telegram id и метаданные.
- Политика CORS: ограничить домен frontend.

## 11. DevOps / Деплоймент

- Каждый сервис упаковывается в Docker-образ.
- Для локальной разработки — Docker Compose (Postgres, Redis/RabbitMQ, API, frontend).
- Для продакшена — Kubernetes (Helm charts) или managed Docker Swarm.
- Миграции БД управляются EF Core migrations; отдельный job запускает их при деплое.
- Бекапы Postgres: регулярные дампы и/или использование облачного snapshot.

## 12. Наблюдаемость и логирование

- Логи: структурированные (JSON) через Serilog, агрегируются в centralized log (Elastic/ Loki).
- Метрики: Prometheus + Grafana — latency, error rate, queue depth, processed receipts/sec.
- Трейсинг: OpenTelemetry (опционально) для цепочек обработки чеков.

## 13. Резервирование и отказоустойчивость

- Настроить репликацию Postgres и резервные бэкапы.
- Ingest и миграционные сервисы должны быть идемпотентны (по source_id чеков) — чтобы избежать дубликатов.
- Очередь задач (Rabbit/Kafka) с уровнем персистентности для повторных попыток.

## 14. Тестирование

- Unit tests для бизнес-логики и правил категоризации.
- Integration tests для EF Core и доступа к Postgres (использовать тестовую БД в CI).
- End-to-end тесты для главных user flows (логин через Telegram mock, импорт чека, категоризация, аналитика).
- Load tests для ETL pipeline (симуляция больших потоков чеков).

## 15. Политики качества кода и конвенции

- C# код: использовать .NET coding style, nullable reference types ON.
- EF Core: использовать схемы миграций и seed-данные для начальных категорий.
- Frontend: TypeScript строгие настройки (noImplicitAny, strict), тесты React (Jest/RTL).

## 16. Конфиденциальность и соответствие требованиям

- Персональные идентификаторы (telegram_id) и транзакционные данные — хранить с минимальной необходимой информацией.
- Псевдонимизация/маскирование чувствительных полей в логах.
- Соответствие GDPR: пользователи должны иметь возможность удалить свой аккаунт и все персональные данные.

## 17. Безопасность данных чеков

- raw JSON чеков можно хранить в Postgres jsonb, но доступ к ним должен быть ограничен.
- Encrypted-at-rest для БД (если возможно в инфраструктуре).
- Регулярный аудит доступа к данным.

## 18. API & Эндпоинты (ориентиры)

- `POST /api/webhook/ingest` — (опционально) для ручной отправки чеков.
- `GET /api/receipts` — листинг чеков с фильтрами.
- `GET /api/receipts/{id}` — детальный чек с позициями.
- `PATCH /api/receipt-items/{id}/category` — ручная постановка категории.
- `GET /api/analytics` — агрегированные данные по фильтрам (date range, category, merchant).
- `POST /api/auth/telegram` — обмен данными Telegram -> JWT.

## 19. Конструктор аналитических запросов

- Предусмотреть возможность пользователю строить запросы через UI: выбрать метрики (sum, avg, count), фильтры (category, date range, merchant, user), группировки (month, year).
- Серверная реализация: готовые SQL-агрегаты + безопасная генерация SQL (avoid SQL injection). Рассмотреть использование prepared queries и whitelist полей.

## 20. Roadmap и приоритеты MVP

**MVP (1-3 месяца):**
- Интеграция с MongoDB для чтения чеков и запись в Postgres.
- Базовая нормализация чеков и сохранение Receipt/ReceiptItems.
- Автоматическая категоризация на основе простых правил (ключевые слова).
- Admin UI для ручной категоризации.
- User UI: просмотр чеков и простая аналитика (сумма по категориям за месяц).
- Авторизация через Telegram.

**v1 (после MVP):**
- ML-модель для категоризации (trained on labeled items).
- Advanced analytics и конструктор запросов.
- Очереди задач, горизонтальное масштабирование.
- Monitoring, бэкапы, политики отказоустойчивости.
